从学习到排行榜：思科如何通过 AWS AI League 在 Agentical AI 中提升 1,200 名工程师
==================================================。 ==================================================

与许多大型工程组织一样，思科正在采用生成和代理人工智能来改变其工程师构建软件的方式。 困难的部分不再是技术。 它正在帮助成千上万的工程师从观看演示转变为自信地使用它进行构建。 录制的会话和幻灯片很少缩小这一差距。 工程师在构建真实的东西时学习最快，看到它失败，修复它，然后再试一次。

AWS 为此设计了 [AWS AI League](/ai/aileague/)。 它将动手式人工智能学习转变为游戏化竞赛，参与者在 AWS 上定制模型并构建代理，在实时排行榜上获得即时反馈，并在游戏展示式的结局中竞争。

什么是 AWS AI 联赛？
========================

AWS AI League 帮助组织通过竞争建立先进的 AI 技能。 每个联赛遵循三个步骤：

1.  **Lear –** 由 AWS 专家领导的动手实践的 2 小时研讨会介绍了这些工具和挑战。
2.  **Build –** 参与者按照自己的节奏进行实验并提交到实时排行榜，自动评估员在每次提交后都会提供实时反馈。
3.  **Compete –** 顶级决赛选手在现场直播的比赛风格大结局中登台演出。

尽管 AWS AI League 提供了多个用例，但在思科 IT 提供了以下两个挑战：

*   **AI 挑战 –** 参与者使用 [Amazon Bedrock AgentCore](/bedrock/agentcore/) 构建代理，这是一个与任何框架或模型大规模构建、连接和优化代理的平台。 特工穿过一个类似迷宫的网格，在通往宝箱的路上解决了挑战。 挑战映射到现实世界的任务，例如处理不当内容、运行代码、从 Web 中检索信息和提取结构化数据。 构建者可以为主管和子代理选择模型，并添加 [AgentCore memory, a capability of Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 和 [AWS Lambda Event Functions](/lambda/lambda-functions/) 等工具。 建筑商使用 [Amazon Bedrock Guardrails](/bedrock/guardrails/) 将安全控制应用于其代理。
*   **Model Customization Challenge –** 参与者使用最新的训练食谱微调 [Amazon SageMaker Studio](/sagemaker/ai/studio/) 中的模型。 当自动评估者将参与者的定制模型评为比参考模型更准确、更全面时，挑战会奖励点。

决赛选手的时间效率、准确性、代理计划和代币消费效率得分。

检查赢得代理 AI 挑战所需的条件
=======================================================

2026年获奖经纪人提供的课程远远超出了游戏范围。 每个设计选择都映射到团队在生产中运行代理时面临的决策。

输出代币是实际成本
------------------------------

代理 AI 挑战在挑战点、宝藏奖金、剩余生命和代币奖金上评分，计算为 `tokenBonus = 1000 - (totalOutputTokens / challengesVisited)`。

在预选赛中，排名前四的特工都解决了地图。 第一名的代理发射了 1,220 个输出代币，第二名的代理发射了 1,430 个，最终保证金仅为近 16,000 个中的 16 个点。 在每个代理人都可以解决问题后，效率决定了赢家。

为了了解哪些令牌很重要，Nishanth 构建了相同代理的九种变体，一次更改一项。 结果很清楚：工具结果和系统提示不计分数，但代理写的所有内容，包括工具调用参数，都做了。 每个工具调用在其参数之上携带大约 52 个固定的开销令牌。

这反映了现实世界的成本。 生成的输出是连续的，并且通常比投入的价格高出几倍，并且在每个步骤中花费化合物的代理循环中。 一个结构良好的系统提示（你也可以缓存）很便宜。 健谈的代理人不是。

一名代理人，而不是五名
--------------------

此挑战的常见架构是 Amazon Bedrock AgentCore 上的主管代理，该代理委派给专业子代理进行导航、计算和 Web 检索。 对于许多生产系统来说，这是一个合理的模式。 获奖设计使用了一个没有子代理的单一代理。 相反，提示开始于一个简短的调度表，该表将每种挑战类型在一个回合中与正确的方法相匹配。

推理很简单：代理之间的每一次交接都是模型必须编写的信息，在这个挑战中，每个书面标记都被评分。 教训不是子代理是坏的。 这是根据您的协调成本选择您的架构。 当协调昂贵时，更平坦的设计可以获胜。

下图显示了 Agent AI 挑战的 AWS 参考架构： 具有专业子代理的 Supervisor Agent。 获胜的设计故意没有使用这种多代理模式。

在此参考架构中，Supervisor Agent 在 Amazon Bedrock AgentCore Runtime（Amazon Bedrock AgentCore 的一种功能）中运行，并协调三个子代理，其中 Amazon Bedrock Guardrails 和 AgentCore 内存连接到运行时。 主管和子代理通过 Amazon Bedrock AgentCore 的功能 Amazon Bedrock AgentCore Gateway 路由到四种工具：导航工具、浏览器工具、代码执行工具和使用 AWS Lambda 函数的自定义工具。

将确定性逻辑放入工具中
--------------------------------

路线规划没有留给模型。 它在 AWS Lambda 函数中运行，该函数将电路板视为优化问题。 每块瓷砖都有一个预期的价值：它支付的积分，减去它可能花费的生命，减去代理人将花费的代币来解决它。 规划者尊重限制，例如在门前收集钥匙，并在时间预算内完善路线。

这对大多数代理来说是一个有用的模式：让模型处理语言和判断，并将搜索、数学和规则转移到更快、更便宜和可重复的工具中。

决定价值而不是习惯
---------------------------------

第二轮决赛被设计成一个陷阱。 一个 7 乘 7 的板几乎完全被价值 25 分的硬币覆盖，而单个日程安排挑战图块价值 1,500 点。 习惯说收集硬币。 计划者的价值表说这些硬币是噪音。 经纪人参加了高价值挑战，在那轮比赛中得到了 7,537 分，而下一个决赛选手则为 5,953 分。 那一轮建立了带领代理人赢得整体胜利的领先优势。
