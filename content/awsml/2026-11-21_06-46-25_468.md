在这篇文章中，我们展示了 [Skyflow](https://www.skyflow.com/) 和 Amazon Bedrock [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 如何将敏感数据排除在您的 AI 代理调用的工具之外，以及这些工具提供的模型上下文之外。 我们将 Skyflow Detect 添加到 Amazon Bedrock AgentCore Gateway 作为请求和响应 [interceptor](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors.html)。 Skyflow 拦截器在到达工具之前对数据进行去识别，在代理读取结果之前对其进行恢复，并在代理打开之前用干净的副本替换文档。 您的代理和工具不会改变。

Skyflow 在 AWS Marketplace 中可用，拦截器在 GitHub 上是开源的。

## 代理通过工具起作用，工具移动数据

代理已从回答问题转变为采取行动，并通过工具采取行动：模型上下文协议 (MCP) 服务器、SaaS API、文档存储和 Web 搜索。 每个代理工具调用都是数据流。 大多数企业控制都涵盖了模型的进出内容。 代理发送给其工具的内容或这些工具发送的内容要少得多。

这种差距以三种方式出现：

*   **敏感数据通过工具参数离开。** 模型从其上下文中的所有内容中写入参数，包括工具不需要的细节。 向代理询问客户，客户的姓名、帐号或电子邮件会直接进入第三方服务器的查询中。 该服务器位于您的 AWS 账户和合规范围之外。
*   **敏感数据返回到工具结果中。 即使任务从未需要它们，也会发生这种情况。
*   **文档绕过文本检查。** 文档工具，如 Amazon Simple Storage Service (Amazon S3)、Box 和 Google Drive 返回签名的 URL，而不是文本。 检查字符串的过滤器看到一个链接并让它通过，然后代理打开原始文件。

修补每个代理不会跨团队和框架进行扩展，也无法访问第三方工具。 控件需要坐在每个工具调用通过的地方，因此授权、内容安全和数据保护以相同的方式应用于每个代理和工具。

AgentCore 网关就是那个地方。 它面向代理使用的每个工具，无论代理运行的框架或模型如何。 它不仅仅是路由该流量。 使用 AgentCore 网关拦截器，您可以在每次通过它的调用上运行自己的代码，作为 AWS Lambda 函数。 请求拦截器在到达工具之前查看每个调用，响应拦截器在到达代理之前查看每个结果。 可以检查有效负载、重写它或阻止呼叫。 这使得网关成为在政策和护栏旁边添加数据保护的自然场所。 这个单一的控件，一次附加，涵盖了网关后面的每个代理和每个工具，没有对代理或工具代码进行任何更改。

### 示例：欧洲大型银行的争议解决代理

考虑一家拥有零售和企业银行业务以及严格数据居住义务的大型欧洲银行。 其运营团队正在采用代理调查卡片纠纷。

分析师要求代理人调查有争议的交易。 代理在网络上搜索商家，然后从 Amazon S3 中提取争议案例说明进行总结。 没有保护，会发生三件事：

*   该模型在上下文中从所有内容中构建搜索查询。 搜索提供商收到“Mateo Jackson 争议 Anycompany Electronics London”。 那是客户的姓名，发送给第三方，进行只需要商家的搜索。
*   被刮掉的商家页面将不相关的个人数据带入模型的上下文中。
*   代理人阅读原始案例说明，并附有客户的全名、电子邮件、电话号码和卡片详细信息。

使用网关上的 Skyflow 拦截器，相同的工作流程以不同的方式播放：

*   搜索提供商收到“\[name\_ajbriud\]争议任何公司电子伦敦”，其中\[name\_ajbriud\]是一个可逆的保险库令牌。 商家结果是一样的，供应商永远不会知道客户是谁，分析师仍然在代理人的回答中看到真名。
*   网页内容到达已经去识别的模型。
*   代理只接收到病例说明的去识别副本的链接。

## 解决方案概述

Skyflow 拦截器是一个 AWS Lambda 函数，它连接到两个 AgentCore 网关拦截点：

*   `REQUEST` 在网关调用工具之前运行。
*   `RESPONSE` 在工具回答之后和代理看到结果之前运行。

在每个点，它都会调用 Skyflow Detect 来查找敏感实体，例如姓名、电子邮件地址、电话号码、政府 ID、卡号、出生日期和地点。 它用令牌替换它们，或恢复原件。 Skyflow Vault 存储原始值，以便授权系统可以反转令牌。

Skyflow Gateway 配置决定了每种工具中的哪种保护模式中的哪一种：屏蔽工具、屏蔽模型和屏蔽文档。

生产中有四种属性：

*   ** 对代理或工具没有任何更改。** 代理程序会像以前一样以其 AWS 身份和访问管理 (AWS IAM) 角色发现网关和签名请求。 为了保护模型，代理将其模型客户端指向网关的推理端点。 拦截器对他们来说是不可见的。
*   **没有重新部署的配置。** 该策略设置每个服务器和每个工具的方向、实体类型和令牌类型（可逆保管库令牌或单向令牌）。 它位于 AWS Systems Manager 参数存储中，更改生效而无需重新部署。
*   **FAIL 关闭。** 如果取消识别无法完成，则取消呼叫而不是发送清除。 拦截器仅从允许列表的位置获取文件，并且它阻止了无法检查而不是静默传递的流量。
*   **基于 AWS 构建的操作。** Skyflow API 密钥存在于 AWS Secrets Manager 中。 每个决定都记录到 Amazon CloudWatch，其中包含警报指标，拦截器从不记录凭据或原始值。

图 1：参考架构。 编号的步骤与以下流程相匹配。

流量：

1.  代理通过 AgentCore 网关调用一个工具，用其 IAM 角色签名。
2.  拦截器将工具与策略匹配，并在需要时将 Skyflow Detection 的参数取消标识。
3.  网关调用该工具，它接收令牌而不是敏感值。
4.  根据策略需要，`RESPONSE` 拦截器重新识别结果、对其进行去识别或交换文档 URL。
5.  代理接收结果。

代理运行在 [AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上，这是 Amazon Bedrock AgentCore 的功能。 除此流程外，拦截器从 Parameter Store 和 Skyflow API Key 中从 Secrets Manager 中读取其策略，并将每个决策记录到 Amazon CloudWatch。 它在批准的区域中调用 Skyflow Detect 和 Skyflow Vault 以去识别和重新识别数据。 目标位于网关之外：第三方 Web 搜索 MCP 服务器、Amazon S3 中的 Case-Note 存储以及网关通过推理目标到达的 Amazon Bedrock 中的模型。 对于模型调用，拦截器在 Amazon DynamoDB 中保留一个短暂的记录，其中每个调用都被铸造，因此它只恢复那些。 该记录不包含原始值。 对于文档，Skyflow Detect 通过预先签名的 URL 直接获取文件，因此文件字节不会通过 lambda。

## 它如何与 AgentCore 的其余部分相匹配

拦截器补充了 AgentCore 和 Amazon Bedrock 已经提供的控制：

*   ** Amazon Bedrock AgentCore 中的政策** 使用雪松和山茱萸授权代理可以做什么。 它超越了决定一个委托人是否可以调用一个工具。 它可以基于代理轨迹中的早期操作，控制对代理和模型的访问，阻止特定参数发送到特定工具，并使用 Amazon Bedrock Guardrails 检查通过网关的数据。 Skyflow 与政策一起工作。 当策略允许调用时，Skyflow 将其中的敏感值换成可逆令牌，因此调用不会将真实数据暴露给工具或模型。 策略决定代理可以做什么，Skyflow 控制敏感数据的处理方式。
*   **亚马逊基岩护栏**处理模型交互的内容安全和敏感信息编辑。 Skyflow 将 Vault 支持的标记化和文档去标识化添加到同一网关。 将它们一起使用以在每个模型和工具调用中进行分层保护。
*   **AgentCore Identity，Amazon Bedrock AgentCore 和 AWS IAM** 的功能。 拦截器不会为代理添加要管理的凭据。
*   **AgentCore Observability，Amazon Bedrock AgentCore 和 Amazon CloudWatch** 的功能，并在网关跟踪中记录拦截器决策。

## 部署解决方案

Skyflow Interceptor 在 MIT 许可证下的 GitHub 上的 [agentcore-skyflow](https://github.com/SkyflowFoundry/agentcore-skyflow) 存储库中是开源的。 Skyflow 在 [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-zysz3tjic76qg) 中可用。 要将拦截器添加到您已经运行的网关：

1.  在 AWS Marketplace 中订阅 SkyFlow，创建保管库，并将其 API 密钥存储在 AWS Secrets Manager 中。
2.  使用 AWS Cloud Development Kit (AWS CDK) 从存储库中部署拦截器堆栈。 它创建 Lambda 函数、其策略参数、用于模型调用记录的 DynamoDB 表以及 Amazon CloudWatch 指标和警报。
3.  在两个拦截点将拦截器连接到网关。 存储库中的脚本执行此操作并授予网关角色权限以仅调用该功能。 如果您使用 AWS CloudFormation 或 AWS CDK 管理网关，请改为在其中声明拦截器，因此稍后的堆栈更新将保留它。
4.  为了屏蔽模型，将推理目标添加到网关，并将代理的模型客户端指向网关的推理端点。

存储库还包含本文中的完整参考部署，包括代理、网关及其目标，您可以使用 Amazon Bedrock AgentCore 的功能 AgentCore CLI 进行部署。

有五种方式：

*   **现有网关。** 将拦截器连接到您已经运行的网关。 代理和工具保持原样。
*   **新代理。** 从第一天起就将工具放在 AgentCore 网关后面。
*   ** AWS 外部的 MCP 服务器。** 作为网关 MCP 服务器的目标，它们的流量通过拦截器。
*   **文档存储。** 通过将其位置添加到策略的允许列表来覆盖返回签名 URL 的工具。
*   **Model 调用。** 添加推理目标并通过网关发送代理的模型调用。

Skyflow 提供了多种 Vault 部署模型和区域选择，以满足居住要求。 见[Skyflow deployment models](https://docs.skyflow.com/docs/fundamentals/product-overview)。

## 考虑

*   **Formats.** 文本和 Office 格式（TXT、JSON、CSV、XML、JSONL、DOCX、XLSX 和 PPTX）保持可逆的保管库令牌。 PDF 和图像已完全去识别，但接收单向令牌，因此无法从这些文件中恢复原始值。
*   **Availability.** 字符串去识别和重新识别通常是可用的。 通过签名的 URL 进行文档去标识化使用 Skyflow Detect v2，它在预览中。 AgentCore 网关可用性因 AWS 区域而异。 在部署之前，请在 Amazon Bedrock AgentCore 文档中检查 [Supported AWS Regions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html)。
*   **文档大小和延迟。** 文档去识别受设计的限制。 拦截器在提交之前检查文件大小，因此您配置的限制以上的文件会立即被拒绝而不是超时。 连接窗口内的文件范围内的文件 AgentCore Gateway 允许。 取消标识时间与文档大小的比例，因此设置大小限制以匹配您的文档。 Skyflow Detect v2 处于预览状态。 在扩大部署之前，在试点期间根据您自己的工作负载和区域验证延迟。

## 结论

代理仅与他们移动的数据一样值得信赖。 使用 AgentCore Gateway 和 Skyflow 拦截器，您可以在每个工具调用通过的一个地方实施隐私控制。 它在两个方向上工作，涵盖文档和文本，不需要更改代理代码。

### 从哪里开始

1.  选择一种触摸客户数据并调用您的帐户之外的工具的代理工作流。
2.  列出绝不能离开的实体类型，以及允许查看它们的工具。
3.  从 [GitHub repository](https://github.com/SkyflowFoundry/agentcore-skyflow) 中部署拦截器并将其附加到该工作流的网关。
4.  从工具屏蔽开始。 然后为您的文档存储添加屏蔽文档，并在代理的模型调用通过网关后屏蔽模型。
5.  在扩大推出范围之前，观看拦截器的 CloudWatch 指标一周。
6.  如果您还有其他问题，请参阅[Skyflow SDK documentation](https://docs.skyflow.com/docs/sdks/overview)。
