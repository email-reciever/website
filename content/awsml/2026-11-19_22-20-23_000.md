宝马集团如何管理数千个开发人员中的数百个代理
========================================。 =========================================

当数百个代理商为数千名开发人员服务时，企业治理就不能成为事后的想法。

在宝马集团的研发中，超过 12,500 名开发人员从事大约 5 亿行车辆软件代码的工作。 该软件由 BMW Connected Vehicle Backend 增强，这是一个基于云的系统，由 1,300 多家微服务提供，为该领域的 2400 万辆汽车提供数字服务。 在受监管的行业中，（软件）质量、稳定性和治理合规性的标准非常高。

虽然研究、框架和指南现在促进了建筑代理商，但以高效、可扩展的方式将高质量的代理工业化和运营仍然是一个重大挑战。

孤立的团队无法在大型组织中扩展代理 AI。 它需要集体努力、本地驱动的实验以及整个企业的积极知识共享。 这创造了一个基本的治理二分法：开发团队需要快速创新的自由，而企业必须执行安全性、安全性、可组合性和成本效益的标准。 没有这种平衡，组织将面临人工智能岛的分散和昂贵的重复工作的风险。 鉴于 BMW 集团的数百个全球分布式团队在 BMW 集团中构建代理，这将带来真正的挑战。

在这篇文章中，我们详细介绍了支持宝马研发团队在不牺牲速度、质量或合规性的情况下大规模构建、管理和运营代理的实践和模式。

解
---------

我们的前提很简单：构建可以从一开始就合作的代理。 这需要一种使多样性可组合、可管理和可自动化的体系结构，而无需单个框架或工具链。

这种架构的核心是代理线束，这是一个围绕大型语言模型 (LLM) 的运行时层。 它为自主操作提供了执行循环、工具调度、内存管理和可观察性钩子。

正如 [AWS Well-Architected Framework](/architecture/well-architected/) 标准化的云基础架构设计一样，代理系统需要从一开始就需要等效模式、可重用的蓝图编码治理、可组合性和操作性最佳实践。

我们围绕自2023年以来在企业规模的企业规模的实践经验构建和操作代理系统的五种互锁实践组织我们的解决方案。每种实践都被编入为代码（IAC）的基础设施，使采用可在团队中重复、可审计和可执行，而不会阻碍DevOps速度。

### 主动管理，不追溯

治理必须从一开始就结构化，并在整个生命周期中保持。 我们提倡有效的代理治理的三种性质：

**Framework-agnostic and Externalized:** 集成层强制执行认证、授权、速率限制和内容过滤等治理规则。 这包括模型上下文协议 (MCP) 网关、中央代理注册表和编排边界，而不是在各个代理代码库中。 这意味着治理在框架迁移、模型交换和团队重组中幸存下来。

**对域敏感和毕业：** 并非每个代理操作都具有相同的风险：起草文档、更新客户记录和生产数据库写入需要非常不同级别的监督。 我们通过逐步自主级别实现分级信任：

*   ** 0 级（人机循环）：** 每个动作都需要明确的人工批准。 这是新代理和高风险操作的起点。
*   ** 1 级（人为循环）：** 代理自动执行，但会显示异步人工复习的决策。 适用于具有定义输入、输出和回滚选项的中等风险任务。
*   ** 2 级（Guardrails 中的自主）：** 代理在严格定义的策略边界内独立运行，确定性地执行而不是通过及时的指示（见下文）。 保留用于具有经过验证的跟踪记录的低风险、了解良好的操作。

每个步骤分配信任级别，而不是每个代理。 单个工作流程可以包括所有三个级别的步骤，因此团队可以保守地开始，并随着信心的建立逐步增加自主权，基于可衡量的评估数据，而不是假设。

**确定性强制执行：** 治理作为代理的推理循环之外的确定性代码运行。 实际上，这主要发生在 CI/CD 管道中。 权限检查、策略作为代码规则和合规性验证会在代理到达生产之前为那里的每个部署提供支持。 因为这些检查与代理分开运行，因此代理及其提示都无法覆盖它们。 出口控制（收件人允许列表、出站秘密扫描）有助于防止持有机密数据的代理通过其他合法的呼叫披露。

### 仪器、验证和连续评估

代理系统中的可观察性超越了传统的应用程序监控。 真正的问题不再是服务是否返回 HTTP 200 状态，而是代理是否产生了忠实的、符合策略的输出，以及如何通过可观察的执行跟踪来证明这一点。 回答需要一个涵盖常见查询和边缘情况的真实数据集。 该数据集从第一天开始用于评估，因此质量是针对具有代表性和适当管理的评估数据集进行评估的，而不是合成提示。

这种基础设施不能改造，必须是初始设计的一部分。 持续集成和持续交付 (CI/CD) 管道强制执行此操作，因此缺乏仪表的代理在评估运行之前无法验证。

我们建议检测三个维度：

*   ** intent tracking:** 捕获每次执行的可观察到的代理轨迹（推理步骤、工具调用和上下文检索）。 OpenTelemetry 跨度创建从用户请求到最终输出的可查询谱系。
*   **Verification and evaluation as CI:** Any change to the agent (prompt edits, tool additions, model swaps) triggers the pipeline. **验证**首先使用涵盖代理组件的自动回归测试运行，然后进行交互。 由于大多数线束组件是确定性的，这些测试是快速且完全可自动化的。 **评估** 运行第二，根据地面真相数据集对非确定性输出进行评分，门控质量阈值。 这种排序是经过深思熟虑的：验证充当门，因此评估仅在经过的构建中运行。
*   **模型分层和路由遥测：**当代理之间路由模型时，捕获路由决策及其理由，而不仅仅是结果。 层级分配来自每个任务类型的评估结果，不良结果作为新的评估案例流回。

### 开始聚焦，构图设计

对于分布式云系统，业界通过采用微服务或服务网格等架构模式解决了端到端工作流程的复杂性。 代理系统的进化需要遵循类似的轨迹，从单一的、通才的代理转向多个合作的特殊代理。

团队应该在考虑代理的功能之前定义问题。 在编写任何编排逻辑之前，它们应该产生五个具体的工件：

1.  **明确的范围定义：** 代理应该做什么和不应该做什么。
2.  **交互模型**：用户和其他代理将如何调用它。
3.  **明确的工具定义：** 精确定义的每个工具和参数。
4.  **Ground-Truth Dataset**：上述评估参考，在任何实施开始之前建立。
5.  **评估标准：** 将衡量代理人的质量阈值和基准。

这种学科阻止了我们观察到的最常见的故障模式：承担太多责任的代理会累积臃肿的提示，降低准确性并增加延迟。

一旦单个代理的范围很好，它必须被设计为可组合的构建块。 因此，我们定义了一个三层组合层次结构：

*   **MCP 工具**是原子集成合约。 每个工具都包含单个功能（例如，API 调用或数据库查询），无需对工作流假设进行编码。 这是稳定的、可重复使用的层。
*   **技能**是捆绑的MCP工具的特定领域组合。 例如，代码审查技能可能会链接静态分析工具、样式检查工具和基于法学硕士的推理步骤。 技能编码域逻辑，但在工作流中保持可移植性。
*   **flows** 是指端到端的技能编排，代表完整的业务流程（例如，整个公关审查管道或需求部署周期）。

每个层在 CI/CD 管道中独立验证。 组件测试涵盖工具和技能，交互测试将其组成内容涵盖为流。

这些层级通过开放标准连接：用于工具集成的 MCP 和代理技能、代理到代理通信的协议以及 OpenTelemetry 之间的可观察性交互。

### 在你学习的时候专业化

在生产中，即使是范围广泛的代理商也会随着实际使用与设计时的预期不同而分解：查询模式的变化、工具选择逻辑的困难和性能的下降不可预知。

正确的反应是将复杂的代理分解为多个特殊的代理，每个都有更清晰的指令、更简单的工具集和更集中的推理。 好处是具体的：

*   **独立进化：** 更新需求工程代理不需要触摸编码代理。
*   **单独比例**：当范围和接口定义明确时，可以独立缩放单个代理，而无需重新部署或调整更广泛的系统的大小。
*   **最小化范围：** 一个代理的失败或幻觉不会在整个工作流程中进行级联。
*   **成本节约：** 范围狭窄的代理通常可以在较小的模型上运行，从而降低推理和托管成本。

可以沿两个轴降低复杂度：

*   **在代理中：** 将能力分解为技能，因为工具和少量示例在每次调用时都消耗上下文，同时降低了准确性和增加的成本。 凭经验确定粒度：合并技能 智能体很少选择并分裂根据输入产生不同行为的技能。
*   **Across Agents**：将代理域外的工作委托给通过A2A协议的专门对等点，而不是扩展当前代理。 代理应该在能力上增长，而不是在上下文中。

至关重要的是，由于每个专业代理仅访问其角色所需的数据和工具，因此这种架构有助于在受监管的行业中实施最小的特权，这是受监管行业的合规性要求。

然而，实现这些好处需要代理人可以找到并相互操作。 为了防止_ai islands_的出现，我们维护了一个代理，工具和技能的_centralized_注册表。 该注册表用于：

*   **发现机制：**根据构建期间存储的元数据对可用的代理、工具和技能进行编目。
*   ** 治理检查点：** 确认批准用于生产用途的资产类型并维持审计跟踪。
*   **安全检查点：**在批准之前应用自动安全检查，例如及时注入和类似问题。
*   **重复数据删除保护：** 识别其他团队已经维护的等效功能，以避免重复工作。 此检查在注册时自动运行，在批准前标记重复。

### 通过编码缩放

从管理单个代理到管理代理队列的转变需要对代理架构进行编纂。 使用 Terraform 或 [AWS CloudFormation](/cloudformation/) 等基础架构即代码框架，对任何生产系统应用相同的严格性，提供和管理代理基础架构：

*   **细粒度的最小权限角色：** 按代理人或工具范围。
*   **CI/CD 管道**：跨账户和区域进行一致的、经过验证的部署，在失败的测试或指标恶化时自动部署停止。
*   **Policy-as-Code**：规则（例如，[AWS Config](/config/)，Open Policy Agent）扫描部署的代理以符合组织标准。

这三个都是作为管道门的强制执行的，在注册前验证，事后未经审计。

采用模式是故意自下而上的中央策展。 个别团队建立技能和 MCP 工具来解决他们的直接问题。 所有团队都可以通过注册表共享其资产来做出贡献。 作为 CI 管道的一部分，中央团队建立了自动治理检查，以维护标准。 为了支持开发团队和 Foster _Shift-Left_，中央团队还提供构建模块作为治理即代码模块。

这种平衡避免了集中授权的架构和非托管的实验。 因此，当出现新的运营问题时，团队可以扩展现有模式，而不是重新设计其架构。

### 在运行时

在运行时，可观察性必须捕获两种漂移。 数据漂移显示为新的或移动的用户查询模式或上游 API 中的更改。 模型漂移显示为误差率上升或刀具选择精度下降。 当客户标记响应时，也会触发调查。 漂移、分布变化、评估分数下降或直接客户标志的警报会引发分阶段的响应。 这些事件被记录并转发给人工审查。 此外，团队可以连续运行治理代理以标记漂移和运营问题，供负责团队调查。

概要
--------

大规模建设和运营代理是一门工程学科，而不是实验练习。

有效的治理必须从一开始就结构化，外部化，对领域敏感，并确定性地执行。 我们引入了三层组合层次结构（MCP 工具、技能和流程），作为可重用、可组合和可互操作的代理的架构基础，分解为特殊的代理以包含复杂性和范围。 我们展示了每个 CI/CD 运行中的验证和评估如何使质量保证成为日常开发的一部分，以及将代理基础架构定义为代码如何让团队将相同的治理规则应用于车队中的每个代理。 最后，我们在整个代理生命周期中实现了这些模式，从预先验证的参考架构和结构化管道到持续评估已部署代理的运行时治理代理。

我们的经验表明，这些做法在一些方面得到了回报。 可重复使用的模板和共享基础设施降低了开发成本。 得益于标准交互模型和自动化部署，团队还可以更快地生产代理。 质量也得到了提高，因为管道在生命周期的每个阶段都实施了经过验证的模式。

扩展代理治理是整个行业的必要条件。 向 AI 和生成式 AI 支持的工作流自动化的转变已经在重塑工程组织的运作方式。 获胜者将是那些超越实验并建立大规模管理自主代理网络的学科的人。 有了这些实践，宝马工程师可以专注于解决重要的问题：建造终极驾驶机器。

要将这些想法应用于您自己的代理，请从 [AWS Well-Architected Framework](/architecture/well-architected/) 开始。 这篇文章使用它作为可重复使用的代理蓝图的模型。 要了解 BMW 如何在其 AWS 环境中编纂治理，请阅读 [How BMW Group uses automation to achieve end-to-end compliance at scale on AWS](/blogs/mt/how-bmw-group-uses-automation-to-achieve-end-to-end-compliance-at-scale-on-aws/)。
