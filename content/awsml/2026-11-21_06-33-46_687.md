保持一个共享的 Slurm 集群以进行 Foundation 模型开发需要保持几个单独维护的配置与节点上运行的配置相匹配。 集群的形状存在于多个配置文件中，其软件在自定义脚本中，其网络拓扑中的网络拓扑必须在节点更改时进行编辑，以及管理员必须维护和重新运行的名单中的用户。 随着时间的推移，这些碎片会远离实际运行的东西，没有任何东西告诉你它们何时运行。

我们认为，群集配置应按照管理 AWS 基础架构的其余部分的方式进行管理。 您通过 API 或控制台声明您想要的内容，AWS 在应用之前对其进行验证，集群连续保持在该状态，您可以查看它是否正常工作。 在 2026 年期间，Amazon SageMaker HyperPod 将这种方法引入了 Slurm 集群，包括 API 驱动的 SLURM 配置、基于 AMI 的配置、连续配置、自动拓扑管理和深度健康检查。 今天，我们推出了集群扩展，为运行节点的软件和设置带来了相同的方法，并通过托管扩展进行可观测性和用户管理。 但是，通过所有这些，您仍然可以完全访问集群中的每个节点，包括控制器节点。 您可以通过 SSH 直接配置节点和运行自己的生命周期脚本。 API 为您提供的维护更少，直接访问为您提供了更多的控制权，您可以选择平衡。

在这篇文章中，我们将介绍我们在 2026 年引入的功能，并解释了为什么运行节点上的软件需要不同的机制。 然后，我们通过 API 和控制台展示集群扩展的工作原理，并在使用它们的集群上的四分之一处跟随平台团队。

## SLURM集群操作的声明性基础

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/image_43512305-1.jpg)

我们可以想到 Slurm 集群的配置分为六层。 其中五个描述了集群本身：其定义、节点设置、容量、网络拓扑和硬件健康。 第六个涵盖了在其节点上运行的软件，我们将在下一节中讨论。 下图显示了六层。

2026年初，我们为前五层带来了声明式管理。 使用 [API-driven Slurm configuration](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-sagemaker-hyperpod-slurm/)，管理员在 CreateCluster 和 UpdateCluster 请求中为 Lustre 和 Amazon FSX 定义节点角色、分区和 Amazon FSX，并连接 [an external accounting database](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-external-accounting-db-slurm.html)。 Hyperpod 在保留其他控制器节点 slurm 自定义的同时更新分区设置。 [AMI-based configuration](https://aws.amazon.com/about-aws/whats-new/2026/05/amazon-sagemaker-hyperpod-ami-based-node/) 将例程设置脚本替换为使用 Slurm、Docker、Enroot、Pyxis 和主目录预配置的图像。 [custom AMI](https://aws.amazon.com/about-aws/whats-new/2026/07/hyperpod-custom-ami-slurm/) 或 OnInitComplete 脚本处理组织特定的软件。 [Continuous provisioning for Slurm](https://aws.amazon.com/about-aws/whats-new/2026/03/amazon-sagemaker-hyperpod-continuous-provisioning/) 在后台重试容量请求； [AMI-based configuration works with it](https://aws.amazon.com/about-aws/whats-new/2025/06/ami-configuration-continuous-slurm/)、[minimum capacity requirements](https://aws.amazon.com/about-aws/whats-new/2026/05/amazon-sagemaker-hyperpod-mincount/) 让 Teams 指定 MinInstanceCount 和 [cluster operations](https://aws.amazon.com/about-aws/whats-new/2026/11/sagemaker-hyperpod-cluster-ops/) 跟踪扩展请求。

[Automatic topology management](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-sagemaker-hyperpod-automatic-slurm-topology/) 在节点缩放或被替换时保持网络布局。 在 Slurm 25.11 或更高版本上，[partition-level topology](https://aws.amazon.com/about-aws/whats-new/2026/07/hyperpod-partition-topology-slurm/) 支持每个分区的树或块拓扑。 对于硬件健康，[on-demand deep health checks](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-sagemaker-hyperpod-on-demand-deep-health-check/) 强调 GPU 和测试 NVIDIA 集体通信库 (NCCL) 连接，而 [deep health checks with continuous provisioning](https://aws.amazon.com/about-aws/whats-new/2026/07/deep-health-check-continuous-slurm/) 以节点的形式运行。 检查的节点保持在 slurm 维护预留中，直到检查完成，使工作保持不变。

## 介绍集群扩展

到目前为止描述的五层是 Hyperpod 在配置节点时可以派生或应用一次的配置。 第六层，在节点上运行的软件，表现不同，因为它在集群的生命周期中不断变化。 当研究人员加入和离开时，一个团队会要求更深入的 GPU 指标一周，而出口商则提供一个修复程序。 对于这一层，生命周期脚本一直是迄今为止的主要机制，当软件不断变化时，它们也有缺点。 脚本仅在配置节点时运行，因此每次更改都意味着编辑它，然后替换节点或在整个队列中重新运行它。 仅当脚本在节点上运行时才会显示错误，并且没有报告安装的内容，因此节点会随着时间的推移而分开。

我们希望软件在一个地方声明，在您提交时进行检查，在节点之间保持一致，然后可见。 2026 年 11 月，我们推出了集群扩展，这些软件包是 AWS 管理的软件包，您可以通过 API 或 Amazon SageMaker AI 控制台安装、配置、更新和删除，从可观察性和用户管理（包括目录集成）开始，作为第一个软件扩展。 与脚本相比，扩展具有以下优点：

*   **Validated up front:** HyperPod checks an extension’s settings against its schema when you submit them, through the API or the console, so a misspelled setting is rejected before anything reaches a node.
*   **在每个节点上一致：** Hyperpod 将扩展应用于每个节点，包括通过放大或替换添加的节点，并在集群扩展和治愈时保持节点一致。
*   **通过 API 或控制台进行更改：** 您使用 API 调用或从 SageMaker AI 控制台更改设置或升级版本，而不是编辑脚本和替换节点。 这两个路径都使用相同的验证配置，这篇文章显示了控制台屏幕截图以及 API 示例。
*   **Visible:** 每个扩展报告其状态和每个节点的运行状况。

当 HyperPod 提供托管软件功能时，使用集群扩展。 将自定义 AMI 和生命周期脚本用于组织特定的软件或可用扩展未涵盖的初始化。 HyperPod 今天支持两个集群托管扩展：

*   可观察性扩展（SageMaker-Observability）收集节点、GPU、弹性结构适配器（EFA）、SLURM 作业和 SLURM 集群指标并将它们发送到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 或 [Amazon Managed Service for Prometheus](https://aws.amazon.com/prometheus/)。
*   用户管理扩展（SageMaker-User-Management）在每个节点上创建具有相同ID的用户和组，控制可以在每个节点类型上使用SSH和SUDO的用户和组，并使用Slurm计数注册用户。 它还可以将集群连接到 Active Directory，例如 [AWS Directory Service for Microsoft Active Directory](https://aws.amazon.com/directoryservice/)。

当您创建或更新扩展时，Hyperpod 在 API 调用期间会根据版本的架构验证您的设置，因此会立即拒绝拼写错误的设置。 然后，它将版本和设置记录为所需的状态并应用它们，每个节点仅安装其角色需要的内容，例如仅在 GPU 节点上的 GPU 导出器。 新节点和替换节点在启动几分钟后获得相同的状态，每个节点都会报告扩展是否应用以及它是否健康。

更新仅发送您要更改的设置，Hyperpod 将它们合并到存储的设置中。 仅在节点上显示的问题，例如其他已使用的端口或用户 ID，出现在 DescribeClusterExtension 的运行状况字段中，按原因分组，使用代码、消息和受影响的节点计数。 Hyperpod 会自行重试内部故障，而对于其他任何问题，您都可以修复原因并调用 UpdateClusterExtension 而无需更改重试受影响的节点。

扩展的状态是在推出更改时创建或更新，当每个节点运行请求的版本和设置时处于活动状态，并且无报告问题，并且在某些节点出现故障或报告问题时降级。 每个扩展都有自己的 ARN，因此平台团队可以拥有 SageMaker-User-Management，而监控团队拥有 SageMaker-Observability。 每个健康问题命名组件，描述对集群的影响，给出下一步，并计算受影响的节点，因此您可以查看在哪里查看而不登录到每个节点，如下图所示。

### 何时使用集群扩展以及何时使用生命周期脚本

一个有用的决定方法是询问谁拥有该软件以及它的更改频率。 集群上的某些软件特定于您的组织，例如安全代理、许可证服务器以及您的数据管道期望的存储布局。 生命周期脚本和自定义 AMI 是它的正确工具，因为只有你的团队知道它需要什么。 其余的是几乎每个集群都需要的软件，例如 GPU 和作业指标以及具有一致 ID 和访问规则的用户帐户。 该软件必须在每个节点上匹配并不断变化，因此集群扩展更适合，因为您声明一次，Hyperpod 验证它，并且每个扩展都报告它是否健康。

这两种方法可以共存，但每个组件都应该有一个所有者。 不要通过生命周期脚本和扩展来管理相同的导出器、用户或服务，因为竞争配置可能会导致安装或运行时冲突。 集群扩展适用于每个生命周期配置选项。

如果您已经从脚本中运行这些功能，则可以一次将一项功能移至扩展，并且脚本和扩展可以同时运行。 对于每种能力，迁移需要四个步骤：

1.  调用 UpdateClusterSoftware 将集群移动到 2026 年 11 月的 Hyperpod AMI 或更高版本。
2.  关闭生命周期脚本中的功能并将其上传到您的 S3 存储桶，以便新节点跳过它。
3.  在计划的维护时段中，停止并删除每个节点上的脚本安装的代理。 这是唯一的手动，全舰队的步骤。
4.  调用 CreateClusterExtension 在 Clean 集群上安装扩展。

如果留下任何东西，安装会命名冲突，例如已在使用的端口，并且 DescribeClusterExtension 在运行状况下显示它。 使用用户管理，您可以保留相同的用户名和用户 ID。 下图显示了四个步骤。

### 您需要什么开始使用集群扩展

您需要在 2026 年 11 月 2 日或之后的 Hyperpod AMI 或之后使用 [continuous provisioning enabled](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-scaling-slurm.html) 进行 Hyperpod Slurm 集群。 扩展在每个节点上以 root 身份运行软件，因此将 CreateClusterExtension、UpdateClusterExtension 和 DeleteClusterExtension 视为管理员权限。 我们建议您不要将它们授予集群的执行角色，因为每个可以登录节点的用户都可以使用其凭据。 该角色确实需要访问扩展程序使用的目标，这意味着用户管理读取的 Active Directory 机密的可观察性和 SecretsManager:GetSecretValue 的 Amazon CloudWatch 或 APS:RemoteWrite。 如果使用客户托管的 AWS 密钥管理服务 (AWS KMS) 密钥对这些机密进行加密，则该角色还需要对该密钥进行 kms:decrypt。 用户管理还需要一个共享文件系统，例如 Amazon FSX for Lustre，用于主目录。

有关过程、IAM 策略和配置参考，请参阅 Amazon SageMaker AI 开发人员指南中的 [Cluster extensions for Amazon SageMaker HyperPod Slurm clusters](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-slurm-extensions.html)。

## 平台团队使用集群扩展管理共享 Slurm 集群的旅程

要了解如何在实践中使用集群扩展，请考虑为多个研究组管理共享 Slurm 集群的平台团队。 该团队需要可审查的集群定义、GPU 和工作指标、公司目录访问、合作伙伴实验室的本地帐户以及可观察性和用户管理的单独所有权。 以下示例显示团队如何配置这些功能并响应日常更改和故障。

### 从一种定义创建集群

管理员在单个 CreateCluster 请求中声明整个集群，包括节点角色、分区、FSX 装载、最小容量、深度健康检查和外部会计数据库。 有关完整的示例请求，请参见 [Getting started with SageMaker HyperPod using the AWS CLI](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html)。

该请求没有生命周期配置、拓扑文件或 SLURM 配置文件。 每个 SlurmConfig 赋予其实例组一个角色，GPU 组加入火车分区。 基于 AMI 的配置设置节点，安全团队的合规性代理已在自定义 AMI 中。 GPU 组要求 8 个节点并需要 6 个节点，因此作业可以在 6 个准备就绪时立即开始，而 Hyperpod 则会在每个 GPU 节点到达时提供其余部分和运行状况检查。 Hyperpod 单独为 P5 节点选择树拓扑，会计写入团队拥有的 Amazon Relational Database Service (Amazon RDS) 数据库。 管理员仍然可以通过 SSH 进入控制器节点以直接检查或调整 Slurm。

### 安装可观察性

领导力需要 GPU 和工作指标，因此管理员安装了可观察性扩展。 在 SageMaker AI 控制台的集群扩展选项卡上，管理员选择可观察性扩展，选择指标类别及其级别和收集间隔，并选择两个指标存储之一：Amazon CloudWatch 或 Amazon Managed Service for Prometheus。 以下屏幕截图显示了选定的一家商店的安装表单。 其他选项在同一字段中可用。

[![Console install form for the observability extension, with configurable metric levels and a choice of metric store](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22428-7.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22428-7.png)

通过 API 进行相同的安装需要一个 create-cluster-extension 调用。 以下示例使用 Amazon CloudWatch 作为指标存储。 要将指标发送到 Amazon Managed Service for Prometheus，请将 Prometheus 目标设置为相同的配置。

管理员通过一个 create-cluster-extension 调用安装扩展：

```bash
aws sagemaker create-cluster-extension \
    --cluster-arn arn:aws:sagemaker:us-west-2:{{111122223333}}:cluster/{{abcd1234efgh}} \
    --extension-name sagemaker-observability \
    --configuration-values file://observability-config.json
```

调用返回分机的 ARN，管理员在以后的调用中使用：

```json
{
    "ExtensionArn": "arn:aws:sagemaker:us-west-2:111122223333:extension/sagemaker-abcd1234efgh/sagemaker-observability/0a1b2c3d4e5f"
}
```

无论安装哪种方式，每个节点都仅运行与其角色相关的组件，例如 GPU 节点上的 DCGM 和 EFA 导出器以及控制器上的 Slurm 集群指标。 在推出之前，架构错误被拒绝，而节点特定的冲突出现在扩展运行状况中。

安装后，该扩展程序将显示在集群的扩展选项卡上，其版本、状态和 ARN。 屏幕截图显示安装了可观察性和用户管理扩展的集群的选项卡，并且两者都处于活动状态。

### 开启更深的GPU和NCCL指标

后来，一个正在调整多节点训练的研究团队要求提供更多细节，因此管理员只发送设置进行更改：

```bash
aws sagemaker update-cluster-extension \
    --cluster-arn {{cluster-arn}} \
    --extension-arn {{observability-extension-arn}} \
    --configuration-values '{"metricsProvider":{"acceleratedComputeMetrics":{"level":"ADVANCED"},"ncclMetrics":{"level":"ENABLED"}}}'
```

Hyperpod 将这些设置合并到存储的配置中，并将它们应用于每个节点，仅重新启动设置更改的组件。 调查结束后，将两者设置为 null 将它们返回到默认值，并且在任何时候都不会替换节点或重新运行脚本。

### 升级扩展以获取无需AMI更新的新功能

当 AWS 发布新的扩展版本时，管理员会列出无需 AMI 更新即可安装和升级的版本：

```bash
aws sagemaker list-cluster-extension-versions \
    --extension-name sagemaker-observability

aws sagemaker update-cluster-extension \
    --cluster-arn {{cluster-arn}} \
    --extension-arn {{observability-extension-arn}} \
    --extension-version {{new-version}}
```

Hyperpod 会根据新版本的模式检查存储的设置并拒绝请求，如果它们对它无效，则不更改任何内容。 否则，新版本会向每个节点推出，以后加入的节点也会得到它。 升级只进行，因此管理员选择维护窗口。 然后，可以通过像之前的更新一样打开版本随附的任何新设置或功能。

### 缩放集群并替换失败的节点

在季度结束运行之前，管理员会在 GPU 组上启动按需深度健康检查，然后使用 batch-add-cluster-nodes 添加节点。 请求在 Hyperpod 接受后立即返回，因此管理员将其作为集群操作进行操作：

```bash
aws sagemaker list-cluster-operations \
    --cluster-name shared-gpu-cluster \
    --status InProgress
```

随着容量的到来，每个节点都经过健康检查，加入 Slurm，在拓扑中占据位置，并获得与其他节点具有相同版本和设置的扩展。 如果 GPU 在运行过程中出现故障，则配置替换并以相同的方式拾取扩展。

### 回顾谁有权访问

在本季度末，Security 询问谁在控制器上有 sudo，管理员在不登录节点的情况下从 API 中回答：

```bash
aws sagemaker describe-cluster-extension \
    --cluster-arn {{cluster-arn}} \
    --extension-arn {{user-management-extension-arn}} \
    --query ExtensionDetails.ConfigurationValues --output text |
jq '[.userSources.localUsers.groups[]?, .userSources.ldap.ldapGroups[]?]
    | map(select(any(.sudo[]?; .nodeTypes | index("controller")))) | map(.name)'
```

答案是 cluster-admins 和 clusteradmin@example.com，目录组的成员身份在目录中进行了审计。 因为每个扩展都有自己的 ARN，平台团队的角色只能更新 SageMaker-User-Management 和监控团队的角色，仅 SageMaker-Observability，而安全性对两者都有只读访问权限。 这些权限都不属于集群的执行角色。 当扩展处于活动状态时，ActiveCount 等于 TotalCount，并且运行状况为空，每个节点都将运行该配置。
