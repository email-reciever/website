为来自多个 AWS 区域的模型提供服务是一种成熟的高可用推理模式：当一个区域的 GPU 容量不足时，请求会移动到另一个区域。 该模式易于描述且难以操作。 到目前为止，如果您在 Amazon SageMaker AI 托管端点上提供模型，跨区域路由是您仍然必须自己构建的一部分。

今天，我们将在 Amazon SageMaker AI 中引入跨区域推理路由。 它使用一种新的资源，即推理路由器，它为您的应用程序提供了一个或多个 AWS 区域和 AWS 账户中已运行的端点和推理组件的调用路径。 您注册服务模型的目标，应用程序会调用路由器而不是特定的端点。 路由器在本地目的地健康时将请求保留在其自己的区域中，在不正常时将新请求转移到另一个注册目的地，并在恢复后逐渐返回流量。

在这篇文章中，我们解释了跨区域推理路由如何决定每个请求的运行位置，在两个区域中使用一个模型进行示例，并涵盖监控、限制和您支付的内容。 有关为多种模型提供服务的跨账户部署，请参见 [How Salesforce is advancing global-scale model serving with cross-Region inference routing in Amazon SageMaker AI](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/)。

## 当一个区域的容量不足时

SageMaker AI 端点在一个 AWS 区域和一个帐户中运行。 当自动扩展无法添加端点所需类型的实例时，请求会限制和超时，即使同一模型在另一个区域中具有备用容量。 要使用该容量，您的应用程序必须检测到陷入困境的端点和交换区，决定在不运行模型两次的情况下安全地重试哪些错误，在恢复后将流量移回，而不会发生故障，并管理对其他帐户中端点的访问权限。 该代码位于每个请求的关键路径上，每个服务于跨区域的模型的团队都维护自己的版本。

## 跨区域推理路由的工作原理

跨区域推理路由基于几个核心思想：

*   **您决定您的模型可能运行的位置 –** 对于每个模型，您可以选择路由器可能使用的端点和推理组件。
*   **SageMaker AI 决定哪个目的地为每个请求提供服务 -** 路由器更喜欢自己的区域，并且仅在本地请求无法可靠地服务时才将新请求转移到另一个目的地。
*   **您的端点保持不变——**您使用与今天相同的模型、配置、实例池和自动缩放来部署端点。 直接 `InvokeEndpoint` 呼叫继续工作，路由器通过 `InferenceId` 和 `CustomAttributes` 一样通过，就像 `InvokeEndpoint` 一样。
*   **您可以看到每个决定 -** 每个实时回复都告诉您哪个目的地服务于请求以及为什么。

几个术语描述了这些作品：

*   **推理路由器** – 您的应用程序调用的帐户中的区域 SageMaker AI 资源。
*   **路由目标** – 路由器上的一个逻辑模型的名称，例如 `fraud-model`。 一个路由器可以容纳许多路由目标，并且每个路由器都独立于其他目标。
*   **Destination** – 在路由目标下注册的实时端点、推理组件或异步端点，由其完整的 Amazon 资源名称 (ARN) 标识，该端点告诉路由器其区域和帐户。 路由目标要么包含实时目标，则可以跨区域和帐户混合端点和推理组件，或者仅将异步端点混合。
*   **LOCAL DESTINATION** – 路由器区域中的目的地，在健康时首选。
*   **Routing Reason** – 每个实时响应都返回的值，该值解释了请求的去向和原因。

您创建路由器的区域是其本地区域。 要更喜欢不同的区域，请在那里创建一个路由器。 路由器不创建容量、扩展端点、部署模型或复制模型工件和容器映像。 每个目的地必须已经在其区域内运行。

### 如何做出路由决策

路由器仅考虑在路由目标上注册并被授权调用的目标。 其中，它更喜欢自己地区的目的地，当不止一个当地目的地是健康的时，它会将请求均匀地分布在它们之间。 仅当本地目的地无法可靠地服务时，请求才会离开该地区。 为了检测到这一点，SageMaker AI 根据其最近的请求计算每个目的地的健康评分，在目的地所在的地区进行测量。 服务器错误 (5xx)、节流和超时会降低分数。 来自 SageMaker AI 平台的错误（例如，健康检查失败）降低了它的最大值。 由请求本身引起的错误，例如无效输入，不要降低它，因为相同的请求将在任何区域失败。 模型延迟不是输入，因此不断返回成功响应的端点保持其流量。 诸如失败实例启动或运行实例的端点比其自动缩放目标更少的信号使路由器的反应更快，但仅在目标开始失败请求后。

路由器评估每个目的地的健康状况并将其作为三个状态之一发布到 Amazon CloudWatch。 `healthy` 目的地正常服务。 `overloaded` 目的地仍然服务，路由器将其部分流量移开。 `degraded` 目标失败或无法服务，因此路由器将大部分流量移开并保留一小部分以检测恢复。

SageMaker AI 管理故障转移阈值和时间，因此您无需调整任何阈值。 如果远程目的地的健康信息过时，路由器会将流量保持在自己的区域，因此监控中的差距永远不会自行移动流量。

### 当流量移动时，当它返回时

请求失败越多，流量越多，因此目的地不需要首先直接失败。 流量开始在持续错误的大约一分钟内移动，或者对于流量很少的目的地的更长。 离开当地地区的交通与健康的偏远地区的健康程度成正比。 您无法设置权重或后备顺序。 恢复后，流量在几分钟内恢复，比剩下的要慢。 正在进行的请求不会中断。

当一个目标在没有运行模型的情况下实时请求失败时，路由器会在不同的目标上重试一次请求。 例如，这涵盖了节流、503 错误、未准备就绪的模型、被跨区域流量上限拒绝或目标拒绝的访问。 路由器永远不会重试超时、500 错误或模型错误。

对于异步请求，路由器尝试每个合格目的地一次，本地目的地，直到一个接受请求。

## 你可以路由什么

以下用例显示了在 Amazon SageMaker AI 中使用跨区域推理路由的常用方法。

*   **当一个区域的GPU容量不足时继续服务。 吸收溢出，并在美国东部（俄亥俄州）恢复后逐渐将流量移回。
*   ** 跨AWS账户拥有的终结点的路由。 我们涵盖此列表之后的设置。
*   **从一台路由器中服务多个模型。** 每个模型创建一个具有一个路由目标的路由器，每个模型列出该模型的目的地，并在每个请求上传递路由目标名称。 每个模型都独立失败。
*   **将路由器放在您自己的网关后面。 例如，参见[Salesforce post](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/)。
*   **路由异步请求。** 路由器帐户或其他帐户中的异步端点可以是目标。 您的应用程序使用路由目标名称和 Amazon Simple Storage Service (Amazon S3) 输入位置调用 `InvokeInferenceRouterAsync`，并返回 `InferenceId` 以及输出和故障位置，如 `InvokeEndpointAsync`。
*   **从其他区域的溢出保护接收端点。 您的端点的本地呼叫者保留其余部分。 我们将在本节后面介绍详细信息。

当目标属于与路由器不同的帐户时，两个帐户都必须允许每个请求。 在端点方面，所有者附加了一种基于资源的策略，该策略允许路由器帐户调用端点，以及 `sagemaker:SourceInferenceRouterArn` 条件密钥限制访问一个命名路由器。 以下策略仅允许帐户 444455556666 中的 `my-router` 调用端点。 它的第二个语句没有路由器条件，允许路由器帐户读取端点的状态。 如果没有该语句，目标将其状态显示为未知。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOneRouter",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::444455556666:root"},
      "Action": ["sagemaker:InvokeEndpoint", "sagemaker:InvokeEndpointAsync"],
      "Resource": "arn:aws:sagemaker:us-west-2:111122223333:endpoint/my-endpoint",
      "Condition": {"ArnEquals": {
        "sagemaker:SourceInferenceRouterArn": "arn:aws:sagemaker:us-east-2:444455556666:inference-router/my-router"}}
    },
    {
      "Sid": "AllowStatusVisibility",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::444455556666:root"},
      "Action": "sagemaker:DescribeEndpoint",
      "Resource": "arn:aws:sagemaker:us-west-2:111122223333:endpoint/my-endpoint"
    }
  ]
}
```

在路由器帐户中，呼叫者需要路由器上的 `sagemaker:InvokeInferenceRouter`（或 `sagemaker:InvokeInferenceRouterAsync`）和每个目的地的 `sagemaker:InvokeEndpoint`（或 `sagemaker:InvokeEndpointAsync`），因为路由器代表呼叫者调用每个目的地。 路由器永远不会让呼叫者访问他们无法直接呼叫的端点。 为了 `DescribeInferenceRouter` 报告每个目的地的状态，呼叫者还需要 `sagemaker:DescribeEndpoint` 上的端点和 `sagemaker:DescribeInferenceComponent` 上的推理组件。 其他帐户中的应用程序通过在路由器帐户中担任角色来调用路由器。 有关演练，请参阅 [How Salesforce is advancing global-scale model serving with cross-Region inference routing in Amazon SageMaker AI](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/) 和 [User Guide on cross-account destinations](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-router-cross-account.html)。

### 使用跨区域流量上限保护接收端点

当路由器将请求从容量不足的区域移开时，这些请求会落在已经为自己区域的呼叫者服务的端点上。 默认情况下，接收端点接受任意数量的跨区域流量，因此溢出的浪涌可以将其推入节流中。 使用跨区域流量上限，端点所有者决定其他区域可能使用的端点容量的多少。

用 `CrossRegionTrafficConfig` 设置 `CreateEndpointConfig` 中的 CAP，这需要两个值。 `MaxInvocationsPerSecondPerInstance` 是一个实例可以进行的每秒调用次数，您可以通过对模型、实例类型和典型有效负载的负载测试进行测量。 `MaxCrossRegionPercentPerEndpoint` 是其他地区可能使用的容量份额。 SageMaker AI 将每个实例的速率乘以服务中的实例并应用百分比，因此上限遵循自动缩放。 例如，每个实例每秒 50 次调用、20% 的上限和 4 个服务实例，端点每秒最多接受来自其他区域的 40 个请求。 当自动扩展添加 2 个实例时，上限会上升到每秒 60 个请求。

```python
sm = boto3.client("sagemaker", region_name="us-west-2")
sm.create_endpoint_config(
    EndpointConfigName="my-model-config-us-west-2",
    ProductionVariants=[...],  # your existing variants, unchanged
    CrossRegionTrafficConfig={
        "MaxInvocationsPerSecondPerInstance": 50,
        "MaxCrossRegionPercentPerEndpoint": 20,
    },
)
```

只有来自其他地区的请求才会计入上限。 来自端点自身区域的请求，包括来自同一区域的路由器的直接 `InvokeEndpoint` 呼叫和呼叫，永远不会被其限制。 当跨区域请求超过上限时，端点在模型运行之前拒绝额外的请求，并且路由器在不同的目标上将每个请求重新尝试一次。 如果没有其他目的地可以接受请求，则您的应用程序会出现限制错误。

CAP 适用于实时端点，并且端点上的所有推理组件共享它。 对于托管推理组件的端点，使用通常的推理组件和有效负载组合来测试一个实例来测量 `MaxInvocationsPerSecondPerInstance`，并在该组合或您的有效负载发生变化时再次运行测试。 如果省略 `CrossRegionTrafficConfig`，端点接受任意数量的跨区域流量。

## 入门：两个区域中的一种模型

在这个例子中，我们在美国东部（俄亥俄州）和美国西部（俄勒冈州）部署了 QWEN3-4B，其中包含 VLLM 容器作为推理组件。 由于推理路由器不支持响应流，应用程序发送非流式请求，每个请求必须在大约一分钟内完成，与 `InvokeEndpoint` 相同的限制。 然后，我们在美国东部（俄亥俄州）创建一个路由器，其中一个路由目标列出了两者：

```python
sm = boto3.client("sagemaker", region_name="us-east-2")
rt = boto3.client("sagemaker-inference-router-runtime", region_name="us-east-2")

sm.create_inference_router(
    InferenceRouterName="my-router",
    RoutingTargets=[{
        "Name": "my-model",
        "Destinations": [
            {"ResourceArn": "arn:aws:sagemaker:us-east-2:111122223333:inference-component/ic-us-east-2"},
            {"ResourceArn": "arn:aws:sagemaker:us-west-2:111122223333:inference-component/ic-us-west-2"},
        ],
    }],
)
```

在发送流量之前，运行 `DescribeInferenceRouter` 并确认每个目的地的 `RoutingStatus` 是 `Routable`。

应用程序使用路由目标名称和发送到 `InvokeEndpoint` 的相同有效负载调用路由器，并从响应中读取服务目标和路由原因：

```python
resp = rt.invoke_inference_router(
    InferenceRouterName="my-router",
    RoutingTargetName="my-model",
    ContentType="application/json",
    Body=json.dumps({"messages": [{"role": "user", "content": "Who are you?"}]}),
)
print("Served by:", resp["InvokedRoutedResourceArn"])
print("Reason:   ", resp["RoutingReason"])
```

## 查看每个请求的去向

推理路由器为您提供两种路由视图：CloudWatch 中每个实时响应和指标的记录。

### 每个请求路由记录

每个实时响应都包括 `InvokedRoutedResourceArn` 中服务请求的目标的 ARN，以及 `RoutingReason` 中的路由原因。 路由原因是以下之一：

*   `local-preferred` – 由路由器区域的健康目的地提供服务。
*   `capacity-available` – 由具有可用容量的目的地提供服务。
*   `failover` – 远离无法可靠服务的目的地。
*   `only-healthy` – 由唯一符合条件的健康目的地提供服务。

我们建议使用应用程序自己的请求日志记录两个值。

异步响应不包括服务目标。 CloudWatch 中的路由器指标显示了异步请求的放置位置。

### CloudWatch中的路由器指标

路由器将 OpenTelemetry 指标发布到其自己的帐户和区域中，并标记为路由器、路由目标和目标：

*   `aws.sagemaker.inference_router.invocations` – 每个目的地的请求，在故障时带有 `error.type` 标签（`invocation_4xx`、`invocation_5xx` 或 `invocation_model_error`）。
*   `aws.sagemaker.inference_router.destination.duration` – 在目的地的时间，包括您的模型。
*   `aws.sagemaker.inference_router.overhead.duration` – 路由器自己的工作加上往返于另一个地区的网络时间。
*   `aws.sagemaker.inference_router.destination.status` – 每个目的地为 `healthy`、`overloaded` 或 `degraded`。

对不健康的目标以及所有错误类型的错误率进行警报。 见[Monitor an inference routers with Amazon CloudWatch and AWS CloudTrail](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-router-monitor.html)。

每个目标端点都在自己的帐户和区域中不断发布其现有的 SageMaker AI 指标。 要在一处查看它们，请使用 CloudWatch 跨帐户可观察性和跨帐户跨区域仪表板。

AWS CloudTrail 将路由器的 API 调用（创建、更新、删除、描述和列表）记录为管理事件和路由器调用作为数据事件。 您可以像对其他 SageMaker AI 数据事件一样在跟踪上启用数据事件。

## 计划您的部署

使用推理路由器进行设计时，请记住以下几点：

*   **将路由器放在您的大部分流量来源的区域。** 路由器总是更喜欢其所在区域的目的地。
*   **为每个区域调整大小，加上您希望它吸收的溢出。 为了保护端点的本地呼叫者，设置一个跨区域的流量上限，如[Protect a receiving endpoint with a cross-Region traffic cap](#protect-a-receiving-endpoint-with-a-cross-region-traffic-cap)中所述。 如果每个远程目的地达到其上限，超出组合上限的请求会返回节流错误。
*   **保留低成本的备用区域。 零拷贝的远程推理组件在故障转移期间只接收一小部分流量，而这些请求在有副本之前会失败。 在您依赖备用区域之前，至少保持一份副本运行，或在副本上配置自动缩放并确认其已扩展。
*   **在入口点计划弹性。** 路由器是区域性的，因此如果其区域受损，则调用它失败。 在两个区域中创建路由器，并在客户端之间切换。
*   **仅注册可能处理您的数据的目的地。** 可以在路由器的区域或您注册目的地的任何区域处理请求。 对于必须保持在一个地理位置的数据，请使用单独的路由器，例如一台路由器用于美国数据，另一种用于欧盟数据。 您负责配置路由器以符合您的数据驻留和合规义务。
*   ** 保持您自己的重试次数。 大约一分钟后，服务不可用的错误意味着请求超时并且模型可能已经运行，因此不要自动重试。
*   **从路由器中删除已删除的目标。
*   ** 私有呼叫路由器。** 虚拟私有云 (VPC) 中的应用程序可以通过支持 IPv4（不支持 IPv6/双堆栈）的接口 VPC 端点（AWS PrivateLink）呼叫路由器。

还要注意以下限制：

*   不支持响应流。
*   目标在大约一分钟内没有响应的实时请求失败并出现服务不可用的错误。
*   每台路由器最多可容纳20个路由目标，每个路由目标最多可容纳10个目标，实时有效载荷可达6 MB。 有关默认配额，例如每个帐户的路由器和请求费率，以及如何请求增加，请参阅 [Service Quotas in the Amazon SageMaker AI documentation.](https://docs.aws.amazon.com/general/latest/gr/sagemaker.html#limits_sagemaker)

## 结论

Amazon SageMaker AI 中的跨区域推理路由为您的应用程序提供了跨多个 AWS 区域和 AWS 账户中的终结点和推理组件的调用路径。 路由器更喜欢自己的区域，在目标无法可靠地服务时转移新请求，恢复后逐渐返回流量，并向您显示每个请求的运行位置以及原因。 您的端点、模型、容器和自动缩放策略不会改变。

从今天开始，大多数商业 AWS 区域（ME-South-1 和 Me-Central-1 除外）开始提供跨区域推理路由，用于实时和异步推理。

Amazon SageMaker AI 中的跨区域推理路由不收取额外费用。 您需要支付 SageMaker AI 端点和推理组件，以标准 SageMaker AI 定价服务您的请求，无论请求是直接到达它们还是通过推理路由器到达。 推理路由器将指标发布到路由器帐户中的 Amazon CloudWatch，并为这些指标和您在它们上运行的任何查询支付标准 CloudWatch 费率。 详情请参阅[Amazon SageMaker AI pricing.](https://aws.amazon.com/sagemaker/ai/pricing/)

要开始，请参阅跨区域推理路由的 [Amazon SageMaker AI documentation](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-router.html) 并探索 GitHub 上的示例 [notebook](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/inference-router)。
