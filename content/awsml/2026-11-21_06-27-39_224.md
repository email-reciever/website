客户越来越多地在GPU上自行托管大型语言模型（LLMs），以控制成本、准确性和延迟。然而，自行托管通常意味着为冗余的GPU工作付费，因为每个服务器上的小型、孤立的缓存无法持有或共享AI代理和聊天应用程序重发的不断增长的上下文。考虑一个可以在每个对话中积累数十万个标记的案例历史的法律AI助手。当律师在午餐后返回线程时，LLM的响应可能需要几分钟。接收请求的GPU服务器在其内存中没有这些历史记录。因此，GPU在写入一个单词之前会重新计算所有这些标记的键值（KV）注意力状态，这一步称为预填充。同样的模式也会减慢恢复的编码代理、代理AI助手和文档Q\&A助手的速度。使用Amazon ElastiCache的分布式KV缓存可以将自行托管的LLM推理成本降低多达40%，并将首个标记的时间（TTFT）降低多达80%。分布式KV缓存通过在GPU舰队旁边添加一个共享层来扩展GPU本地缓存，因此任何服务器都可以在会话、路由转换和服务器故障期间重用KV状态数天。“[宣布为自行托管LLM发布分布式KV缓存，配备Amazon ElastiCache](https://aws.amazon.com/blogs/database/announcing-distributed-kv-caching-for-self-hosted-llms-with-amazon-elasticache/)”深入探讨了技术细节和性能基准。

本文详细介绍了 [分布式 KV 缓存技能](https://github.com/aws/agent-toolkit-for-aws/tree/main/skills/specialized-skills/database-skills/distributed-kv-caching) 在 AWS Agent Toolkit 中的应用。通过此技能，您可以在几个提示中评估和设置分布式 KV 缓存，从而在您的编码代理中实现缓存。该技能指导代理完成检查工作负载是否受益于分布式 KV 缓存、设置测试或生产工作负载的缓存集群以及排除 LLM 推理缓存故障等步骤。该技能支持 [Kiro](https://kiro.dev/)、Claude Code、OpenAI Codex 和其他支持 Agent Skills 的编码代理。我们通过四次对话来演示该技能的工作原理：诊断第一个 token 过慢、缓存大小和价格、设置缓存以及修复传输失败。

## 为什么需要 KV 缓存技能以及它能做什么？

您的工作负载的益处取决于诸如 LLM 模型、用户流量模式和提示路由选择等特征，并且可能很难估计。我们创建了 [KVTrace 工具](https://github.com/aws-samples/amazon-elasticache-samples/tree/main/kvtrace) ，以便在不部署任何基础设施的情况下，从您自己的模型和流量中获得您工作负载的益处的近似估计，并且不收取额外费用。该技能简化了此评估和设置，并指导您的编码代理在更改任何内容之前遵循以下最佳实践：

* **在任何花费之前进行合规性检查。** 代理以只读的 `describe-instances` 调用读取您的 GPU 集群，并计算 Elastic Fabric Adapter (EFA) 接口的数量。它只询问无法看到的信息：引擎、模型、张量并行（TP）大小、KV 数据类型、服务器价格以及提示重复的频率。当某些内容不匹配时，它会停止并解释。
* **来自您的工作负载的数据。** 对于短提示，加载 KV 状态可能比重新计算它更耗时。在某个提示长度（阈值）以上，读取操作会更快。该阈值和您的提示重复频率决定了是否值得使用缓存。代理使用 KVTrace 估计您的流量带来的节省，并且不会产生额外的费用。如果节省的成本不能覆盖缓存的费用，它会停止。每个数字都指明了其来源。
* **使用现有的栈在推理服务器上管理配置。** 代理将 LMCache 连接器添加到现有的 vLLM 或 SGLang 引擎，包括在服务框架（如 llm-d 和 Ray Serve）下运行的 vLLM 工作器。它保持您的路由和引擎的设置，并将推理集群中的服务器设置为一个 KV ID 机制（哈希和种子）和一个显式的 KV 数据类型。匹配的设置可以避免密钥不匹配的情况，即每个服务器写入的 KV 状态其他服务器无法找到。
* **实施最佳实践。** 在生产流量到来之前，代理清空本地层次并检查两次缓存加载的运行结果是否相同，因为布局不匹配可能会产生健康的命中计数器和错误的答案。该技能指导代理在进行高影响操作（如创建、更改或删除资源）时寻求显式的批准。

## 前置条件

这些流程，从估计好处到设置，需要以下条件：

* 支持 Agent Skills 的编码代理，例如 Kiro 或 Claude Code。
* 支持 EFA RDMA 写的 GPU 实例，例如 p5。
* LMCache 0.5.8rc1 或更高版本和 vLLM 0.11.1 或更高版本（SGLang 0.5.13 或更高版本）。
* Valkey 9.1 或更高版本的 ElastiCache，在 cache.i8ge.48xlarge 节点上（如果设置缓存）。

## 流程 1：分布式 KV 缓存是否有帮助？

我们给代理以下提示： *“我的 vLLM 舰队在 p5 实例上提供 64K 令牌上下文的法律助手。对话返回需要 13 秒才能获取第一个令牌，因为 GPU 每次转折都会重新计算整个对话历史。如何解决这个问题？”*

代理将请求匹配到技能，并在 Kiro 中在加载之前请求批准。答案确定延迟是由冷预填充引起的，有三件事对于真实的部署很重要。首先，它检查不需要新基础设施的修复。如果您关闭了前缀缓存，重新打开它可以加快连续转弯的速度。如果具有会话亲和性的 GPU 前缀缓存命中率已经超过 90%，您可能不需要共享的 KV 缓存。第二，它确定特定于法律 AI 助手的约束。共享的 KV 缓存可以让一个租户从响应时间判断另一个租户是否发送了相同的文本。必须保持隔离的用例获得单独的缓存，而共享缓存的租户将自己的 ID 添加到 KV 哈希中。第三，它不猜测大小。它询问模型和 TP 大小、KV 数据类型、副本数量和路由，以及用户在转弯之间等待多长时间。

## 流程 2：估算节省

为了确定节省的规模，我们为代理提供了一个包含 8 个 p5 实例的示例集群，这些实例为多轮检索增强生成（RAG）助手提供 64,000 个令牌的提示。代理查找了 GPU 和缓存节点的价格，并从基准测试中推导出预填充率和 KV 大小。最后，代理推荐了两个 cache.i8ge.48xlarge 节点用于分布式 KV 缓存。下面的图表显示了代理的总结和它使用的输入。

[![代理的成本摘要，显示它查找的GPU和缓存节点价格以及两个推荐的缓存.i8ge.48xlarge节点](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22449-2.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22449-2.png)

图 2：代理的摘要和输入。它在 AWS 价格列表中查找了两个价格，并解释了它如何得出重新计算的数字

我们没有提供缓存命中率，即缓存可以服务的重新计算令牌的比例。因此，代理呈现场景并推荐运行KVTrace来确定缓存命中率。KVTrace [记录KV缓存事件](https://aws.amazon.com/blogs/database/announcing-distributed-kv-caching-for-self-hosted-llms-with-amazon-elasticache/#savings-for-your-workload)来自vLLM或SGLang。然后，它将事件在每个候选大小的共享KV缓存上离线重放。记录器从不写入令牌ID或提示文本。跟踪记录块哈希和令牌计数。块哈希来自令牌内容，因此当您的提示敏感时，请传递`--anonymize-key-file`。技能在每个GPU服务器上记录代表性窗口，例如整个工作日。代理还指出，释放的GPU时间只有在您运行更少的服务器或在同一服务器上提供更多流量时才会转化为美元。

## 流程 3：设置分布式 KV 缓存

我们提示代理：“从头开始设置共享的 L2 KV 缓存以用于 LLM 推理。” 在创建任何内容之前，代理会请求您确认在可用区中设置建议的缓存节点数，并估计价格。 一旦确认，代理会创建具有 EFA 权限的正确安全组和 Valkey 9.1 集群，该集群使用带有缓存驱逐策略的自定义参数组。 LMCache 获取 [自己的缓存用户](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/distributed-kv-caching-security.html#distributed-kv-caching-security.lmcache-user)，密码存储在 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 中。 代理准备 GPU 服务器，并为每个 GPU 服务器启动一个 LMCache 服务器。 然后它使用一个小的测试对象检查集群，并确认重复的提示从缓存中加载其 KV 状态，使用远程直接内存访问 (RDMA)。 在 GPU 舰队中，技能检查测量的 L2 共享与 KVTrace 预测。 要查看完整的设置以及每个命令，请参阅 Amazon ElastiCache 文档中的 [开始使用分布式 KV 缓存](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/distributed-kv-caching-getting-started.html)。

## Flow 4: 故障排除

> 提示： “我的 LMCache 服务器连接到 ElastiCache 集群，BLOB.RDMA_HELLO 成功，但实际数据传输失败。INFO largeobj 显示 rdma_write_errors 增加。问题出在哪里？”

按照技能的故障排除指南，代理根据症状模式推理，确定可能的原因是安全组阻止了其自身成员之间的 EFA 流量。它提供命令来检查和修复规则。

[![代理的故障排除答案：最可能的原因是缺少自引用的出站规则。它解释了为什么 HELLO 成功而 RDMA 传输失败，给出了 describe-security-groups 命令来检查规则，并提供 authorize-security-group-egress 和 ingress 命令来修复它们，并列出了四个检查项，如果规则已经正确，则运行这些检查项。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22449-4.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22449-4.png)

## 开始使用

您可以从 [Agent Toolkit for AWS](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/) 获取 [分布式 KV 缓存](https://github.com/aws/agent-toolkit-for-aws/tree/main/skills/specialized-skills/database-skills/distributed-kv-caching) 技能或 AWS MCP Server。然后，描述您的问题或要求您的 AI 代理在您的 GPU 集群上减少成本和延迟，以开始使用。要了解更多关于 ElastiCache 的分布式 KV 缓存及其性能基准的信息，请参阅 [AWS 博客](https://aws.amazon.com/blogs/database/announcing-distributed-kv-caching-for-self-hosted-llms-with-amazon-elasticache/)。您可以在 [Amazon ElastiCache 文档](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/distributed-kv-caching-getting-started.html) 中找到有关使用 AWS 命令行接口 (AWS CLI) 入门的信息，并在 [GitHub 仓库](https://github.com/aws-samples/amazon-elasticache-samples/tree/main/kvtrace) 中了解更多关于 KVTrace 的信息。
