Amazon SageMaker 推理：2026 发布在审查中，第 2 部分
===========================================================

从第一个端点到全球舰队：托管端点和超足点推理的 14 次发射

9 月，[Amazon SageMaker Inference: 2026 year-to-date launches in review](/blogs/machine-learning/amazon-sagemaker-inference-2026-year-to-date-launches-in-review/) 涵盖了 13 次发布，缩短了从模型到生产端点的路径。 他们中的大多数人回答了一个问题：我如何让这个模型快速可靠地服务？ 这篇文章涵盖了接下来的 13 次发射，使 2026 年的总数达到 26 次。

一旦模型投入生产，问题就会发生变化。 团队想知道现在流量是真实的模型应该在哪个配置上运行，如何将更多模型安装到他们已经付费的GPU上，当下一个模型对于一台机器来说太大时该怎么办，为什么请求在一个区域等待而GPU在另一个区域中等待，以及为什么在没有人改变任何东西时延迟会上升。 这篇文章在团队通常遇到的订单中处理这些问题。

对于 Hyperpod 推理，它列出了额外的路由策略、对模型服务框架的更广泛支持以及扩展的多区域网络。 推理网关和全球推理网关提供路由和多区域工作，托管 NVIDIA Dynamo 是一个新的服务框架。 对于托管端点，路线图指向了与 AWS AI 环境的其他部分更深入的集成。 推理建议现在由 Amazon SageMaker AI Studio、SageMaker Python SDK 和工程师已经使用的编码代理运行，终端节点现在可以跨区域和帐户路由请求。

为了保持每个部分的具体，我们通过博客文章跟踪一个假设的团队。 在春季，他们使用第 1 部分的发布，在单个 SageMaker AI 端点后面的 70B 参数模型后面推出了客户支持助手。到秋天，他们需要支持更多的产品线，采用更大的推理模型，在第二个区域为客户服务，并保持他们的 GPU账单平。

### SageMaker AI Studio中的推理推荐（2026年7月）

_blog:_ [Launching UI for generative AI inference recommendations in Amazon SageMaker AI](/blogs/machine-learning/launching-ui-for-generative-ai-inference-recommendations-in-amazon-sagemaker-ai/)

通过 API 启动自动实例、容器和优化选择。 SageMaker AI Studio 中的推理建议现在也可以作为引导的低代码工作流程提供。 在 Studio 中，选择 **Jobs**，然后选择 **Inference Optimization**。 选择用例配置文件（交互、生成、汇总或自定义）、优化目标（最小化延迟、最大化吞吐量或最小化成本）以及来自 SageMaker JumpStart、Amazon Simple Storage Service (Amazon S3)、模型注册表或现有 SageMaker 的模型 模型。

SageMaker AI 使用 NVIDIA AIPERF 在真实 GPU 基础设施上对候选配置进行基准测试，并应用与目标相匹配的技术，例如用于吞吐量的推测解码或延迟内核调整。 您可以通过 TTFT、令牌间延迟、吞吐量和成本比较排名结果，然后将所选配置部署到 Studio 的实时端点。

### 推理建议中的LoRa适配器支持（2026年9月）

_开发者指南_：[Get recommendations for models with LoRA adapters](https://docs.aws.amazon.com/sagemaker/latest/dg/generative-ai-inference-recommendations-adapters.html)

许多团队使用 LoRa 适配器专门针对多个用例提供一种基础模型。 保存在 GPU 内存中的每个适配器都减少了端点可以服务的并发请求的数量，而正确的平衡取决于实例类型、适配器的数量和流量配置文件。

推理建议现在接受适配器作为模型包 Amazon 资源名称 (ARN)，用于 SageMaker 微调或 S3 URI 生成的适配器，用于来自外部管道的适配器，例如 Hugging Face PEFT。 SageMaker AI 对真实 GPU 基础架构上的适配器数量和并发性进行基准测试，并为您的工作负载返回排名结果。 输出列出了每个适配器的两种格式。 建议的部署使用 SageMaker 推理组件，基本模型有一个组件，每个适配器使用一个组件，因此您可以添加、更新或删除适配器，而不会中断基本模型或其他适配器。

### 基于SLA的并发搜索（2026年9月）

_blog:_ [Right-size generative AI endpoints with concurrency sweeps on Amazon SageMaker AI](/blogs/machine-learning/right-size-generative-ai-endpoints-with-concurrency-sweeps-on-amazon-sagemaker-ai/)

正确调整端点的大小意味着找到它可以维持的最高并发性，而不会突破延迟或错误目标。 到目前为止，这意味着手动选择并发级别，运行扫描，根据服务级别协议 (SLA) 检查结果，并在模型或实例更改时以更窄的范围重复。

推理推荐现在包括直接找到该边界的搜索。 将 `search_recipe` 设置为 `max-concurrency-under-sla` 并为最大 TTFT、每个输出令牌的最大时间、最大端到端延迟和最大错误率的任何组合提供目标。 基准测试引擎（AIPERF）从广泛的范围开始，根据探测通过或失败的范围缩小它的范围，并且比线性扫描的迭代次数更少。 结果报告了最大的通过并发（`feasible_max`），或者，如果没有级别限定，最小的失败一个（`infeasible_min`）。

搜索使用与并发扫描相同的 `CreateAIWorkloadConfig` 和 `CreateAIBenchmarkJob` API。 可选参数（`concurrency_min`、`concurrency_max`、`search_max_iterations` 和 `search_initial_points`）约束成本并加快收敛速度。

### 优化生成人工智能推理的代理技能（2026年10月）

_blog:_ [New agent skill: Amazon SageMaker optimized generative AI inference for your coding agent](/blogs/machine-learning/new-agent-skill-amazon-sagemaker-optimized-generative-ai-inference-for-your-coding-agent/)

工程师越来越多地询问他们的编码代理使用哪个实例和容器。 如果没有扎根的知识和获得真正的基准，代理只能猜测，错误的实例选择稍后会显示为错过的延迟目标或浪费的花费。

通过 [Agent Toolkit for AWS](/products/developer-tools/agent-toolkit-for-aws/) 获得的 AWS-AI-ML 技能提供了 Kiro 内置 SageMaker AI 推理专业知识的编码代理。 工程师用通俗易懂的语言描述他们需要的东西，代理可以做到以下几点：

*   **查找正确的实例。** 针对 Amazon S3、SageMaker JumpStart 或 Hugging Face Hub 中的模型的测量吞吐量、延迟和 TTFT 的排名部署选项。
*   **benchmark 一个实时端点。** 来自真实负载覆盖吞吐量、p50 和 p99 延迟、令牌间延迟和支持的并发的报告。

答案以测量性能为基础，并作为工程师在自己的凭据下审查和运行的 SageMaker Python SDK v3 代码提供。 设置大约需要 10 分钟。 该技能适用于任何支持模型上下文协议 (MCP) 和 SageMaker AI Studio JupyterLab Spaces 的代理。

对于支持团队，一项包含所有四个适配器的推荐作业，然后针对 500 毫秒 TTFT 目标进行并发搜索，取代了他们在 4 月运行的手动扫描。 拥有它的工程师可以从笔记本开始工作或要求编码代理运行它。

### SageMaker AI 控制台中的推理组件（2026 年 10 月）

_开发者指南：_ [Inference Components in the SageMaker AI Console](https://docs.aws.amazon.com/sagemaker/latest/dg/realtime-endpoints-deploy-models.html)

使用推理组件，您可以在一个端点和大小上分别托管多个模型，并分别缩放每个模型。 到目前为止，它们只能通过 SDK 和 AWS 命令行界面 (AWS CLI) 获得。 每个创建、调整大小和缩放策略都必须编写脚本，并且没有对每个模型使用的内容的单一视图。

在 SageMaker AI 控制台中，您现在可以创建、查看、更新和删除推理组件：

*   **创建和编辑。** 创建一个包含推理组件的端点，稍后添加或删除组件，并更改每个组件的加速器、CPU、内存和复制计数。
*   ** 缩放每个模型。** 为每个组件设置自动缩放策略，减少到零副本，因此空闲模型停止持有加速器。
*   **MONITOR.** 查看同一页面上的警报和每个组件指标。

控制台调用与 SDK 和 CLI 相同的 SageMaker AI API，因此团队可以在控制台上启动并进行自动化，或者可视化地管理脚本化组件。

### NVIDIA多实例GPU的GPU分区（2026年10月）

_blog:_ [SageMaker Inference now supports Multi-Instance GPU to maximize GPU utilization for model endpoints](/blogs/machine-learning/sagemaker-inference-now-supports-multi-instance-gpu-to-maximize-gpu-utilization-for-model-endpoints/)

[GPU partitioning](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-components-accelerator-partitioning.html) 使用 NVIDIA 多实例 GPU (MIG) 技术将一个物理 GPU 划分为多达七个分区，具体取决于加速器。 每个分区都有专用的 GPU 计算和内存，具有完整的硬件隔离。 为推理组件创建端点并为每个组件选择分区类型时，定义分区布局。 应用程序通过推理组件名称继续调用模型，因此客户端代码不会更改。

MIG 隔离分区之间的 GPU 计算和内存。 同一实例上的模型仍然共享主机 CPU、主机内存、网络、存储和端点路由。 您支付整个实例小时的标准费率，因此节省的费用来自在每个实例上放置更多模型，而不是来自较低的小时价格。

### 在Hyperpod推理上管理的Nvidia Dynamo（2026年11月）

_blog:_ [Managed NVIDIA Dynamo on Amazon SageMaker HyperPod Inference](/blogs/machine-learning/managed-nvidia-dynamo-on-amazon-sagemaker-hyperpod-inference/)

第 1 部分涵盖了 HyperPod 上大型模型的两个构建块：推理算子 V3.2 中的分解预填充和解码，以及作为托管分层 KV 缓存的一部分的 KV 感知路由。 此启动增加了多节点服务并更改了操作堆栈的人。 NVIDIA Dynamo 是一个开源推理框架，提供多节点分片服务、分解预填充和解码以及 KV 感知路由。 团队已经可以在自己的 Kubernetes 集群上运行 Dynamo，但他们必须围绕它构建和操作所有节点：将副本的所有节点放在一起，布线弹性结构适配器 (EFA) 网络，以便 Prefill 可以将其 KV 缓存交付给以硬件速度解码，维护服务图像，并恢复 当一个失败的节点删除一个多节点副本时。

通过此次发布，Dynamo 作为 HyperPod 上的托管服务引擎运行。 Dynamo 做出服务决策：模型如何分片、预填充和解码如何拆分以及每个请求的去向。 Hyperpod 提供了这些决定所依赖的内容：

*   **容量和网络。** GPU 容量和 EFA 网络，预置和有线自动连接。
*   **Node Recovery.** 节点健康监控和替换，当节点发生故障时自动重新安排多节点工作人员。
*   **端点操作。** 自动缩放、端点注册、TLS 和可观察性。
*   **一个安装和升级路径。

Dynamo 为 Hyperpod 带来的功能是：

*   **多节点（分片）服务。** 模型的一份副本跨越多个节点，因此您可以提供不适合任何单个实例的模型。
*   **分解的预填充和解码。** 提示处理和令牌生成在单独的 GPU 池上运行，每个池都在适合其工作的实例类型上运行，因此长长的提示不再会减慢其他用户的响应速度。
*   **KV-AWARE 路由。** 每个请求都发送给已经保存其 KV 缓存的工作人员，从而减少了 TTFT。

有三种方式开始。 在自我管理的 Kubernetes 上运行 Dynamo 的团队可以使他们现有的 `DynamoGraphDeployment` (DGD) 表现基本保持不变。 已经在 Hyperpod 推理上的团队可以更新附加组件并向现有 `InferenceEndpointConfig` 添加一个短 `dynamoSpec` 块，Hyperpod 将其转换为 DGD，而现有的端点继续服务。 新手团队可以在控制台中启用附加组件和 Dynamo 的情况下创建集群。 在每种情况下，客户端都会调用标准的 OpenAI 兼容端点，因此客户端代码不会更改。

托管 Dynamo 支持 VLLM、SGLANG 和 TensorRT-LLM，并且在 [Amazon SageMaker HyperPod](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod.html#sagemaker-hyperpod-available-regions) 可用的区域中可用。

### 端点的kv-cache-aware路由(2026年11月)

_blog:_ [Amazon SageMaker AI real-time endpoints now support KV cache aware routing](/blogs/machine-learning/amazon-sagemaker-ai-real-time-endpoints-now-support-kv-cache-aware-routing/)

具有较长提示或多回合对话的应用程序在请求中重复一个大前缀。 模型服务器可以重复使用匹配的 KV 缓存，但仅当下一个请求到达保存它的实例时。 第 1 部分涵盖的前缀感知路由指纹对每个提示的开始进行指纹，并将匹配提示发送到同一实例。 因为它在请求历史记录中工作，因此随着模型服务器添加和驱逐条目，它对每个实例缓存的视图变得不那么准确。

kv-cache-aware 路由使用模型容器报告的缓存状态。 容器将创建缓存和驱逐事件发布到中央缓存索引，SageMaker AI 将每个请求路由到保存最长匹配缓存前缀的合格实例。 这会为长时间上下文提示、多回合对话和共享动态提示前缀的工作负载引发缓存重用。

它适用于使用推理组件（包括 LoRa 适配器）的单模型端点和端点。 它支持 `InvokeEndpoint`、`InvokeEndpointWithResponseStream` 以及与 OpenAI 兼容的 API 进行完成和聊天完成负载。 在端点配置中打开它。 第一个版本需要一个经过 AWS 验证的模型容器，它实现了缓存事件、令牌化、度量和 OpenAI 兼容的接口。 您可以在详细的推理可观察性中跟踪 KV 缓存命中率。

**使用哪一种。** 前缀感知路由适用于任何容器，无需更改容器。 kv-cache-aware 路由需要一个经过验证的容器并跟踪实际的缓存，这在前缀变化或缓存快速切换时最有帮助。

### Hyperpod的推理网关（2026年9月）

_blog:_ [Introducing Amazon SageMaker HyperPod Inference Gateway](/blogs/machine-learning/introducing-amazon-sagemaker-hyperpod-inference-gateway/)

在超足类群中，容量和需求很少排队。 一个 pod 可以通过一个长上下文请求的一部分，其 KV 缓存几乎已满，而下一个 Pod 处于空闲状态，或者已经保存了下一个请求所需的提示前缀或 LoRa 适配器。 在无法查看该 GPU 状态的情况下，新请求在繁忙的 Pod 后面排队，团队会添加 GPU 以保护延迟，而不是使用它们拥有的延迟。 每个模型也有自己的端点，因此客户必须跟踪每个模型的一个端点。

推理网关是一个 GPU 感知的路由器，它与超足底推理 Operator 插件一起安装，并为每个集群提供一个 OpenAI 兼容的所有模型的端点。 对于每个请求，它从每个模型 pod 中读取实时信号并选择最好的一个，您可以根据每个工作负载调整权重：

*   **kv 缓存利用率。** 避免缓存几乎已满的 pod。
*   **队列深度和运行请求。** 避免具有积压的 Pod 并平衡活动工作。
*   **前缀缓存命中率。** 首选 Pod 可能保留提示前缀。
*   **Lora Adapter Residency.** 更喜欢已经保存请求的适配器的 Pod，从而避免了交换延迟。

与循环路由相比，它在混合 GPU 世代中将 P99 TTFT 降低了高达 97%，在突发流量下降低了 98%。 它适用于 SageMaker Hyperpod 可用的所有地区。

### Hyperpod的全球推理网关（2026年11月）

_blog：[Introducing Amazon SageMaker HyperPod Global Inference Gateway](/blogs/machine-learning/introducing-amazon-sagemaker-hyperpod-global-inference-gateway-one-endpoint-across-regions-and-clusters/)_

推理网关在集群中路由，每个集群只能服务发送给它的请求。 一个请求可以在一个区域中的饱和集群上等待，而 GPU 在另一个区域中处于空闲状态。 客户必须自己选择集群，当集群失败时，工程师必须手动移动流量。

全局推理网关为团队提供了一个 SageMaker 管理的端点，跨越他们注册的每个集群。 对于每个请求，它对队列深度、空闲 KV 缓存、与来电者的接近和最近的错误率进行评分，并通过 AWS 私有骨干将请求发送到最佳的请求。 该集群中的推理网关仍然选择 Pod。 请求使用 SIGv4 和 IAM 进行身份验证。 当集群变得饱和或不健康时，流量会在 30 秒内转移到下一个最佳集群，而客户端没有任何操作，集群在恢复时会重新加入池。 路由权重是可调的，如果你让它们未设置，则默认设置。

添加或删除模型或集群不会更改调用端点的应用程序的任何内容。 在您发布集群之前，无法访问集群，并且已发布的资源会保留在您的帐户中。 全局推理网关可在 [AWS documentation.](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-model-deployment-global-inference-gateway.html) 中列出的区域中使用

### Amazon SageMaker AI 中的跨区域推理路由

_blog:_ [Keep inference running through regional capacity shortfalls with cross-Region inference routing in Amazon SageMaker AI](/blogs/machine-learning/keep-inference-running-through-regional-capacity-shortfalls-with-cross-region-inference-routing-in-amazon-sagemaker-ai/)

在托管端点上，相同的想法采用跨区域推理路由的形式，即跨区域端点发送实时和异步请求的托管路由，同一帐户中或不同帐户中。 您将在路由目标下提供相同模型的端点分组，应用程序会调用目标而不是特定的区域端点。 路由器不添加容量、复制模型或部署端点，并且现有的调用路径继续工作。

路由器替换了当今团队构建的故障转移逻辑：

*   **一个调用路径。** SageMaker 首先尝试本地端点，并在本地的端点无法处理请求时将流量移动到另一个注册的端点。
*   **一个路由策略。** 该策略将端点指标与服务端容量信号相结合，包括客户无法自行观察到的容量错误。
*   **私人连接。** 跨区域流量使用受管跨帐户授权模型在 AWS PrivateLink 上运行，因此路由到另一个区域或帐户不需要 Internet 或 NAT 网关。
*   **溢出和驻留护栏。

### 连续性能监控（2026年11月）

博客：[Amazon SageMaker AI now detects latency drift, idle GPUs, and missed optimizations on your inference endpoints](/blogs/machine-learning/amazon-sagemaker-ai-now-detects-latency-drift-idle-gpus-and-missed-optimizations-on-your-inference-endpoints/)

Amazon SageMaker AI 现在持续监控您的生成式 AI 推理端点，并告诉您更改何时可以提高性能或降低成本。 默认情况下，SageMaker AI 推理端点的监控处于启用状态，无需设置，您可以选择退出端点。 SageMaker AI 只关注操作信号：延迟、GPU 利用率和端点的服务配置。 它不会读取您的请求或回复。 当发现清除其置信度阈值时，AWS 管理控制台上会显示一条通知，并且在笔记本电脑和 CLI 中工作的团队通过电子邮件发送相同的消息。 建议的操作在 SageMaker AI Studio 中打开了 SageMaker AI 代理体验，结果已经填写，因此分析、比较和部署更改发生在一次对话中。 在您应用它之前，什么都不会部署，您可以随时关闭监控。

发现有以下三种类型：

*   **流量更改后的延迟漂移。** 当添加检索等更改延长提示时，TTFT 会上升。 该发现每周量化回归，并建议针对最近的流量重新运行推理建议，以找到使 TTFT 退缩的配置。
*   **自部署以来存在配置差距。** 终点从未针对其工作负载进行过调整，并且发现指向将缩小差距的变化。
*   **空闲GPU容量。

### 就地滚动模型更新（2026年11月）

标准滚动更新一次一批替换一个端点，每个批次都在新配置的实例上运行。 在大型 GPU 车队中，这意味着在每一步都能找到新的容量，当下一批实例不可用时，更新可能会中途失败。 每个释放的实例还必须完成清理，然后才能再次使用，这会减慢推出的速度。

SageMaker AI 现在更新了模型。 它在开始时提供一小批附加实例，将流量转移到该批次，然后更新它释放的实例，重新使用它们以在车队的其余部分中滚动更改。 更新仍然分阶段推出，但它只需要一次新的容量。 对于批量大小为 2 的 20 个实例的队列，更新会获取 2 个新实例而不是 20 个。客户不需要更改任何内容。 与第 1 部分中的容器缓存一样，该改进会自动应用于滚动模型更新。

图 6：滚动更新在每一步获取新实例。 就地滚动更新在开始时获取一批并重复使用机队的其余部分

对于支持团队，漂移观察发现量化了 TTFT 回归，并针对最近的流量打开了新的推荐作业。 他们用一批额外的实例推出更新的模型，而不是为车队中的每个实例找到新的 GPU 容量。
