Amazon SageMaker AI 现在可以检测推理端点上的延迟漂移、空闲 GPU 和错过的优化
======================================================= 。 =======================================================

每个推理端点在投入生产的那一天都得到了很好的调整。 团队在启动时选择适合模型及其流量的实例类型、服务配置和扩展设置。 随着端点的顺利运行，他们可以理解地继续下一个优先级。 然而，工作量很少保持不动。 流量模式不断发展，提示增长更长，VLLM 提供新版本的服务引擎，SageMaker 推理开发新的优化技术，新的微调检查点改变了模型所需的资源。 随着时间的推移，一个经过良好调整的端点悄悄地漂移。 第一个令牌边缘向上的延迟和时间。 从来没有非常理想的配置会缺少可用的性能提升。 为从未实现的需求提供的 GPU 一周又一周地处于空闲状态。 因为没有任何故障，没有警报响起，并且在用户感觉到或账单反映它之前，这种漂移被忽视了。

[Amazon SageMaker AI](/sagemaker/ai/) 现在监控您的生成式 AI 推理端点，并通过在 [SageMaker JupyterLab](https://docs.aws.amazon.com/sagemaker/latest/dg/studio-updated-jl.html) 中使用 [Generative AI optimized inference recommendations](/blogs/machine-learning/amazon-sagemaker-ai-now-supports-optimized-generative-ai-inference-recommendations/) 功能来告诉您更改何时可以提高性能或降低成本。 默认情况下，使用 VLLM 服务容器和 GPU 实例的 SageMaker AI 推理端点的监视处于打开状态，无需设置，您可以选择退出端点。 SageMaker AI 只关注操作信号：延迟、GPU 利用率和端点的服务配置。 它不会读取您的请求或回复。 从这些信号中可以看出三种发现：

*   **延迟漂移：** 中位数 (P50) 的端到端延迟或第一个令牌的时间的周一周上升。
*   **未使用的容量：**您为该坐位付费的GPU大部分是闲置的。
*   **配置差距：** 缺少更新的性能改进或安全补丁的服务容器，或您的模型支持但端点不使用的投机解码或 GPU 内核调整等优化。

SageMaker AI 通过 AWS Health 发送一个发现，每个端点有一份通知，涵盖该端点的发现。 当通知到达时，您可以在一个地方对其进行操作。 它通过端点打开了 SageMaker AI 代理体验，并通过其最近的流量填写了 SageMaker AI 代理体验。从那里，您运行推理建议，将您的当前配置与替代方案进行比较，并在响应时间、吞吐量和每百万代币成本方面进行比较。 这将判断电话变成了以数据为支持的决策。 基准在单独的计算上运行，并且在您选择应用结果之前，您的端点不会发生任何变化。

在这篇文章中，我们展示了 SageMaker AI 如何监控您的端点以及如何阅读它通过 AWS Health 发送的通知。 然后，我们展示了如何在 SageMaker Studio 中从通知转到基准决策。 我们介绍了三个示例场景，展示了如何安全地应用或驳回推荐，并解释如何选择终端之外的监控。

解决方案概述
------------------

SageMaker AI 推理建议遵循四步循环：观察、通知、推荐和决定。 每个步骤的设计都是为了让您保持控制，并且您的生产端点在没有您明确的操作的情况下不会改变。

1.  **Observe –** 对符合条件的端点的延迟和容量使用情况进行监控。 它不会读取您的请求或响应，也不会带来额外的 GPU 成本。
2.  **NOTIFY –** 当有一些值得采取的措施时，您会在 AWS Health 中收到一则简单的语言通知，以及电子邮件，解释观察到的内容、重要性以及推荐的下一步。
3.  **推荐（选择）-** 一项选择打开 SageMaker AI 代理体验，预先填充了端点及其观察到的流量，因此您可以在单独的计算中对备选方案进行基准测试。
4.  **Decide –** 并排比较响应时间、吞吐量和成本。 在您应用结果之前不会更改生产。

先决条件
--------------

监控本身不需要设置，默认情况下是打开的。 当您选择通过运行基准测试并（可选地）应用更改来对发现采取行动时，以下先决条件适用：

1.  访问 AWS Health 和 AWS 用户通知控制台。
2.  SageMaker Studio 域和 AWS 身份和访问管理 (IAM) 权限，用于运行推理推荐作业和更新端点。
3.  您要测试的基准实例的充足服务配额。

**成本说明：** 监控没有 GPU 成本。 基准测试使用标准 SageMaker AI 费用，或您的机器学习 (ML) 预留（如果您有的话）。

了解发现通知
--------------------------------

您在控制台和电子邮件中的 AWS Health 中收到通知，并且每个都遵循相同的结构，因此可以快速扫描：

1.  ** endpoint:** 发现适用于哪个端点。
2.  **我们注意到的：** 清楚地说明的观察结果，估计值清楚地标记为估计值。
3.  **为什么重要：** 对延迟、容量或成本的影响。
4.  **推荐行动：**在SageMaker Studio中的代理体验中进行单一的选择来调查。

通知报告观察和标签估计。 此时还没有运行基准。 代表通知如下：

主题：\[可能需要采取行动\] SageMaker AI 推理改进对您的终点

默认情况下，SageMaker AI 跟踪推理端点的延迟和容量使用情况，并发现其中之一的改进。 它不会读取您的请求或回复。

_我们注意到的：在过去的一周里，与前一周相比，这个终点上的第一个令牌的时间增加了。

建议操作：打开 SageMaker Studio 以对单独计算的替代方案进行基准测试。 您的生产端点没有更改。

**cadence**：每个端点都会收到一份涵盖适用调查结果的通知。 您一次最多收到每个端点的一个通知，涵盖其所有发现，并且 SageMaker AI 限制了一次帐户收到的数量。 通知是特定于 AWS 区域的，因此当您登录到该端点的区域时，您会看到端点的发现。

演练：从通知到决定
----------------------------------------

在本节中，我们回顾了一些端点优化的场景，这些场景将触发要报告的发现。

### 情景1：每周捕获延迟回归

一个团队在单个 SageMaker AI 端点上运行聊天助手。 他们添加检索以提高答案质量，因此每个请求现在都包含检索到的上下文页面，提示会变得更长。 没有任何中断，也没有警报，他们设置了行程，但反应开始得更慢。

SageMaker AI 将端点 (P50) 的中位数时间与上周的第一个令牌和中值端到端延迟进行了比较。 当任何一个在一周内上升到足够多时，它会标记变化。 因为比较是与端点自己的历史，所以团队不需要提前设置阈值。

*   **通知：** AWS Health 报告说，与前一周相比，第一个令牌的时间增加了。
*   **Studio 会话：** 一种选择打开代理体验，预填充端点及其观察到的流量。
*   **benchmark:** 会话在单独的计算上测试张量并行设置和其他实例类型或大小。
*   **决定：**团队比较延迟、吞吐量和成本，然后将获胜配置应用于一种变体。

### 场景 2：打开您的流量可以从中受益的优化

平台团队在 SageMaker AI 端点上托管内部代码完成模型。 他们使用默认服务设置部署它，并且从未重新访问它们。 模型和服务容器支持投机解码，这是一种用于更快响应的技术，但未启用。 SageMaker AI 将此视为机会。 它是否有帮助取决于端点的流量，例如并发运行的请求数量以及提示和响应的时间长短。 该通知建议运行推理建议，以对端点的最近流量进行投机解码的基准测试，并显示它是否值得开启。

*   **通知：** AWS Health 报告说，支持但未启用旨在使响应更快的技术。
*   **Studio Session:** 加载端点配置后，代理体验会打开。
*   **Benchmark:** 会话将当前配置与启用投机解码进行比较。 与非高峰流量相比，结果可能在峰值不同。
*   **决定：** 如果收益在重要的交通上保持，则团队应用它。 否则，它们会保持当前配置。

### 场景 3：大小适中的 GPU

一个总结终点的大小用于吸引一小部分计划的受众，因此它的 GPU 大部分时间都处于空闲状态。 这种情况还显示了一个正确的决定可能是根本不做出改变的情况。

1.  **通知：** AWS Health 报告说，端点支付了大部分未使用的 GPU 容量。
2.  **Studio 会话：** 代理体验以端点及其观察到的峰值流量打开。
3.  **benchmark:** 会话在观察到的峰值流量时测试更便宜的实例类型和更小的大小。
4.  **决定：** 团队权衡每月节省的空间与他们想要的计划增长空间，并可能决定保持当前的规模。

申请或驳回建议
--------------------------------

您始终处于控制状态，并且不会自动部署任何内容。 从通知的推荐操作中选择 SageMaker AI 中的 **Open** 时，[Amazon SageMaker Studio](/sagemaker/ai/studio/) 打开 JupyterLab 空间并显示将在代理聊天中运行的提示。 以下屏幕截图显示了在也运行较旧的 VLLM 服务容器的端点上查找延迟漂移的提示：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ml-22416-edit1.png)

当您选择 **Run** 时，代理体验将在 SageMaker Studio 的 JupyterLab 空间的聊天面板中打开。 它用简单的语言总结了这一发现，重述了你要求它做什么，并在它采取任何行动之前与你核对。 以下屏幕截图显示了代理总结调查结果并要求继续：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ml-22416-edit2.png)

确认后，代理会生成一个笔记本，为终结点创建推理推荐作业。 笔记本使用 SageMaker Python SDK，从端点获取模型，并从其指标中获取流量配置文件，并使用 AWS Health 事件标记作业，以便将结果追溯到发现。 每个步骤都是一个单独的笔记本单元，因此您可以在运行之前对其进行查看或编辑。

以下屏幕截图显示了记录作业详细信息并在三种候选实例类型中启动推荐作业的笔记本单元。

作业完成后，您可以将当前配置与响应时间、吞吐量和成本的替代方案进行比较。 当您准备好对基准测试结果采取行动时，我们建议使用安全的推出模式：

*   在应用之前查看建议的更改，包括配置差异和基准的延迟、吞吐量和成本。
*   首先应用一种生产型号，并保持当前配置可用于回滚。
*   持有或驳回发现是正常结果。 该通知将保留在您的 AWS 健康事件历史记录中。

管理监控和通知
---------------------------------

您可以管理监控以及通知您的方式：

1.  管理您在 AWS 用户通知控制台中接收通知的方式。
2.  可选地，例如每月安排重复性建议。

**收集和未收集的内容：** 监控在端点级别读取聚合的延迟和容量遥测。 它不会读取您的请求或响应内容，也没有 GPU 成本。

**退出监控：** 如果您不希望 SageMaker AI 监控端点，请在模型的容器上设置 `OPT_OUT_TRACKING` 环境变量，并使用您选择的值。 当您在 `PrimaryContainer` 或模型中的另一个容器上调用 `CreateModel` 时，您可以在 `Environment` 映射中设置它。

如果端点上的容器携带此变量，SageMaker AI 将不收集该端点的监控遥测数据，包括引擎指标、GPU 指标和启动配置详细信息。 因此，它不会发送该端点的通知。

清理
---------

为避免持续收费，请在关注此帖子时清理您创建的资源：

1.  删除您为演练创建的任何测试端点或资源。
2.  如果适用，请在 Amazon Simple Storage Service (Amazon S3) 中删除基准工件。
3.  恢复您应用的任何测试配置更改。

总结
-----------

借助 SageMaker AI 推理建议现在自动监控您的端点，优化会从时间点快照转变为持续信号。

您的端点不断告诉您他们何时漂移、何时错过了改进或何时为闲置容量付费。 单一选择将带您进行您控制的基准、并排决策。

有关如何开始的更多信息，请访问 [Amazon SageMaker AI](/sagemaker/ai/) 并查看 [Amazon SageMaker AI documentation](https://docs.aws.amazon.com/sagemaker/)。
