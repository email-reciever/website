# Using light-dark() without getting caught out

![](https://secure.gravatar.com/avatar/a8e040142716a4b44d014d80fbcf99c635b1d8faabfe469b6954a8ef2f168595?s=80&d=retro&r=pg)

By [Geoff Graham](https://css-tricks.com/author/geoffgraham/) on Nov 27, 2026

I honestly hadn’t thought about “getting caught” by `light-dark()` — particularly when [leaning heavily on it for this site](https://css-tricks.com/css-tricks-version-20/) — but [Martin Underhill explains](https://www.tempertemper.net/blog/using-light-dark-without-getting-caught-out):

> Without fallbacks, browsers that don’t support `light-dark()`typically use black text on a white background in Light Mode, and white text on a dark grey background in Dark Mode. They’re not the exact colours I’d want, but my website looks fine.
> 
> Again, it’s risky, so test thoroughly.

Like Martin, I initially began implementing color themes based on media queries sniffing out user preferences. But it became super cumbersome to write `prefers-color-scheme` time and again. I mean, totally DX-world problems. I also remembered [the piece Sara Joy wrote](https://css-tricks.com/come-to-the-light-dark-side/) with us a while back encouraging a jump into the `light-dark()` waters and thought it’d be nice to take that advice.

Doing that, I ran into another DX annoyance: writing two color values for each `light-dark()`. CSS variables help, of course, but even then it exhausted me. That says something more about me than the feature, but I digress. So, I took Martin’s process one step further to abstract all the things:

```css
:root {
  --gray-1: #eaeaea; /* Light */
  /* ... */
  --gray-10: #111; /* Dark */

  --text: light-dark(var(--gray-1), var(--gray-10));
}

.article-content {
  color: var(--text);
}
```

Very nice, at least for my penchant for laziness. But I ran into another issue because sometimes text needs to go the other direction. Keep abstracting. I could define the background variable which is normally the contrast to text:

```css
:root {
  --gray-1: #eaeaea; /* Light */
  /* ... */
  --gray-10: #111; /* Dark */

  --text: light-dark(var(--gray-1), var(--gray-10));
  --surface: light-dark(var(--gray-10), var(--gray-1));
}

.widget-content {
  color: var(--surface);
}
```

Works, but using a helper called “surface” on a property controlling `color` bothers me too. I may be lazy, but I’m a little anal with semantics. Hence:

```css
:root {
  --gray-1: #eaeaea; /* Light */
  /* ... */
  --gray-10: #111; /* Dark */

  --text: light-dark(var(--gray-1), var(--gray-10));
  --text-reverse: light-dark(var(--gray-10), var(--gray-1));
}

.article-content {
  color: var(--text-reverse); /* Light then dark */
}

.widget-content {
  color: var(--text-reverse); /* Dark then light */
}
```

…where “reverse” means it goes the opposite direction of a normal “light-dark” call and the “dark” value is called first. But even that is still too much for my brain to handle because now I’m left with multiple tokens to remember if I want things to be super semantic:

```css
:root {
  --gray-1: #eaeaea; /* Light */
  /* ... */
  --gray-10: #111; /* Dark */

  --text: light-dark(var(--gray-1), var(--gray-10));
  --text-reverse: light-dark(var(--gray-10), var(--gray-1));

  --surface: light-dark(var(--gray-1), var(--gray-10));
  --surface-reverse: light-dark(var(--gray-10), var(--gray-1));
}

.article-content {
  background-color: var(--surface); /* Dark then light */
  color: var(--text-reverse); /* Light then dark */
}

.widget-content {
  background-color: var(--surface-reverse); /* Light then dark */
  color: var(--text-reverse); /* Dark then light */
}
```

so I went with an even more general abstraction:

```css
:root {
  --gray-1: #eaeaea; /* Light */
  /* ... */
  --gray-10: #111; /* Dark */

  --light-dark: light-dark(var(--gray-1), var(--gray-10));
  --dark-light: light-dark(var(--gray-10), var(--gray-1));
}

.article-content {
  background-color: var(--dark-light); /* Dark then light */
  color: var(--light-dark); /* Light then dark */
}

.widget-content {
  background-color: var(--dark-light); /* Dark then light */
  color: var(--light-dark); /* Light then dark */
}
```

Perfect, no. But I’m pretty happy with it.

Back to Martin and fallbacks, he goes about it with a classic cascade safeguard:

```css
color: black;
color: light-dark(black, white);

background-color: white;
background-color: light-dark(white, black);
```

He’s totally right and I ought to be doing that as well. Maybe I will, but I could help thinking that a `light-dark()` fallback argument would be nice. Spitballing here, of course:

```css
color: light-dark(var(--dark-light), var(--light-dark) / var(--dark-light));
```

Now we’re getting verbose. But so are fallbacks in general. Indeed, Martin asked if moving to `light-dark()` is even worth it given the need to think about fallbacks. Is it really more efficient than a media query at this point? His byte-savings were negligible. I decided to compare what the differences would have been on CSS-Tricks:
