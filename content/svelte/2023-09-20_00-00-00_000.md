2019年，Svelte 3将JavaScript变成了[reactive language](/blog/svelte-3-rethinking-reactivity)。 Svelte是一个Web UI框架，它使用编译器来改变这样的声明性组件代码...

应用程式

    <script>
让计数 = 0；
    
函数增量() {
计数 += 1；
}
    </script>
    
    <button on:click={increment}>
点击次数：{计数}
    </button>

    <script lang="ts">
让计数 = 0；
    
函数增量() {
计数 += 1；
}
    </script>
    
    <button on:click={increment}>
点击次数：{计数}
    </button>

...进入严格优化的JavaScript，当`count`状态发生变化时更新文档。 因为编译器可以“看到”引用 `count` 的地方，所以生成的代码是 [highly efficient](/blog/virtual-dom-is-pure-overhead)，而且因为我们像 `let` 和 `=` 一样劫持了语法，而不是使用繁琐的 API，你可以 [write less code](/blog/write-less-code)。

我们得到的一个常见反馈是“我希望我能像这样写下我所有的 JavaScript”。 当你习惯了组件内部的东西神奇地更新时，回到无聊的旧程序代码感觉就像从颜色到黑白。

svelte 5 用 _runes_ 改变了所有这些，它解锁了 _universal、细粒度的反应性_。

介绍符文

在我们开始之前[](#Before-we-begin)
---------------------------------

尽管我们正在改变幕后的工作方式，但 Svelte 5 应该是几乎所有人的临时替代品。 新功能可选——您现有的组件将继续工作。

我们还没有 Svelte 5 的发布日期。我们在这里向您展示的是一个可能会改变的正在进行的工作！

什么是符文？[](#What-are-runes)
---------------------------------

> **符文** /ro͞on/ _noun_
> 
> 用作神秘或魔法符号的字母或标记。

符文是影响 svelte 编译器的符号。 而 Svelte 今天使用 `let`、`=`、`export` 关键字和 `$:` 标签来表示特定的东西，而符文使用 _function syntax_ 来实现同样的事情等等。

例如，要声明一个反应状态，我们可以使用 `$state` 符文：

应用程式

    <script>
让计数 = 0；
让计数 = $state(0);
    
函数增量() {
计数 += 1；
}
    </script>
    
    <button on:click={increment}>
点击次数：{计数}
    </button>

    <script lang="ts">
让计数 = 0；
让计数 = $state(0);
    
函数增量() {
计数 += 1；
}
    </script>
    
    <button on:click={increment}>
点击次数：{计数}
    </button>

乍一看，这似乎是退一步——甚至可能[un-Svelte-like](https://twitter.com/stolinski/status/1438173489479958536)。 如果 `let count` 默认是响应式的，那不是更好吗？

嗯，没有。 现实情况是，随着应用程序的复杂性越来越高，弄清楚哪些值是反应性的，哪些值不是很棘手。 启发式仅适用于组件顶层的 `let` 声明，这可能会导致混淆。 在 `.svelte` 文件中使用代码和 `.js` 中的另一种方式可能会使代码难以重构，例如，如果您需要将某些内容转换为 [store](/tutorial/svelte/introducing-stores)，以便可以在多个地方使用它。

运行时反应性[](#Runtime-reactivity)
----------------------------------------

今天，Svelte 使用 _compile-time reactivity_。 这意味着如果您有一些代码在依赖关系发生变化时使用 `$:` 标签自动重新运行，则在 svelte 编译您的组件时确定这些依赖关系：

    <script>
导出出租宽度；
出口让高度；
    
// 编译器知道它应该重新计算 `area`
// 当 `width` 或 `height` 更改时...
$：面积 = 宽度 * 高度；
    
// ...它应该记录 `area` 的值
// 当 _it_ 更改时
$: console.log(area);
    </script>

这很好......直到它没有。 假设我们重构了上面的代码：

const multiplyByHeightConst MultiplyByHeight: (width: any) => number = (width(parameter) width: any) => width(parameter) width: any * heightany;
$: areaany = multiplyByHeightConst 乘以高度: (width: any) => number(widthany);

因为 `$: area = ...` 声明只能“看到”`width`，所以当 `height` 更改时不会重新计算它。 因此，代码很难重构，并且了解 Svelte 选择何时更新哪些值会变得相当棘手，而超出一定程度的复杂性。

Svelte 5 引入了 `$derived` 和 `$effect` 符文，它们在评估它们时确定它们的表达式的依赖关系：

    <script>
让 { 宽度，高度 } = $props(); // 代替 `export let`
    
常量面积 = $派生（宽度 * 高度）；
    
$效果(() => {
console.log（区域）；
});
    </script>

与 `$state` 一样，`$derived` 和 `$effect` 也可用于 `.js` 和 `.ts` 文件中。

信号提升[](#Signal-boost)
-----------------------------

像所有其他框架一样，我们已经意识到 [Knockout](https://knockoutjs.com/) 一直是正确的。

Svelte 5 的反应性由 _signals_ 提供支持，本质上是 [what Knockout was doing in 2010](https://dev.to/this-is-learning/the-evolution-of-signals-in-javascript-8ob)。 最近，信号已被 [Solid](https://www.solidjs.com/) 推广并被许多其他框架采用。

不过，我们做的事情有点不同。 在 Svelte 5 中，信号是一个底层实现细节，而不是直接与之交互的内容。 这意味着我们没有相同的 API 设计约束，并且可以最大限度地提高效率_和人体工程学。 例如，我们避免了在通过函数调用访问值时出现的缩小类型问题，并且在服务器端渲染模式下编译时，我们可以完全放弃信号，因为在服务器上它们只是开销。

信号解锁 _fine-gained reactivity_，这意味着（例如）更改为大列表中的值不需要使列表中的所有_other_ 成员无效。 因此，Svelte 5 的速度非常快。

更简单的时间[](#Simpler-times-ahead)
-----------------------------------------

符文是一个附加功能，但它们使一大堆现有概念过时：

*   组件顶层 `let` 与其他任何地方的区别
*   `export let`
*   `$:`，连同其所有的怪癖
*   `<script>`和`<script context="module">`之间的不同行为
*   `$$props`和`$$restProps`
*   生命周期函数（`afterUpdate`之类的东西可以只是`$effect`函数）
*    store API 和 `$` store 前缀（虽然不再需要商店，但它们不被弃用）

对于那些已经使用 Svelte 的人来说，这是要学习的新东西，尽管希望这些东西可以让您的 svelte 应用程序更容易构建和维护。 但新人不需要学习所有这些东西——它只会出现在名为“旧东西”的文档的一部分中。

这只是一个开始。 对于后续版本，我们有一长串的想法，这些想法将使 Svelte 更简单、更有能力。
