如果您上个月参加了 [Svelte Summit](https://sveltesummit.com/)，您可能已经看到了我的演讲，未来主义的 Web 开发，我终于解决了关于 Svelte 的最常见问题之一：Sapper 什么时候到达 1.0 版？

答案：从来没有。

这有点半开玩笑——正如演讲所解释的那样，它实际上更多的是对 Sapper 和更名的重写——但它引起了社区的许多新问题，现在是我们对 Sapper 的继任者的期望更清晰的时候了， 斯维特基特。

来自[Svelte Summit](https://sveltesummit.com/)的“未来网络开发”

什么是 Sapper？[](#What's-Sapper)
--------------------------------

[Sapper](https://sapper.svelte.dev) 是一个 _app 框架_（或“metaframework”）构建在 svelte（这是一个 _component_ 框架）之上。 它的工作是让使用所有现代最佳实践（如服务器端渲染 (SSR) 和代码分割）轻松构建苗条的应用程序，并提供使开发高效和有趣的项目结构。 它使用 _filesystem-based routing_ （由 [Next](https://nextjs.org/) 推广并被许多其他框架采用，尽管有一些增强功能）——您的项目的文件结构反映了应用程序本身的结构。

虽然 svelte 主页和文档鼓励您 [degit](https://github.com/Rich-Harris/degit) [sveltejs/template](https://github.com/sveltejs/template) 存储库开始构建应用程序，但 Sapper 长期以来一直是我们推荐的构建应用程序的方式； 这篇博文（在撰写本文时！）是用 Sapper 渲染的。

为什么我们要迁移到新事物？[](#Why-are-we-migrating-to-something-new)
--------------------------------------- ---------------------------------------

首先，[sveltejs/template](https://github.com/sveltejs/template) 和 [sveltejs/sapper-template](https://github.com/sveltejs/sapper-template) 之间的区别是令人困惑的，特别是对于新手来说，要变得很小。 使用 Svelte 开始构建应用程序的单一推荐方法将带来巨大的好处：我们简化了入职，减少了维护和支持负担，并可能开始探索通过具有可预测的项目结构解锁的新可能性。 （这最后一部分故意含糊不清，因为需要时间来充分了解这些可能性是什么。）

除此之外，我们一直被改写 Sapper 的想法所吸引。 这部分是因为多年来代码库变得有点不稳定（[Sapper started in 2017](/blog/sapper-towards-the-ideal-web-app-framework)），但主要是因为网络最近发生了很大变化，是时候重新考虑我们的一些基本假设了。

这个新东西有什么不同？[](#How-is-this-new-thing-different)
---------------------------------------------------------------

这些基础假设中的第一个假设是您需要使用 [webpack](https://webpack.js.org/) 或 [Rollup](https://rollupjs.org/) 之类的模块捆绑器来构建应用程序。 这些工具跟踪应用程序的依赖关系图，分析和转换代码（例如，将 svelte 组件转换为 JS 模块），以便创建可以在任何地方运行的代码束。 作为 Rollup 的原始创建者，我可以证明这是一个令人惊讶的复杂问题，适用于 Fiendish Edge 情况。

几年前你当然需要一个捆绑器，因为浏览器本机不支持 `import` 关键字，但今天它不太正确。 现在，我们看到了_Unbundled开发工作流的兴起，这非常简单：开发服务器可以提供模块（如果需要转换为JavaScript）_on-demand_，这意味着启动本质上是即时的 您的应用程序变大。

[Snowpack](https://www.snowpack.dev/) 是这个运动的先锋，这就是 Sveltekit 的力量。 它速度惊人，并且具有出色的开发经验（热模块重新加载、错误覆盖等），我们一直在与 Snowpack 团队密切合作，开发 SSR 等功能。 如果您习惯于使用带有 rollup 的 Sapper（由于其架构，它的架构优先于最有效的输出），热模块重新加载是特别具有启发性的。

这并不是说我们完全放弃了捆绑商。 优化您的应用程序以进行生产仍然至关重要，Sveltekit 使用 Rollup 使您的应用程序尽可能快速和精简（其中包括将样式提取到静态 `.css` 文件中）。

另一个基本假设是服务器提供的应用程序需要服务器。 Sapper 有效地有两种模式 — `sapper build`，它创建了一个必须在节点服务器上运行的独立应用程序，以及 `sapper export` 将您的应用程序作为适合托管在 GitHub 页面上的服务中的静态文件集合。

静态文件几乎可以在任何地方运行，但运行节点服务器（以及监控/扩展等）不太简单。 如今，我们正在目睹_serverless平台_的转变，其中您作为应用程序作者不需要考虑您的代码正在运行的服务器，所有的复杂性。 由于 [vercel-sapper](https://github.com/thgh/vercel-sapper) 之类的内容，您可以在无服务器平台上运行 Sapper 应用程序，但这肯定不是您所说的惯用语。

Sveltekit 完全支持无服务器范例，并将在所有主要的无服务器提供商的支持下推出，并使用“适配器”API 来针对我们未正式迎合的任何平台。 此外，我们将能够进行部分预渲染，这意味着可以在构建时生成静态页面，但动态页面可以按需呈现。

我什么时候可以开始使用它？[](#When-can-I-start-using-it)
----------------------------------------------------

如果你感到勇敢，你可以立即开始：

npm init svelte@next

这将搭建一个新项目并安装 `@sveltejs/kit` CLI，它提供了开发和构建应用程序的工具。

我们不推荐它！ 没有文档，我们将无法提供任何形式的支持。 它也很可能经常坏掉。

当我们仍处于探索模式时，这项工作正在私人单仓完成。 我们的计划是准备好公开测试版并在我们完成一些问题后在此处宣布 - 回购本身将保持私密性，但我们将创建一个地方来收集 Yolo 人群的反馈。 之后，我们将努力实现 1.0 版本，其中涉及打开 repo。

我不会对时间做出任何坚定的承诺，因为我不喜欢违背承诺。 但我认为_我们谈论的是几周而不是几个月。

如果我不想使用 sveltekit 怎么办？[](#What-if-I-don't-want-to-use-SvelteKit)
--------------------------------------- ---------------------------------------

您不必这样做 — 总是可以将 Svelte 作为独立软件包或通过像 [rollup-plugin-svelte](https://github.com/sveltejs/rollup-plugin-svelte) 这样的捆绑器集成来使用。 我们认为您必须弯曲 Svelte 以适应您的工作流程，无论多么深奥，并使用 [Elder.js](https://github.com/Elderjs/elderjs)、[Routify](https://routify.dev/)、[Plenti](https://plenti.co/)、[Crown](https://crownframework.com/)、[JungleJS](https://www.junglejs.org/) 等第三方应用程序框架。

打字稿？[](#TypeScript)
---------------------------

不用担心，如果没有完整的 TypeScript 支持，我们不会推出。

如何迁移现有的 Sapper 应用程序？[](#How-can-I-migrate-my-existing-Sapper-apps)
------------------------------------------ ------------------------------------------

在大多数情况下，迁移 Sapper 代码库应该相对简单。

有一些不可避免的变化（能够在无服务器平台上运行意味着我们需要用更多可移植的等效值替换自定义 `server.js` 文件和 `(req, res) => {...}` 功能），我们正借此机会修复一些设计缺陷，但总的来说，Sveltekit 应用程序会感觉非常熟悉 给 Sapper 用户。

详细的迁移指南将伴随 1.0 发布。
