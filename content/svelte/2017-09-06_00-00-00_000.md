不喜欢 CSS 很时尚。 有很多原因，但归结为：CSS 是 _不可预测的_。 如果您从未有过调整风格规则并意外破坏您认为完全不相关的布局的经验——通常是在您尝试发货的时候——那么您要么是新手，要么您是比我们其他人更好的程序员。

因此，JavaScript 社区卷起袖子开始工作。 在过去的几年里，库的寒武纪爆发了，旨在使 CSS 表现，统称为 _css-in-js_。

您可能没有意识到的是** CSS最大的问题可以在没有CSS-in-JS**的情况下解决。 没有这些问题，编写 CSS 不仅仅是可以忍受的——它是令人愉快的。 而且您不必为 CSS-in-JS 引入的其他问题找到解决方案。

这篇文章绝不是对 CSS-in-JS 社区所做的辛勤工作的批评。 它是 JS 生态系统中最活跃的角落之一，每周都会出现新的想法。 相反，我的目的是说明为什么另一种方法——基于具有真正 CSS 的单文件组件——如此令人愉快。

## CSS最大的问题[](#The-biggest-problem-with-CSS)

CSS中的一切都是全球性的。 正因为如此，用于一点标记的样式通常最终会影响另一个标记。 由于_that_，开发人员经常求助于野生的命名空间约定（不是“规则”，因为它们很难强制执行），这主要只是增加了RSI的风险。

当你在团队中工作时，情况会变得更糟。 没有人敢触及其他人创作的风格，因为通常不清楚他们在做什么，他们应用什么标记，以及如果您删除它们会发生什么灾难。

所有这一切的结果是 **append-only 样式表**。 没有办法知道哪些代码可以安全地删除，因此通常使用另一种更具体的样式撤消一些现有样式——即使在相对较小的项目中也是如此。

## 单个文件组件更改了所有[](#Single-File-Components-change-all-that)

SFCS 背后的想法很简单：您将组件写入 HTML 文件中，该文件（可选地）包含描述组件样式和行为的 `<style>` 和 `<script>` 属性。 Svelte、Ractive、Vue 和 Polymer 都遵循这种基本模式。

[Read the introductory blog post](/blog/frameworks-without-the-framework) 如果您是 Svelte 的新手。 或 [read](https://twitter.com/padolsey/status/899717303234908160) [the](https://twitter.com/sveltejs/status/901818357644701696) [testimonials](https://twitter.com/sveltejs/status/901818106309476352)。

（对于本文的其余部分，我们将使用 svelte，显然。但是如果使用模板语言的想法让你不寒而栗——你的恐惧是错位的，但这是另一天的话题——那么只需使用 Vue ，让你在你的 证监会。）

结果发生了几件奇妙的事情：

*   您的样式被_scopeed to the component_。 没有更多的泄漏，不再是不可预测的级联。 并且不再有旨在防止冲突的 Sesquipedalian 类名。
*   您无需在文件夹结构中找到破坏您的东西的规则。
*   编译器（在 Svelte 的情况下）可以 **识别和删除未使用的样式**。 没有更多仅附加的样式表！

这就是他们所说的“使用平台”的意思吗？

每个代码编辑器都已经知道 CSS，因此您很有可能获得自动完成、linting、语法突出显示等——所有这些都没有额外的 js-fatigue-inducting 工具。

而且因为它是真正的CSS，而不是一些camelcased引用——无处不在，我们可以利用“DevTools中的调整，粘贴回我们的源代码”工作流程，这是我个人无法生活的。 请注意，我们开箱即用地获取 CSS 源地图，因此您可以立即确定有问题的线条。 很难夸大这一点的重要性：当您处于所见即所得的模式时，您没有考虑组件树的考虑，因此有一种强大的方法来确定_这些该死的样式的来源_是必不可少的。 如果其他人最初编写了组件，那么双重如此。 （我向您保证，这是对 CSS 工作流程的最大生产力提升。如果您在没有源代码地图的情况下编写样式，那么您几乎可以肯定会浪费大量时间。我知道我是。）

svelte 转换您的选择器（使用也应用于受影响元素的属性，尽管确切的机制不重要且可能会发生变化）以实现范围界定。 它警告并删除任何未使用的规则，然后缩小结果并将其写入 `.css` 文件。 还有一个实验性的新选项可以编译到 Web 组件，使用 Shadow DOM 来封装样式，如果这是你的果酱。

这一切都是可能的，因为您的 CSS 被解析（使用 [css-tree](https://github.com/csstree/csstree)）并在标记的上下文中进行静态分析。 静态分析为各种令人兴奋的未来可能性打开了大门——更智能的优化、a11y 提示——如果在运行时动态计算您的样式，则会更加困难。 我们才刚刚开始。

## 但是我们可以添加工具来做\[x\]![](#But-we-can-add-tools-to-do-x)

如果您对视频的反应“很好，但是如果我们为每个编辑器使用TypeScript并编写插件，那么我们可以获得所有自动完成和语法突出显示的内容” - 换句话说，如果您相信为了与CSS实现对等性，那么构建、记录、推广和维护一个车队是有意义的 辅助项目——那么，你和我可能永远不会对视！

## 我们没有所有的答案——但是[](#We-don't-have-all-the-answers-yet)

说了这么多，css-in-js 确实指出了一些挥之不去的问题的答案：

*   我们如何从npm安装样式？
*   我们如何重用在一个地方定义的常量？
*   我们如何编写声明？

就个人而言，我还没有发现这些问题超过了上述方法的好处。 您可能有一组不同的优先级，它们可能是您放弃 CSS 的足够理由。

但归根结底，无论如何你都必须知道 CSS。 爱它或厌恶它，你至少必须_学习_它。 作为 Web 的保管人，我们有一个选择：创建使 Web Dev 学习曲线更陡峭的抽象，或者共同解决 CSS 的坏部分。 我知道我选择了哪个。
