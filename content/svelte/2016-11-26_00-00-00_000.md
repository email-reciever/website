> 等等，这个新框架有一个_runtime_？ 呃。 谢谢，我会通过。 **– 2018年的前端开发人员**

我们向用户发送了太多的代码。 像许多前端开发人员一样，我一直在否认这一事实，认为在您的应用程序已经交互后，可以在页面加载时提供 100KB 的 JavaScript 是可以的——只需使用 [one less .jpg!](https://twitter.com/miketaylr/status/227056824275333120) 即可。

但我错了。 100kb 的 .js 不等于 100kb 的 .jpg。 不仅仅是网络时间会扼杀你的应用程序的启动性能，而是分析和评估脚本所花费的时间，在此期间浏览器变得完全没有响应。 在移动设备上，这些毫秒级的速度非常快。

如果您不相信这是一个问题，请在 Bluesky 上关注 [Alex Russell](https://bsky.app/profile/infrequently.org)。 亚历克斯 [hasn’t been making many friends in the framework community lately](https://twitter.com/slightlylate/status/728355959022587905)，但他没有错。 但是，使用 Angular、React 和 Ember 等框架的提议替代方案尚未在前端世界中获得关注，而且肯定不是缺乏营销。

也许我们需要重新思考整个事情。

## 框架_really_解决了什么问题？[](#What-problem-do-frameworks-really-solve)

常见的观点是，框架可以更轻松地管理代码的复杂性：框架使用虚拟 DOM 差异等技术抽象出所有繁琐的实现细节。 但这不是真的。 充其量，框架会改变复杂性，远离你必须编写的代码和你没有的代码。

相反，像 React 这样的想法如此疯狂和当之无愧地成功的原因是它们可以更轻松地管理您的 _concepts_ 的复杂性。 框架主要是构建思想的工具，而不是代码。

鉴于此，如果框架_没有在浏览器中实际运行怎么办？ 如果它将您的应用程序转换为纯普通的 JavaScript，就像 Babel 将 ES2016+ 转换为 ES5 一样？ 您无需支付大量运行时间的前期费用，而且您的应用程序会变得非常快，因为您的应用程序和浏览器之间没有抽象层。

## 介绍纤细[](#Introducing-Svelte)

Svelte 是一个新的框架，可以做到这一点。 您使用 HTML、CSS 和 JavaScript 编写组件（加上一些额外的位 [learn in under 5 minutes](https://v2.svelte.dev/guide)），在构建过程中，Svelte 将它们编译为小型独立的 JavaScript 模块。 通过静态分析组件模板，我们可以确保浏览器尽可能少地完成工作。

[Svelte implementation of TodoMVC](https://svelte-todomvc.surge.sh/) 重 3.6kb 拉链。 相比之下，React Plus ReactDOM _without 任何应用程序代码_ 的压缩约为 45kb。 浏览器只需要大约 10 倍的时间来评估 React，就像 Svelte 使用交互式 toDomvc 启动和运行一样。

一旦你的应用程序_is_启动并运行，根据[js-framework-benchmark](https://github.com/krausest/js-framework-benchmark) **svelte速度快**。 它比 React 快。 它比 Vue 快。 它比 Angular、Ember、Ractive、Preact、Riot 或 Mithril 快。 它与 Inferno 竞争，目前可能是世界上最快的 UI 框架，因为 [Dominic Gannaway](https://bsky.app/profile/trueadm.dev) 是一个向导。 （Svelte 在移除元素方面较慢。我们是 [working on it](https://github.com/sveltejs/svelte/issues/26)。）

它基本上和 Vanilla JS 一样快，这是有道理的，因为它_is_ Vanilla JS – 只是您不必编写的 Vanilla JS。

## 但这不是重要的事情[](#But-that's-not-the-important-thing)

嗯，这很重要——性能很重要。 然而，这种方法真正令人兴奋的是，我们最终可以解决 Web 开发中一些最棘手的问题。

考虑互操作性。 想要 `npm install cool-calendar-widget` 并在您的应用程序中使用它？ 以前，如果您已经使用了（正确版本的）小部件设计的框架，您才能做到这一点——如果 `cool-calendar-widget` 是在 React 中内置的，并且您正在使用 Angular 那么硬奶酪。 但是，如果小部件作者使用了 Svelte，则可以使用您喜欢的任何技术构建使用它的应用程序。 （在待办事项列表中：将 svelte 组件转换为 Web 组件的方法。）

或 [code splitting](https://twitter.com/samccone/status/797528710085652480)。 这是一个好主意（仅加载用户在初始视图中需要的代码，然后再获取其余部分），但是有一个问题——即使您最初只提供一个 React 组件而不是 100，_您仍然必须自己提供 React 本身。 有了svelte，代码分割可以更有效，因为框架嵌入在组件中，组件很小。

最后，作为一个开源维护者，我已经与很多人进行了很多工作：您的用户总是希望_他们的_功能优先考虑，并且低估了不需要这些功能的人的成本。 框架作者必须始终平衡项目的长期健康状况与满足用户需求的愿望。 这非常困难，因为很难预料到——更不清楚——增量膨胀的后果，而且需要认真的软技能来告诉人们（他们可能一直在热情地宣传你的工具）他们的功能还不够重要。 但是使用像 Svelte 这样的方法，可以为不使用它们的人绝对没有成本地添加许多功能，因为实现这些功能的代码在不必要的情况下不会由编译器生成。

## 我们刚刚开始[](#We're-just-getting-started)

Svelte 非常新。 还有很多工作要做——创建构建工具集成、添加服务器端渲染器、热重载、过渡、更多文档和示例、入门工具包等。

但是您已经可以使用它构建丰富的组件，这就是为什么我们直接进入稳定的 1.0.0 版本。 [Read the guide](https://v2.svelte.dev/guide)、[try it out in the REPL](/repl)，然后前往 [GitHub](https://github.com/sveltejs/svelte) 以帮助启动前端发展的下一个时代。
