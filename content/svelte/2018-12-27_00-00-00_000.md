是时候仔细看看了。

那么...是虚拟dom_slow_吗？[](#So-is-the-virtual-DOM-slow)
-----------------------------------------------------------

不完全是。 这更像是“虚拟 DOM 通常足够快”，但有一些警告。

React 的最初承诺是，您可以在每个状态更改上重新渲染整个应用程序，而不必担心性能。 在实践中，我认为这并不准确。 如果是这样，就不需要像 `shouldComponentUpdate` 这样的优化（这是一种告诉 React 当它可以安全地跳过组件时的方式）。

即使使用 `shouldComponentUpdate`，一口气更新整个应用程序的虚拟 DOM 也是一项工作。 不久前，React 团队引入了一种叫做 React Fiber 的东西，它允许将更新分解成更小的块。 这意味着（除其他外）更新不会长时间阻塞主线程，尽管它不会减少总工作量或更新所花费的时间。

开销是从哪里来的？[](#Where-does-the-overhead-come-from)
---------------------------------------------------------------------

最明显的是[diffing isn’t free](https://twitter.com/pcwalton/status/1015694528857047040)。 如果不先将新的虚拟 DOM 与之前的快照进行比较，您就无法将更改应用到真实 DOM。 以前面的 `HelloMessage` 为例，假设 `name` 道具从“世界”变为“每个人”。

1.  两个快照都包含一个元素。 在这两种情况下，它都是 `<div>`，这意味着我们可以保持相同的 DOM 节点
2.  我们列举了旧的 `<div>` 和新的所有属性，以查看是否需要更改、添加或删除任何属性。 在这两种情况下，我们都有一个属性——一个值为 `"greeting"` 的 `className`
3.  下降到元素中，我们看到文本发生了变化，所以我们需要更新真正的DOM

在这三个步骤中，只有第三个在这种情况下具有价值，因为与绝大多数更新一样——应用程序的基本结构没有变化。 如果我们可以直接跳到第 3 步，那将更有效率：

为什么框架会使用虚拟 DOM？[](#Why-do-frameworks-use-the-virtual-DOM-then)
------------------------------------------- -------------------------------------------

重要的是要了解虚拟 DOM 不是功能_。 这是一种达到目的的手段，目的是声明性的、国家驱动的 UI 开发。 Virtual DOM 很有价值，因为它允许您在不考虑状态转换的情况下构建应用程序，性能通常足够好_。 这意味着更少的错误代码，更多的时间花在创造性的任务上，而不是乏味的任务上。

但事实证明，我们可以在不使用虚拟 DOM 的情况下实现类似的编程模型——这就是 Svelte 的用武之地。
