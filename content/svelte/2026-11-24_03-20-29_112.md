如果您在过去的几年中使用过JavaScript框架，您可能已经听过这样一句话：“虚拟DOM很快”，通常这是为了说明它比*真实*的DOM更快。这种说法出乎意料地具有持久性——例如，人们问Svelte如何在不使用虚拟DOM的情况下实现快速。

是时候更仔细地看看这个问题了。

## 什么是虚拟DOM？[](#What-is-the-virtual-DOM)

在许多框架中，您通过创建`render()`函数来构建应用程序，例如这个简单的[React](https://reactjs.org/)组件：

```ts
function HelloMessage(props) {
	return <div className="greeting">Hello {props.name}</div>;
}
```

您可以不使用JSX来实现同样的事情...

```js
function HelloMessage(props) {
	return React.createElement('div', { className: 'greeting' }, 'Hello ', props.name);
}
```

...但结果是相同的——一个表示页面现在应该如何显示的对象。这个对象就是虚拟DOM。每当您的应用程序状态更新时（例如，当`name`属性更改时），您都会创建一个新的虚拟DOM。框架的任务是将新的虚拟DOM与旧的虚拟DOM*对比*，以确定必要的更改并将其应用于真实DOM。

## 这个说法是如何开始的？[](#How-did-the-meme-start)

关于虚拟DOM性能的误解可以追溯到React的发布。 在[重新思考最佳实践](https://www.youtube.com/watch?v=x7cQ3mrcKaY)中，前React核心团队成员Pete Hunt在2013年的一个开创性演讲中，我们了解到以下内容：

> 这实际上非常快，主要是因为大多数DOM操作往往很慢。 已经有很多对DOM的性能优化工作，但大多数DOM操作往往会丢帧。

![Pete Hunt at JSConfEU 2013](/media/rethinking-best-practices.jpg)

来自 [重新思考最佳实践](https://www.youtube.com/watch?v=x7cQ3mrcKaY) 的截图，于JSConfEU 2013

但是等一下！ 虚拟DOM操作是*除了*最终对真实DOM的操作。 它唯一可能更快的方式是如果我们将其与一个效率较低的框架（2013年有很多这样的框架！）进行比较，或者反对一个稻草人 —— 即认为另一个选择是做一些没有人实际做的事情：

```js
onEveryStateChange(() => {
	document.body.innerHTML = renderMyApp();
});
```

Pete很快就澄清了...

> React 不是魔法。就像你可以使用汇编语言以 C 语言的方式来优化 C 编译器一样，你可以使用原始的 DOM 操作和 DOM API 调用来优化 React，如果你愿意的话。然而，使用 C 或 Java 或 JavaScript 可以带来数量级的性能改进，因为你不必担心...关于平台的具体细节。使用 React，你可以构建应用程序而不必考虑性能问题，且默认状态下速度很快。

...但这并不是让我印象深刻的部分。

## 那么... 虚拟 DOM *慢* 吗？[](#So-is-the-virtual-DOM-slow)

并不完全是这样。更像 ‘虚拟 DOM 通常足够快’，但有一些注意事项。

React 的原始承诺是，你可以在每个状态变化时重新渲染整个应用程序，而不必担心性能问题。实际上，我不认为这已经被证明是准确的。如果是这样的话，就不会需要像 `shouldComponentUpdate` 这样的优化（它是一种告诉 React 何时可以安全地跳过一个组件的方法）。

即使使用 `shouldComponentUpdate`，一次性更新整个应用的虚拟 DOM 仍然是一项大量的工作。 一段时间前，React 团队引入了一个叫做 React Fiber 的东西，它允许将更新分解成更小的块。 这意味着（除其他事项外）更新不会长时间阻塞主线程，尽管它不会减少工作的总量或更新所需的时间。

## Where does the overhead come from?[](#Where-does-the-overhead-come-from)

最明显的是，[diffing 不是免费的](https://twitter.com/pcwalton/status/1015694528857047040)。您不能在比较新虚拟 DOM 与之前的快照之前，将更改应用于实际 DOM。以之前的 `HelloMessage` 示例为例，假设 `name` 属性从 'world' 改变为 'everybody'。

1. 两个快照都包含一个元素。在两种情况下，它都是一个 `<div>`，这意味着我们可以保持相同的 DOM 节点
2. 我们枚举旧的 `<div>` 和新的 `<div>` 上的所有属性，以查看是否需要更改、添加或删除任何属性。在两种情况下，我们都有一个单一的属性 —— 一个 `className`，其值为 `"greeting"`
3. 进入元素后，我们发现文本已经改变，因此我们需要更新实际的 DOM

在这三个步骤中，只有第三个步骤在这种情况下有价值，因为 —— 与大多数更新一样 —— 应用的基本结构没有改变。如果我们可以直接跳到步骤 3，那将会更加高效：

```js
if (changed.name) {
	text.data = name;
}
```

（这几乎与 Svelte 生成的更新代码相同。与传统的 UI 框架不同，Svelte 是一个编译器，它在构建时就知道应用程序可能如何更改，而不是等到运行时才执行这些工作。）

## 不仅仅是 diffing 算法[](#It's-not-just-the-diffing-though)

React 和其他虚拟 DOM 框架使用的 diffing 算法很快。可以说，组件本身的开销更大。你不会写这样的代码...

```js
function StrawManComponent(props) {
	const value = expensivelyCalculateValue(props.foo);

	return <p>the value is {value}</p>;
}
```

...因为你会在每次更新时不必要地重新计算 `value`，而不管 `props.foo` 是否发生了变化。但是，人们常常会以看似更为无害的方式进行不必要的计算和分配：

```js
function MoreRealisticComponent(props) {
	const [selected, setSelected] = useState(null);

	return (
		<div>
			<p>Selected {selected ? selected.name : 'nothing'}</p>

			<ul>
				{props.items.map((item) => (
					<li>
						<button onClick={() => setSelected(item)}>{item.name}</button>
					</li>
				))}
			</ul>
		</div>
	);
}
```

这里，我们会在每次状态变化时生成一个新的虚拟 `<li>` 元素数组 —— 每个元素都有自己的内联事件处理器 —— 而不管 `props.items` 是否发生了变化。除非你对性能有着不健康的痴迷，否则你不会去优化它。没必要，它已经足够快了。但你知道什么会更快吗？ *不做这些事情.*

[React Hooks](https://reactjs.org/docs/hooks-intro.html) 在默认情况下会执行不必要的工作，并带来 [可预测的结果](https://twitter.com/thekitze/status/1078582382201131008)。

默认执行不必要的工作的危险之处在于，即使这些工作是微不足道的，你的应用程序最终也会因为“千刀之伤”而陷入困境，一旦需要优化时，就会没有明显的瓶颈来针对。

Svelte 的设计宗旨是防止你陷入这种情况。

## 为什么框架使用虚拟 DOM 呢？[](#为什么框架使用虚拟-DOM-呢)

理解虚拟 DOM *不是一个特性* 很重要，它是达到目的的一种手段，而这个目的就是声明式、状态驱动的 UI 开发。虚拟 DOM 有价值，因为它允许你构建应用程序而不需要思考状态转换，并且具有 *一般足够好的* 性能。这意味着更少的漏洞代码，并且花费更多时间在创造性任务上，而不是枯燥的任务上。

但事实证明，我们可以在不使用虚拟 DOM 的情况下实现类似的编程模型 —— 这就是 Svelte 的用途。
