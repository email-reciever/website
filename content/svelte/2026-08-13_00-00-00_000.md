Sveltekit 3 现在处于发布候选阶段。 如果一切顺利——这意味着像你这样的人尝试并发现它按预期工作——我们将在不久的将来发布一个稳定的版本，没有进一步的重大变化。

但是，自 Sveltekit 2 以来，有一些重大变化。我们正在利用此版本来修剪代码库中的一些杂草，并为 Sveltekit 的持续进化奠定了基础，更多的是 [below](#Remote-functions)。

要迁移现有应用程序，您可以使用 [`sv migrate`](/docs/cli/sv-migrate) 的 `next` 版本：

```bash
npx sv@next migrate sveltekit-3 --tasks all --confirm
```

这将自动迁移尽可能多的代码。 对于其他所有内容，它将为您（或您选择的 Clanker）生成一个待办事项列表以供您完成工作。 如果您尝试运行尚未更新的代码，Sveltekit 将打印有用的诊断警告和错误。

要创建 _new_ 应用程序，请运行 [`sv create`](/docs/cli/sv-create)：

```bash
npx sv@next create my-new-app
```

## 发生了什么变化？[](#What's-changed)

有关更改的完整列表，请参阅 [next.svelte.dev](https://next.svelte.dev) 上的 [migration guide](https://next.svelte.dev/docs/kit/migrating-to-sveltekit-3)，这是 sveltekit 3 文档将在稳定发布之前运行的位置。 大多数更改相当小，但有一些值得指出：

### 配置现在存在于 Vite.config.ts[](#What's-changed-Configuration-now-lives-in-vite.config.ts)

以前，您将通过 `svelte.config.js` 文件配置 sveltekit。 这被证明是限制性的：Vite插件可以立即访问您的配置是有用的，而不是必须经过异步解析过程（直到我们解决了整个Vite配置之后才开始，因为像Viste这样的工具可能会与当前的工作目录一起运行 那不是项目根），毕竟为什么_不会_我们将配置放在一个地方而不是两个地方？

### $lib 别名现在是 #lib[](#What's-changed-The-$lib-alias-is-now-lib)

在 Sveltekit 2 中，您将在 `src/lib` 中放置共享代码并通过 `$lib` 别名导入它。 这比从 `../../../../somewhere` 导入更好，这在较大的代码库中不可避免地会发生。

但在现代项目中，别名是不必要的，因为我们有更好的东西：[subpath imports](https://nodejs.org/api/packages.html#subpath-imports)。 Vite 和 TypeScript 等工具本机支持此节点功能，这意味着我们可以删除以前协调的代码。 有一个小问题：Node 和 TypeScript 要求您的子路径导入是明确的——而不是从 `#lib/foo` 导入，您需要从 `#lib/foo.ts` 或 `#lib/foo/index.ts` 导入。

### TypeScript 配置变得更简单[](#What's-changed-TypeScript-configuration-got-simpler)

在 Sveltekit 2 中，您的 `tsconfig.json` 需要扩展看起来有点邋遢的 `./.svelte-kit/tsconfig.json`。 在 sveltekit 3 中，您将 `$app/tsconfig` 扩展为。 此生成的配置文件将写入 `node_modules/$app` 并包含特定于您的应用程序的配置。 虽然它比 sveltekit 2 版本更简单（例如，我们不再需要将 `$lib` 别名添加到 `"paths"`），它还包括更多推荐的编译器选项，这意味着除非您有深奥的要求，否则您可能可以删除自己的 `compilerOptions`。

您应该明确指定您的 `include` 和 `exclude` 数组，后者应包含您的服务工作者。 说到它：

### 服务工作者进行了整容[](#What's-changed-Service-workers-got-a-facelift)

在 Sveltekit 3 中使用 Service Workers 更好。而不是奇怪的 `$service-worker` 模块，它暴露了执行离线缓存的必要工具（例如），您现在可以像应用程序的所有其他部分一样从 `$app/env`、`$app/paths` 和新的 `$app/manifest` 模块中导入这些内容。 您还可以从 `$app/service-worker` 导入 `self` 以获取 `fetch` 事件等的准确类型，前提是您在扩展 `$app/tsconfig/service-worker` 的服务工作者旁边创建了一个 `tsconfig.json`。

将来，我们可能会为不同的缓存策略公开辅助函数，以便更容易构建离线友好的 PWA 之类的东西，而无需遇到铁丝网。

### 环境变量更强大[](#What's-changed-Environment-variables-are-more-powerful)

Sveltekit 已经拥有所有框架中最复杂和最灵活的环境变量处理。 sveltekit 3 更进一步地使用 [explicit environment variables](/docs/kit/environment-variables) 功能，该功能不再位于 `experimental` 标志后面。 要点是，您在`src/env.ts`中定义了您的应用程序所依赖的环境变量，并指定它们是否应该公开可用（在这种情况下，您可以将它们导入到将在客户端运行的代码）以及是否应该在构建时解决它们（在这种情况下，它们可以用于像死代码这样的优化 消除）或当应用程序启动时。 您还可以使用 [Standard Schema](https://standardschema.dev/) 库来验证您的环境变量。

在 Exchange 中，您可以获得轻松的类型安全、安全、经过验证的环境变量，这些变量可以在您需要时自动导入。

### 错误处理要好得多[](#What's-changed-Error-handling-is-way-better)

Sveltekit 2 受到其对 Svelte 4 的支持的限制，它没有 [error boundaries](/docs/svelte/svelte-boundary) 的概念。 这意味着我们只能在 _load_ 而不是 _render_ 期间出现错误时显示您的 `+error.svelte` 组件。 Sveltekit 3 需要 Svelte 5，这意味着可以使错误处理更加全面和一致。

另一个变化是所有错误都通过你的 [`handleError`](/docs/kit/hooks#handleError) 逻辑进行，包括您故意使用 [`error(...)`](/docs/kit/@sveltejs-kit#error) 创建的错误 以前被忽略的假设是你已经对他们做了一些事情。 这为您提供了更多的灵活性，并且可以减少跳环。

哦，我们现在将源映射应用于堆栈跟踪。 没什么大的。 （每个适配器都需要一分钟才能在生产中正确显示源映射的堆栈跟踪，但这是必要的第一步。）

### 现在 goto[](#What's-changed-Shallow-routing-now-happens-with-goto) 发生浅路由

您现在将 [`goto`](/docs/kit/$app-navigation#goto) 与 `shallow: true` 选项一起使用，而不是使用 `pushState` 和 `replaceState` 来使用 [shallow routing](/docs/kit/shallow-routing)。 浅层导航现在会触发 `beforeNavigate` 等，您可以使用 `persistState: true` 重新加载页面状态。

## Vite 8：Rolldown 和环境 API[](#Vite-8:-Rolldown-and-the-Environment-API)

Sveltekit 2 支持 Vite 8，但 Sveltekit 3 需要它。 这意味着您可以获得更快的构建速度，这要归功于 [Rolldown](https://rolldown.rs/)。

我们还采用了 [Vite Environment API](https://vite.dev/guide/api-environment)，这简化了我们的一些构建逻辑。 我们不支持的一件事是 [`FetchableDevEnvironment`](https://vite.dev/guide/api-environment-frameworks#fetchabledevenvironment)——我们试图完成这项工作，但最终得出的结论是，它迫使框架吸收过多的复杂性。 我们认为它旨在解决的问题（最值得注意的是，在本地开发期间提供对 Cloudflare 工作人员绑定的访问）可以通过其他方式来解决，我们正在积极探索。

## 远程功能[](#Remote-functions)

如果您在过去一年中一直在关注 Sveltekit 的发展，那么您可能会遇到 [remote functions](/docs/kit/remote-functions)。 这与 [async Svelte](/docs/svelte/await-expressions) 一起，是我们对如何处理客户端与服务器通信的愿景。

我们对远程功能感到不合理的兴奋，迫不及待地想在任何地方使用它们。 坦率地说，它们使其他一切看起来有点笨拙，包括 Sveltekit 的 `load` 函数和 `actions`。

不过，就目前而言，当我们消除最后几个扭结时，它们仍然在 `experimental` 标志后面。
