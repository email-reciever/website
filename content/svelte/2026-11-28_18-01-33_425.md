经过近18个月的开发，包含了来自数十个贡献者的成千上万个提交，Svelte 5终于稳定了。

这是项目历史上最重要的版本。Svelte 5是一个从头开始的重写：你的应用将会更快、更小、更可靠。你将能够写出更一致和更符合惯用的代码。对于新来的框架用户，需要学习的东西更少。

尽管如此，Svelte 几乎完全向后兼容 Svelte 4 —— 对于大多数用户来说，初始升级将是完全无缝的：

```json
{
	"devDependencies": {
		"@sveltejs/vite-plugin-svelte": "^3.0.0",
		"svelte": "^4",
		"@sveltejs/vite-plugin-svelte": "^4.0.0",
		"svelte": "^5",
		// …
	}
}
```

## 什么是 Svelte？[](#什么是-Svelte)

Svelte 是一个用于构建 Web 用户界面的框架。它使用一个编译器将基于 HTML、CSS 和 JavaScript 的声明式组件代码转换为紧密优化的 JavaScript。

因为编译器将大量工作从浏览器转移到了 `npm run build`，所以 Svelte 应用程序很小很快。但是，除了这些之外，Svelte 还被设计为一种愉快和直观的构建应用程序的方式：它优先考虑完成任务。

Svelte 的开发团队同时维护着 SvelteKit，这是一个处理路由、数据加载、服务器端渲染以及构建现代网站和应用程序的所有细节的应用程序框架。

## 有什么变化，为什么？[](#What-changed-and-why)

首先，我们重新设计了我们的网站。你可以在 [这里](the-omnisite) 了解更多关于这方面的信息。

至于 Svelte 本身，我们将首先介绍 *为什么* 会有变化。我们并不喜欢无故的改变 —— 事实上，在 2019 年（我们发布 Svelte 3）和现在之间，Svelte 的变化比其他任何主要框架都少，这在前端开发中已经是一个很长的时间了。人们真的很喜欢 Svelte 3 和 4 —— 它经常在开发者满意度调查中名列前茅。

所以，当我们做出改变时，我们不会轻易地做出改变。

随着越来越多的人使用 Svelte 构建越来越大的应用程序，我们最初的一些设计决策的局限性开始变得更加明显。例如，在 Svelte 4 中，响应性完全由编译器驱动。如果您改变 Svelte 4 中一个响应式对象的单个属性，整个对象都会失效，因为这就是编译器所能做到的全部。同时，其他框架采用了基于 *signals* 的细粒度响应性，超越了 Svelte 的性能。

同样，Svelte 4 中的组件组合比它应该有的要更别扭，主要是因为它将事件处理程序和“插槽内容”视为与传递给组件的 props 分开的概念。这是因为在 2019 年，人们认为 Web 组件将成为组件的主要分发机制，我们希望与平台保持一致。这是一个错误。

虽然 `$:` 构造对于反应性地重新运行语句来说是一个很酷的技巧，但它最终变成了一个隐患。它混淆了两个概念（派生状态和副作用），这些概念实际上应该分开考虑，而且由于依赖项是在语句编译时确定的（而不是在运行时确定的），因此它抵制重构并成为复杂性的磁铁。

Svelte 5 删除了这些不一致性和隐患。它引入了 *runes* ，一种用于声明反应性状态（以及其他事物）的显式机制：

```js
let count = 0;
let count = $state(0);
```

与状态的交互没有变化：使用 Svelte —— 与其他框架不同 —— `count` 只是一个数字，而不是一个函数，或者具有 `value` 属性的对象，或者只能使用对应的 `setCount` 修改：

```js
function increment() {
	count += 1;
	console.log({ count });
}
```

Runes 可以在 `.svelte.js` 和 `.svelte.ts` 模块中使用，除了 `.svelte` 组件之外，这意味着您可以使用单一机制创建可重用的反应逻辑。

事件处理程序现在只是像其他任何道具一样，可以轻松地（例如）知道组件的用户是否提供了特定的事件处理程序（这对于避免昂贵的设置工作很有用），或者将任意事件处理程序传播到某些元素上 - 这对于库作者来说特别重要。

用于在组件之间传递内容的“slot”机制（以及令人困惑的“let:”和“<svelte:fragment>”语法）已被“{#snippet …}”取代，这是一个更强大的工具。

除了这些变化之外，还有无数的改进：原生 TypeScript 支持（不再有预处理器！）、许多错误修复以及全面的性能和可扩展性改进。

## 如何升级？[](#How-do-I-upgrade)

如果您当前使用的是 Svelte 3，请首先[迁移到 Svelte 4](/docs/svelte/v4-migration-guide)。

从那里，您可以更新 `package.json` 以使用最新版本的 `svelte` 和辅助依赖项，例如 `vite-plugin-svelte`。

你不必立即更新你的组件——在几乎所有情况下，你的应用程序将继续按原样工作（只是速度更快）。但我们建议你开始将组件迁移到使用新的语法和功能。你可以使用 `npx sv migrate svelte-5` 将整个应用程序迁移，或者——如果你使用的是带有 Svelte 扩展的 VS Code ——你可以通过在命令面板中选择“将组件迁移到 Svelte 5 语法”来一次迁移一个组件。

Svelte 拥有一个大型且健壮的组件库生态系统，你可以在应用程序中使用这些库，例如 [shadcn-svelte](https://shadcn-svelte.com/), [Skeleton](https://www.skeleton.dev/), 和 [Flowbite Svelte](https://flowbite-svelte.com/)。但是，你不必等待这些库升级到 Svelte 5 才能升级自己的应用程序。

最终，Svelte 4 语法的支持将被逐步淘汰，但这不会很快发生，你会有足够的警告。

有关更多详细信息，请参阅 [全面 Svelte 5 迁移指南](/docs/svelte/v5-migration-guide)。

## 我们的新 CLI[](#Our-new-CLI)

随着新版 Svelte 的发布，我们还推出了新的命令行界面（CLI）`sv`。您可以在 [公告博客文章](sv-the-svelte-cli) 中了解更多关于它的信息。

## 接下来会发生什么？[](#What's-next)

我们计划在不久的将来发布新的 SvelteKit 版本，以利用新的 Svelte 5 特性。与此同时，您可以今天就使用 Svelte 5 与 SvelteKit，一起使用 `npx sv create` 创建一个新的 SvelteKit 项目，Svelte 5 将与其一起安装。

之后，我们有一个很长的想法清单，我们希望在 Svelte 本身中实现。这个版本为许多改进奠定了基础，这些改进如果是在 Svelte 4 的基础上构建将是不可行的，我们迫不及待地想要开始工作。
