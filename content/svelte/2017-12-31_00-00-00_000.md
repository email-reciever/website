> 不耐烦的快速入门：[the Sapper docs](https://sapper.svelte.dev)和[starter template](https://github.com/sveltejs/sapper-template)

如果您必须列出完美的 Node.js Web 应用程序框架的特征，您可能会想出这样的东西：

1.  它应该进行服务器端渲染，用于快速初始加载和SEO周围没有任何警告
2.  作为一个推论，你的应用程序的代码库应该是通用的——为服务器_and_客户端写一次
3.  客户端应用程序应该_hydrate_服务器渲染的HTML，将事件侦听器（等等）附加到现有元素，而不是重新渲染它们
4.  导航到后续页面应该是即时的
5.  离线和其他渐进式Web应用程序特性，必须开箱即用地支持
6.  只有第一页所需的 JavaScript 和 CSS 才应该最初加载。 这意味着框架应该在路由级别进行自动代码分割，并支持 Dynamic `import(...)` 进行更细化的手动控制
7.  性能上没有妥协
8.  一流的开发者经验，热模块重新加载和所有的修剪
9.  生成的代码库应该易于grok和维护
10.  应该可以理解和定制系统的各个方面——没有 webpack 配置锁定在框架中，并且尽可能少地隐藏“管道”
11.  在一个小时内学习整个框架应该很容易，而不仅仅是经验丰富的开发人员

[Next.js](https://github.com/zeit/next.js) 接近这个理想。 如果您还没有遇到它，我强烈建议您阅读 [learnnextjs.com](https://learnnextjs.com) 的教程。 接下来引入了一个绝妙的想法：您的应用程序的所有页面都是 `your-project/pages` 目录中的文件，每个文件只是一个 React 组件。

其他一切都源于这一突破性的设计决策。 查找负责给定页面的代码很容易，因为您可以只看文件系统，而不是播放“猜测组件名称”。 项目结构自行车脱落已成为过去。 SSR（服务器端渲染）和代码分割的组合——React Router 团队 [gave up on](https://reacttraining.com/react-router/web/guides/code-splitting) 的组合，宣布“Godspeed 那些尝试服务器渲染的、代码分割应用程序的人”——是微不足道的。

但它并不完美。 尽管列出某些东西的缺陷可能很粗鲁，但有一些：

*   Next 使用称为“路由屏蔽”的东西来创建漂亮的 URL（例如 `/blog/hello-world` 而不是 `/post?slug=hello-world`）。 这破坏了与 app 结构对应的目录结构的保证，并迫使您保持在两种形式之间转换的配置
*   假设您的所有路线都是通用的“页面”。 但是通常需要仅在服务器上呈现的路由，例如为您的页面提供数据的 301 重定向或 API 端点，然后没有一个很好的解决方案。 您可以在 `server.js` 文件中添加逻辑来处理这些情况，但与页面的声明性方法感觉不一致
*   要使用客户端路由器，链接不能是标准的 `<a>` 标签。 相反，您必须使用特定于框架的 `<Link>` 组件，这在博客文章的 Markdown 内容中是不可能的，例如

然而，真正的问题是所有的善良都是有代价的。 最简单的下一个应用程序——一个渲染静态文本的“Hello World”页面——涉及 66KB 的压缩 JavaScript。 解压后，它是 204KB，这是移动设备在性能是决定用户是否会留下来的关键因素时解析的重要代码量。 这就是_baseline_。

我们可以做得更好！

编译器作为框架的范式移位[](#The-compiler-as-framework-paradigm-shift)
---------------------------------------- -----------------------------------------

[Svelte introduced a radical idea](/blog/frameworks-without-the-framework)：如果您的 UI 框架根本不是框架，而是将组件变成独立的 JavaScript 模块的编译器怎么办？ 与其使用像 React 或 Vue 这样的库，它对您的应用一无所知，因此必须是一种单一尺寸的解决方案，我们可以提供高度优化的 Vanilla JavaScript。 只是您的应用程序需要的代码，并且没有基于虚拟 DOM 的解决方案的内存和性能开销。

JavaScript 世界是 [moving towards this model](https://tomdale.net/2017/09/compilers-are-the-new-frameworks/)。 [Stencil](https://stenciljs.com) Ionic 团队的 Svelte 受启发的框架编译为 Web 组件。 [Glimmer](https://glimmerjs.com) _doesn't_ 编译为独立的 JavaScript（其优点和缺点应该单独写一篇博文），但该团队正在围绕将模板编译为字节码进行一些引人入胜的研究。 （React 是 [getting in on the action](https://twitter.com/trueadm/status/944908776896978946)，尽管他们目前的研究重点是优化您的 JSX 应用程序代码，这可能与 Angular、Ractive 和 Vue 几年来一直在进行的提前优化更相似。）

如果我们使用新模型作为起点，会发生什么？

介绍工兵[](#Introducing-Sapper)
----------------------------------------

[Sapper](https://sapper.svelte.dev) 是这个问题的答案。 **Sapper 是 Next.js 风格的框架，旨在满足本文顶部的 11 个标准，同时大幅减少发送到浏览器的代码量。** 它实现为 Express 兼容的中间件，这意味着它易于理解和定制。

同一个“Hello World”应用程序，使用 React 和 Next 的重量仅为 7KB。 随着我们探索优化可能性的空间，这个数字可能会在未来进一步下降，例如在处理客户端路由的微小运行时之外的页面中没有任何 JavaScript _at all_ 不交互。

一个更“现实世界”的例子呢？ 方便的是，[RealWorld](https://github.com/gothinkster/realworld) 项目挑战了框架来开发中克隆的实现，为我们提供了一种找出答案的方法。 [Sapper implementation](https://github.com/sveltejs/realworld) 需要 39.6KB（11.8KB 压缩）来呈现交互式主页。

整个应用程序的成本为 132.7kb（39.9kb 压缩），比 327kb (85.7kb) 的参考 React/Redux 实现要小得多，但即使它一样大，它也会_feel_更快 代码分割。 这是一个关键点。 我们被告知我们需要对应用程序进行代码拆分，但是如果您的应用程序使用了像 React 或 Vue 这样的传统框架，那么初始代码分割块的大小就有一个硬下限——框架本身，这可能是您应用程序总大小的很大一部分。 采用苗条的方法，情况不再如此。

但规模只是故事的一部分。 Svelte 应用程序也非常高效且内存效率高，并且该框架包含强大的功能，如果您选择“最小”或“简单”的 UI 库，您将牺牲这些功能。

权衡[](#Trade-offs)
--------------------------

对于许多评估 Sapper 的开发人员来说，最大的缺点是“但我喜欢 React，而且我已经知道如何使用它”，这是公平的。

如果你在那个阵营，我会邀请你至少尝试替代框架。 您可能会感到惊喜！ [Sapper RealWorld](https://github.com/sveltejs/realworld) 实现总计 1,201 行源代码，而参考实现为 2,377 行，因为您可以使用 Svelte 的模板语法（其中 [takes all of five minutes to master](https://v2.svelte.dev/guide#template-syntax)）非常简洁地表达概念。 您将获得 [scoped CSS](/blog/the-zen-of-just-writing-css)，内置未使用的样式移除和缩小功能，并且您可以根据需要使用预处理器。 您不再需要使用 Babel。 SSR 速度快得离谱，因为它只是字符串连接。 我们最近引入了 [svelte/store](https://v2.svelte.dev/guide#state-management)，这是一个微小的全局存储，可以在组件层次结构中使用零样板同步状态。 可能发生的最糟糕的事情是你最终会感到被证明是正确的！

但仍有权衡取舍。 有些人对任何形式的“模板语言”都有病态的厌恶，也许这适用于你。 JSX 的支持者会用“它只是 JavaScript”的口头禅来欺骗你，而这就是 React 最大的优势，那就是它是无限灵活的。 这种灵活性伴随着自己的一套权衡，但我们不是在这里讨论这些。

然后是_生态系统_。 尤其是 React 周围的宇宙——DevTools、编辑器集成、辅助库、教程、StackOverflow 答案、地狱，甚至工作机会——是无与伦比的。 虽然将“生态系统”作为选择工具的主要原因是您被困在局部最大值的迹象，但容易被不断上涨的水域所困扰，但它仍然是有利于现有企业的主要点。

路线图[](#Roadmap)
--------------------

我们还没有达到 1.0.0 版，在我们到达那里之前，有些事情可能会发生变化。 一旦我们这样做（很快！），就会有很多令人兴奋的可能性。

我相信网络性能的下一个前沿是“全应用优化”。 目前，Svelte 的编译器在组件级别运行，但理解这些组件边界的编译器可以生成更有效的代码。 React 团队的 [Prepack research](https://twitter.com/trueadm/status/944908776896978946) 基于类似的想法，Glimmer 团队正在这个领域做一些有趣的工作。 Svelte 和 Sapper 能够充分利用这些想法。

说到 Glimmer，将组件编译为字节码的想法是我们可能会在 2018 年窃取的一种想法。像 Sapper 这样的框架可以根据应用程序的特性确定要使用哪种编译模式。 它甚至可以为初始路由提供最快的启动时间的JavaScript，然后懒惰地为后续路由提供字节码解释器，从而实现启动大小和总应用程序大小的最佳组合。

不过，大多数情况下，我们希望 Sapper 的方向由其用户决定。 如果您是那种享受生活处于领先地位并希望帮助塑造我们构建 Web 应用程序的未来的开发人员，请加入我们的 [GitHub](https://github.com/sveltejs/svelte) 和 [Discord](/chat)。
