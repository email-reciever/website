今天我们很高兴地宣布 TypeScript 7.0 的发布候选者！

如果您还没有关注 TypeScript 7.0 的开发，那么此版本的重要性在于它建立在一个全新的基础上。 在过去的一年中，我们一直将现有的 TypeScript 代码库从 TypeScript（作为编译为 JavaScript 的引导代码库）移植到 Go 中。 结合本机代码速度和共享内存并行性，**TypeScript 7.0 通常比 TypeScript 6.0 快 10 倍**。

要获得新的编译器，您只需在 npm 上的 `typescript` 包中安装它，就像任何其他版本一样：

```text
npm install -D typescript@rc
```

新的 Go 代码库是从我们现有的实现中有条不紊地移植的，而不是从头开始重写，其类型检查逻辑在结构上与 TypeScript 6.0 相同。 这种体系结构确保编译器继续执行您已经依赖的完全相同的语义。 TypeScript 7.0 是针对我们在十年内建立的庞大测试套件进行评估的，并且已经在 Microsoft 内部和外部的多个数百万行代码中使用。 它非常稳定，高度兼容，随时可以在您的日常工作流程和 CI 管道中进行测试。

一年多来，我们一直在与许多内部微软团队合作，以及 Bloomberg、Canva、Figma、Google、Linear、Miro、Notion、Slack、Vanta、Vercel、Voidzero 等公司的团队，以尝试预发布版本 打字稿 7.0 在他们的代码库上。 反馈非常积极，许多团队报告了类似的加速，减少了他们的大部分构建时间，并享受了更轻巧和流畅的编辑体验。 反过来，我们确信发布候选人的状态很好，我们迫不及待地想让您尝试一下。

## 使用打字稿 7.0 RC

如上所述，要获得 TypeScript 7.0 RC，您可以通过 npm 进行安装：

```sh
npm install -D typescript@rc
```

从那里，您可以像使用任何先前版本的 TypeScript 一样运行 `tsc`，并且您应该看到与以前相同的结果 - 只是更快！

```text
> npx tsc --version
Version 7.0.1-rc
```

要尝试编辑体验，您可以安装 [TypeScript Native Preview extension for VS Code](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview)。 编辑支持是坚如磐石的，并且已经被许多团队广泛使用了几个月。 立即在代码库上尝试 TypeScript 7.0 是一种简单的低摩擦方式。 它使用与命令行体验相同的基础，因此您可以在编辑器中获得与在命令行上相同的性能改进。 值得注意的是，它还建立在语言服务器协议 (LSP) 上，使在大多数现代编辑器甚至 Copilot CLI 等工具中运行都很容易。

## TypeScript 6.0 并排运行

尽管 7.0 RC 接近于生产就绪，但至少几个月后使用 TypeScript 7.1 才能获得稳定的程序化 API。 鉴于此，我们已将 TypeScript 与 TypeScript 6.0 并排运行作为优先事项，在可预见的将来，“哪个 `tsc` 是哪个？”没有任何冲突。

作为 6.0/7.0 过渡过程的一部分，我们发布了一个新的兼容性包 `@typescript/typescript6`。 此软件包提供了一个名为 `tsc6` 的可执行文件，因此如果需要，您可以并排安装 TypeScript 7.0（它自己的 `tsc` 二进制文件）并排安装，而无需命名冲突。 新软件包还重新导出了 TypeScript 6.0 API，因此您可以将 `tsc` 用于 TypeScript 7，而其他工具可以继续依赖 6.0。

因为一些像 typescript-eslint 这样的工具希望通过对等依赖项直接从 `typescript` 导入，因此我们建议通过 npm 别名实现此目的。 您应该能够运行以下命令

```sh
npm install -D typescript@npm:@typescript/typescript6
```

或修改您的 `package.json` 如下：

```json
{
  "devDependencies": {
    "typescript": "npm:@typescript/typescript6@^6.0.0",
  }
}
```

请注意，这样做只会留下一个 `tsc6` 可执行文件。 要获得 7.0 的 `tsc`，您可以为 TypeScript 7 添加另一个别名，`npx tsc` 将仅适用于 7.0：

```json
{
  "devDependencies": {
    "typescript": "npm:@typescript/typescript6@^6.0.0",
    "typescript-7": "npm:typescript@rc",
  }
}
```

### 每晚发布

TypeScript 7 Nightlies 目前仍在 NPM 上的 `@typescript/native-preview` 包下发布，并且可以通过

```text
npm install -D @typescript/native-preview
```

## 并行化和控制

TypeScript 7.0 现在并行执行了许多步骤，包括解析、类型检查和发射。 其中一些步骤，如解析和发射，主要可以跨文件独立完成。 因此，并行化可以在较大的代码库中自动扩展，并且开销相对较少。 但并非 TypeScript 构建中的每个步骤都可以轻松并行化。

### 检查器并行化

其他步骤，如类型检查，在文件之间具有更复杂的依赖关系。 大多数文件最终依赖于来自它们的依赖和全局范围的相同类型信息，因此完全独立运行类型检查器将是浪费的——无论是计算还是内存。 另一方面，类型检查偶尔依赖于程序中信息的相对顺序，因此从头开始进行类型检查必须始终以相同的顺序检查相同的文件以确保相同的结果。

为了在避免这些陷阱的同时启用并行化，TypeScript 7.0 创建了固定数量的类型检查器，并使用自己的世界视图。 这些类型检查工作人员最终可能会复制一些常见的工作，但如果输入相同的输入文件，它们将始终将它们分割并产生相同的结果。

默认的类型检查工作人员的数量是 4，但可以使用新的 `--checkers` 标志配置它。 您可能会发现，增加这个数量可以进一步加快在典型机器具有更多 CPU 内核的较大代码库上的构建，但通常会以增加内存使用为代价。 同样，CPU 内核较少、内存较少的机器（例如 CI 运行器）可能希望减少此数量以避免不必要或偶然的开销。

在极少数情况下，改变 `--checkers` 的数量可能会导致表面有序。 在构建环境中指定固定数量的检查器有助于确保每个人都获得相同的结果，但由每个团队的自由裁量权决定。

### 项目参考构建器并行化

TypeScript 7.0 可以并行化项目中的构建，但现在也可以同时构建多个项目。 可以使用新的 `--builders` 标志配置此行为，该标志控制可以一次运行的并行项目参考构建器的数量。 这对于具有许多项目的Monorepos特别有用。

与 `--checkers` 一样，增加构建器的数量可以加快构建速度，但可能会以增加内存使用为代价。 它还具有 `--checkers` 的乘法效果，因此为您的机器和代码库找到合适的平衡非常重要。 例如，使用 `--checkers 4 --builders 4` 构建最多允许 16 个类型检查器同时运行，这可能是过度的。

与 `--checkers` 不同，改变构建器的数量不应产生不同的结果； 但是，构建项目引用的项目的依赖关系图（除了对利用`--isolatedDeclarations`和单独的语法声明文件发出的代码库进行类型检查除外）从根本上是瓶颈。

### 单线程模式

在某些情况下，在整个编译器中强制执行单线程操作可能会有所帮助。 这可能有助于调试、将性能与 TypeScript 6 和 7 进行外部编排并行构建时的性能，或者在资源非常有限的环境中运行。 要启用单线程模式，您可以使用新的 `--singleThreaded` 标志。 这不仅将类型检查工作人员的数量限制为 1，还可以确保在单个线程中进行解析和发射。

## 改进 `--watch` 模式

值得指出的是 TypeScript 7 的重建 `--watch` 模式。 `--watch` 现在建立在源自 [the Parcel bundler’s file-watcher](https://github.com/parcel-bundler/watcher) 的新基础上，该基础提供了高效稳定的跨平台文件监视功能。

当我们的团队着手移植我们的文件观看逻辑时，我们在 Go 中遇到了跨平台文件观看的一些挑战。 标准库不提供内置文件监视 API，我们探索的现有第三方库存在稳定性、性能、跨平台支持或构建工具集成问题的各种问题。 我们能够定期围绕轮询构建解决方案以检查文件更改，这在整个操作系统中广泛使用； 然而，它的计算成本很高，尤其是在 `node_modules` 中具有许多依赖性的大型项目中。 即使使用动态调度策略，我们也发现纯轮询解决方案对一般用途来说太费力了。

多年来，Visual Studio Code 一直依赖 [`@parcel/watcher`](https://www.npmjs.com/package/@parcel/watcher)，而近年来，VS Code 中的 TypeScript 间接依靠其文件查看功能。 虽然看起来很有希望，但 Parcel 的 Watcher 的问题之一是它是用 C++ 编写的，反过来又需要一个完整的 C++ 工具链来构建。 鉴于我们在 VS Code 中使用 Parcel 的 Watcher 的积极体验，我们探索了将其移植到一些最小的装配垫片中，以避免引入新的工具链依赖性。

探索取得了成功——最初是从 C++ 到 Go 的非常直接的翻译，进一步完善了仍然通过移植的测试套件的惯用语 Go。 Watcher 是一个独立的软件包，它使我们能够在我们关注的内容和原因之间保持关注的清晰分离。 我们现在看到跨平台的 `--watch` 模式有了显着的资源改进，并且一直从 TypeScript 7 的早期用户那里听到积极的反馈。

我们要感谢 Devon Govett，他在 Parcel 上的工作为 Visual Studio 代码和 TypeScript 项目提供了巨大的好处。 我们希望这个端口能够随着时间的推移为原始包裹观察者代码库提供机会和见解。

## 自 5.x 以来的更新，以及 6.0 的新行为

TypeScript 7.0 与 TypeScript 6.0 的类型检查和命令行行为兼容。 实际上，任何使用 TypeScript 6.0 （打开 `stableTypeOrdering` 标志，没有任何 `ignoreDeprecations` 标志集）编译干净的 TypeScript 代码都应该在 TypeScript 7.0 中进行相同的编译。

话虽如此，TypeScript 7.0 采用 6.0 的新默认设置，并在 TypeScript 6.0 中不推荐使用的任何标志和构造的情况下提供严重错误。 这一点值得注意，因为 6.0 仍然相对较新，许多项目需要适应其新行为。 我们鼓励开发人员采用 TypeScript 6.0 来简化向 TypeScript 7.0 的过渡，您还可以阅读 [the TypeScript 6.0 release blog post](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/) 以获取有关这些弃用的更多详细信息。

一目了然，配置的显着默认更改是：

*   `strict` 默认为 `true`。
*   `module` 默认为 `esnext`。
*   `target` 默认为当前 `esnext` 之前的稳定 ECMAScript 版本。
*   `noUncheckedSideEffectImports` 默认为 `true`。
*   `libReplacement` 默认为 `false`。
*   `stableTypeOrdering` 默认为 `true`，无法关闭。
*   `rootDir`现在默认为`./`，必须明确设置内部源目录。
*   `types`现在默认为`[]`，可以通过将其设置为`["*"]`来恢复旧行为。

我们相信 `rootDir` 和 `types` 的变化可能是最“令人惊讶”的变化，但它们可以很容易地缓解。 `tsconfig.json` 位于 `src` 之类的目录之外的项目只需要包含 `rootDir` 以保留相同的目录结构。

```diff
  {
      "compilerOptions": {
          // ...
+         "rootDir": "./src"
      },
      "include": ["./src"]
  }
```

对于 `types` 更改，依赖于特定全局声明的项目将需要明确列出它们。 比如，

```diff
  {
      "compilerOptions": {
          // Explicitly list the @types packages you need (e.g. bun, mocha, jasmine, etc.)
+         "types": ["node", "jest"]
      }
  }
```

已经变成了无操作行为的硬错误的弃用是：

*   `target: es5` 不再受支持。
*   `downlevelIteration` 不再受支持。
*   `moduleResolution: node/node10` 不再支持，建议改为 `nodenext` 和 `bundler`。
*   `module: amd, umd, systemjs, none` 不再支持，`esnext` 或 `preserve` 与捆绑器或基于浏览器的模块分辨率一起被推荐。
*   `baseUrl` 不再支持，`paths` 可以更新为相对于项目根而不是 `baseUrl`。
*   `moduleResolution: classic` 不再受支持，`bundler` 或 `nodenext` 是推荐的替代品。
*   `esModuleInterop` 和 `allowSyntheticDefaultImports` 不能设置为 `false`。
*   `alwaysStrict` 假定为 `true`，不能再设置为 `false`。
*   在命名空间声明中不能使用 `module` 关键字。
*   `asserts` 关键字不能用于导入，必须改用 `with` 关键字（以与 ECMAScript 的导入属性语法的发展相一致）。
*   `/// <reference no-default-lib />` 指令不再受 `skipDefaultLibCheck` 尊重。
*    除非通过显式 `--ignoreConfig` 标志，否则当前目录包含 `tsconfig.json` 文件时，命令行构建不能获取文件路径。

### 模板文字类型现在保留Unicode代码点

TypeScript 7.0 现在从模板文字类型推断出更自然的处理 Unicode 代码点。 例如：

```typescript
type HeadTail<S> = S extends `${infer Head}${infer Tail}` ? [Head, Tail] : never;

type Result = HeadTail<"😀abc">;
//   ^
// In 7.0: ["😀", "abc"]
// Previously: ["\ud83d", "\ude00abc"]
```

以前，TypeScript 遵循 JavaScript 的 UTF-16 索引行为，并将 `"😀"` 分成替代对的两半（`\ud83d` 和 `\ude00`）。 这在技术上与 JavaScript 中的索引（例如推断的 `Head` 类型等于 `"😀abc"[0]`）在技术上是一致的，但通常不是人们的意图，并且可以生成包含语义上没有意义的未配对代理的字符串文字类型。

这是类型级字符串操作的突破性变化，故意对 UTF-16 代码单元进行建模，例如某些字符串 `Length` 实用程序。 在实践中，我们希望新行为更有用且不那么令人惊讶：模板字面推理现在遵循与用 `for...of` 迭代字符串或用 `[...str]` 传播字符串相同的直觉，其中 `"😀"` 被视为一个单元。

### JavaScript 差异

当我们移植现有的代码库时，我们还借此机会重新审视了 JavaScript 支持的工作方式。

TypeScript 最初通过使用 JSDOC 注释和识别某些代码模式来支持 JavaScript 文件进行分析和类型推断。 很多时候，这是基于流行的编码模式，但偶尔它是基于人们写的闭包和JSDOC文档生成工具可能理解的任何内容。 虽然这种方法对编写松散的 JSDoc 代码库的开发人员很有帮助，但它需要一些妥协和特殊情况才能正常工作，并且在许多方面与 TypeScript 在 `.ts` 文件中的分析中的分析不同。

在 TypeScript 7.0 中，我们重新设计了 JavaScript 支持，以与我们分析 TypeScript 文件的方式更加一致。 其中一些差异包括：

*   在预期类型的地方不能使用值 - 相反，写`typeof someValue`
*   `@enum` 不再特别识别 – 在 `(typeof YourEnumDeclaration)[keyof typeof YourEnumDeclaration]` 上创建 `@typedef`。
*    独立式 `?` 不再可用作类型 – 使用 `any` 代替。
*   `@class` 不使函数成为构造函数——改用 `class` 声明。
*   不支持 Postfix `!` – 只需使用 `T`。
*   类型名称必须在 `@typedef` 标记（即 `/** @typedef {T} TypeAliasName */`）内定义，与标识符不相邻（即 `/** @typedef {T} */ TypeAliasName;`）。
*   不再支持关闭样式的函数语法（例如 `function(string): void`）——改用 TypeScript 简写（例如 `(s: string) => void`）。

此外，一些 JavaScript 模式，如 aliasing `this` 和重新分配函数 `prototype` 的全部内容，不再被特殊处理。

虽然我们的一些 JS 支持在不断变化，但我们一直在更新 [`CHANGES.md` 文件](https://github.com/microsoft/typescript-go/blob/main/CHANGES.md) 以更详细地捕获 TypeScript 6.0 和 7.0 之间的差异。

## 编辑经验

TypeScript 7.0 的性能改进不仅限于命令行体验——它们也扩展到了编辑器的体验。 对于 VS Code 用户，[TypeScript Native Preview extension](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview) 提供了一种在编辑器中试用 TypeScript 7.0 的无缝方式，并得到了广泛使用。 对于 Visual Studio 用户，最新版本的编辑器将根据您的工作空间自动启用 TypeScript 7。 当然，TypeScript 7 在您选择的任何编辑器中都应该很好地工作。 新的基础建立在语言服务器协议 (LSP) 上，能够利用多个线程尽快同时处理请求。

自首次亮相以来，我们添加了缺少的功能，例如自动导入、可扩展悬停、嵌入式提示、代码镜头、转到源定义、JSX 链接编辑和标记完成等。 TypeScript 7.0 Beta 中缺少的功能，例如语义突出显示、“排序导入”、“删除未使用的导入”等。

此外，在过去的几个月中，我们继续推动性能和稳定性。 我们重建了大部分的测试和诊断基础架构，以确保高质量的栏目，我们能够根据 GitHub 上的顶级 TypeScript 和 JavaScript 代码库对语言服务器进行模糊测试。 基于我们的数据洞察，我们相信与 TypeScript 6.0 相比，TypeScript 7 实际上减少了失败的语言服务器命令 20 倍以上。

此扩展包含与 Visual Studio Code 的内置 TypeScript 扩展相同的大多数配置设置，以及大多数相同的功能。
