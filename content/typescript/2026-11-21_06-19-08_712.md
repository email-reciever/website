今天我们很高兴地宣布 TypeScript 7.1 的 Beta 版本！

```sh
npm install -D typescript@beta
```

让我们来看看 TypeScript 7.1 中的新功能！

## 支持环境模块中的导入属性

[Import attributes](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/with) 是附加到导入语句的元数据。 通常，它们旨在指导运行时和捆绑程序如何解释导入的内容以及生成的模块的形状。 比如，

```typescript
import myData from "./data/someData.json" with { type: "json" };
```

`with` 关键字后面的对象中的所有内容都是导入属性。 像浏览器这样的环境不能简单地根据 `.json` 等文件扩展名来决定如何处理导入。 指定 `type: "json"` 告诉任何运行时 `someData.json` 需要被解释为 JSON 文件，解析出来并通过默认导入提供（在我们上面的示例中，这是 `myData`）。

`type` 属性已成为运行时自定义此行为的事实方式。 [ECMAScript (JavaScript) has a proposal](https://github.com/tc39/proposal-import-text) 允许代码指定 `type: "text"`，将导入的内容作为字符串返回。

```typescript
import readme from "../README.md" with { type: "text" };

console.log(readme);
```

`type: "bytes"` 有 [also a proposal](https://github.com/tc39/proposal-import-bytes) 返回 `Uint8Array` 原始字节。

```typescript
import { pngToPixels, boxBlur } from "./photoUtils.js";

import photo from "./myPhoto.png" with { type: "bytes" };
const blurryPhoto = boxBlur(pngToPixels(photo));
```

几年来，浏览器还允许将 CSS 文件与 `type: "css"` 一起导入 `CSSStyleSheet`s。

```typescript
import someTheme from "./themes/someCoolTheme.css" with { type: "css" };

document.adoptedStyleSheets.push(someTheme);
```

要支持导入这些文件，人们可以使用通配符模式（例如 `*.css`）在 TypeScript 中使用 _ambient 模块声明。

```typescript
// You can write this in a global `.d.ts` file with no import statements.

declare module "*.css" {
    const content: CSSStyleSheet;
    export default content;
}

declare module "*.txt" {
    const content: string;
    export default content;
}

declare module "*.md" {
    const content: string;
    export default content;
}

declare module "*.bin" {
    const content: Uint8Array;
    export default content;
}
```

这没关系，但它不适用于所有环境，因为它根本不考虑导入属性。

您可能会问为什么这是一个问题 - 乍一看，似乎唯一的问题是它只是允许人们不小心离开 import 属性。

```typescript
// ❌ oops, forgot an import attribute
import readme from "../README.md";

// ✅ what we were supposed to write
import readme from "../README.md" with { type: "text" };
```

但这仍然是一个值得解决的问题。 另一个问题是它变得重复。 对于导入属性，整个问题是运行时关心属性，而不是文件扩展名。 如果两者都要使用 `type: "text"`，我们不必为 `.txt` 和 `.md` 文件重新声明一个模式。

但一个主要问题是运行时环境可能完全支持不同的导入属性，并且可能会根据它们是否存在而采取不同的行动。 例如，Bundlers 可能会在导入 `.css` 文件时使用称为 [CSS Modules](https://github.com/css-modules/css-modules) 的构建时功能作为默认行为，但在 import 语句中指定浏览器支持的 `type: "css"` 将覆盖此行为并确保 `.css` 文件作为 `CSSStyleSheet` 对象引入。

这就是 TypeScript 7.1 在环境模块声明中引入对导入属性的支持的原因。 您现在可以在 TypeScript 项目中声明以下内容，如果您尝试导入没有所需导入属性的文件，并根据导入属性获取正确的类型，则会出现错误。

```typescript
declare module "*" with { type: "css" } {
    const content: CSSStyleSheet;
    export default content;
}

declare module "*" with { type: "text" } {
    const content: string;
    export default content;
}

declare module "*" with { type: "bytes" } {
    const content: Uint8Array;
    export default content;
}
```

请注意，与这些声明匹配的导入未针对磁盘上的文件进行验证。 与当前导入匹配环境模块声明时的行为一样，失败的查找将在运行时或捆绑程序的构建过程中报告。

另请注意，这些声明不是作为 TypeScript 内置库的一部分提供的。 我们建议库 **not** 将它们包含在其已发布的软件包中，如果需要，最终用户将需要在自己的项目中声明它们。 这将为最终用户提供全局范围的配置（例如 `lib.dom.d.ts` 与 `@types/node`）的灵活性，并将在未来防止与内置声明的冲突。

有关详细信息，请参阅 [our implementing pull request here](https://github.com/microsoft/TypeScript/pull/63931)。

## 源相位导入

[Source phase imports](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/source) 是 [a proposed new feature in ECMAScript](https://github.com/tc39/proposal-source-phase-imports)。 该功能引入了一个新的 `source` 修饰符/关键字，该修饰符/关键字位于 `import` 关键字之后。 只能使用 `import source` 编写默认导入。

```typescript
import source SomeModule from "some-module";
```

这个特性的想法是，当我们使用 `import source` 时，我们将在运行时解析和分析后返回一个表示模块的对象，但是 _before_ 已加载它的导入（因此，在它们被验证或链接到其他模块之前，以及在任何之前， 模块中包含的代码可以运行）。 这个对象本身就是一种“惰性”——它是一个被称为 `AbstractModuleSource` 的实例，它被_最终_意味着要被导入或实例化。

对于 WebAssembly (WASM) 导入，该对象将是 `WebAssembly.Module` 的实例。 这些对象的有用之处在于它们可以直接传递到 `WebAssembly.instantiate` 中。

```typescript
import source SuperFastThing from "./super-fast-thing.wasm";
import { WASI } from "node:wasi";

const wasi = new WASI({ /*...*/ });
const fastThingInstance = await WebAssembly.instantiate(SuperFastThing, {
    wasi_snapshot_preview1: wasi.wasiImport
});

wasi.start(fastThingInstance);
```

已经支持 WebAssembly 源导入 [in recent versions of Node.js](https://beta.docs.nodejs.org/esm#wasm-source-phase-imports)。

目前，您无法使用 JavaScript 文件的源导入功能。 提案的精神意味着在某个时候我们可以将 JavaScript 模块源直接传递到 `import()` 调用中。

```typescript
import source SomeModule from "./someModule.js";
const moduleInstance = await import(SomeModule);
```

JavaScript 源导入的另一部分是，随着时间的推移，我们可能会获得其他功能，这些功能使我们能够自定义围绕模块加载和实例化的行为，类似于我们在上面的 `WebAssembly.instantiate` 中所做的那样。 但我们还没有到那里，事实上，许多环境和工具目前仍然不支持 JavaScript 源代码导入。

不过，源导入不仅限于导入语句。 您还可以通过 `import.source` 元属性函数执行 _dynamic_ 源导入。

```typescript
const SuperFastThing = await import.source("./super-fast-thing.wasm");
const fastThingInstance = await WebAssembly.instantiate(SuperFastThing, {
    // ...
});
```

源导入保留身份。 这意味着您可以在 `Map` 和 `Set` 中使用它们，或者可靠地与它们进行比较。

```typescript
// Note that `WebAssembly.instantiate` always returns a distinct object.
import source source1 from "./plugin.wasm"
import source source2 from "./plugin.wasm"
const source3 = await import.source("./plugin.wasm");

console.log(source1 === source2); // true
console.log(source2 === source3); // true
```

使用 `import source` 时，每个导入的模块都具有 `AbstractModuleSource` 类型，这是 `lib.esnext.d.ts` 中的新全局类型。 您必须有适当的 `--module` 设置（即 `esnext`、`nodenext` 或 `preserve`）才能使用源导入以及 `--lib` 或 `--target` 中的适当 `esnext` 选项。

[This feature was implemented](https://github.com/microsoft/TypeScript/pull/63915) 感谢 [Oleksandr Tarasiuk](https://github.com/a-tarasyuk) 的工作。

## TypeScript 7.1 API

TypeScript 7.1 提供了一个新的 API，允许使用我们的语法和语义分析构建强大的工具和实用程序。

TypeScript 7.1 不是公开一个单一的 API，而是将多个入口点组织起来，每个都用于特定目的。

入口点

目的

`typescript/sync`

同步编译器客户端，支持编译器选项、类型检查器和程序 API

`typescript/async`

一个 `Promise`\ 的同步客户端的等效

`typescript/fs`

请求范围的完整和分层文件系统

`typescript/ast`

语法树节点 (AST) 类型和枚举，例如 `SyntaxKind` 和 `ScriptTarget`

`typescript/ast/is`

节点类型保护

`typescript/ast/factory`

`create*` 和不可变的 `update*` 功能

以下是如何使用 TypeScript 7.1 API 进行简单编译的示例，文件名和编译器选项在命令行上显式传递。 与 `tsc` 不同，此示例不发现或加载 `tsconfig.json` 文件，也不支持 `--project`。

```typescript
// Compile explicit filenames using command-line compiler options.

import { API, formatDiagnosticsWithColorAndContext, type Diagnostic } from "typescript/sync";

using api = new API();
const reportErrors = (diagnostics: readonly Diagnostic[]) => {
    console.log(formatDiagnosticsWithColorAndContext(diagnostics, api))
};

// Parse command-line filenames and compiler options, report any errors.
const commandLineArgs = process.argv.slice(2);
const parsedCommandLine = api.parseCommandLine(commandLineArgs);
if (parsedCommandLine.errors.length > 0) {
    reportErrors(parsedCommandLine.errors);
    process.exit();
}

// Create the program by resolving and parsing all files in the entry point.
using program = api.createProgram(parsedCommandLine.fileNames, parsedCommandLine.options);

// Collect and report any diagnostics from the program before emitting.
// You can customize whether any of these block reporting errors in subsequent passes if desired.
const diagnostics = [
    ...program.getGlobalDiagnostics(),
    ...program.getProgramDiagnostics(),
    ...program.getSyntacticDiagnostics(),
    ...program.getSemanticDiagnostics(),
];
if (diagnostics.length > 0) {
    reportErrors(diagnostics);
}

// Emit files - this respects the `noEmitOnError` option,
// so nothing will be emitted if an earlier step reported errors.
const emitResult = program.emit();
if (emitResult.diagnostics.length > 0) {
    reportErrors(emitResult.diagnostics);
}
```

注意我们上面声明中的 `using` 关键字。 您可能不熟悉 [`using`，因为它在 JavaScript](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/using) 中有些新，但不要担心。

`API` 实例和 `Program` 实例都是 [`Disposable` 对象](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Symbol/dispose)。 当我们要求创建它们时，TypeScript 会分配内存并进行簿记，以确保它们在 Go 和 JavaScript 运行时之间停留； 但是，当我们完成它们时，我们不能只是让垃圾收集器处理它们，否则我们会在旅途中泄漏。 相反，我们必须执行以下操作之一：

*   通过显式方法调用（例如 `api.close()`、`program.dispose()` 或 `api[Symbol.dispose]()`）手动处置它们，或
*   当它们超出范围时，使用 `using` 关键字声明它们时，它们会自动处置它们。

处理完一个程序后，我们将无法再次使用它。

### 快照

上面，我们使用 API 对直线“批”编译进行了建模； 但是，许多带有 TypeScript 的工作流都围绕着可能随着时间的推移而发生的变化。 TypeScript 可以通过新的文件更新（磁盘或用户类型）对状态进行建模，而不是每次我们需要构建整个世界。

API 的核心是 _snapshot_ 的概念。 快照是某个时间点的所有项目和程序的版本。 我们总是可以使用 `api.createSnapshot` 创建一个新快照，其中包含我们需要的所有信息，但我们也可以从之前的 `snapshot.update(/*...*/)` 中获得一个新快照。 这通常可以节省大量工作，无论是发送所有原始信息，还是让编译器重建世界。

```typescript
import { ScriptTarget } from "typescript/ast";
import { createFileSystemLayer, createFileSystemWithLib } from "typescript/fs";
import { API } from "typescript/sync";
import { resolve } from "node:path";

const fileName = resolve("snapshot-example.ts");

using api = new API();
using before = api.createSnapshot({
    fileSystem: createFileSystemWithLib([
        [fileName, 'export const answer: number = "forty-two";'],
    ]),
    createPrograms: [
        {
            rootFiles: [fileName],
            compilerOptions: {
                strict: true,
                noEmit: true,
                target: ScriptTarget.ES2022,
            },
        },
    ],
});

using beforeProgram = before.operation.createdPrograms[0];
console.log("before:", beforeProgram.getSemanticDiagnostics().length);

using after = before.update({
    fileSystem: createFileSystemLayer([
        [fileName, "export const answer: number = 42;"],
    ]),
    ensurePrograms: [beforeProgram.id],
});

using afterProgram = after.getProgram(beforeProgram.id);
if (!afterProgram) {
    throw new Error("The updated program was not found.");
}

console.log("after:", afterProgram.getSemanticDiagnostics().length);
console.log("before again:", beforeProgram.getSemanticDiagnostics().length);

// Outputs:
//  before: 1
//  after: 0
//  before again: 1
```

我们稍后会回到这些文件系统 API。

这里要注意的一件事是，我们能够从名为 `before` 的原始快照开始，并在进行名为 `after` 的更改后获得新快照。 快照可以包含 `Program` 对象（和 `Project`），它们具有 `id` 在快照更改之间保留的 `id`。 我们使用 `ensurePrograms` 来指定我们关心在新快照中观察更新的 `Program` （当前默认值为 lazier 并允许您堆叠 `update()` 调用而不将更新强制为 `Program`s）。

请注意，即使在调用 `update` 之后，我们也可以使用先前快照中的信息。 例如，我们仍然可以要求对 `beforeProgram` 和 `afterProgram` 进行诊断。 也就是说，请确保不要混合和匹配来自一个快照的程序、项目或检查器的对象。

快照与我们上面的其他类型一样 `Disposable`，因此我们需要手动 `dispose()` 或使用 `using` 声明为它们创建本地绑定。 处置 `Snapshot` 后，我们无法再次使用它。

### 文件系统 API

默认情况下，TypeScript 的 API 将在主机文件系统上运行。 这意味着除非我们另有说明，否则它将在“磁盘上”命中文件。

功能

行为

`createFileSystem(files)`

定义一个完整的文件系统。 除非明确装载，否则未列出的文件不存在。

`createFileSystemWithLib(files)`

定义一个完整的文件系统，并以只读方式挂载编译器的默认库目录。

`createFileSystemLayer(files)`

在回退到基本快照的文件系统或主机文件系统时覆盖选定的文件。

在我们之前的示例中，我们使用 `createFileSystemWithLib` 创建了一个（部分）虚拟文件系统，并且仅指定了我们关心的程序中的文件。 当我们想进行更新时，我们只能将 `createFileSystemLayer` 用于更改的文件，其他文件（如 `lib.d.ts` 和其他任何内容）继续通过我们在初始快照中创建的基本文件系统层进行解析。

```typescript
// ...

using snapshot = api.createSnapshot({
    fileSystem: createFileSystemWithLib([
        [
            mainFile,
            [
                'import { greeting } from "./generated.js";',
                "export const message: string = greeting;",
            ].join("\n"),
        ],
        [generatedFile, 'export const greeting = "Hello from memory!";'],
    ]),
    createPrograms: [
        {
            rootFiles: [mainFile],
            compilerOptions: {
                strict: true,
                module: ModuleKind.ESNext,
                moduleResolution: ModuleResolutionKind.Bundler,
                target: ScriptTarget.ES2022,
            },
        },
    ],
});

using program = snapshot.operation.createdPrograms[0];

// ...
// Get emit without writing files to any file system.
const emitResult = program.emitToString();
```

有一些方法可以控制在这些层上观察文件的方式。 例如，`removedPaths` 可以阻止来自底层系统的请求。

如果您需要提供一定程度的文件监视，目前需要单独完成。 文件创建/删除/修改需要通过 `snapshot.update()` 中的 `fileNotifications` 选项提供。 任何不在 _host_ 文件系统中发生的修改都需要提供另一个文件系统层。

### 内容映射器

TypeScript 长期以来一直对 TypeScript 和 JavaScript 代码进行强大的检查和工具。 但是，许多开发人员使用专门的文件类型来写出他们的组件。 例如，Vue.js 在单个 `.vue` 文件中包含 HTML、JavaScript 和 CSS 区域，以及该 HTML 中的 JavaScript 嵌入区域。 对于像 Astro、Ember、Svelte 和其他库这样的库来说也是如此——这些框架遵循类似的方式来声明其组件。 在某个时候，出现了一个名为 Volar 的项目，为这些单文件组件格式提供 TypeScript 工具，以在编辑器中提供无缝的开发体验。 Volar 通过使用 TypeScript 的语言服务显示错误、代码完成、导航等，并能够将其功能扩展到其他格式，例如 MDX 文件。

不幸的是，Volar 面临的挑战之一是 TypeScript 缺乏一些 API 来轻松提供有凝聚力的体验。 例如，虽然 Volar 的模型支持编辑器支持，但这些其他文件格式的命令行类型检查器无法真正使用 Volar，因为它们与 TypeScript 完全不同的 API 集成在一起。 另一个问题是 Volar 必须将 TypeScript 作为子组件嵌入并完全接管编辑器体验，要么必须使用尴尬的解决方法来集成给定的 API 中的限制。 借助 TypeScript 7.0，我们借此机会重新思考 Toolset 如何更好地支持嵌入 JavaScript 和 TypeScript 代码的格式。 事实上，在 TypeScript 7.1 中，Volar 的核心模型现在是一流的公民。

TypeScript 7.1 引入了对名为 _Content Mappers_ 的新插件点的支持。 内容映射器可以使用特定的文件扩展名注册，并且能够生成文件的虚拟表示以供 TypeScript 查看。 此表示还具有映射回原始文件的区域，通常在包含相应 JavaScript 或 TypeScript 代码的区域中。 这允许 TypeScript 提供更准确的错误消息和跨度，并为这些嵌入区域提供工具。

要使用内容映射器，您需要将其注册到项目 `tsconfig.json` 中的一组特定扩展中。 例如，如果我们安装了一个名为 `@vue/content-mapper` 的包（它是 _not_ 当前在 npm 上），我们可以将其包含在 `tsconfig.json` 中，如下所示：

```json
{
  "compilerOptions": {
    // ...
  },
  "contentMappers": [
    {
      "package": "@vue/content-mapper",
      "extensions": [".vue"],
      "options": {
        "target": 3.5
      }
    }
  ]
}
```

每当程序中包含文件时——无论是通过 `tsconfig.json` 中的 `files`/`include` 还是通过 `import`，TypeScript 将检查已注册的内容映射器并为该文件请求内容和映射。 然后我们可以直接从命令行运行。

```sh
tsc --runExternalCode
```

注意允许 TypeScript 执行内容映射器所需的 `--runExternalCode` 标志。 内容映射器实际上是 TypeScript 调度到的任意可执行文件，因此 `--runExternalCode` 标志使这一点变得明确。

在像 VS Code 这样的编辑器中，TypeScript 7.1 “Just”适用于 Content Mappers，尽管它需要授予工作空间信任和内容映射器权限。 在我们的 VS Code 扩展中，您还可以通过配置新的 `js/ts.contentMappers.enabled` 设置来完全禁用此功能。

### 使用分布式参数时更强的检查

在 TypeScript 中，根据类型变量进行计算的条件类型（例如，`T extends Whatever ? TrueType : FalseType` 中的 `T`）将在提供该类型变量时分布在联合类型上。 例如：

```typescript
type Foo<T> = T extends "a" | "b" | "c" ? { known: T } : { unknown: T };

// { known: "a" } | { known: "b" } | { unknown: "x" } | { unknown: "y" }
type Bar = Foo<"a" | "b" | "x" | "y">;
```

这里，`T`是一个类型参数，字符串字面类型`"a"`、`"b"`、`"x"`和`"y"`分别根据`extends`右侧的类型进行单独评估。 为 Union 的每个成员实例化适当的分支，然后将生成的类型联合在一起以 `Bar` 的类型联合在一起。

而在上面的条件类型的每个分支中，我们提到了`T`，这与原始类型参数不同。 分发时，`T` 将代表原始联合类型的更具体的子集。 然而，以前版本的 TypeScript 并没有区分两者。

```typescript
type Show<A extends number, B extends A> = `${B} extends ${A}`;

type Issue<A extends number, B extends A> =
    A extends B ?
        never :
        Show<A, B>; // We shouldn't be allowed to write this branch!
```

在类型 `Issue` 中，我们在 false 分支中写下了 `Show<A, B>`，我们将说明为什么不应该这样做。

`Show` 类型确保其第二类型参数是第一个的子类型。 在 TypeScript 7.0 和之前，这似乎是正确的——`Issue` 类型声明了 `B extends A`，那么为什么不是这样呢？ 在这个假设中，井分布引发了一个扳手。

```typescript
// Forms the string literal type `"0 extends 1"`
type UhOh = Issue<0 | 1, 0>;
```

同样，问题在于，虽然像 `0` 这样的字面类型是联合 `0 | 1` 的一个子类型，但将每个分支中的联合分解确实让我们拥有可能不相关的不同类型。 您可以以不同的方式重新构建它：`Cat` 可能是 `Animal` 的子类型，但它肯定不会是每种 `Animal` 的子类型。

TypeScript 7.1 对此更严格。 在每个分支中，您可以有效地将 `T` 视为原始类型参数，它是原始类型的子类型，但与其他类型参数约束的其他类型没有任何关系。

```typescript
type Show<A extends number, B extends A> = `${B} extends ${A}`;

type Issue<A extends number, B extends A> =
    A extends B ?
        never :
        Show<A, B>;
//              ~
// error!
// Type 'B' does not satisfy the constraint 'A'.
//   'B' is only assignable to the non-distributed 'A', but 'A' has been distributed here.
```

遇到此问题的代码可能需要修改，如果不必要的话，要么删除原始约束，要么添加额外的条件类型检查以满足其他类型的必需约束。

有关详细信息，请参阅 [the reporting issue](https://github.com/microsoft/TypeScript/issues/63708) 和 [the pull request that introduced this change](https://github.com/microsoft/TypeScript/pull/64237)。
