今天我们很高兴地宣布TypeScript 7.1的beta版本发布！

```sh
npm install -D typescript@beta
```

让我们来看看TypeScript 7.1中有什么新功能！

## 环境模块中支持导入属性

[导入属性](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/with)是附加到导入语句上的元数据。通常，它们的目的是指示运行时和打包工具如何解释导入的内容，以及所得模块的形状。例如，

```typescript
import myData from "./data/someData.json" with { type: "json" };
```

`with`关键字后面的对象中的所有内容都是导入属性。像浏览器这样的环境不能简单地根据文件扩展名（如`.json`）决定如何处理导入。指定`type: "json"`告诉运行时，`someData.json`需要被解释为JSON文件，解析并通过默认导入提供（在我们上面的示例中，即`myData`）。

`type` 属性已经成为运行时自定义此行为的事实上的方法。 [ECMAScript (JavaScript) 有一个提议](https://github.com/tc39/proposal-import-text) ，允许代码指定 `type: "text"` ，它将导入的内容作为字符串返回。

```typescript
import readme from "../README.md" with { type: "text" };

console.log(readme);
```

也有 [一个提议](https://github.com/tc39/proposal-import-bytes) 用于 `type: "bytes"` 以返回原始字节的 `Uint8Array` 。

```typescript
import { pngToPixels, boxBlur } from "./photoUtils.js";

import photo from "./myPhoto.png" with { type: "bytes" };
const blurryPhoto = boxBlur(pngToPixels(photo));
```

浏览器也已经允许将 CSS 文件作为 `CSSStyleSheet` 导入，使用 `type: "css"` 已有几年了。

```typescript
import someTheme from "./themes/someCoolTheme.css" with { type: "css" };

document.adoptedStyleSheets.push(someTheme);
```

为了支持导入这些文件，人们可能会在 TypeScript 中使用带有通配符模式（例如 `*.css` ）的 *ambient module declarations* 。

```typescript
// You can write this in a global `.d.ts` file with no import statements.

declare module "*.css" {
    const content: CSSStyleSheet;
    export default content;
}

declare module "*.txt" {
    const content: string;
    export default content;
}

declare module "*.md" {
    const content: string;
    export default content;
}

declare module "*.bin" {
    const content: Uint8Array;
    export default content;
}
```

这样可以，但它不能适用于所有环境，因为它根本没有考虑导入属性。

你可能会问为什么这是一个问题——乍一看，这似乎只是允许人们不小心省略导入属性的问题。

```typescript
// ❌ oops, forgot an import attribute
import readme from "../README.md";

// ✅ what we were supposed to write
import readme from "../README.md" with { type: "text" };
```

但这仍然是一个值得解决的问题。另一个问题是它变得重复。使用导入属性，整个问题在于运行时环境关心属性，而不是文件扩展名。如果两个 `.txt` 和 `.md` 文件都将使用 `type: "text"`，我们不应该为两个文件重新声明一个模式。

但一个主要问题是，运行时环境可能支持完全不同的导入属性，并且可能根据它们是否存在而表现出不同的行为。例如，打包工具可能会使用构建时的功能，称为 [CSS Modules](https://github.com/css-modules/css-modules) ，作为导入 `.css` 文件时的默认行为，但指定浏览器支持的 `type: "css"` 在导入语句中将覆盖此行为，并确保 `.css` 文件被带入作为 `CSSStyleSheet` 对象。

这就是为什么 TypeScript 7.1 引入了对环境模块声明中导入属性的支持。您现在可以在 TypeScript 项目中声明以下内容，如果尝试在没有必要的导入属性的情况下导入文件，则会得到一个错误，并根据导入属性得到正确的类型。

```typescript
declare module "*" with { type: "css" } {
    const content: CSSStyleSheet;
    export default content;
}

declare module "*" with { type: "text" } {
    const content: string;
    export default content;
}

declare module "*" with { type: "bytes" } {
    const content: Uint8Array;
    export default content;
}
```

请注意，匹配这些声明的导入不会被验证为磁盘上的文件。与当前行为一致，当导入匹配环境模块声明时，失败的查找将在运行时或捆绑器的构建过程中报告。

另外，请注意，这些声明不会作为TypeScript内置库的一部分发布。我们建议库**不**将它们包含在其发布包中，如果需要，终端用户需要在自己的项目中声明它们。这将为终端用户提供灵活性，以配置全局作用域（例如，`lib.dom.d.ts`与`@types/node`），并将防止与内置声明的未来冲突。

有关更多信息，请参阅[我们实现的拉取请求](https://github.com/microsoft/TypeScript/pull/63931)。

## 源阶段导入

[源阶段导入](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/source)是[ECMAScript中提议的新功能](https://github.com/tc39/proposal-source-phase-imports)。该功能引入了一个新的`source`修饰符/关键字，位于`import`关键字之后。只有默认导入可以使用`import source`编写。

```typescript
import source SomeModule from "some-module";
```

这个特性的想法是，当我们使用 `import source` 时，我们将得到一个代表模块的对象，该对象在运行时解析和分析后，但*在* 其导入被加载之前（因此，在它们被验证或链接到其他模块之前，以及在模块中的任何代码运行之前）。这个对象本身有点“惰性” – 它是 `AbstractModuleSource` 的一个实例，这个实例最终是要被导入或实例化的。

对于 WebAssembly (wasm) 导入，该对象将是一个 `WebAssembly.Module` 的实例。这些对象的有用之处在于，它们可以直接传递到 `WebAssembly.instantiate` 中。

```typescript
import source SuperFastThing from "./super-fast-thing.wasm";
import { WASI } from "node:wasi";

const wasi = new WASI({ /*...*/ });
const fastThingInstance = await WebAssembly.instantiate(SuperFastThing, {
    wasi_snapshot_preview1: wasi.wasiImport
});

wasi.start(fastThingInstance);
```

WebAssembly 源导入已经在 [Node.js 的最新版本中得到了支持](https://beta.docs.nodejs.org/esm#wasm-source-phase-imports)。

目前，你不能对 JavaScript 文件的源导入做太多事情。该提案的精神意味着在某个时候，我们可能能够直接将 JavaScript 模块源传递到 `import()` 调用中。

```typescript
import source SomeModule from "./someModule.js";
const moduleInstance = await import(SomeModule);
```

另一个与 JavaScript 源导入相关的想法是，随着时间的推移，我们可能会获得其他功能，这些功能将允许我们自定义模块加载和实例化的行为，类似于我们之前对 `WebAssembly.instantiate` 所做的那样。但我们还没有达到那一步，事实上，许多环境和工具仍然不支持 JavaScript 源导入。

源导入并不局限于导入语句。你也可以通过 `import.source` 元属性函数执行 *动态* 源导入。

```typescript
const SuperFastThing = await import.source("./super-fast-thing.wasm");
const fastThingInstance = await WebAssembly.instantiate(SuperFastThing, {
    // ...
});
```

源导入保持身份。这意味着你可以在 `Map`s 和 `Set`s 中使用它们，或者可靠地比较它们。

```typescript
// Note that `WebAssembly.instantiate` always returns a distinct object.
import source source1 from "./plugin.wasm"
import source source2 from "./plugin.wasm"
const source3 = await import.source("./plugin.wasm");

console.log(source1 === source2); // true
console.log(source2 === source3); // true
```

使用 `import source` 时，每个导入的模块都具有 `AbstractModuleSource` 类型，这是 `lib.esnext.d.ts` 中的一个新全局类型。要使用源导入，你必须具有适当的 `--module` 设置（即 `esnext`、`nodenext` 或 `preserve`），以及 `--lib` 或 `--target` 中的适当 `esnext` 选项。

[该功能得以实现](https://github.com/microsoft/TypeScript/pull/63915) 多亏了 [Oleksandr Tarasiuk](https://github.com/a-tarasyuk) 的工作。

## TypeScript 7.1 API

TypeScript 7.1 提供了一个新的 API，允许使用我们的语法和语义分析构建强大的工具和实用程序。

与其暴露一个单一的 API，不如说 TypeScript 7.1 被组织成几个入口点，每个入口点都服务于特定的目的。

入口点 | 目的
\----|----
`typescript/sync` | 一个同步编译器客户端，它支持编译器选项、类型检查器和程序 API

`typescript/async`

一个基于 `Promise` 的同步客户端等价物

`typescript/fs`

请求范围的完整和分层文件系统

`typescript/ast`

语法树节点（AST）类型和枚举，例如 `SyntaxKind` 和 `ScriptTarget`

`typescript/ast/is`

节点类型守卫

`typescript/ast/factory`

`create*` 和不可变的 `update*` 函数

下面是一个使用 TypeScript 7.1 API 进行简单编译的示例，文件名和编译器选项显式传递在命令行上。与 `tsc` 不同，该示例不发现或加载 `tsconfig.json` 文件，也不支持 `--project`。

```typescript
// Compile explicit filenames using command-line compiler options.

import { API, formatDiagnosticsWithColorAndContext, type Diagnostic } from "typescript/sync";

using api = new API();
const reportErrors = (diagnostics: readonly Diagnostic[]) => {
    console.log(formatDiagnosticsWithColorAndContext(diagnostics, api))
};

// Parse command-line filenames and compiler options, report any errors.
const commandLineArgs = process.argv.slice(2);
const parsedCommandLine = api.parseCommandLine(commandLineArgs);
if (parsedCommandLine.errors.length > 0) {
    reportErrors(parsedCommandLine.errors);
    process.exit();
}

// Create the program by resolving and parsing all files in the entry point.
using program = api.createProgram(parsedCommandLine.fileNames, parsedCommandLine.options);

// Collect and report any diagnostics from the program before emitting.
// You can customize whether any of these block reporting errors in subsequent passes if desired.
const diagnostics = [
    ...program.getGlobalDiagnostics(),
    ...program.getProgramDiagnostics(),
    ...program.getSyntacticDiagnostics(),
    ...program.getSemanticDiagnostics(),
];
if (diagnostics.length > 0) {
    reportErrors(diagnostics);
}

// Emit files - this respects the `noEmitOnError` option,
// so nothing will be emitted if an earlier step reported errors.
const emitResult = program.emit();
if (emitResult.diagnostics.length > 0) {
    reportErrors(emitResult.diagnostics);
}
```

请注意我们上述声明中的 `using` 关键字。你可能不熟悉 [`using`，因为它在 JavaScript 中相当新](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/using)，但不必担心。

`API` 实例和 `Program` 实例都是 [`Disposable` 对象](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Symbol/dispose)。当我们请求创建它们时，TypeScript 分配内存并进行记录以确保它们在 Go 和 JavaScript 运行时之间保持存在；但是，当我们使用完它们后，我们不能简单地让垃圾收集器处理它们，否则我们将在 Go 侧泄漏内存。相反，我们必须执行以下操作之一：

* 使用显式方法调用手动释放它们（例如 `api.close()`、`program.dispose()` 或 `api[Symbol.dispose]()`），或
* 通过使用 `using` 关键字声明它们，当它们超出范围时自动释放它们。

程序被释放后，我们将无法再次使用它。

### 快照

上述内容中，我们使用 API 模型化了一条直线的“批”编译；但是，许多 TypeScript 工作流都是围绕随时间可能发生的更改而构建的。与其每次需要时都构建整个世界，TypeScript 可以使用新文件更新（无论是磁盘上的更新还是用户输入）来模型状态的转变。

API 的核心概念是 *快照* 。快照是指在某一时刻所有项目和程序的版本。我们可以使用 `api.createSnapshot` 创建一个包含所有所需信息的新快照，但也可以使用 `snapshot.update(/*...*/)` 从之前的快照中派生出一个新快照。这通常可以节省很多工作，不仅可以减少发送原始信息的量，还可以避免编译器重新构建整个世界。

```typescript
import { ScriptTarget } from "typescript/ast";
import { createFileSystemLayer, createFileSystemWithLib } from "typescript/fs";
import { API } from "typescript/sync";
import { resolve } from "node:path";

const fileName = resolve("snapshot-example.ts");

using api = new API();
using before = api.createSnapshot({
    fileSystem: createFileSystemWithLib([
        [fileName, 'export const answer: number = "forty-two";'],
    ]),
    createPrograms: [
        {
            rootFiles: [fileName],
            compilerOptions: {
                strict: true,
                noEmit: true,
                target: ScriptTarget.ES2022,
            },
        },
    ],
});

using beforeProgram = before.operation.createdPrograms[0];
console.log("before:", beforeProgram.getSemanticDiagnostics().length);

using after = before.update({
    fileSystem: createFileSystemLayer([
        [fileName, "export const answer: number = 42;"],
    ]),
    ensurePrograms: [beforeProgram.id],
});

using afterProgram = after.getProgram(beforeProgram.id);
if (!afterProgram) {
    throw new Error("The updated program was not found.");
}

console.log("after:", afterProgram.getSemanticDiagnostics().length);
console.log("before again:", beforeProgram.getSemanticDiagnostics().length);

// Outputs:
//  before: 1
//  after: 0
//  before again: 1
```

我们稍后会回来讨论那些文件系统 API。

这里需要注意的一点是，我们可以从原始快照 `before` 开始，修改后派生出一个新的快照 `after`。快照可以包含 `Program` 对象（和 `Project` 对象），这些对象的 `id` 在快照更改之间保持不变。我们使用 `ensurePrograms` 指定在新快照中要观察更新的 `Program` 对象（当前默认值更懒惰，允许你堆叠 `update()` 调用而不强制更新 `Program` 对象）。

注意，即使在调用 `update` 之后，我们仍然可以使用来自之前快照的信息。例如，我们仍然可以请求 `beforeProgram` 和 `afterProgram` 的诊断信息。然而，确保不要混合来自一个快照的程序、项目或检查器的对象。

快照是 `Disposable`，像我们上面提到的其他类型一样，所以我们需要手动调用 `dispose()` 或使用 `using` 声明为它们创建一个局部绑定。一旦快照被dispose，我们就不能再使用它了。

### 文件系统API

默认情况下，TypeScript 的 API 将在宿主文件系统上操作。这意味着它将访问“磁盘”上的文件，除非我们指定其他方式。

函数

行为

`createFileSystem(files)`

定义一个完整的文件系统。未列出的文件将被认为不存在，除非显式地挂载。

`createFileSystemWithLib(files)`

定义一个完整的文件系统，并以只读方式挂载编译器的默认库目录。

`createFileSystemLayer(files)`

覆盖选定的文件，同时回退到基础快照的文件系统或宿主文件系统。

在我们之前的例子中，我们使用 `createFileSystemWithLib` 创建了一个（部分的）虚拟文件系统，并且只指定了我们关心的程序文件。当我们想要进行更新时，我们可以使用 `createFileSystemLayer` 只更新更改的文件，而其他文件（如 `lib.d.ts` 和其他文件）继续通过我们最初创建的基准文件系统层解析。

```typescript
// ...

using snapshot = api.createSnapshot({
    fileSystem: createFileSystemWithLib([
        [
            mainFile,
            [
                'import { greeting } from "./generated.js";',
                "export const message: string = greeting;",
            ].join("\n"),
        ],
        [generatedFile, 'export const greeting = "Hello from memory!";'],
    ]),
    createPrograms: [
        {
            rootFiles: [mainFile],
            compilerOptions: {
                strict: true,
                module: ModuleKind.ESNext,
                moduleResolution: ModuleResolutionKind.Bundler,
                target: ScriptTarget.ES2022,
            },
        },
    ],
});

using program = snapshot.operation.createdPrograms[0];

// ...
// Get emit without writing files to any file system.
const emitResult = program.emitToString();
```

有一些方法可以控制文件在这些层中如何被观察。例如，`removedPaths` 可以阻止对底层系统的请求。

如果你需要提供某种程度的文件监视，目前需要单独完成。文件的创建、删除和修改需要通过 `snapshot.update()` 中的 `fileNotifications` 选项提供。发生在 *宿主* 文件系统之外的任何修改都需要提供另一个文件系统层。

### 内容映射器

TypeScript 已经拥有强大的检查和工具来支持 TypeScript 和 JavaScript 代码；然而，很多开发者使用专门的文件类型来编写组件。例如，Vue.js 在单个 `.vue` 文件中包含 HTML、JavaScript 和 CSS 的区域，以及在 HTML 中嵌入的 JavaScript 区域。同样，像 Astro、Ember、Svelte 等库也遵循类似的组件声明方式。后来，一个名为 Volar 的项目出现了，旨在为这些单文件组件格式提供 TypeScript 工具，从而在编辑器中提供无缝的开发体验。Volar 通过使用 TypeScript 的语言服务，提供错误提示、代码补全、导航等功能，并且能够扩展其能力以支持其他格式，例如 MDX 文件。

不幸的是，Volar 之前面临的一个挑战是 TypeScript 缺乏一些 API，使得难以提供一个连贯的体验。例如，虽然 Volar 的模型在编辑器支持方面表现出色，但命令行类型检查器对于这些其他文件格式却无法真正使用 Volar，因为它们与 TypeScript 的完全不同 API 集成。另一个问题是 Volar 要么必须将 TypeScript嵌入为子组件并完全接管编辑器体验，要么必须使用笨拙的变通方法来与现有的 TypeScript 工具集成，限制了我们的 API。有了 TypeScript 7.0，我们抓住机会重新思考工具集如何更好地支持嵌入 JavaScript 和 TypeScript 代码的格式。事实上，有了 TypeScript 7.1，Volar 的核心模型现在成为了一个一流公民。

TypeScript 7.1 引入了对一个新插件点的支持，称为 *内容映射器*。内容映射器可以注册一个特定的文件扩展名，并能够为 TypeScript 生成一个文件的虚拟表示。此表示还具有可以映射回原始文件的区域，通常位于包含相应 JavaScript 或 TypeScript 代码的区域。这使得 TypeScript 能够提供更准确的错误消息和跨度，并为这些嵌入区域提供工具。

要使用内容映射器，您需要在项目的 `tsconfig.json` 中将其注册为一组特定的扩展名。例如，如果我们安装了一个名为 `@vue/content-mapper` 的包（目前尚未在 npm 上发布），我们可以在 `tsconfig.json` 中将其包含如下：

```json
{
  "compilerOptions": {
    // ...
  },
  "contentMappers": [
    {
      "package": "@vue/content-mapper",
      "extensions": [".vue"],
      "options": {
        "target": 3.5
      }
    }
  ]
}
```

每当一个文件被包含在程序中 – 无论是通过 `tsconfig.json` 中的 `files`/`include`，还是通过 `import`，TypeScript 都会检查已注册的内容映射器，并请求该文件的内容和映射。然后我们可以直接从命令行运行。

```sh
tsc --runExternalCode
```

请注意 `--runExternalCode` 标志，它是允许 TypeScript 执行内容映射器所需的。内容映射器本质上是任意可执行文件，TypeScript 会派发到它们，因此 `--runExternalCode` 标志使其显式化。

### 使用分配类型参数时的更强检查

在 TypeScript 中，一个条件类型（例如，`T extends Whatever ? TrueType : FalseType` 中的 `T`）将在联合类型被提供给该类型变量时在联合类型上分配。例如：

```typescript
type Foo<T> = T extends "a" | "b" | "c" ? { known: T } : { unknown: T };

// { known: "a" } | { known: "b" } | { unknown: "x" } | { unknown: "y" }
type Bar = Foo<"a" | "b" | "x" | "y">;
```

这里，`T` 是一个类型参数，字符串字面量类型 `"a"`、`"b"`、`"x"` 和 `"y"` 每个都单独与 `extends` 右边的类型进行评估。对于联合类型的每个成员，适当的分支都会被实例化，所得到的类型然后被联合起来作为 `Bar` 的类型。

虽然在上述条件类型的每个分支中，我们都引用了 `T`，但那并不是完全相同的原始类型参数。分布时，`T` 将代表原始联合类型的一个更具体的子集。然而，之前的 TypeScript 版本并没有区分这两者。

```typescript
type Show<A extends number, B extends A> = `${B} extends ${A}`;

type Issue<A extends number, B extends A> =
    A extends B ?
        never :
        Show<A, B>; // We shouldn't be allowed to write this branch!
```

在 `Issue` 类型中，我们在 false 分支中写出了 `Show<A, B>`，我们将解释为什么不应该允许这样做。

`Show` 类型确保其第二个类型参数是第一个类型参数的子类型。在 TypeScript 7.0 及之前版本中，这似乎是正确的——`Issue` 类型声明了 `B extends A`，那么为什么这不成立呢？好吧，分布打破了这个假设。

```typescript
// Forms the string literal type `"0 extends 1"`
type UhOh = Issue<0 | 1, 0>;
```

同样，问题在于虽然像 `0` 这样的字面类型是联合 `0 | 1` 的子类型，但是在每个分支中拆开联合后，我们实际上得到了不同的类型，这些类型可能没有任何关联。你可以从不同的角度来看待这个问题：一只 `Cat` 可能是 `Animal` 的子类型，但它绝对不会是每一种 `Animal` 类型的子类型。

TypeScript 7.1 对此更加严格。在每个分支中，你可以有效地认为 `T` 是一个新的类型参数，它是原始类型的子类型，但它不会与其他受原始类型参数约束的类型有任何关联。

```typescript
type Show<A extends number, B extends A> = `${B} extends ${A}`;

type Issue<A extends number, B extends A> =
    A extends B ?
        never :
        Show<A, B>;
//              ~
// error!
// Type 'B' does not satisfy the constraint 'A'.
//   'B' is only assignable to the non-distributed 'A', but 'A' has been distributed here.
```

遇到这种情况的代码可能需要被修改， либо删除原始约束（如果它不必要）， либо添加额外的条件类型检查以满足其他类型的必需约束。

有关更多信息，请参阅 [报告问题](https://github.com/microsoft/TypeScript/issues/63708) 和 [引入此更改的拉取请求](https://github.com/microsoft/TypeScript/pull/64237)。
