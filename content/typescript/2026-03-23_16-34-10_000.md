今天我们很高兴地宣布 TypeScript 6.0 的可用性！

如果您不熟悉 TypeScript，它是一种通过为类型添加语法的 JavaScript 构建的语言，它使类型检查能够捕获错误，并提供丰富的编辑器工具。 您可以了解有关 TypeScript 以及如何开始使用 [TypeScript website](https://www.typescriptlang.org/) 的更多信息。

但是如果你已经熟悉了这种语言，你可以通过 npm 使用以下命令获得 TypeScript 6.0：

npm install -d 打字稿
    

TypeScript 6.0 是一个独特的版本，我们打算将其作为基于当前 JavaScript 代码库的最后一个版本。 [As announced last year](https://devblogs.microsoft.com/typescript/typescript-native-port/) （与 [recent updates here](https://devblogs.microsoft.com/typescript/progress-on-typescript-7-december-2025/)），我们正在为 Go 中编写的 TypeScript 编译器和语言服务开发一个新的代码库，该代码库利用了本机代码和共享内存多线程的速度。 新的代码库将成为 TypeScript 7.0 及更高版本的基础。

TypeScript 6.0 作为 TypeScript 5.9 和 7.0 之间的桥梁。 因此，TypeScript 6.0 中的大多数更改旨在帮助对齐并准备采用 TypeScript 7.0。 说起来似乎令人惊讶，但 TypeScript 7.0 ** 实际上非常接近完成**。 您可以 [try it out in Visual Studio Code](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview) 或 [install it from npm](https://npmx.dev/package/@typescript/native-preview)。 事实上，如果您能够采用 TypeScript 6.0，我们鼓励您尝试 TypeScript 7.0 的本机预览。

话虽如此，TypeScript 6.0s 中有一些新功能和改进，不仅仅是对齐。 让我们来看看这个版本的一些亮点，然后更详细地了解 7.0 的变化以及如何准备。

自测试版和RC以来有什么新的？
--------------------------------

自 TypeScript 6.0 Beta 以来，我们进行了一些值得注意的更改——主要是为了与 TypeScript 7.0 的行为保持一致。

一种调整是对泛型调用中的函数表达式进行类型检查，尤其是那些出现在泛型 JSX 表达式中的函数表达式（[see this pull request](https://github.com/microsoft/TypeScript/pull/63163)）。 这通常会捕获现有代码中的更多错误，尽管您可能会发现某些通用调用可能需要显式类型参数。

我们还扩展了对导入断言语法（即 `import ... assert {...}`）的弃用 [to `import()` 调用](https://github.com/microsoft/TypeScript/pull/63172) ，如 `import(..., { assert: {...}})`

最后，我们更新了 DOM 类型以反映最新的 Web 标准，包括对时间 API 的一些调整。

`this`\-less 函数上的上下文敏感性较少
----------------------------------------------

当参数没有写出的显式类型时，TypeScript 通常可以根据预期的类型，甚至通过同一函数调用中的其他参数来推断它们。

声明函数 callit<T>(obj: {
生产：（x：数）=> t，
消费：(y:t)=> 无效，
})：无效；
    
// 工作，没有问题。
呼叫（{
生产：（x：数）=> x * 2，
消费：y => y.toFixed()，
});
    
// 工作，即使属性的顺序被翻转，也没有问题。
呼叫（{
消费：y => y.toFixed()，
生产：（x：数）=> x * 2，
});
    

在这里，无论属性的顺序如何，TypeScript 都可以根据 `produce` 函数推断 `consume` 函数中 `y` 的类型。 但是，如果这些函数是使用 _method syntax_ 而不是箭头函数语法编写的呢？

声明函数 callit<T>(obj: {
生产：（x：数）=> t，
消费：(y:t)=> 无效，
})：无效；
    
// 工作正常，`x` 被推断为一个数字。
呼叫（{
produce(x: number) { 返回 x * 2; },
消耗（y）{返回y.toFixed（）； },
});
    
呼叫（{
消耗（y）{返回y.toFixed（）； },
// ~
// 错误：'y' 类型为“未知”。
    
produce(x: number) { 返回 x * 2; },
});
    

奇怪的是，第二次调用 `callIt` 会导致错误，因为 TypeScript 无法推断 `consume` 方法中 `y` 的类型。 这里发生的事情是，当 TypeScript 试图找到 `T` 的候选者时，它将首先跳过参数没有显式类型的函数。 这样做是因为某些函数可能需要正确检查 `T` 的推断类型 - 在我们的情况下，我们需要知道 `T` 的类型来分析我们的 `consume` 功能。

这些函数称为 _contextually 敏感函数_ - 基本上，没有显式类型的参数的函数。 最终，类型系统需要找出这些参数的类型——但这与泛型函数中推理的工作方式有点不同，因为这两个“拉”了不同方向的类型。

函数 callFunc<T>(callback: (x: t) => void, value: t) {
返回回调（值）；
}
    
callfunc(x => x.toFixed(), 42);
// ^
// 我们需要在这里找出 `x` 的类型，
// 但我们还需要找出 `T` 的类型来检查回调。
    

为了解决这个问题，TypeScript 在类型参数推断过程中跳过上下文敏感的函数，而是首先检查和推断其他参数。 如果跳过上下文敏感的函数不起作用，那么推理只会在任何未经检查的参数中继续进行，在参数列表中从左到右进行。 在上面的示例中，TypeScript 将在 `T` 的推理过程中跳过回调，但随后将查看第二个参数 `42`，并推断 `T` 是 `number`。 然后，当它回来检查回调时，它将具有 `(x: number) => void` 的上下文类型，这允许它推断 `x` 也是 `number`。

那么我们之前的例子中发生了什么？

// 箭头语法 - 没有错误。
呼叫（{
消费：y => y.toFixed()，
生产：（x：数）=> x * 2，
});
    
// 方法语法 - 错误！
呼叫（{
消耗（y）{返回y.toFixed（）； },
// ~
// 错误：'y' 类型为“未知”。
    
produce(x: number) { 返回 x * 2; },
});
    

在这两个示例中，`produce` 都被分配了一个具有显式类型 `x` 参数的函数。 不应该相同地检查它们吗？

问题很微妙：大多数函数（如使用方法语法的函数）都有一个隐式 `this` 参数，但箭头函数没有。 `this` 的任何用法都可能需要对 `T` 的类型进行“拉动”——例如，知道包含对象的类型反过来可能需要 `consume` 的类型，它使用 `T`。

但我们没有使用`this`！ 当然，该函数在运行时可能具有 `this` 值，但从未使用过！

TypeScript 6.0 在决定一个函数是否上下文敏感时会考虑到这一点。 如果 `this` 在函数中实际上从未 _used_ ，那么它就不被认为是上下文敏感的。 这意味着在类型推断方面，这些函数将被视为优先级更高，我们上面的所有示例现在都可以工作！

[This change was provided](https://github.com/microsoft/TypeScript/pull/62243) 感谢 [Mateusz Burzyński](https://github.com/Andarist) 的工作。

以 `#/` 开头的子路径导入
---------------------------------

当 Node.js 添加对模块的支持时，它添加了一个名为 ["subpath imports"](https://nodejs.org/api/packages.html#subpath-imports) 的功能。 这基本上是 [一个名为 `imports`](https://nodejs.org/api/packages.html#imports) 的字段，它允许包为其包中的模块创建内部别名。

{
“名称”：“我的包裹”，
“类型”：“模块”，
“进口”：{
"#root/*": "./dist/*"
}
}
    

这允许 `my-package` 中的模块从以 `#root/` 开头的路径导入

import * 作为“#root/utils.js”中的 utils；
    

而不是使用如下的相对路径。

import * as utils 从 "../../utils.js";
    

对此功能的一个小问题是，在指定子路径导入时，开发人员总是必须在 `#` 之后写 _something_ 。 在这里，我们使用了`root`，但它有点无用，因为除了`./dist/`之外没有我们正在映射的目录

使用捆绑程序的开发人员也习惯于使用路径映射来避免较长的相对路径。 与 Bundlers 熟悉的惯例是使用简单的 `@/` 作为前缀。 不幸的是，子路径导入根本无法从 `#/` 开始，这会导致开发人员在项目中采用它们时产生了很多混乱。

但最近，[Node.js 添加了对以 `#/`](https://github.com/nodejs/node/pull/60864) 开头的子路径导入的支持。 这允许包在其子路径导入中使用简单的 `#/` 前缀，而无需添加额外的段。

{
“名称”：“我的包裹”，
“类型”：“模块”，
“进口”：{
"#/*": "./dist/*"
}
}
    

这在较新的 Node.js 20 版本中支持，因此 TypeScript 现在支持 `--moduleResolution` 设置的选项 `nodenext` 和 `bundler` 下的 TypeScript。

这项工作得益于 [magic-akari](https://github.com/magic-akari) 和 [the implementing pull request can be found here](https://github.com/microsoft/TypeScript/pull/62844)。

将 `--moduleResolution bundler` 与 `--module commonjs` 相结合
-----------------------------------------------------------

TypeScript 的 `--moduleResolution bundler` 设置以前只允许与 `--module esnext` 或 `--module preserve` 一起使用； 然而，随着 `--moduleResolution node` 的弃用（又名 `--moduleResolution node10`），这种新组合通常是许多项目最适合的升级路径。

项目通常会想要计划向任何一个迁移

*   `--module preserve`和`--moduleResolution bundler`
*   `--module nodenext`

取决于您的项目类型（例如，捆绑的 Web 应用程序、Bun 应用程序或 Node.js 应用程序）。

更多信息可以在[this implementing pull request](https://github.com/microsoft/TypeScript/pull/62320)找到。

`--stableTypeOrdering` 标志
------------------------------

作为我们正在进行的 [TypeScript’s native port](https://devblogs.microsoft.com/typescript/typescript-native-port/) 工作的一部分，我们引入了一个名为 `--stableTypeOrdering` 的新标志，旨在协助 6.0 到 7.0 的迁移。

今天，TypeScript 按照遇到的顺序将类型 ID（内部跟踪号）分配给类型，并使用这些 ID 以一致的方式对联合类型进行排序。 属性发生了类似的过程。 因此，程序中声明事物的顺序可能会对声明发射等事物产生令人惊讶的影响。

例如，考虑此文件发出的声明：

// 输入：some-file.ts
导出函数 foo(条件：布尔) {
返回条件？ 100：500；
}
    
// 输出：some-file.d.ts
导出声明函数 foo(条件：布尔值): 100 | 500；
// ^^^^^^^^^
// 注意这个联合的顺序：100，然后是 500。
    

如果我们添加一个不相关的 `const` _above_ `foo`，声明会发出更改：

// 输入：some-file.ts
常数 x = 500；
导出函数 foo(条件：布尔) {
返回条件？ 100：500；
}
    
// 输出：some-file.d.ts
导出声明函数 foo(条件：布尔值): 500 | 100；
// ^^^^^^^^^
// 注意这里的变化顺序。
    

发生这种情况是因为文字类型 `500` 的类型 ID 低于 `100`，因为它在分析 `const x` 声明时首先被处理。 在极少数情况下，这种排序的更改甚至可能导致基于程序处理顺序的错误出现或消失，但一般来说，您可能会注意到此顺序的主要位置是在发出的声明文件中，或者在编辑器中显示类型的方式。

TypeScript 7 的主要架构改进之一是并行类型检查，这显着缩短了整体检查时间。 然而，并行性带来了一个挑战：当不同的类型检查器以不同的顺序访问节点、类型和符号时，分配给这些结构的内部 ID 变得非确定性。 这反过来会导致混淆非确定性输出，其中同一程序中两个内容相同的文件可以生成不同的声明文件，甚至在分析同一文件时计算不同的错误。 为了解决这个问题，TypeScript 7.0 根据基于对象内容的确定性算法对其内部对象（例如类型和符号）进行排序。 这可确保所有检查器都遇到相同的对象顺序，无论它们是如何以及何时创建的。 因此，在给定的示例中，TypeScript 7 将 _Always_ 打印 `100 | 500`，完全消除了排序不稳定性。

这意味着 TypeScript 6 和 7 有时可以并且确实显示不同的顺序。 虽然这些排序更改几乎总是良性的，但如果您在运行之间比较编译器输出（例如，在 6.0 与 7.0 中检查发出的声明文件），这些不同的排序可能会产生大量噪音，从而难以评估正确性。 有时，您可能会看到排序发生变化，导致类型错误出现或消失，这可能会更加令人困惑。

为了帮助解决这种情况，在 6.0 中，您可以指定新的 `--stableTypeOrdering` 标志。 这使得 6.0 的类型排序行为匹配 7.0，减少了两个代码库之间的差异数量。 请注意，我们不一定鼓励始终使用此标志，因为它可以为类型检查增加大幅减速（取决于代码库，最高可达 25%）。

如果您使用 `--stableTypeOrdering` 遇到类型错误，这通常是由于推理差异造成的。 先前没有 `--stableTypeOrdering` _happened_ 的推理基于程序中类型的当前顺序来工作。 为了帮助您解决这个问题，您通常会从某处提供显式类型中受益。 通常，这将是一个类型参数

    - SomeFunctionCall(/*...*/);
    + SomeFunctionCall<SomeExplicitType>(/*...*/);
    

或您打算传递到调用中的参数的变量注释。

    - const someVariable = { /*... 一些复杂的对象 ...*/ };
    + const someVariable: someexplicittype = { /*... 一些复杂的对象 ...*/ };
    
someFunctionCall(somevariable);
    

**请注意，此标志仅用于帮助诊断 6.0 和 7.0 之间的差异 – 它不打算用作长期功能**

[See more at this pull-request](https://github.com/microsoft/TypeScript/pull/63084)。

`Temporal`的新类型
-------------------------

期待已久的 [Temporal proposal](https://github.com/tc39/proposal-temporal) 已达到第 4 阶段，将成为未来 ECMAScript 标准的一部分。 Typescript 6.0 现在包含临时 API 的内置类型，因此您可以通过 `--target esnext` 或 `"lib": ["esnext"]`（或更细粒度的 `esnext.temporal`）在 TypeScript 代码中开始使用它。

让昨天 = 时间.now.instant().subtract({
时间：24，
});
    
让明天 = 时间.now.instant().add({
时间：24，
});
    
控制台.log(`Yesterday: ${yesterday}`);
控制台.log(`Tomorrow: ${tomorrow}`);
    

Temporal 在多个运行时已经可用，在第 4 阶段状态下，它现在正式成为 JavaScript 语言的一部分。 [Documentation on the Temporal APIs is available on MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Temporal)。

“upsert”方法的新类型（又名`getOrInsert`）
-------------------------------------------------

`Map`s 的一个常见模式是检查一个键是否存在，如果不存在，设置和获取一个默认值。

函数 ProcessOptions(CompilerOptions: Map<string, unknown>) {
让 StrictValue：未知；
if (compileroptions.has("strict")) {
strictValue = compileRoptions.get("strict");
}
其他{
严格值 = 真；
compileRoptions.set("strict", strictvalue);
}
// ...
}
    

这种模式可能很乏味。 [ECMAScript’s "upsert" proposal](https://github.com/tc39/proposal-upsert) 最近达到了第 4 阶段，并在 `Map` 和 `WeakMap` 上介绍了 2 种新方法：

*   `getOrInsert`
*   `getOrInsertComputed`

这些方法已添加到 `esnext` 库中，以便您可以立即在 TypeScript 6.0 中开始使用它们。

用 `getOrInsert`，我们可以将上面的代码替换为以下代码：

函数 ProcessOptions(CompilerOptions: Map<string, unknown>) {
让 strictValue = compileRoptions.getOrInsert("strict", true);
// ...
}
    

`getOrInsertComputed` 工作类似，但适用于默认值计算成本可能很高的情况（例如，需要大量计算、分配或长时间运行的同步 I/O）。 相反，它需要一个仅在密钥不存在时才调用的回调。

somepMap.GetOrInsertComputed("SomeKey", () => {
返回 computeSomeExpensiveValue(/*...*/);
});
    

这个回调也被赋予 key 作为参数，这对于默认值基于 key 的情况很有用。

Somemap.GetOrInsertComputed(SomeKey, ComputeSomeExpensiveDefaultValue);
    
函数 computesomeExpensiveValue(key: string) {
// ...
}
    

[This update](https://github.com/microsoft/TypeScript/pull/62612) 得益于 GitHub 用户 [Renegade334](https://github.com/Renegade334)。

`RegExp.escape`
----------------

构造一些文字字符串以在正则表达式中匹配时，重要的是转义特殊的正则表达式字符，如 `*`、`+`、`?`、`(`、`)` 等。[RegExp Escaping ECMAScript proposal](https://github.com/tc39/proposal-regex-escaping) 已达到阶段 4，并引入了一个新的 `RegExp.escape` 函数来处理这个问题 为你。

函数 matchWholeWord(word: string, text: string) {
const 转义字 = regexp.escape(word);
const regex = new regexp(`\\b${escapedWord}\\b`, "g");
返回 text.match(regex);
}
    

`RegExp.escape` 在 `es2025` 库中可用，因此您可以在 TypeScript 6.0 中开始使用它。

[This work](https://github.com/microsoft/TypeScript/pull/63046) 被贡献感谢 [Kenta Moriuchi](https://github.com/petamoriken)。

`dom` lib 现在包含 `dom.iterable` 和 `dom.asynciterable`
--------------------------------------------------------------

TypeScript 的 `lib` 选项允许您指定目标运行时具有哪些全局声明。 一种选择是 `dom` 表示 Web 环境（即浏览器，实现 [the DOM APIs](https://developer.mozilla.org/en-US/docs/Web/API/Document_Object_Model)）。 以前，对于不支持 `Iterable`s 和 `AsyncIterable`s 的环境，DOM API 被部分拆分为 `dom.iterable` 和 `dom.asynciterable`。 这意味着您必须明确添加 `dom.iterable` 才能在 `NodeList` 或 `HTMLCollection` 等 DOM 集合上使用迭代方法。

在 TypeScript 6.0 中，`lib.dom.iterable.d.ts` 和 `lib.dom.asynciterable.d.ts` 的内容完全包含在 `lib.dom.d.ts` 中。 您仍然可以在配置文件的 `"lib"` 数组中引用 `dom.iterable` 和 `dom.asynciterable`，但它们现在只是空文件。

// 在 TypeScript 6.0 之前，这个必需的 "lib": ["dom", "dom.iterable"]
// 现在它只适用于 "lib": ["dom"]
for (const 元素的 document.QuerySelectorAll("div")) {
console.log(element.textContent);
}
    

这是生活质量的改进，消除了常见的混淆点，因为没有主要的现代浏览器缺乏这些功能。 如果您已经同时包含 `dom` 和 `dom.iterable`，您现在可以简化为 `dom`。

查看更多 [at this issue](https://github.com/microsoft/TypeScript/issues/60959) 及其 [corresponding pull request](https://github.com/microsoft/TypeScript/pull/62111)。

TypeScript 6.0 中的更改和弃用
-----------------------------------------------

TypeScript 6.0 是一个重要的过渡版本，旨在为开发人员准备 TypeScript 7.0，TypeScript 编译器即将推出的本机端口。 虽然 TypeScript 6.0 与您现有的 TypeScript 知识保持完全兼容性，并且继续与 TypeScript 5.9 兼容 API，但此版本引入了许多反映不断演变的 JavaScript 生态系统并为 TypeScript 7.0 设置阶段的重大更改和弃用。

在 TypeScript 5.0 之后的两年里，我们看到开发人员编写和发布 JavaScript 的方式不断发生变化：

*   几乎每个运行时环境现在都是“常绿”。 真正的传统环境 (ES5) 非常罕见。
*   Bundlers 和 ESM 已成为新项目最常见的模块目标，尽管 CommonJS 仍然是一个主要目标。 AMD 和其他浏览器用户区模块系统比 2012 年少得多。
*   几乎所有的包都可以通过某个模块系统使用。 UMD 包仍然存在，但实际上没有新代码作为全局变量_only_ 可用。
*   `tsconfig.json` 作为一种配置机制几乎是通用的。
*   对“更严格”打字的食欲继续增长。
*   TypeScript 构建性能是首要考虑因素。 尽管 TypeScript 7 取得了进展，但性能必须始终是一个关键目标，并且无法以高性能的方式支持的选项需要更有力地证明是合理的。

因此，TypeScript 6.0 和 7.0 的设计考虑到了这些现实。 对于 TypeScript 6.0，可以通过在 tsconfig 中设置 `"ignoreDeprecations": "6.0"` 来忽略这些弃用； 但是，请注意，TypeScript 7.0 _will 不支持任何这些已弃用的选项。

可以使用 CodeMod 或工具自动执行一些必要的调整。 例如，[实验 `ts5to6` 工具](https://github.com/andrewbranch/ts5to6) 可以在您的代码库中自动调整 `baseUrl` 和 `rootDir`。

### 前期调整

我们将在下面介绍具体的调整，但我们必须注意，一些弃用和行为更改不一定有直接指向潜在问题的错误消息。 因此，我们将提前注意到 **许多项目至少需要执行以下一项操作**：

*   将 TSConfig 中的 `"types"` 数组设置为 `"types": ["node"]`。
    
`"types": ["*"]` 将恢复 5.9 的行为，但我们建议使用显式数组来提高构建性能和可预测性。
    
如果您看到与缺少标识符或未解析的内置模块相关的类型错误，您通常会知道这是问题。
    
*   设置 `"rootDir": "./src"` 如果您之前依赖于此推断
    
如果您看到文件正在写入 `./dist/src/index.js` 而不是 `./dist/index.js`，您通常会知道这是问题所在。
    

### 简单的默认更改

几个编译器选项现在更新了默认值，以更好地反映现代开发实践。

*   **`strict` 默认为 `true` 默认**：对更严格的打字的需求继续增长，我们发现大多数新项目都希望启用 `strict` 模式。 如果您已经在使用 `"strict": true`，则没有任何改变。 如果您依赖于 `false` 的先前默认值，则需要在 `tsconfig.json` 中显式设置 `"strict": false`。
    
*   **`module` 默认为 `esnext`**：同样，新的默认值 `module` 是 `esnext`，承认 ESM 现在是主要的模块格式。
    
*   **`target` 默认为当前年份 ES 版本**：新默认 `target` 是最新支持的 ECMAScript 规范版本（实际上是浮动目标）。 现在，这个目标是`es2025`。 这反映了大多数开发人员正在向 Evergreen 运行时提供的现实，并且不需要将其转换为较旧的 ECMAScript 版本。
    
*   **`noUncheckedSideEffectImports` 默认为 `true` 默认**：这有助于捕获仅副作用导入中的错别字的问题。
    
*   **`libReplacement` 默认是 `false` 现在是 `false`**：此标志以前每次运行都会产生大量失败的模块解析，这反过来又增加了我们在 `--watch` 和编辑器场景下需要观察的位置数量。 在一个新项目中，`libReplacement`在其他显式配置发生之前永远不会做任何事情，因此默认情况下为了更好的性能而默认关闭它是有意义的。
    

如果这些新默认值破坏了您的项目，您可以在 `tsconfig.json` 中明确指定先前的值。

### `rootDir` 默认为 `.`

`rootDir` 控制输出文件相对于输出目录的目录结构。 以前，如果您没有指定 `rootDir`，则根据所有非声明输入文件的公共目录推断它。 但这通常意味着不可能知道一个文件是否属于一个项目而不尝试加载和解析该项目。 这也意味着 TypeScript 必须花费更多时间通过分析程序中的每个文件路径来推断该公共源目录。

在 TypeScript 6.0 中，默认的 `rootDir` 将始终是包含 `tsconfig.json` 文件的目录。 `rootDir` 仅在没有 `tsconfig.json` 文件的命令行使用 `tsc` 时才会推断。

如果您的源文件比您的 `tsconfig.json` 目录更深，并且依赖于 TypeScript 来推断源文件的公共根目录，则需要显式设置 `rootDir`：

{
“编译器选项”：{
// ...
    +         "rootdir":"./src"
},
“包含”：[]./src"]
}
    

同样，如果您的 `tsconfig.json` 引用的文件包含在 `tsconfig.json` 之外，则需要调整 `rootDir` 以包含这些文件。

{
“编译器选项”：{
// ...
    +         "rootdir":"../src"
},
“包含”：[../src/**/*.tests.ts"]
}
    

在 [the discussion here](https://github.com/microsoft/TypeScript/issues/62194) 和 [the implementation here](https://github.com/microsoft/TypeScript/pull/62418) 处查看更多信息。

### `types` 默认为 `[]`

在 `tsconfig.json` 中，`compilerOptions` 的 `types` 字段指定了编译期间要包含在全局范围内的包名称列表。 通常，`node_modules` 中的软件包会通过导入自动包含在源代码中； 但为了方便起见，TypeScript 还会默认包含 `node_modules/@types` 中的所有包，这样您就可以从 `@types/node` 或 `"fs"` 模块中获取全局声明，或者 `describe` 和 `it` 来自 `@types/jest`，而无需直接导入它们。

从某种意义上说，`types` 值以前默认为“枚举 `node_modules/@types` 中的所有内容”。 这可能会非常昂贵，因为现在的正常存储库设置可能会传递数百个 `@types` 包，尤其是在具有扁平化 `node_modules` 的多项目工作空间中。 现代项目几乎总是只需要 `@types/node`、`@types/jest` 或少数其他常见的全球影响包。

在 TypeScript 6.0 中，默认的 `types` 值为 `[]`（空数组）。 此更改可防止项目在构建时无意中提取数百甚至数千个不需要的声明文件。 我们看过的许多项目都通过适当地设置 `types` 将它们的构建时间从 20% 提高到 50%。

**这会影响许多项目。** 您可能需要添加 `"types": ["node"]` 或其他一些：

{
“编译器选项”：{
// 明确列出你需要的 @types 包
    +         "类型": ["节点", "开玩笑"]
}
}
    

您还可以指定 `*` 条目以重新启用旧的枚举行为：

{
“编译器选项”：{
// 加载所有类型 - 来自 TypeScript 5.9 和之前的默认值。
    +         "类型": ["*"]
}
}
    

如果您最终收到如下新的错误消息：

找不到模块“...”或其相应的类型声明。
找不到名称“fs”。 是否需要为节点安装类型定义？ 尝试 `npm i --save-dev @types/node`，然后将“节点”添加到 tsconfig 中的类型字段。
找不到名称“路径”。 是否需要为节点安装类型定义？ 尝试 `npm i --save-dev @types/node`，然后将“节点”添加到 tsconfig 中的类型字段。
找不到名称“进程”。 是否需要为节点安装类型定义？ 尝试 `npm i --save-dev @types/node`，然后将“节点”添加到 tsconfig 中的类型字段。
找不到名称“bun”。 是否需要为bun安装类型定义？ 尝试 `npm i --save-dev @types/bun`，然后将“bun”添加到 tsconfig 中的类型字段。
找不到名称“描述”。 是否需要为测试运行程序安装类型定义？ 尝试 `npm i --save-dev @types/jest` 或 `npm i --save-dev @types/mocha`，然后将 'jest' 或 'mocha' 添加到您的 tsconfig 的类型字段。
    

您可能需要向 `types` 字段添加一些条目。

在 [the proposal here](https://github.com/microsoft/TypeScript/issues/62195) 和 [the implementing pull request here](https://github.com/microsoft/TypeScript/pull/63054) 中查看更多信息。

### 已弃用：`target: es5`

长期以来，ECMAScript 5 目标对于支持传统浏览器很重要； 但其继任者 ECMAScript 2015 (ES6) 是十多年前发布的，所有现代浏览器都支持它多年。 随着 Internet Explorer 的退休以及 Evergreen 浏览器的普遍性，今天 ES5 输出的用例很少。

TypeScript 的最低目标现在将是 ES2015，并且 `target: es5` 选项已弃用。 如果您使用 `target: es5`，则需要迁移到较新的目标或使用外部编译器。 如果您仍然需要 ES5 输出，我们建议使用外部编译器直接编译您的 TypeScript 源，或对 TypeScript 的输出进行后处理。

[See more about this deprecation here](https://github.com/microsoft/TypeScript/issues/62196) 连同 [its implementing pull request](https://github.com/microsoft/TypeScript/pull/63067)。

### 已弃用：`--downlevelIteration`

`--downlevelIteration` 仅对 ES5 发射产生影响，并且由于 `--target es5` 已被弃用，`--downlevelIteration` 不再起作用。

巧妙地，在 TypeScript 5.9 和更早版本中使用 `--downlevelIteration false` 和 `--target es2015` 没有错误，即使它没有效果。 在 TypeScript 6.0 中，设置 `--downlevelIteration` 将导致弃用错误。

见[the implementation here](https://github.com/microsoft/TypeScript/pull/63071)。

### 不推荐：`--moduleResolution node`（又名`--moduleResolution node10`）

`--moduleResolution node`编码了一个特定版本的Node.js模块解析算法，最准确地反映了Node.js 10的行为。不幸的是，这个目标（及其名称）忽略了对Node.js的解析算法的许多更新，而不再是 现代 Node.js 版本行为的良好表现。

在 Typescript 6.0 中，`--moduleResolution node`（特别是 `--moduleResolution node10`）被弃用。 使用 `--moduleResolution node` 的用户通常应迁移到 `--moduleResolution nodenext`，如果他们计划直接定位 Node.js，或者如果他们计划使用 Bundler 或 BUN，则应迁移到 `--moduleResolution nodenext`。

查看更多 [at this issue](https://github.com/microsoft/TypeScript/issues/62200) 和 [its corresponding pull request](https://github.com/microsoft/TypeScript/pull/62338)。

### 已弃用：`amd`、`umd`和`systemjs`的`module`值

不再支持以下标志值

*   `--module amd`
*   `--module umd`
*   `--module systemjs`
*   `--module none`

在 JavaScript 模块的早期，当浏览器缺乏本机模块支持时，AMD、UMD 和 SystemJS 很重要。 “无”的语义从来没有明确定义，经常导致混乱。 如今，ESM 在浏览器和 Node.js 中得到普遍支持，导入地图和捆绑器都已成为填补空白的首选方式。 如果您仍在针对这些模块系统，请考虑迁移到适当的 ECMAScript 模块发射目标、采用捆绑器或不同的编译器，或停留在 TypeScript 5.x 上，直到您可以迁移。

这也意味着对 `amd-module` 指令的放弃支持将不再产生任何影响。

在 [the proposal issue](https://github.com/microsoft/TypeScript/issues/62199) 和 [the implementing pull request](https://github.com/microsoft/TypeScript/pull/62669) 中查看更多信息。

### 已弃用：`--baseUrl`

`baseUrl` 选项最常与 `paths` 结合使用，通常用作 `paths` 中每个值的前缀。 不幸的是，`baseUrl` 也被认为是模块分辨率的查找根。

例如，给定以下 `tsconfig.json`

{
“编译器选项”：{
// ...
“baseurl”：“./src”，
“路径”：{
"@app/*": ["app/*"],
"@lib/*": ["lib/*"]
}
}
}
    

和一个导入

import * 作为“somemodule.js”中的somemodule；
    

TypeScript 可能会将此解决为 `src/someModule.js`，即使开发人员仅打算为以 `@app/` 和 `@lib/` 开头的模块添加映射。

在最好的情况下，这也经常导致捆绑者会忽略的“看起来更差的”路径； 但这通常意味着许多在运行时永远不会工作的导入路径被 TypeScript 认为“很好”。

`path` 映射很长一段时间都不需要指定 `baseUrl`，实际上，大多数使用 `baseUrl` 的项目仅将其用作 `paths` 条目的前缀。 在 TypeScript 6.0 中，`baseUrl` 已弃用，将不再被视为模块分辨率的查找根。

使用 `baseUrl` 作为路径映射条目的前缀的开发人员可以简单地删除 `baseUrl` 并将前缀添加到他们的 `paths` 条目中：

{
“编译器选项”：{
// ...
    -     "BASEURL":"./src",
“路径”：{
    -       "@app/*": ["App/*"],
    -       "@lib/*": ["lib/*"]
    +       "@app/*": ["./src/app/*"],
    +       "@lib/*":[]./src/lib/*"]
}
}
}
    

实际上 _did_ 将 `baseUrl` 用作查找根的开发人员还可以添加显式路径映射以保留旧行为：

{
“编译器选项”：{
// ...
“路径”：{
// 替换 baseUrl 的新 catch-all：
"*": ["./src/*"],
    
// 现在所有其他路径都有一个明确的公共前缀：
"@app/*": [./src/app/*"],
"@lib/*": ["./src/lib/*"],
}
}
}
    

然而，这是极为罕见的。 我们建议大多数开发人员只需删除 `baseUrl` 并将适当的前缀添加到他们的 `paths` 条目中。

查看更多 [at this issue](https://github.com/microsoft/TypeScript/issues/62207) 和 [the corresponding pull request](https://github.com/microsoft/TypeScript/pull/62509)。

### 已弃用：`--moduleResolution classic`

`moduleResolution: classic` 设置已被移除。 `classic` 分辨率策略是 TypeScript 的原始模块解析算法，早于 Node.js 的分辨率算法成为事实上的标准。 今天，所有实际用例都由 `nodenext` 或 `bundler` 提供服务。 如果您正在使用 `classic`，请迁移到这些现代解决策略之一。

在 [this issue](https://github.com/microsoft/TypeScript/issues/62206) 和 [the implementing pull request](https://github.com/microsoft/TypeScript/pull/62669) 处查看更多信息。

### 不推荐：`--esModuleInterop false`和`--allowSyntheticDefaultImports false`

以下设置不能再设置为 `false`：

*   `esModuleInterop`
*   `allowSyntheticDefaultImports`

`esModuleInterop` 和 `allowSyntheticDefaultImports` 最初是选择加入以避免破坏现有项目。 但是，它们启用的行为多年来一直是推荐的默认设置。 将它们设置为 `false` 通常会在使用 ESM 的 CommonJS 模块时导致微妙的运行时问题。 在 TypeScript 6.0 中，始终启用更安全的互操作行为。

如果您有依赖旧行为的导入，您可能需要调整它们：

// before (with esModuleInterop: false)
导入 * 作为“express”中的表达式；
    
// after (ESModuleInterop 始终启用)
从“Express”导入快递；
    

在 [this issue](https://github.com/microsoft/TypeScript/issues/62529) 和 [its implementing pull request](https://github.com/microsoft/TypeScript/pull/62567) 处查看更多信息。

### 已弃用：`--alwaysStrict false`

`alwaysStrict` 标志是指 `"use strict";` 指令的推理和发射。 在 TypeScript 6.0 中，所有代码都将假定为 [JavaScript strict mode](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Strict_mode)，这是一组 JS 语义，最明显地影响保留字周围的句法角案例。 如果您有使用 `await`、`static`、`private` 或 `public` 等保留字作为常规标识符的“草率模式”代码，则需要重命名它们。 如果您在非严格代码中依赖于 `this` 含义的微妙语义，您可能还需要调整代码。

查看更多 [at this issue](https://github.com/microsoft/TypeScript/issues/62213) 和 [its corresponding pull request](https://github.com/microsoft/TypeScript/pull/63089)。

### 已弃用：`outFile`

`--outFile` 选项已从 TypeScript 6.0 中删除。 此选项最初旨在将多个输入文件连接到单个输出文件中。 但是，Webpack、Rollup、Esbuild、Vite、Parcel 等外部捆绑程序现在可以更快、更好、更具可配置性地完成这项工作。 删除此选项简化了实现，并允许我们专注于 TypeScript 最擅长的内容：类型检查和声明发出。 如果您当前使用 `--outFile`，则需要迁移到外部捆绑器。 大多数现代捆绑器都提供了开箱即用的出色的 TypeScript 支持。

### 不推荐使用：命名空间的传统 `module` 语法

早期版本的 TypeScript 使用 `module` 关键字来声明命名空间：

// ❌ 已弃用的语法 - 现在是一个错误
模块 foo {
导出常量条 = 10；
}
    

此语法后来使用 `namespace` 关键字被别名为现代首选形式：

// ✅ 正确的语法
命名空间 foo {
导出常量条 = 10；
}
    

当引入 `namespace` 时，`module` 语法被简单地禁止了。 几年前，TypeScript 语言服务开始将关键字标记为已弃用，建议 `namespace` 取而代之。

在 TypeScript 6.0 中，使用 `module` 的 `namespace` 是一个硬的弃用。 此更改是必要的，因为 `module` 块是可能与传统 TypeScript 语法冲突的 ECMAScript 提议。

环境模块声明表仍然完全受支持：

// ✅ 仍然完美运行
声明模块“some-module”{
导出函数 doSomething(): void;
}
    

有关详细信息，请参阅 [this issue](https://github.com/microsoft/TypeScript/issues/62211) 及其 [corresponding pull request](https://github.com/microsoft/TypeScript/pull/62876)。

### 已弃用：`asserts` 导入关键字

`asserts` 关键字是通过导入断言提案向 JavaScript 语言提出的； 然而，提案最终变成了 [the import attributes proposal](https://github.com/tc39/proposal-import-attributes)，它使用 `with` 关键字而不是 `asserts`。

因此，`asserts` 语法现在在 TypeScript 6.0 中被弃用，使用它将导致错误：

// ❌ 已弃用的语法 - 现在是一个错误。
从“./blahb.json”导入 blob 断言 { type: "json" }
// ~~~~~~~
// 错误：导入断言已被导入属性替换。 使用 'with' 代替 'asserts'。
    

相反，使用 `with` 语法对导入属性：

// ✅ 使用新的导入属性语法。
使用 { type: "json" } 从 "./blahb.json" 导入 blob
    

在 [this issue](https://github.com/microsoft/TypeScript/issues/62210) 及其 [corresponding pull request](https://github.com/microsoft/TypeScript/pull/63077) 处查看更多信息。

### 已弃用：`no-default-lib` 指令

`/// <reference no-default-lib="true"/>` 指令在很大程度上被误解和误用。 在 TypeScript 6.0 中，不再支持此指令。 如果您正在使用它，请考虑使用 `--noLib` 或 `--libReplacement`。

[See more here](https://github.com/microsoft/TypeScript/issues/62209) 和 [the corresponding pull request](https://github.com/microsoft/TypeScript/pull/62435)。

### 当 `tsconfig.json` 存在时指定命令行文件现在是一个错误

当前，如果您在 `tsconfig.json` 存在的文件夹中运行 `tsc foo.ts`，则将完全忽略配置文件。 如果您希望检查和发出应用于输入文件的选项，这通常会非常混乱。

在 TypeScript 6.0 中，如果您在包含 `tsconfig.json` 的目录中运行带有 file 参数的 `tsc`，将发出错误以使此行为显式：

错误 TS5112：Tsconfig.json 存在，但如果在命令行上指定了文件，将不会加载。 使用 '--ignoreconfig' 跳过此错误。
    

如果您想忽略 `tsconfig.json` 并使用 TypeScript 的默认值编译 `foo.ts`，则可以使用新的 `--ignoreConfig` 标志。

tsc --ignoreconfig foo.ts
    

查看更多 [at this issue](https://github.com/microsoft/TypeScript/issues/62197) 及其 [corresponding pull request](https://github.com/microsoft/TypeScript/pull/62477)。

准备打字稿 7.0
-----------------------------

TypeScript 6.0 设计为过渡版本。 虽然在 TypeScript 6.0 中弃用的选项将在设置 `"ignoreDeprecations": "6.0"` 时继续正常工作，但这些选项将在 TypeScript 7.0**（本机 TypeScript 端口）中完全删除。 如果您在升级到 TypeScript 6.0 后看到弃用警告，我们强烈建议您在项目中采用 TypeScript 7.0（或尝试 [native previews](https://www.npmjs.com/package/@typescript/native-preview)）之前解决它们。

下一步是什么？
-------------

既然 TypeScript 6.0 在 NPM 上可用，该团队将专注于将 TypeScript 7.0 稳定化。 这比听起来更接近：我们预计在几个月内发布，我们已经在微软内部和外部看到了极大的代码库的广泛采用。 因此，我们鼓励团队与 [VS Code extension too](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview) 一起尝试每晚构建 TypeScript 7.0 的 [native previews on npm](https://www.npmjs.com/package/@typescript/native-preview)。 对 TypeScript 7.0 的反馈将有很长的路要走，您可以提出问题 [on our issue tracker](https://github.com/microsoft/typescript-go/issues)。

尽管如此，TypeScript 6.0 是您今天应该能够采用的稳定版本，它包含了许多可以立即开始使用的改进和新功能。 我们希望这个版本对每个人来说都是一个顺利的过渡，我们期待听到你的经历。

快乐黑客！

– Daniel Rosenwasser 和 TypeScript 团队
