今年早些时候，[the TypeScript team announced that we’ve been porting the compiler and language service to native code](https://devblogs.microsoft.com/typescript/typescript-native-port/) 利用了更好的原始性能、内存使用和并行性。 这项工作（代号为“Project Corsa”和很快的“TypeScript 7.0”）是一项重大任务，但我们在过去几个月中取得了长足的进步。 我们很高兴提供一些关于我们所处位置的更新，并向您展示新的 TypeScript 工具集是多么“真实”。

我们还获得了有关即将推出的路线图的新闻，以及我们如何优先考虑 TypeScript 7.0 的工作以推动我们的端口完成。

编辑支持和语言服务
---------------------------------

对于很多开发人员来说，在最终发布之前，项目重写可能完全是理论上的。 这不是这里的情况。

**TypeScript 的原生预览现在快速、稳定且易于使用——包括在编辑器中**。

TypeScript 的语言服务（为编辑器的 TypeScript 和 JavaScript 功能提供支持的东西）也是本机端口工作的核心部分，并且易于尝试。 您可以从 [Visual Studio Code Marketplace](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview) 中获取每天更新的最新版本。

我们的团队仍在移植功能并修复小错误，但真正使现有 Typescript 编辑体验的大部分内容都在那里并且运作良好。

其中包括：

*   代码完成（_包括自动导入！_）
*   进入定义
*   进入类型定义
*   去实现
*   查找所有引用
*   重命名
*   快速信息/悬停工具提示
*   签名帮助
*   格式化
*   选择范围
*   编码镜头
*   呼叫层次结构
*   文档符号
*   缺少导入的快速修复

您可能会注意到自我们上次重大更新以来最突出的一些事项——自动导入、查找所有引用、重命名等。 我们知道，这些功能是许多开发人员无法尝试本机预览的缺失部分。 我们很高兴地说，这些现在已经重新实现并准备好进行日常使用！ 这些操作现在适用于任何 TypeScript 或 JavaScript 代码库——包括那些具有项目引用的代码。

我们还重新构建了语言服务的一部分，以提高可靠性，同时利用共享内存并行性。 虽然一些团队报告说最初的体验有时有点“崩溃”，但由于速度的提高，他们经常忍受它。 新架构更健壮，应该能够处理大大小小的代码库，而不会出现任何问题。

虽然肯定还有更多的移植和打磨，但您的团队可能会发现尝试 Typescript 的本机预览是值得的。 您可以期待更快的加载时间、更少的内存使用以及整体更快速/响应的编辑器。

如果您对体验不满意，我们的扩展程序可以轻松地在 VS Code 的内置 TypeScript 体验和新的体验之间切换。 我们真的鼓励您和您的团队 [try out the native preview extension for VS Code today](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview)！

编辑
---------

TypeScript 编译器在本机端口上也取得了重大进展。 就像我们的 VS Code 扩展一样，[we have been publishing nightly preview builds of the new compiler](https://www.npmjs.com/package/@typescript/native-preview) 在包名 `@typescript/native-preview` 下。 您可以通过 npm 进行安装，如下所示：

    # 本地开发依赖
npm install -d @typescript/native-preview
    
    # 全球安装
npm install -g @typescript/native-preview
    

此软件包提供了一个 `tsgo` 命令，其工作方式与现有的 `tsc` 命令类似。 两者可以并排运行。

我们经常遇到的一个问题是使用 TypeScript 7 来验证构建是否“安全”。 换句话说，它是否可靠地找到了与 TypeScript 5.9 相同的错误？

答案是响亮的是。 TypeScript 7 的类型检查几乎完成了。 对于上下文，我们有大约 20,000 个编译器测试用例，其中大约 6,000 个在 TypeScript 6.0 中产生至少一个错误。 除 74 种情况外，TypeScript 7 还至少产生一个错误。 在剩下的 74 个案例中，所有都是已知的不完整工作（例如正则表达式语法检查或 `isolatedDeclarations` 错误）或与已知的故意更改（弃用、默认设置更改等）有关。 您现在可以自信地使用 TypeScript 7 对项目进行类型检查，以了解错误。

除了单程/单项目类型检查之外，命令行编译器也达到了主要的平价。 `--incremental`、项目参考支持和 `--build` 模式等功能现在也全部移植并工作！ 这意味着大多数项目现在可以尝试进行最小更改的本机预览。

    # 在 --build 模式下运行 TSC ...
tsc -b some.tsconfig.json --extendedDiagnostics
    
    # 在 --build 模式下运行 *new 编译器*...
tsgo -b some.tsconfig.json --extendedDiagnostics
    

这些功能不仅现在可用，而且它们应该比 TypeScript 5.9 及更早版本中实现的现有版本（也称为“Strada 代码库”）更快。 [As we’ve described previously](https://devblogs.microsoft.com/typescript/typescript-native-port/)，这部分来自本机代码性能，也来自使用共享内存并行性。 更具体地说，这意味着 TypeScript 现在不仅可以在单个项目上进行快速的多线程构建； 它现在也可以并行构建多个项目！ 结合我们对 `--incremental` 的重新实现，我们接近于让 TypeScript 构建感觉瞬间发生在大型项目中的较小变化中。

提醒一下，即使没有 `--incremental`，TypeScript 7 也经常看到在完整版本中的 6.0 编译器上接近 10 倍的加速！

与打字稿 5.9 的预期差异
---------------------------------------

使用我们要调用的新编译器有一些注意事项。 其中许多是我们计划在最终 7.0 版本之前解决的时间点问题，但有些问题更多地受到长期决策的推动，以使默认的 Typescript 体验更好。 TypeScript 7.0 的承诺意味着我们需要将重点转移到新的代码库上，以缩小现有的差距，并将新的工具链交到更多的开发人员手中。 但是，让我们首先深入了解当前的一些变化和限制。

### 弃用兼容性

TypeScript 7.0 将删除我们计划在 TypeScript 6.0 中弃用的行为和标志。 现在，你可以看到[the list of upcoming deprecations in 6.0 on our issue tracker](https://github.com/microsoft/TypeScript/issues?q=milestone%3A%22TypeScript%206.0.0%22%20label%3A%22Breaking%20Change%22)。 一些突出的例子包括：

*   [`--strict` 将默认启用](https://github.com/microsoft/TypeScript/issues/62333)
*   [`--target` 将默认为最新的稳定 ECMAScript 目标（例如 `es2025`)](https://github.com/microsoft/TypeScript/issues/62198)
*   [`--target es5` 将被移除，`es2015` 是支持最低的目标](https://github.com/microsoft/TypeScript/issues/62196)
*   [`--baseUrl`将被移除](https://github.com/microsoft/TypeScript/issues/62207)
*   [`--moduleResolution node10`（又名 `node`）将被移除，支持 `bundler` 和 `nodenext`](https://github.com/microsoft/TypeScript/issues/62200)
*   [`rootDir` 默认为当前目录，使用 `outDir` 需要明确的 `rootDir` 或顶级源文件与 `tsconfig.json`](https://github.com/microsoft/TypeScript/issues/62194) 位于同一目录中

这并不全面，所以[check out the issue tracker](https://github.com/microsoft/TypeScript/issues?q=milestone%3A%22TypeScript%206.0.0%22%20label%3A%22Breaking%20Change%22)对于当前的状态。 如果您的项目依赖于任何这些弃用的行为，您可能需要对代码库或 `tsconfig.json` 进行一些更改以确保与 TypeScript 7.0 的兼容性。

我们的团队[一直在尝试一种名为`ts5to6`的工具来帮助自动更新您的`tsconfig.json`](https://github.com/andrewbranch/ts5to6)。 该工具使用 `extends` 和 `references` 上的启发式方法来帮助更新代码库中的其他项目。 目前它只能更新 `baseUrl` 和 `rootDir` 设置，但将来可能会添加更多设置。

npx @andrewbranch/ts5to6 --fixbaseurl your-tsconfig-file-here.json
npx @andrewbranch/ts5to6 --fixrootdir your-tsconfig-file-here.json
    

### 发射、`--watch`和API

即使有 6.0 准备，在某些情况下，新编译器也无法立即交换。

一方面，JavaScript emit 管道并不完全完整。 如果您_Dont_需要从TypeScript发出的JavaScript（例如，如果您使用babel、esbuild或其他东西），或者如果您针对的是现代浏览器/运行时，那么为您的构建运行`tsgo`就可以正常工作。 但是，如果您依靠 TypeScript 来定位较旧的运行时，我们对下级编译的支持实际上只能追溯到 `es2021` 目标，并且不支持编译装饰器。 我们计划在完全 `--target` 支持回到 `es2015` 的情况下解决这个问题，但这项工作仍在进行中。

另一个问题是我们的新 `--watch` 模式在某些情况下可能比现有的 TypeScript 编译器效率低。 在某些情况下，您可以找到其他解决方案，例如使用 `--incremental` 标志运行 [nodemon](https://www.npmjs.com/package/nodemon) 和 `tsgo`。

最后，Corsa/TypeScript 7.0 将不支持现有的 Strada API。 Corsa API 仍在进行中，没有稳定的工具集成。 这意味着任何依赖 Strada API 的工具（例如 linter、格式化程序或 IDE 扩展）都不适用于 Corsa。

其中一些问题的解决方法可能是并排安装 `typescript` 和 `@typescript/native-preview` 包，并使用 ≤6.0 API 进行需要它的工具，以及 `tsgo` 进行类型检查。

### JavaScript 检查和 JSDOC 兼容性

我们要呼吁的另一件事是，我们的 JavaScript 类型检查支持（部分由 JSDOC 注释提供支持）已从头开始重写。 为了简化我们的内部结构，我们剥夺了对我们之前认识和分析的复杂和一些使用较少的模式的一些支持。 例如，TypeScript 7.0 无法识别 `@enum` 和 `@constructor` 标签。 我们还在 JavaScript 中删除了一些“放松”的类型检查规则，例如解释：

*   `Object` 作为 `any`，
*   `String` 作为 `string`，
*   `Foo` 作为 `typeof Foo` 在 TypeScript 文件中有效时，
*   所有 `any`、`unknown` 和 `undefined`\ 类型参数可选

还有更多。 其中一些是 [reviewed and documented here](https://github.com/microsoft/typescript-go/pull/1426)，但列表可能需要更新。

这意味着一些 JavaScript 代码库可能会看到比以前更多的错误，并且可能需要更新以与新编译器配合使用。 另一方面，我们相信新的实现更加健壮和可维护，并将 TypeScript 的 JSDOC 支持与其自己的类型语法对齐。

如果您觉得我们的 JavaScript 类型检查支持中有什么工作或缺少某些东西，我们鼓励您 [file an issue on our GitHub repository](https://github.com/microsoft/typescript-go)。

聚焦未来
-----------------------

当我们去年开始重写 TypeScript 时，存在很多不确定性。 社区会兴奋吗？ 代码库需要多长时间才能稳定下来？ 团队可以多快采用这个新工具集？ 我们能够提供多大程度的兼容性？

在各个方面，我们都非常惊喜。 我们已经能够实现具有极高兼容性的类型检查器。 因此，Microsoft 内部和外部的项目报告说，他们能够轻松地轻松使用本机编译器。 稳定性进展顺利，到年底我们有望完成大多数语言服务功能。 许多团队已经在没有任何阻塞问题的情况下使用 Corsa 进行日常工作。

随着 6.0 的临近，我们必须考虑 JavaScript 代码库中接下来会发生什么。 我们最初的计划是继续在 6.0 行中“直到 TypeScript 7+ 达到足够的成熟度和采用率”。 我们知道，解锁更多开发人员（例如，在 API 表面上进行更多工作）仍有工作要做，并且在 Strada 行上关闭开发——我们基于 JavaScript 的编译器——是我们尽快删除这些阻止程序的最佳方式。 为了帮助我们尽快完成这些工作，我们将在 Strada 项目中采取一些步骤。

### TypeScript 6.0 是最后一个基于 JavaScript 的版本

TypeScript 6.0 将是我们基于现有 TypeScript/JavaScript 代码库的最后版本。 换句话说，我们不打算发布 TypeScript 6.1，尽管在更罕见的情况下我们可能有补丁版本（例如 6.0.1、6.0.2）。

您可以将 TypeScript 6.0 视为 TypeScript 5.9 行和 7.0 之间的“桥梁”版本。 6.0 将弃用与 7.0 对齐的功能，并且在类型检查行为方面具有高度兼容性。

大多数需要编辑器端 Strada 特定功能的代码库（例如语言服务插件）应该能够使用 6.0 进行编辑器功能，而 7.0 用于快速命令行构建没有太多麻烦。 反之亦然：开发人员可以使用 7.0 在他们的编辑器中获得更快的体验，以及依赖于 TypeScript 6.0 API 的命令行工具的 6.0。

TypeScript 6.0 发布后的附加服务将以补丁版本的形式发布，并且仅在以下情况下发布：

*   安全问题，
*   高严重性回归（即5.9中没有的新的和严重的错误），
*   与 6.0/7.0 兼容性相关的高严重性修复。

与以前的版本一样，补丁版本很少，并且仅在绝对必要时才发布。

但就目前而言，我们希望确保 TypeScript 6.0 和 7.0 尽可能兼容。 我们将持有一个非常高的标准，其中开放式 PR 并入 6.0 线。 这在今天生效，这意味着大多数开发人员将不得不为将在 TypeScript 6.0 中解决哪些问题设定预期。 此外，贡献者应该明白，我们不太可能将拉取请求合并到 6.0 中，我们的大部分重点都将 7.0 带入奇偶校验和稳定性。 我们希望在这方面保持透明，这样就不会有“浪费”的工作，这样我们的团队就可以避免两个代码库之间移植更改的复杂性。

### 重置语言服务问题

虽然大多数核心类型检查代码都被移植到没有任何行为差异的情况下，但语言服务却是另一回事。 鉴于新的架构，为完成、悬停工具提示、导航等提供支持的大部分代码已被大量重写。 此外，TypeScript 7.0 使用标准 LSP 协议而不是自定义 TSServer 协议，因此某些特定于 TypeScript VS Code 扩展的行为可能已更改。

因此，任何特定于语言服务行为的错误或建议都可能不会在 7.0 行中重现，也不会在对话中进行“重置”。

手动验证这些问题非常耗时，因此我们将关闭与语言服务行为相关的现有问题。 如果您在“7.0 LS 迁移”标签下遇到已关闭的问题，请在验证是否可以在本机夜间扩展中重现后，_log a new issue_。 对于尚未移植到 7.0 的功能，请等到该功能出现后再提出新问题。

下一步是什么？
-------------

几个月前，当我们 [unveiled our native previews](https://devblogs.microsoft.com/typescript/announcing-typescript-native-previews/) 时，我们必须管理对项目状态的期望。 我们现在可以自信地说本机 TypeScript 体验是真实的、稳定的，并且可以更广泛地使用。 但我们绝对仍在寻找反馈。

因此，我们鼓励您安装 [VS Code native preview extension](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview)，使用 [`@typescript/native-preview` 编译器包](https://www.npmjs.com/package/@typescript/native-preview)，并在您的项目中进行尝试。 让我们知道您的想法，并在我们的 [GitHub repository](https://github.com/microsoft/typescript-go/issues) 上归档问题，以帮助我们解决任何问题并确定下一步要做的事情的优先级。

我们对 TypeScript 的未来感到兴奋，我们迫不及待地想让 TypeScript 7.0 掌握在您手中！
