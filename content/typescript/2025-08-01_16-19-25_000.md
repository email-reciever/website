今天我们很高兴地宣布 TypeScript 5.9 的发布！

如果您不熟悉 TypeScript，它是一种通过为类型添加语法的 JavaScript 构建的语言。 对于类型，TypeScript 可以检查您的代码以提前避免错误。 TypeScript 类型检查器可以完成所有这些工作，也是编辑器和其他地方的出色工具的基础，使编码变得更加容易。 如果您已经在 Visual Studio 和 VS Code 等编辑器中编写了 JavaScript，那么 TypeScript 甚至可以为您可能已经使用的功能提供支持，例如完成、转到定义等。 你可以 [learn more about TypeScript at our website](https://typescriptlang.org/)。

但是，如果您已经熟悉了，您可以立即开始使用 TypeScript 5.9！

```sh
npm install -D typescript
```

## 自Beta和RC以来有什么新的？

自从候选版本发布以来，TypeScript 5.9 没有发生任何变化。

已对报告的问题进行了一些修复[since the 5.9 beta](https://devblogs.microsoft.com/typescript/announcing-typescript-5-9-beta/)，包括将`AbortSignal.abort()`恢复到DOM库。 此外，我们添加了一个关于[Notable Behavioral Changes](#notable-behavioral-changes)的部分。

## 最小和更新 `tsc --init`

有一段时间，TypeScript 编译器支持一个 `--init` 标志，可以在当前目录中创建 `tsconfig.json`。 在过去的几年里，Running `tsc --init` 创建了一个非常“完整”的 `tsconfig.json`，充满了注释的设置及其描述。 我们设计此目的是为了使选项可发现且易于切换。

但是，鉴于外部反馈（以及我们自己的经验），我们发现立即删除这些新 `tsconfig.json` 文件的大部分内容是很常见的。 当用户想要发现新选项时，我们会发现他们依赖于从编辑器自动完成，或者导航到 [the tsconfig reference on our website](https://www.typescriptlang.org/tsconfig/)（生成的 `tsconfig.json` 链接到！）。 每个设置的功能也记录在同一页面上，可以通过编辑器悬停/工具提示/快速信息查看。 虽然浮出一些注释的设置可能会有所帮助，但生成的 `tsconfig.json` 通常被认为是矫枉过正。

我们还认为，是时候用一些比我们已经启用的更多的规定性设置进行初始化了。 我们查看了用户创建新 TypeScript 项目时的一些常见痛点和 Papercuts。 例如，大多数用户写入模块（不是全局脚本），`--moduleDetection` 可以强制 TypeScript 将每个实现文件视为一个模块。 开发人员还经常希望在运行时直接使用最新的 ECMAScript 功能，因此 `--target` 通常可以设置为 `esnext`。 JSX 用户经常会发现，回到 SET `--jsx` 是不必要的摩擦，其选项有点混乱。 通常，项目最终会从 `node_modules/@types` 中加载比 TypeScript 实际需要的更多的声明文件； 但是指定一个空的 `types` 数组可以帮助限制这一点。

在 TypeScript 5.9 中，没有其他标志的普通 `tsc --init` 将生成以下 `tsconfig.json`：

```json
{
  // Visit https://aka.ms/tsconfig to read more about this file
  "compilerOptions": {
    // File Layout
    // "rootDir": "./src",
    // "outDir": "./dist",

    // Environment Settings
    // See also https://aka.ms/tsconfig_modules
    "module": "nodenext",
    "target": "esnext",
    "types": [],
    // For nodejs:
    // "lib": ["esnext"],
    // "types": ["node"],
    // and npm install -D @types/node

    // Other Outputs
    "sourceMap": true,
    "declaration": true,
    "declarationMap": true,

    // Stricter Typechecking Options
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,

    // Style Options
    // "noImplicitReturns": true,
    // "noImplicitOverride": true,
    // "noUnusedLocals": true,
    // "noUnusedParameters": true,
    // "noFallthroughCasesInSwitch": true,
    // "noPropertyAccessFromIndexSignature": true,

    // Recommended Options
    "strict": true,
    "jsx": "react-jsx",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "moduleDetection": "force",
    "skipLibCheck": true,
  }
}
```

有关详细信息，请参阅 [implementing pull request](https://github.com/microsoft/TypeScript/pull/61813) 和 [discussion issue](https://github.com/microsoft/TypeScript/issues/58420)。

## 支持`import defer`

TypeScript 5.9 使用新的 `import defer` 语法引入了对 [ECMAScript’s deferred module evaluation proposal](https://github.com/tc39/proposal-defer-import-eval/) 的支持。 此功能允许您在不立即执行模块及其依赖关系的情况下导入模块，从而更好地控制何时发生工作和副作用。

语法仅允许命名空间导入：

```typescript
import defer * as feature from "./some-feature.js";
```

`import defer` 的主要优点是仅在首次访问其导出之一时才评估模块。 考虑这个例子：

```typescript
// ./some-feature.ts
initializationWithSideEffects();

function initializationWithSideEffects() {
  // ...
  specialConstant = 42;

  console.log("Side effects have occurred!");
}

export let specialConstant: number;
```

使用 `import defer` 时，在实际访问导入命名空间的属性之前，不会调用 `initializationWithSideEffects()` 函数：

```typescript
import defer * as feature from "./some-feature.js";

// No side effects have occurred yet

// ...

// As soon as `specialConstant` is accessed, the contents of the `feature`
// module are run and side effects have taken place.
console.log(feature.specialConstant); // 42
```

因为模块的评估被推迟到模块中的成员关闭，因此您不能将命名导入或默认导入与 `import defer` 一起使用：

```typescript
// ❌ Not allowed
import defer { doSomething } from "some-module";

// ❌ Not allowed  
import defer defaultExport from "some-module";

// ✅ Only this syntax is supported
import defer * as feature from "some-module";
```

请注意，当您写入 `import defer` 时，模块及其依赖项已完全加载并准备执行。 这意味着该模块将需要存在，并将从文件系统或网络资源中加载。 常规 `import` 和 `import defer` 之间的主要区别在于 _ 语句和声明的执行被延迟，直到您访问导入的命名空间的属性。

此功能对于有条件地加载昂贵或特定于平台的初始化的模块特别有用。 它还可以通过将模块评估推迟到实际需要的应用程序功能来提高启动性能。

请注意，`import defer` 根本没有被打字稿转换或“降级”。 它旨在用于本地支持该功能的运行时，或由可以应用适当转换的捆绑器等工具使用。 这意味着 `import defer` 只能在 `--module` 模式 `preserve` 和 `esnext` 下工作。

我们要感谢 [Nicolò Ribaudo](https://github.com/nicolo-ribaudo) 在 TC39 中支持该提案并提供 [the implementation for this feature](https://github.com/microsoft/TypeScript/pull/60757)。

## 支持`--module node20`

TypeScript 为 `--module` 和 `--moduleResolution` 设置提供了多个 `node*` 选项。 最近，`--module nodenext` 支持从 CommonJS 模块 `require()` ECMAScript 模块的能力，并正确拒绝导入断言（支持标准绑定 [import attributes](https://github.com/tc39/proposal-import-attributes)）。

TypeScript 5.9 为这些设置提供了一个稳定的选项 `node20`，旨在对 Node.js V20 的行为进行建模。 与 `--module nodenext` 或 `--moduleResolution nodenext` 不同，此选项在未来不太可能有新的行为。 与 `nodenext` 不同，指定 `--module node20` 将暗示 `--target es2023`，除非另有配置。 另一方面，`--module nodenext` 意味着浮动 `--target esnext`。

欲了解更多信息，[take a look at the implementation here](https://github.com/microsoft/TypeScript/pull/61805)。

## DOM API 中的摘要描述

以前，TypeScript 中的许多 DOM API 仅链接到 API 的 MDN 文档。 这些链接很有用，但它们没有提供 API 功能的快速摘要。 由于 [Adam Naji](https://github.com/Bashamega) 的一些更改，TypeScript 现在包含基于 MDN 文档的许多 DOM API 的摘要描述。 您可以看到更多这些变化 [here](https://github.com/microsoft/TypeScript-DOM-lib-generator/pull/1993) 和 [here](https://github.com/microsoft/TypeScript-DOM-lib-generator/pull/1940)。

## 可扩展悬停（预览）

_quick info_（也称为“编辑器工具提示”和“悬停”）对于查看变量以查看它们的类型或以类型别名查看它们实际引用的内容非常有用。 尽管如此，人们通常想要_更深入_并从快速信息工具提示中显示的任何内容中获取详细信息。 例如，如果我们将鼠标悬停在以下示例中的参数 `options` 上：

```typescript
export function drawButton(options: Options): void
```

我们剩下`(parameter) options: Options`。

![Tooltip for a parameter declared as which just shows .](https://devblogs.microsoft.com/typescript/wp-content/uploads/sites/11/2025/06/bare-hover-5.8-01.png)

我们真的需要跳到类型 `Options` 的定义来查看这个值的成员吗？

以前，事实就是如此。 为了在这里提供帮助，TypeScript 5.9 现在正在预览一个名为 _expandable hovers_ 或“快速信息详细”的功能。 如果您使用 VS Code 之类的编辑器，您现在会在这些悬停工具提示的左侧看到一个 `+` 和 `-` 按钮。 单击 `+` 按钮将更深入地扩展类型，同时单击 `-` 按钮将折叠到最后一个视图。

## 可配置的最大悬停长度

有时，快速信息工具提示可能会变得如此之长，以至于 TypeScript 会截断它们以使它们更具可读性。 这里的缺点是通常会从悬停工具提示中省略最重要的信息，这可能会令人沮丧。 为了帮助您解决这个问题，TypeScript 5.9 的语言服务器支持可配置的悬停长度，可以通过 `js/ts.hover.maximumLength` 设置在 VS Code 中配置。

此外，新的默认悬停长度远大于之前的默认值。 这意味着在 TypeScript 5.9 中，默认情况下，您应该在悬停工具提示中看到更多信息。 有关更多详细信息，请参阅 [the PR for this feature here](https://github.com/microsoft/TypeScript/pull/61662) 和 [the corresponding change to Visual Studio Code here](https://github.com/microsoft/vscode/pull/248181)。

## 优化

### 映射器上的缓存实例化

当 TypeScript 用特定的类型参数替换类型参数时，它最终可能会一遍又一遍地实例化许多相同的中间类型。 在 ZOD 和 TRPC 等复杂库中，这可能会导致性能问题和报告类型实例化深度过多的错误。 多亏了[Mateusz Burzyński](https://github.com/Andarist)中的[a change](https://github.com/microsoft/TypeScript/pull/61505)，TypeScript 5.9能够在特定类型实例上的工作已经开始时缓存许多中间实例化。 这反过来又避免了大量不必要的工作和分配。

### 避免在`fileOrDirectoryExistsUsingSource`中创建闭包

在 JavaScript 中，函数表达式通常会分配一个新的函数对象，即使包装函数只是将参数传递给另一个没有捕获变量的函数。 在围绕文件存在检查的代码路径中，[Vincent Bailly](https://github.com/VincentBailly) 找到了这些传递函数调用的示例，即使底层函数只使用单个参数。 鉴于大型项目中可能进行的存在检查数量，他引用了约 11% 的加速。 [See more on this change here](https://github.com/microsoft/TypeScript/pull/61822/)。

## 显着的行为变化

### `lib.d.ts` 更改

为 DOM 生成的类型可能会对代码库进行类型检查。

此外，一个显着的变化是 `ArrayBuffer` 以一种方式发生了变化，它不再是几种不同 `TypedArray` 类型的超类型。 这还包括 `UInt8Array` 的子类型，例如来自 Node.js 的 `Buffer`。 结果，您将看到新的错误消息，例如：

```text
error TS2345: Argument of type 'ArrayBufferLike' is not assignable to parameter of type 'BufferSource'.
error TS2322: Type 'ArrayBufferLike' is not assignable to type 'ArrayBuffer'.
error TS2322: Type 'Buffer' is not assignable to type 'Uint8Array<ArrayBufferLike>'.
error TS2322: Type 'Buffer' is not assignable to type 'ArrayBuffer'.
error TS2345: Argument of type 'Buffer' is not assignable to parameter of type 'string | Uint8Array<ArrayBufferLike>'.
```

如果您遇到 `Buffer` 问题，您可能首先要检查您是否使用了 `@types/node` 包的最新版本。 这可能包括运行

```text
npm update @types/node --save-dev
```

很多时候，解决方案是指定更具体的底层缓冲区类型，而不是使用默认的 `ArrayBufferLike`（即显式写出 `Uint8Array<ArrayBuffer>` 而不是普通的 `Uint8Array`）。 在某些 `TypedArray` （如 `Uint8Array`）被传递给期望 `ArrayBuffer` 或 `SharedArrayBuffer` 的函数的情况下，您还可以尝试访问该 `TypedArray` 的 `buffer` 属性，如下例所示：

```diff
  let data = new Uint8Array([0, 1, 2, 3, 4]);
- someFunc(data)
+ someFunc(data.buffer)
```

## 类型参数推理更改

为了在推理过程中修复类型变量的“泄漏”，TypeScript 5.9 可能会在某些代码库中引入类型的更改和可能的新错误。 这些很难预测，但通常可以通过向通用函数调用添加类型参数来修复。 [See more details here](https://github.com/microsoft/TypeScript/pull/61668)。

## 下一步是什么？

现在 TypeScript 5.9 出来了，你可能想知道下一个版本的内容是什么：TypeScript 6.0。

您可能听说过，我们最近的大部分重点都放在 [the native port of TypeScript](https://devblogs.microsoft.com/typescript/typescript-native-port/) 上，最终将作为 TypeScript 7.0 提供。 那么这对 TypeScript 6.0 意味着什么？

我们对 TypeScript 6.0 的愿景是作为开发人员为 TypeScript 7.0 调整其代码库的过渡点。 虽然 TypeScript 6.0 仍可能提供更新和功能，但大多数用户应该将其视为采用 TypeScript 7.0 的准备检查。 这个新版本旨在与 TypeScript 7.0 保持一致，在某些设置周围引入弃用，并可能以小的方式更新类型检查行为。 幸运的是，我们没有预测大多数项目在升级到 TypeScript 6.0 时会遇到太多麻烦，而且它可能与 TypeScript 5.9 完全兼容 API。

我们很快就会有更多细节。 这也包括 TypeScript 7.0 的详细信息，您可以 [try it out in Visual Studio Code today](https://marketplace.visualstudio.com/items?itemName=TypeScriptTeam.native-preview) 和 [install it right in your project](https://devblogs.microsoft.com/typescript/announcing-typescript-native-previews/)。

否则，我们希望 TypeScript 5.9 能很好地对待您，并让您的日常编码成为一种乐趣。
