虽然 React Server 组件依赖于自定义飞行协议来流式传输交互式 UI，但同样的机制引入了攻击者可以利用的强大的反序列化接收器。 Durgesh Pawar 分解了 CVSS 10.0 “React2Shell”漏洞背后的机制，以展示协议操作如何导致远程代码执行。 它还涵盖了从严格的模式验证到 CSRF 硬化的实用、排名的防御系统，用于保护 React 应用程序免受这些结构性风险。

React Server 组件不会将 HTML 发送到您的浏览器。 他们也不发送 JSON。 当服务器组件呈现时，实际通过线传输的是一个名为 **flight** 的自定义流式传输协议。 它是一种分行的格式，具有自己的类型系统、自己的参考分辨率，以及用于在客户端上重构可执行行为的规则。

大多数 React 开发人员从未打开过网络选项卡，实际上查看了飞行有效载荷。 它看起来像是 JSON 片段、美元符号前缀引用以及 React 运行时静默地重新组合成实时组件树的模块指针的混合。 框架处理它，所以没有人质疑它。

我不确定大多数团队是否仔细考虑过这种信任实际上意味着什么。

在 2025 年 12 月 [CVE-2025-55182](https://react.dev/blog/2025/12/03/critical-security-vulnerability-in-react-server-components) 放弃后，我开始拆开飞行协议。安全社区称它为 **react2shell**，这是有充分理由的。 这是一个CVSS 10.0，未经身份验证的远程代码执行漏洞位于飞行反序列化层中。 一个对服务器功能端点的 HTTP 请求，攻击者具有 shell 访问权限。 无需凭证。

联邦网络安全与基础设施局 (CISA) 将其添加到 [Known Exploited Vulnerabilities catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)。 [Sysdig](https://sysdig.com/blog/etherrat-dprk-uses-novel-ethereum-implant-in-react2shell-attacks/) 将野外开发与通过以太坊区块链部署无文件植入物的朝鲜国家赞助的参与者联系在一起。 这就是引起你注意的CVE。

在源代码（主要是 `getOutlinedModel` 和 `getChunk` ）之后，我意识到 React2Shell 不是一次性的解析错误。 这是一个症状。 Flight 从文本流中重构可执行引用、延迟加载的组件、服务器 RPC 端点和异步状态。 这是一个**反序列化系统**。

攻击面远远超出单一缺失的 [`hasOwnProperty`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/hasOwnProperty) 检定。 本文介绍了飞行在电线上的工作方式、反序列化下沉、攻击者已经武器化以及仍暴露的内容。

这会为您自己的服务器组件提供**排名、实用的防御系统**：每个服务器操作的架构验证、[`server-only` 包](https://react.dev/reference/react/experimental_taintUniqueValue#using-server-only-and-taintuniquevalue-to-prevent-leaking-secrets)、跨站点请求伪造 (CSRF) 强化超出框架默认值，以及对 Taint API 和 Web 的评估 应用程序防火墙 (WAF) 提供。

电线上的飞行
-------------------

在任何 next.js 应用程序路由器页面上打开浏览器的网络选项卡并查找返回 `Content-Type: text/x-component` 的请求。 那是飞行。 它不是一个 JSON Blob。 它是一种流式分隔的格式，其中每行都是一个独立的“行”，客户端 React 运行时在连接上到达。

以下是简单的飞行有效载荷在实践中的样子：

1:i["./src/components/clientcomponent.js",["chunks/main.js"],"default"]
2:j["$""文章",null,{"children":"$1"}]
0:d{"name":"rootlayout","env":"server"}
    

第 1 行是一个导入指令。 它告诉客户端从捆绑器的块映射中加载 `ClientComponent.js`。 第2行是构造`<article>` HTML元素的JSON树，`children`中的`"$1"`是对块1（导入的组件）的引用。 第 0 行定义了服务器执行上下文，将其标记为 `Server` 环境中运行的 `RootLayout`。 即使在这个微小的示例中，您也可以看到结构数据、模块引用和交叉块指针的组合，这些指针使 Flight 与普通 JSON 不同。

### 行格式

每一行都遵循相同的语法：`<ROW_ID>:<ROW_TAG><PAYLOAD>\n`。 行 ID 是其他行可以引用的数字标识符。 标记是单个字符（或短字符串），告诉解析器遵循什么样的数据。 有效载荷是实际内容。

到目前为止，这可能看起来像是一种带有一些自定义标签的良性结构化数据格式，但真正的复杂性和攻击面存在于**前缀系统**中。

### `$`前缀系统

这是我开始更加关注的地方。

当客户端解析器遇到以 `$` 开头的字符串值时，它不会将其视为文字文本。 它拦截字符串，检查前缀，并通过特定类型的分辨率路径将其路由。 `ReactFlightClient.js` 中的 `parseModelString` 功能是发生这种情况的地方。 它本质上是 `$` 之后的字符上的一个大开关语句。

字首

`$`

每个其他前缀解析一个块并为您提供解析的结果。 `$@` 相反，将原始内部 `Chunk` 对象交给您，包装器 React 用于跟踪解析状态、未决回调和内部元数据（这就是为什么它被用于 Promise 以及利用它来获取可变句柄的原因）。 通过协议公开框架管道对我来说似乎是一个设计错误，尽管我很想听听是否有一个设计错误。

和 `$:`（属性访问）是另一个关键前缀。 它允许协议指定一个像`$1:user:name`这样的路径，它告诉解析器解析块1，然后访问`.user`，然后访问`.name`的结果。 这是由流中的数据驱动的任意属性遍历。 如果您花时间审核 JavaScript 原型污染，那么这种模式应该会让人感到熟悉。

### 这不仅仅是数据格式

飞行不是带有额外步骤的JSON。 JSON 为您提供数据。 航班给你**行为**。 它重构了触发客户端代码加载的模块引用，创建了客户端可以作为 RPC 调用调用的服务器操作端点，设置了 React 运行时将 `await` 将 `await` 的承诺链，并构建了按需执行的延迟加载的组件边界。

无论 React 开发人员是否这样想，这些机制看起来都非常类似于历史上引起问题的反序列化系统。 流不仅描述了用户界面的外观。 它指示客户端运行时加载什么代码、调用什么函数以及信任什么。

如果您想自己阅读实现，公平警告：块解析路径很糟糕。 状态转换在辅助函数之间反弹，并且命名掩盖了代码实际执行的操作。 我放弃了静态读取，只是设置了断点。 关键文件是客户端解析器的 [`react-client/src/ReactFlightClient.js`](https://github.com/react/react/blob/main/packages/react-client/src/ReactFlightClient.js)（查找 `parseModelString`、`getChunk`、`reviveModel` 和 `getOutlinedModel`）和 [`react-server/src/ReactFlightServer.js`](https://github.com/react/react/blob/main/packages/react-server/src/ReactFlightServer.js) 的序列化方面。 服务器操作的回复处理程序位于 [`react-server/src/ReactFlightReplyServer.js`](https://github.com/react/react/blob/main/packages/react-server/src/ReactFlightReplyServer.js) 中。

为什么飞行是反序列化的水槽
----------------------------------

反序列化模式很熟悉：Java 的 `ObjectInputStream` 给了我们 YSOserial，Python 的 `pickle` 在 `load()`、PHP 的 `unserialize` 链 `__wakeup` 和 `__destruct` 方法上执行代码，并且 .NET `BinaryFormatter` 被弃用 完全。

> 模式：反序列化攻击者控制的输入→在重建过程中调用行为→失去对执行的控制。

所以 JavaScript 应该对此免疫，对吧？ `JSON.parse()` 仅生成普通数据对象。 没有构造函数触发。 没有魔法方法运行。 你得到的正是 JSON 字符串所描述的内容，仅此而已。

对于 RAW `JSON.parse()` 也是如此。 但当框架将自定义反序列化逻辑包裹在其周围时，它就不再是真实了。 这正是 Flight 的作用。

### 原型污染

JavaScript 使用基于原型的继承。 每个对象都有一个指向其原型的 `__proto__` 链接，并且属性查找遍历这条链。 如果攻击者在重建过程中将 `__proto__` 或 `constructor.prototype` 作为密钥注入，它们会修改所有对象继承的共享基础原型。 下游代码在不知情的情况下读取攻击者控制的值。

Flight `$:` 前缀对反序列化对象执行属性遍历。 `getOutlinedModel` 函数通过遍历每个段并在父对象上访问它来遍历冒号分隔的路径 `$1:user:name`。 如果这些路径段包括 `__proto__` 或 `constructor`，则遍历会直接沿着原型链走上。 这不是理论上的风险。 这正是 React2Shell 的工作方式。

###  鸭子打字和 thenables

V8 引擎（和 JavaScript 规范）将具有 `.then` 属性的任何对象视为 **thenable**。 当您 `await` 某事时，运行时会检查 `.then` 并在存在时调用它。 没有课堂检查。 没有内部插槽验证。 如果 `.then` 是可调用的，它将被调用。

飞行异步解析块。 如果攻击者构造一个具有操纵的 `.then` 属性的对象并将其放入块解析管道，则运行时在正常的等待行为中调用攻击者的函数。 语言语义完成了这项工作。

我最初专注于 `$F`，因为伪造服务器操作引用似乎是明显的攻击面。 在追踪分辨率路径之后，`$:` 属性遍历看起来更有趣。 我还花了几个小时检查块状态转换（挂起、阻塞、解决、错误），看看你是否可以强制一个块进入意外状态，尽管这种方法没有产生任何结果。

### 核心问题

这两个风险在飞行中收敛，因为该协议不只是反序列化数据。 它反序列化_Behavior_。 `$` 前缀系统指示解析器采用的执行路径： `$F` 创建可调用的服务器端点，`$L` 设置惰性代码加载，`$B` 触发 Blob 处理程序，`$@` 暴露内部框架状态。 解析器的控制流完全由流中的内容驱动。

如果攻击者可以影响流的内容，他们可以控制解析器调用的函数、它构造的对象以及它公开的内部状态。

React2Shell的机制
-----------------------------

这是证明理论的CVE。 [CVE-2025-55182](https://nvd.nist.gov/vuln/detail/CVE-2025-55182)，昵称 React2Shell，是飞行反序列化层中未经身份验证的远程代码执行漏洞的 CVSS 10.0。 一种HTTP请求，无需登录，完全外壳访问。

我想遍历整个小工具链，因为了解它会揭示飞行协议向可以控制流的攻击者提供的力量有多大。

### 根本原因

该漏洞位于 `getOutlinedModel` 中，该函数负责从 `$:` 参考系统解析深层属性路径。 漏洞利用链中使用的实例位于服务器端回复处理代码 (`ReactFlightReplyServer.js`) 中。 当解析器遇到像 `$1:user:name` 这样的引用时，它会在冒号上分裂并逐段遍历路径。 这是脆弱的循环：

for (key = 1; key < reference.length; key++)
父对象 = 父对象[参考[键]]；
    

两条线。 否 `hasOwnProperty` 检查。 没有验证属性存在于对象本身而不是原型链上的某个位置。 只是 `parentObject[reference[key]]` 并继续前进。

所以攻击者提供`$1:__proto__:constructor:constructor`，循环从一个普通的JSON对象到`Object.prototype`到`Object`构造函数到`Function`构造函数。 `Function` 在 JavaScript 中的行为类似于 `eval()`。 `Function("arbitrary code")()` 执行。

没有关于财产名称的允许名单。 没有检查 `__proto__`。 我搜索了 `reviveModel` 和任何过滤的块初始化路径。 什么都没有。

### 小工具链

从 _“我可以到达函数构造函数”_ 到 _“我有 RCE”_ 需要将几个飞行协议功能链接在一起。 [Resecurity write-up](https://resecurity.com/blog/article/react2shell-explained-cve-2025-55182-from-vulnerability-discovery-to-exploitation) 详细覆盖了全链； 以下是高级序列：

*   **第 1 步：原型步行功能。**
`$:` 路径 `__proto__:constructor:constructor` 从任何普通对象到 `Object.prototype`，然后到 `Object` 构造函数，然后到 `Function` — JavaScript 的内置 `eval()` 。
*   **第 2 步：原始块自引用。**
`$@0` 返回原始内部 `Chunk` 包装器而不是其解析值，为攻击者提供了 React 内部状态机上的可变句柄。
*   **第 3 步：然后可劫持。**
攻击者将块的 `.then` 设置为 `Chunk.prototype.then`，因此 React 的解析管道将被操纵的块视为一个合法的 Promise 对象并等待它。
*   **第 4 步：上下文混淆。**
在第二次反序列化过程中，payload 覆盖 `_response._formData.get` 以指向被劫持的 `Function` 构造函数并将攻击者的 shell 命令置于 `_response._prefix` 中。
*   **第 5 步：通过 Blob 处理程序触发。**
`$B0` 调用 Blob 处理程序，它在内部调用 `response._formData.get(response._prefix + blobId)` — 现在相当于 `Function("attacker_shell_command")()`。 那是任意代码执行，具有 Node.js 进程的任何权限。

每个步骤都以设计师没有预料到的方式使用了合法的飞行协议功能。 没有单一的“破碎”功能。 当攻击者控制输入时，这些功能的构成方式会出现漏洞。

### 影响

这一款的数字是鲜明的：

*   CVSS 10.0。 可能的最大分数。
*   未经身份验证和预验证。 不需要凭据——反序列化发生在任何应用程序级身份验证运行之前，因此即使是登录墙后面的端点也暴露出来。
*   单一HTTP请求。 一个 POST 到服务器功能端点。
*   受影响的 React 19.0.0、19.1.0、19.1.1 和 19.2.0，跨 `react-server-dom-webpack`、`react-server-dom-parcel` 和 `react-server-dom-turbopack`。
*   CISA 在几天内将其添加到已知的利用漏洞目录中。

### 野外发生了什么

剥削是立即的。 [Sysdig](https://sysdig.com/blog/etherrat-dprk-uses-novel-ethereum-implant-in-react2shell-attacks/) 已发表的研究将 **Etherrat** 部署与朝鲜国家赞助的参与者联系起来，这些行为者在披露后的数小时内将漏洞武器化。 [EtherRAT](https://www.sysdig.com/blog/etherrat-dprk-uses-novel-ethereum-implant-in-react2shell-attacks) 是一种无文件植入物，它使用以太坊区块链进行命令和控制通信——这是研究人员称之为“以太隐藏”的技术——因为你无法抓住区块链，因此几乎不可能删除。

另外，Palo Alto 的 [Unit 42 documented](https://unit42.paloaltonetworks.com/cve-2025-55182-react-and-cve-2025-66478-next/) 一个名为 **kswapdoor** 的后门，伪装成受感染的 Linux 系统上的 `[kswapd1]`，与合法的 `kswapd0` 内核交换守护程序一起融入进程列表； 他们的分析证实，KSWAPDOOR 使用 RC4 加密来保护其内部字符串和配置数据，而 C2 通信通过 P2P 网状网络通过 AES-256-CFB 使用 [Diffie-Hellman key exchange](https://en.wikipedia.org/wiki/Diffieâ€“Hellman_key_exchange) 运行。 这些活动的速度和复杂性——国家赞助的参与者通过一个未经认证的 HTTP 请求部署新型植入物——强调了为什么反序列化层中的 CVSS 10.0 需要立即修补，而不是分类。

修复
--------

React 团队的补丁干净且有针对性。 核心更改在模块加载时缓存 genuine `hasOwnProperty` 方法：

var hasOwnProperty = object.prototype.hasownProperty;
    

然后反序列化路径中的每个属性检查都使用 `.call()` 来调用缓存的引用：

hasOwnProperty.call(值，i);
    

即使攻击者在恶意对象上显示 `hasOwnProperty` ，检查也使用原始原型方法。 为小工具链提供动力的原型链遍历被阻止。 此修复程序在 React 19.0.1、19.1.2 和 19.2.1 中提供。

修复是正确的。 但是阅读这些补丁，我注意到 React 团队在保持属性遍历模型完好无损的情况下进行了所有权检查。 `$:` 前缀仍然走在结肠分隔的路径中； 它现在只是验证每个步骤。 我认为通过网络协议暴露任意属性遍历是一个设计错误，补丁可以处理症状。 如果未来出现错误，它们可能来自同一领域。

框架补丁关闭了已知的小工具链，但它不会改变基本的动态：飞行协议仍然从文本流中重构行为——可执行引用、模块导入、RPC 端点、异步状态。 重建在您的应用程序代码运行之前，在验证逻辑触发之前，甚至在您的身份验证中间件看到请求之前发生。 仅依靠框架来保护您的服务器组件意味着相信复杂的反序列化解析器中的每个边缘情况都已被发现并修复。 接下来的防御是您可以自行限制爆炸半径的实际步骤。

### 2\。 `server-only` 包

`server-only` 包是简单有效的。

在包含数据库凭据、原始 API 调用、内部业务逻辑或其他任何不应跨越服务器客户端边界的文件的顶部导入 `server-only`。 如果客户端组件尝试导入该文件（直接或可传递），则构建失败并出现明显错误。

导入“仅限服务器”

需要注意的故障模式是 [barrel files](https://www.educative.io/answers/what-are-barrel-files)。 如果你通过一个也导出客户端安全实用程序的 `index.ts` 重新导出一个仅服务器的函数，那么从该 barrel 中导入的任何客户端组件都将可传递地拉入 `server-only` 模块并破坏构建 - 或者更糟糕的是，如果桶不包含 `server-only` 导入本身，它可能会 默默地让服务器代码通过。 将仅限服务器的模块保存在具有自己导入路径的单独文件中。

// src/utils/index.ts

// 客户端组件直接从“src/utils/dates”导入
// 服务器组件直接从“src/utils/users”导入
    

它也不会保护您免受_return values_的数据泄漏。 如果服务器组件调用 `getUser()` 并将完整的用户对象（包括 `passwordHash` 或 `internalRole`）作为道具传递给客户端组件，则该数据将飞行流传输到浏览器。 `server-only` 保护防止 _code_ 跨越边界，而不是 _data_ 代码返回。 您必须明确过滤您的返回形状。

### 5\。 污点 API

React 的 `taintObjectReference` 和 `taintUniqueValue` 函数将对象或字符串与运行时一起寄存。 如果受污染的数据试图通过飞行序列化器，则会引发错误。 这个想法是为了防止敏感数据——用户记录、API 密钥、令牌——意外泄漏到客户端中。

下面是它在实践中的样子：

导入 {
experiment_taintObjectReference 作为 TaintObjectReference
} 来自“反应”
导入“仅限服务器”
    
导出异步函数 getUserRecord(id: string) {
const user = await db.users.findunique({ where: { id } })

“不要将完整的用户对象传递给客户端组件。” +
“仅选择您需要的字段。”，
用户
)
返回用户
}
    

如果服务器组件将受污染的 `user` 对象作为道具传递给客户端组件，则 React 在序列化时将其与您的自定义错误消息抛出。 这作为开发时间护栏真的很有用。

问题——而且它是一个重要的——是 taint 跟踪 _object references_，而不是数据内容。 任何派生都会破坏跟踪：

const user = await getUserRecord(ID)
    
// 污点丢失。 传播创建一个新对象。
    <ClientProfile user={{ ...user }} />
    
// 污点丢失。 未跟踪单个属性。
    <ClientProfile token={user.apiToken} />
    
// 污点丢失。 序列化往返 创建新的 refs。
    <ClientProfile user={JSON.parse(JSON.stringify(user))} />
    
// 污染火灾。 相同的对象引用。
    <ClientProfile user={user} />
    

`taintUniqueValue` 适用于特定的字符串（如 API 键），但它也是基于引用的。 如果相同的键值出现在不同的变量中，则不会出现污点。

将污染视为发展护栏，而不是安全边界。 它捕获了诚实的错误：开发人员不小心将完整的用户对象传递给客户端。 它不会阻止可以影响序列化的攻击者，也不会阻止您自己的代码执行的常规数据转换。 这是一个有用的深度防御层，但不应该是你的主要边界。

### 6\。 瓦夫斯

Web 应用程序防火墙可以为已知的攻击模式添加检测层。 他们可以检查带有 `Next-Action` 标头的 POST 请求、包含 `constructor:constructor` 或 `__proto__` 链的块有效负载，以及包含 `E{"digest"` 模式的标志错误响应，表明服务器正在泄漏内部错误详细信息。

如果您正在运行 WAF，以下是值得添加的特定模式：

    # 在请求体中阻止原型污染尝试
规则： body 包含“__proto__”或“构造函数：构造函数”
行动：块
范围：带有标题“next-action”的 POST 请求
    
    # 在响应中标记潜在的飞行错误泄漏
规则：响应正文匹配 /e\{"digest":"[^"]+"/
行动：日志+警报
范围：内容类型“text/x-component”的响应
    
    # 阻止过大的服务器操作有效负载
规则： Content-Length > 1MB 用于带有“Next-Action”标头的帖子
行动：阻塞（缓解CVE-2026-23864 Zipbomb向量）
    

但攻击者知道 WAF 检查缓冲区，它们通常在 128KB 左右。 在恶意有效载荷之前添加 130KB 的填充，WAF 检查填充，找不到任何东西，并让请求通过。 分块传输编码技巧完成了同样的事情。

故障模式将 WAF 覆盖率视为安全边界而不是降噪层。 WAF 捕获自动扫描仪和低力攻击，这具有真正的价值。 但是有动力的攻击者会用填充或编码技巧绕过它们。 实际上阻止复杂攻击的防御是在此列表中的前面：在输入到达业务逻辑之前验证输入，使敏感代码远离线索，并保持修补版本。

`action-handler.ts` 中的 Next.js 解析器将字符串 `'null'` 视为缺失的原点而不是显式的跨源指示符。 因此，攻击者可以将表单嵌入到沙盒化的 iframe 中，提交，并使用受害者的身份验证会话 cookie 调用服务器操作。 修复了 Next.js 16.1.7 中的问题。

什么仍然暴露
---------------------

上面的 CVE 有补丁。 但其中一些风险是结构性的，融入了飞行的设计方式。

### 飞行流中的中间人（MITM）

如果攻击者可以坐在服务器和客户端之间（CDN 泄露、缓存中毒、恶意代理），修改传输中的飞行流似乎是可行的。 格式是具有可预测结构的纯文本。

假设流控制，攻击者可以更改 `$I`（导入）行将组件加载重定向到 Webpack 块映射中的另一个模块。 他们可以将 `$F`（服务器参考）标签嵌入渲染的 UI 中以嵌入隐藏的 RPC 触发器。 他们可以修改 `D`（数据）行来更改组件道具，如果目标组件使用 `dangerouslySetInnerHTML`，那是直接的 XSS 向量。

Flight Escapes `$` 在用户提供的字符串中添加前缀，以防止数据被解释为协议指令。 但这仅适用于流经序列化程序的数据。 MITM 攻击者将原始协议直接写入流中。 逃跑没有帮助。

### 服务器操作枚举

服务器操作 ID 是在构建时生成的混淆散列。 他们看起来很随意。 但是 `server-reference-manifest.json` 将每个动作 ID 映射到其源实现。 公共清单递给攻击者一个完整的 API 映射。 这种暴露通常源于配置错误的主机、暴露的 `.next` 目录或路径遍历。

已知的操作 ID 将服务器操作暴露给标准 IDOR 和参数篡改攻击。 攻击者可以使用操纵的参数伪造直接请求。 开发人员通常会盲目地信任这些输入，因为它们来自 React 的内部机制。 这种错位信任的建筑后果将是我下一篇文章的重点。

### 加密闭合篡改

当服务器操作从其周围的范围（关闭）捕获变量时，Next.js 在发送到客户端之前对其进行加密。 密钥在 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` 中，带有 base64 编码密钥的 AES（16、24 或 32 字节）。 `decryptActionBoundArgs` 处理每次调用的解密。

默认情况下，此密钥将重新生成每个版本。 但多服务器设置通常使用静态密钥。 如果攻击者获得文件读取访问权限（路径遍历，SSRF），则提取密钥，解密闭包状态，修改（更改`userId`，`role`，查询参数），并重新加密。 服务器接受伪造的闭包是合法的。

### 通过模块 ID 提供链条激活

我还没有演示这端到端的，但这个理论很简单。

Flight 按模块 ID 引用客户端组件，类似于 `["360","static/chunks/app/page-7f3480.js"]`。 Bundler 根据模块图表在构建时分配这些 ID。 作为可传递依赖项的受损 npm 包被捆绑到块中，但从未加载，因为没有组件引用它。 惰性。

但是，如果攻击者将 `$I` 导入引用注入到飞行流（通过 MITM、缓存中毒或服务器端注入），则解析器应该加载该休眠模块。 我可能没有看到块级验证。 但是，如果模块 ID 是有效的并且存在于清单中，我看不到是什么阻止了它。 攻击不需要在代码中的任何位置导入软件包。 它只需要存在于捆绑输出中。

这发生在以前
-------------------------

React Flight 并不是第一个为服务器-客户端通信发明自定义序列化格式然后发现它是攻击面的框架。 它不会是最后一次。

[Google Web Toolkit (GWT)](https://www.gwtproject.org) 使用自定义 RPC 协议在浏览器和服务器之间同步 Java 对象。 BishopFox 证明攻击者可以操纵线格式以实现任意反序列化； GWT 最终完全禁用了二进制序列化。 花了好几年的时间。

Java Server （JSF）和ASP.NET 都将**`ViewState`** 序列化为隐藏的表单字段。 当加密签名弱或缺失时，攻击者篡改了序列化状态并实现了远程代码执行。 微软和甲骨文反复修补它。 底层模式不断重新浮出水面。

模式始终相同：框架发明了一种自定义的线格式，以在服务器和客户端之间移动丰富的、有状态的、有时是可执行的数据。 设计人员假定服务器是该数据的唯一生产者，而客户端是可信消费者。 然后有人演示了可以在传输中操作线路格式，或者服务器可以被欺骗将攻击者控制的输入反序列化。 React Flight 是此模式中的最新条目。 这不是**异常**。

接下来会去哪里
---------------------

React Flight 协议解决了一个真正困难的问题：将交互式组件树从服务器流式传输到客户端，实现渐进式水化、异步数据加载和服务器驱动的代码分割。 它有效。 我不想忽视这一点。

但它的工作方式是通过流式文本协议对可执行引用、异步状态、模块指针和 RPC 端点进行序列化，然后在两端信任该流的结构。 React 团队已经修补了已知的小工具。 `hasOwnProperty` 修复是正确的。 DOS 修复到位。 源代码暴露错误已关闭。

我认为通过面向网络的协议暴露任意属性遍历和可执行的可执行性重建是一个**设计错误**。 `$:`、`$@` 和 `$B` 是强大的内部原语，可以通过未验证其遍历的属性的所有权的解析器访问。 一张支票丢失，结果是 CVSS 10.0。
