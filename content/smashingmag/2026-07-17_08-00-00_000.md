一般的经验法则是在运行 JavaScript 任务时切勿“阻止”浏览器的主线程。 但这是一个硬规则吗？ Victor Ayomipo 描述了他遇到的一个涉及屏幕截图扩展的用例，他对规则做出了例外，并决定阻止主线程绝对是正确的做法。

我们都听说过现代网络开发中的神圣规则，永远不会被打破的规则。 _“永远不要阻塞主线程”的规则。

作为 Web 开发人员，您几乎不能错过它； 它几乎出现在每个性能指南中，公平地说，这是一个很好的建议。 我们都知道浏览器的主线程是**单线程**，这意味着它一次只能做一件事。

另外，正如我们所知，[the main thread isn’t ours alone](https://www.smashingmagazine.com/2023/10/speedcurve-fight-main-thread/)； 我们与浏览器的渲染引擎、输入处理程序和其他关键任务共享它。 因此，我们抓住主线程的时间越少，应用程序的响应速度就越快。 这导致我们与后台工作人员共享任务，因为我们已经确信 UI 和任何计算之间应该有一条强硬的界限，并且不应该越界。

这就是“推荐”架构的样子。

但我敢说，\*有时\*_,_ 将数据移动到工作人员比让主线程完成工作要慢。

几个月前，我在构建一个名为 Fastary 的屏幕截图功能的 Chrome 扩展程序时发现了这一点。 即使在使用 [Offscreen Document](https://developer.chrome.com/docs/extensions/reference/api/offscreen#main-content) （Chrome 扩展中的后台进程）来处理画布操作之后，我也一直在所有测试中找到大约 2 到 3 秒的延迟。 毕竟，屏幕截图任务应该感觉即时没有延迟。

具有讽刺意味的是，通过反射，我们将工作从主线程移开以避免冻结 UI，但有时移动该工作的行为（例如，序列化、复制和反序列化）也会冻结 UI。 并且_有时_让后台完成工作的推荐方法可能比在主线程上进行工作要慢。

让我们谈谈这一点。

浏览器上下文隔离的架构
-------------------------------------------

换个角度来看，让我们了解为什么我们隔离浏览器上下文以及它们如何相互通信，重点是 _communication_ 部分。

浏览器不仅仅是一个环境。 不同的环境同时运行，每个环境都有自己的内存空间、可以访问的内容和规则：

*   **主线程**是我们最熟悉的； 这是 JavaScript 逻辑运行的地方、DOM 所在的位置、渲染样式的位置以及用户交互的位置。
*   **Web Workers**是单独的线程，也可以在没有DOM访问的情况下执行JavaScript。 我们主要将其用于繁重的数据任务。
*   **服务工作者**是负责拦截网络请求的网络相关代理，甚至可以在页面关闭时运行。
*   然后是**Chrome扩展上下文**，其中我们有后台服务工作者、内容脚本和屏幕外文档（本文的相关内容）。

其中每一种都与其他人隔离。 Web Worker 或后台脚本位于与主线程不同的内存空间中。 他们不能只是到达和读取彼此的变量或逻辑，这被称为**“共享-无”架构**。

这些孤立的环境如何沟通？ 他们使用 API 来回显式地互相发送消息，例如 `postMessage()`。

### 结构化克隆算法

`postMessage()` 告诉浏览器获取一段数据并将其传递到请求它的上下文中。 但要做到这一点，浏览器依赖于 [Structured Clone Algorithm (SCA)](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm)。

您可能熟悉 `JSON.stringify()`。 SCA 是相似的，但更强大和更智能。 在最简单的形式中，SCA 是一种深度的递归复制操作，即克隆。 它遍历给出的整个数据结构，克隆每个值，将其序列化为可传输的格式，将这些字节发送到目标上下文，然后在接收端重构原始对象。

SCA 是快的，或者可能是 fast-_ish_... 对于像 `{theme: "dark"}` 这样的小型常规配置对象，它是难以察觉的； 你甚至没有注意到它。 然而，在处理大量数据时，故事发生了变化，因为 SCA 是一个同步阻塞 `O(n)` 操作，即成本随数据的大小线性增加。

让我们把它放在眼里。 用户单击一个按钮，并在内部发送一个 8MB 图像有效负载到后台工作器进行处理。 当您调用 `postMessage()` 时，主线程必须立即停止运行此序列化和复制过程的操作。

> 那么，如果打包、发货、解包数据所需的时间，再回到起点的时间比处理主线程上的数据的时间长，为什么不这样做呢？

可转移的对象呢？
--------------------------------

我敢肯定你们中的一些人已经在想，_“为什么不只使用可转移的物体？”_这是一个有效的观点。 让我们谈谈这一点。

真正追求超高性能 Web 应用程序的开发人员通常使用 [Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)（例如 `ArrayBuffer`、`ImageBitmap` 或 `MessagePort`）来绕过结构化克隆算法。 这是因为当您转移对象时，您不是在制作副本（如 SCM）。 相反，浏览器将数据的所有权从一种上下文切换到另一种上下文。

浏览器执行切换，从而发送上下文立即失去对数据的访问权限，接收上下文完全控制。 它实际上速度非常快。 根据 [Chrome Developers’ benchmark](https://developer.chrome.com/blog/transferable-objects-lightning-fast#benchmark_demo) 的说法，转移一个巨大的 32MB `ArrayBuffer` 可以在 7 毫秒以下，而使用 SCM 克隆时大约需要 300 毫秒。 这是一个 43 倍的速度提升。

[![Structured cloning vs. Transferable Objects by Chrome Developers](https://res.cloudinary.com/indysigner/image/fetch/f_auto,q_80/w_400/https://files.smashing.media/articles/when-makes-sense-block-main-thread/1-structured-cloning-transferable-objects.png)](https://developer.chrome.com/blog/transferable-objects-lightning-fast#benchmark_demo)

Chrome 开发人员的结构化克隆与可转移对象。 （图片来源：[Chrome for Developers](https://developer.chrome.com/blog/transferable-objects-lightning-fast#benchmark_demo)）（[Large preview](https://files.smashing.media/articles/when-makes-sense-block-main-thread/1-structured-cloning-transferable-objects.png)）

但就像所有美好的事物一样，也有缺点。 举几例：

*   **发送后您会丢失它。**
如果 UI 仍然需要该数据（例如显示图像预览），则无法再访问它。
*   ** 并非所有数据都可以传输。**
普通的 JS 对象不是。 斑点不是。 即使是 base64 字符串也不是。
*   **API 限制。**
在浏览器扩展的上下文中，Chrome 的内部消息 (`chrome.runtime.sendMessage`) 传统上通过 JSON 序列化来强制一切。

因此，就我的屏幕截图扩展名而言，可转移的对象不是一种选择。

无论如何，为什么我们隔离上下文
------------------------------

为什么我们甚至要打扰隔离上下文？ 为什么不把它全部留给主线程呢？

将长时间运行的 CPU 任务卸载到后台线程绝对是正确的做法。 浏览器需要绘制一个新框架 **每 16.6ms** 以保持流动性； 这意味着 [any task that takes >50ms is generally considered “long”](https://developer.mozilla.org/en-US/docs/Glossary/Long_task#:~:text=A%20long%20task%20is%20a%20task%20that%20takes%20more%20than%2050ms%20to%20complete.)。 卸载到后台绝对是正确的做法。

然而，问题是我们已经把这个_“永远不要阻止主线程”_变成了一个绝对的规则，而不问_这个任务的处理成本是昂贵还是移动成本很高？

当正确的架构是错误的架构时
-------------------------------------------------

Fastary 扩展的目标是让它感觉像一个原生应用程序，像您期望的原生应用程序一样流畅和即时运行。

如您所知，我用 [the recommended approach](https://developer.chrome.google.cn/blog/Offscreen-Documents-in-Manifest-v3) 来使用屏幕外的文档来处理后台的 DOM 工作。 但令我惊讶的是，这发生了不同的转变。

屏幕外文档 API 是一个明显的赢家。 您创建一个完全在后台运行的隐藏的、未显示的文档。 它有一个 DOM 并支持画布。 例如，如果我想裁剪屏幕截图，将多个屏幕截图拼接在一起，执行大量图像操作，或添加水印，则为其制作了屏幕外的文档。

事实证明，这不是最好的方法。 这是我的架构：

1.  后台服务工作者用 `chrome.tabs.captureVisibleTab()` 捕获屏幕截图，返回一个 base64 编码的数据 URL 字符串。
2.  后台服务工作者使用 `chrome.runtime.sendMessage()` 将此图像有效载荷运送到屏幕外文档。
3.  屏幕外的文档接收图像，将其加载到 `<img>` 元素中，然后将其绘制到画布上，然后再应用用户的裁剪坐标，对结果进行编码，并将处理后的图像发送回背景工作人员。

但是当我测试它时，屏幕截图并没有立即感觉到。 正如我之前所说，有一个持续的 2-3 秒滞后。

我发现当 `captureVisibleTab()` 截屏时，它会返回一个 base64 url 字符串，并且在标准的 1080p 屏幕上，该字符串可能约为 1MB 或更多，具体取决于图像的详细程度。 它在现代 Retina 显示器（例如 MacBooks）上变得更加有趣，因为它们倾向于默认自动将图像的大小加倍。

请记住，由于图像有效负载可以加倍，并且扩展消息依赖于 JSON 序列化（截至本文撰写时），我们可能会处理**大规模同步通信**，这会花费整个回程。

图像字符串数据至少被 JSON 序列化两次：一次进入屏幕外的文档时，一次返回到后台工作人员。 毫无疑问，在屏幕外文档中完成的实际图像处理（裁剪）速度很快，但我不能对传输开销说同样的话。

### 视网膜高DPI问题

好像延迟本身还不够，我注意到一个相当微妙的错误——现在我想到它，更多的是我的无知。 截取截图后，裁剪结果完全以奇怪的方式缩放图像或导致不正确的坐标。

事实证明，当用户选择要裁剪的区域时，内容脚本会使用 `getBoundingClientRect()` 获取框坐标，该坐标以 **css 像素***** 为单位进行测量； 这是DOM使用的。 但是当在 Chrome 中本地捕获屏幕截图时，浏览器不会自动裁剪它； 相反，它使用**物理硬件像素**来获取全屏捕获。 浏览器使用 `devicePixelRatio` (DPR) 来知道有多少物理像素应该代表一个 CSS 像素。 基本上，如果用户在视网膜显示器（DPR = 2）上突出显示 400x300 厘米像素的区域，则实际捕获的图像区域为 800x600 物理像素。

> ** 注意：** 一台标准显示器上的 1 个 CSS 像素等于 1 个物理像素（DPR 为 1）。 然而，在MAC Retina显示器或现代4K显示器上，DPR通常是2或3。

为了准确的作物，我需要使用正确的 DPR 应用这两种不同的测量系统，即按 DPR 缩放作物坐标。 但请记住，屏幕外的文档没有物理显示。 处理任何图像的默认 DPR 将具有等于 1 的默认值。要解决此问题，我必须从活动选项卡中捕获确切的 `devicePixelRatio`，将其序列化，将其传递到图像有效负载旁边，并在屏幕外手动执行缩放数学。 复杂性开始复杂化。

_如果我打破了黄金法则并在主线程上工作了怎么办？

在主线程上工作
---------------------------

一些开发人员会争辩说，UI 任务是主线程上唯一应该运行的事情，但我并不完全同意这一点。 就个人而言，我相信需要立即结果的用户明确调用的操作有时可以在主线程上运行，前提是工作令人难以置信的_fast_（例如，1s）。

这就是我所做的：删除屏幕外的文档并重新设计逻辑。 而不是：

背景 → [序列化] → 屏幕文档 → [序列化] → 背景 → 内容脚本

…我决定在活动选项卡中运行整个图像处理：

1.  后台服务工作者捕获屏幕并获取base64字符串（与以前相同）。
2.  后台使用`chrome.scripting.executeScript()`将有效载荷直接发送到活动选项卡中的内容脚本。
3.  内容脚本（在主线程上运行）接收有效载荷，将其绘制到画布上，使用正确的 DPR 值执行裁剪，并将结果复制到剪贴板。

// 背景脚本
const screenshowTurl = await chrome.tabs.CaptureVisibleTab(undefined, { format: "png" });
    
// 将处理函数作为内容脚本注入活动选项卡
等待 Chrome.Scripting.ExecuteScript({
目标：{ tabID：activetab.id }，
func: 流程和复印图像，
args: [{ base64image: screenshowTurl, cropData: userSelection }]
});
    

这种方法完全清除了 JSON 序列化所需的多个上下文跳跃和往返行程。 唯一的跨上下文传输涉及将数据 URL 从后台发送到内容脚本。

Retina DPI 问题基本上解决了，因为内容脚本直接在真实的活动浏览器选项卡内运行，因为它知道显示器的真实 `devicePixelRatio`。

但是房间里有一头大象，你可能已经注意到了。

当然，图像现在在主线程上处理，背景会在活动选项卡中操纵画布。 从技术上讲，我可以阻止主线程。 在那里我将“不阻塞主线程”规则修改为“不阻塞主线程_for to long_”。 在这种特定情况下，至少阻塞用户请求大约一秒钟的任务的主线程是合理的。 相反，它也有效：如果数据传输成本大于处理成本**，也许**不要隔离流程。

结论：何时隔离，何时不隔离
-----------------------------------------

我把它归结为一个心理模型，取决于任务是否是：

### 1\ 计算繁重的任务（CPU-bound）

这些是主要成本是计算而不是数据本身大小的任务。 这些任务大部分时间都花在进行计算或重型变换上，例如图像压缩、音频分析、物理模拟等。

与实际工作相比，这些任务的转移成本微不足道。

### 2\。 数据繁重的任务（数据绑定）

这些任务恰恰相反。 这些任务只是因为大小而昂贵。 处理时间几乎是微不足道的，但数据传输的成本很高，例如图像裁剪、过滤数组、浅拷贝等。

在我的具体情况下，将任务卸载到后台主要属于 **负和效率**。 如果我们谈论移动兆字节的数据来执行 50 毫秒的操作，将其卸载到后台没有任何好处。

也许我们可以这样想：

总时间 = 序列化成本
      + 过境
      + 背景处理时间
      + 反序列化成本
    

看看这个，如果**“背景处理时间”**是您操作中最主要的任务，那么隔离是明显的赢家。 但是，如果序列化加上反序列化加上 Transit 超过了这个成本，那么就没有必要隔离东西了。

如果您无法确定任务是 CPU 繁重还是数据繁重，那么测量它肯定不会有什么坏处，例如，使用 [`performance.mark()`](https://developer.mozilla.org/en-US/docs/Web/API/Performance/mark) 和 [`performance.measure()`](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceMeasure) 周围的 `postMessage` 调用来分析传输成本。
