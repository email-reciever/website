说实话，我错过了 CSS Container Queries 首次发布的新闻。当我终于听说它时，我的第一反应是，*“我已经有媒体查询了，为什么还需要这个？”*

我并不为这种反应感到骄傲，但知道我不是唯一一个有这种想法的人让我感到安心。事实上，我们这种人有很多。

让我感到困惑的是，容器查询并不是新功能，因为目前它已经有大约 [94% 的浏览器支持](https://caniuse.com/css-container-queries)。然而，实际使用它的人却很少。根据 [CSS 现状](https://2025.stateofcss.com/en-US/features/) 调查，86% 的开发人员知道容器查询，但只有 41.4% 的人实际使用它。调查可能存在偏见，并不能完全代表我们整个领域，但这份调查绝对是我们目前最好的指标。

[Kevin Powell 也讨论了这个问题](http://youtu.be/4IBXIFe2CKA?si=2g3869tmp0yLOYz_\&t=297) 在 SmashingConf Amsterdam 2026 上：**容器查询的采用率非常糟糕**。而这对我来说很奇怪，因为我知道组件能够适应其外部容器的大小这一功能 [多年来一直是许多 CSS 愿望清单中的首选](https://css-tricks.com/2019-css-wishlist/)。

我并不特别关心有多少人正在使用容器查询，而是关心他们 *如何* 使用它们。我不能代表所有人，但从我所看到的内容来看 —— 包括我自己的早期尝试 —— 我们中的很多人都在以 *错误* 的方式使用它们。

归根结底，错误的使用归结为我学习容器查询时的相同印象：**它们乍一看绝对就像媒体查询**。由于它们看起来相似，因此很容易假设它们具有相似的目的和工作方式。

但事实并非如此。

**注意**: 在这篇文章中，我主要关注使用容器 *尺寸* 查询，即一种响应式设计技术，用于响应特定容器的大小。还有一种容器 *样式* 查询，它响应容器的计算样式（在本文写作时仍处于实验阶段）。您可以在 [Juan Diego 的 Smashing Magazine 文章](https://www.smashingmagazine.com/2024/06/what-are-css-container-style-queries-good-for/) 中了解更多关于它们的可能用例。

媒体查询向外看

视口是一个代理。它一直都是。媒体查询让我们产生了这样的幻觉：屏幕宽度 alone 就能决定响应式应用如何适应环境。

问问自己：当你写 `@media` 时，你在问浏览器什么？

```text
@media (min-width: 1024px) {
  .card {
    display: flex;
  }
```

我，像大多数开发者一样，在问浏览器：*屏幕当前的宽度是多少？* 就是这样。

媒体查询很好地回答了这个问题，但当这个 `.card` 组件被放在一个 `300px` 宽的网格单元中，而屏幕宽度为 `1920px` 的桌面屏幕上会发生什么？

媒体查询并不关心；它只是做自己的工作。视口仍然是 `1920px`，所以 `min-width: 1024px` 生效，并应用匹配的查询样式，即使卡片只有 `300px` 的空间可用。最终，卡片中的所有内容都会变得变形、溢出或拥挤。

> “媒体查询很愚笨。不愚笨是指概念，而是它们不知道的太多。事实上，大多数人认为它们知道的比实际上更多。”
>
> — [Kevin Powell](https://css-tricks.com/smart-layouts-with-container-queries/#:~:text=Because%20of%20how,than%20they%20do.)

人们常常认为响应式设计纯粹是一个用于更新整个页面布局的系统，例如从大屏幕上的两列变为小屏幕上的单列。

容器查询向内看

容器查询比这更智能。它们使响应式布局更依赖于组件内部发生的事情，而不是依赖于外部上下文，这个外部上下文对组件的内容没有任何了解。它更像：*“在这个特定的位置，我现在有多少可用空间？”*

这里是我们在上一节中看到的同一个卡片代码示例，但使用了容器查询：

```text
.card-wrapper {
  container-name: card;
  container-type: inline-size;
}

@container card (min-width: 450px) {
  .card {
    display: flex;
    flex-direction: row;
  }
}
```

这改变了一切。卡片并不受视口的影响；它唯一关心的是 `.card` 组件的父容器是否至少有 `450px` 的内联（即，左至右书写模式下的水平）空间。如果该条件为真，组件将变为水平布局；如果不为真，它将保持默认的 `block` 显示。

![](https://files.smashing.media/articles/stop-treating-css-container-queries-traditional-media-queries/1-normal-state-vs-wrapped-state.jpg)

逻辑如下：

1. 当有足够的空间时，两个项目（`.flex-item`）并排排列，每个项目的宽度恰好是父容器宽度的一半。
2. 当空间有限时，第二个项目将换行到下一行。
3. 由于每个项目都启用了 `flex-grow`，换行的项目将拉伸以填充父容器的大部分宽度。
4. 如果项目本身也是一个容器，它将检测到突然的宽度扩张并触发。

```text
/* The flex parent */
.flex-layout {
  display: flex;
  flex-wrap: wrap;
}

/* Register a flex item as a container */
.flex-item {
  container-type: inline-size;
  flex: 1 1 390px; /* Grow to fill space, wrap at 390px */
}

/* Default Card Styles (narrow / side-by-side) */
.card {
  display: flex;
  flex-direction: column;
  background: #f4f4f4;
}

/* Once there's enough room for a full row */
@container (min-width: 600px) {
  .card {
    flex-direction: row;
    align-items: center;
    background: #e2f0d9;
  }
}
```

这有效。随着父容器的大小缩小，卡片换行到两行，卡片项目扩张，容器查询触发，并应用必要的样式。

![](https://files.smashing.media/articles/stop-treating-css-container-queries-traditional-media-queries/2-reusable-component.jpg)

结论

归根结底，容器查询看起来与媒体查询非常相似，主要是因为人们对其更熟悉。 它们并不是完全“新”的东西，但它们的理解和采用程度却远远低于媒体查询。 但是媒体查询也有自己的局限性；否则，我们就不会需要容器查询来填补这些空白。

我们拥有的是一种更有效的功能，用于检测特定组件的上下文何时发生变化，以及根据其内容调整样式的方法，这正是当该组件可以存在于多个上下文时应该做的事情。
