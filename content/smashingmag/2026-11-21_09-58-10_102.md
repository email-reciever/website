尽管浏览器支持广泛，但容器查询仍令人惊讶地未被使用，并且经常被误解。 让我们看看它们与媒体查询有何不同，何时到达每个查询，以及容器查询如何帮助可重用组件自然地响应它们出现的上下文。

老实说，当 CSS 集装箱查询首次发货时，我错过了这个消息。 当我终于听说它时，我的第一个想法是，“当媒体查询已经存在时，我为什么需要这个？”_

我并不为这种反应感到自豪，我知道我现在所知道的，但知道我并不孤单，我感到很欣慰。 事实上，我们有很多人在那里。

令我困惑的是，容器查询不是一个新功能，因为它目前位于 [94% browser support](https://caniuse.com/css-container-queries) 左右。 然而，真正使用它的人很少。 根据 [State of CSS](https://2025.stateofcss.com/en-US/features/) 调查，86% 的开发人员知道容器查询，但只有 41.4% 的开发人员实际使用它们。 调查可能是有偏见的，不能完全代表我们的整个领域，但这肯定是我们所拥有的最好的指标。

[Kevin Powell also talked about this](http://youtu.be/4IBXIFe2CKA?si=2g3869tmp0yLOYz_&t=297) 在 SmashingConf Amsterdam 2026 上：**Container 查询采用非常糟糕。** 这对我来说太奇怪了，因为知道组件多年来能够适应其外部容器的大小 [has been at the top of so many CSS wishlists](https://css-tricks.com/2019-css-wishlist/)。

我对有多少人使用容器查询并不特别感兴趣，就像他们使用的_how_一样。 我不能解释每个人，但从我所看到的——包括在我自己的早期尝试中——我们中的许多人都在使用它们_wrong_。

最重要的是，不正确的使用归结为我在了解它们时的相同印象：**乍一看，它们绝对看起来像媒体查询**。 而且由于它们看起来相似，因此很容易假设它们具有相似的目的并以相同的方式工作。

他们没有。

**注意**：我应该预先声明我在本文中关注的是使用容器_size_查询，即响应特定容器大小的响应设计技术。 还有容器 _style_ 查询响应容器的计算样式（并且在撰写本文时是实验性的）。 您可以在 [Juan Diego’s piece here on Smashing Magazine](https://www.smashingmagazine.com/2024/06/what-are-css-container-style-queries-good-for/) 中了解他检查可能用例的内容。

媒体查询向外看
---------------------------

视口是代理。 一直都是。 媒体查询让我们有一种错觉，即屏幕宽度仅负责响应应用程序如何适应其环境。

问问自己：当你写`@media`时，你在问浏览器什么？

@media（最小宽度：1024px）{
.卡{
显示：弹性；
}
    

我和大多数开发人员一样，在问浏览器：_现在屏幕有多宽？_就是这样。

媒体查询很好地回答了这一点，但是当这个 `.card` 组件放置在 `1920px` 桌面屏幕上 `300px` 宽的网格单元中会发生什么？

媒体查询不在乎； 它完成了它的工作。 视口仍然 `1920px`，因此 `min-width: 1024px` 会触发并应用匹配的查询样式，即使该卡片只有 `300px` 的空间可以使用。 最终，卡片中的所有内容都会变形、溢出或抽筋。

> “媒体查询是愚蠢的。就概念而言，不是愚蠢的，而是愚蠢的，因为他们不太了解。事实上，大多数人认为他们比他们知道的更多。”
>   
> — [Kevin Powell](https://css-tricks.com/smart-layouts-with-container-queries/#:~:text=Because%20of%20how,than%20they%20do.)

通常将响应式设计视为更新完整页面布局的系统，例如从大屏幕上的两列到小屏幕上的单个列。

容器查询向内看
-----------------------------

容器查询比这更智能。 它们使响应式布局更依赖于**内部**组件而不是对组件内容没有洞察力的外部上下文。 更像是：_“我现在在这个特定的地方有多少可用空间？”_

这是我们在上一节中看到的相同的卡片代码示例，但使用了容器查询：

.卡片包装器 {
容器名称：卡片；
容器类型：内联大小；
}
    
@Container卡（最小宽度：450像素）{
.卡{
显示：弹性；
弯曲方向：行；
}
}
    

这改变了一切。 该卡不受视口的影响； 它唯一的担忧是 `.card` 组件的父包装器是否具有至少 `450px` 的内联（即从左到右书写模式中的水平）空间。 如果该条件为真，则组件将呈水平方向； 如果没有，它会进入其默认的 `block` 显示。

“宏观”布局与 “微”布局
---------------------------------

区分 `@media` 和 `@container` 查询的一个非常有趣的方法是 **Layout 类型**。

媒体查询是针对“宏”布局的； 他们向外看。 诸如页面结构、跨越窗口的页眉、主网格布局、系统偏好设置（`prefers-color-scheme`）、设备功能（触摸屏）之类的东西。 你知道，任何与整个页面结构基本相同的东西。

我想说，容器查询是用于“微型”布局，即大多数存在于“宏”布局中的东西。 当任何内容需要响应地适应分配的任何空间时，我们会使用它们。 想到的组件是卡片、小部件、表单、导航等。

换句话说，想想 **“页面布局”与“组件布局”**。

一个元素不应该仅仅因为宽度超过像`768px`那样的抽象宽度阈值而神奇地变成“平板大小”。 相反，它应该在有足够的空间时切换布局，无论是在移动视口还是在桌面侧边栏中。

示例：组件内的流体排版
------------------------------------------

响应式排版是我们许多人依赖媒体查询的一个很好的例子。 媒体查询带有自己的 CSS 单元（例如 `vw`、`vh` 等）的事实，这些单元相对于视口大小，这使得媒体查询看起来非常适合根据用户的屏幕大小调整字体大小。

.卡片标题{
字体大小：夹子（100%，1rem + 2vw，24px）；
}
    

直到将同一组件移动到不同的上下文中，例如侧边栏，视口完全无关紧要。 现在，因为我们将响应性与错误的参考点联系起来，因此缩放的排版可能会变得太大或太小。

容器查询带有 [their very own units](https://www.w3.org/TR/css-contain-3/#container-lengths) — `cqi`、`cqw`、`cqb` 等——我们可以通过将这些单元与 CSS `clamp()` 函数结合使用来进一步获取响应组件，将其用于 [fluid typography](https://www.smashingmagazine.com/2022/01/modern-fluid-typography-css-clamp/) 与组件而不是视口进行缩放：

    
.卡片标题{
字体大小：夹子（1rem，.5rem + 3cqi，2rem）；
}
    

请参阅 [Vayo](https://codepen.io/vayospot) 的笔 \[流体排版 \[分叉\]\](https://codepen.io/smashingmag/pen/01a0a73f-1a44-750c-8b40-9b0ab774d981)。

请参阅 [Vayo](https://codepen.io/vayospot) 的笔 [流体排版 \[forked\]](https://codepen.io/smashingmag/pen/01a0a73f-1a44-750c-8b40-9b0ab774d981)。

有了这一点，整个代码就被独立到该元素的特定容器中。

示例：Flexbox 包装检测
------------------------------

有趣的是，容器查询可以在某种程度上检测组件内部布局的状态。 它不是防弹的，但它也是媒体查询不能做的事情，因为它们只观察外部浏览器窗口，并且在结构上对内部布局事件视而不见，例如，弹性项目包装到新行中。 让我们戳一下。

Flexbox 在包装内容（`flex-wrap: wrap`）方面非常出色，当 Flex 容器用完空间以将它们装入单行时，Flex 项目可以自动包装到新行中。 但CSS本身无法判断何时发生这种包装。 没有像 `:wrapped` 伪类或媒体查询之类的东西可以让我们到达那里。

媒体查询仅观察浏览器窗口，因为它们看不到内部更改。 这几乎就是 Flex 包装的内容：项目本身的宽度状态更改。

例如，如果您有一个与 Flexbox 对齐的水平菜单，并且您希望这些项目仅在包装时重新样式化，那么您将处于 JavaScript 领域，使用 `ResizeObserver` 来获取该信息。 但是，当我们在 flex 项目中嵌套容器查询时，我们可以想出一个解决方法来获得我们需要的东西，而无需 JavaScript，[thanks to this technique I learned from Kevin Powell](https://www.youtube.com/watch?v=9XKWnvpdSlU)。 当我们查询容器的内联大小时，核心思想是允许 flex 项目 `flex-grow: 1`。

请参阅 [Vayo](https://codepen.io/vayospot) 的笔 \[流体排版 \[分叉\]\](https://codepen.io/smashingmag/pen/01a0a73f-1a44-750c-8b40-9b0ab774d981)。

请参阅 [Vayo](https://codepen.io/vayospot) 的笔 [流体排版 \[forked\]](https://codepen.io/smashingmag/pen/01a0a73f-1a44-750c-8b40-9b0ab774d981)。

[![Normal and wrapped states of two responsive items.](https://res.cloudinary.com/indysigner/image/fetch/f_auto,q_80/w_400/https://files.smashing.media/articles/stop-treating-css-container-queries-traditional-media-queries/1-normal-state-vs-wrapped-state.jpg)](https://files.smashing.media/articles/stop-treating-css-container-queries-traditional-media-queries/1-normal-state-vs-wrapped-state.jpg)

（[Large preview](https://files.smashing.media/articles/stop-treating-css-container-queries-traditional-media-queries/1-normal-state-vs-wrapped-state.jpg)）

逻辑是这样的：

1.  当有足够的空间时，两个项目 (`.flex-item`) 并排坐着，每个项目都正好是父容器宽度的一半。
2.  当空间有限时，第二项将包裹到下一行。
3.  因为 `flex-grow` 在每个项目上都处于活动状态，因此包装的项目会拉伸以填充父级的大部分宽度。
4.  如果该项目是容器本身，它会检测到突然的宽度膨胀和火灾。

/* 灵活的父母 */
.flex-布局 {
显示：弹性；
弹性包装：包裹；
}
    
/* 将弹性项目注册为容器 */
.flex-item {
容器类型：内联大小；
弯曲：1 1 390 像素； /* 增长到填充空间，以 390px 包裹 */
}
    
/* 默认卡片样式（窄/并排） */
.卡{
显示：弹性；
弯曲方向：列；
背景：#f4f4f4；
}
    
/* 一旦有足够的空间容纳整排 */
@Container（最小宽度：600px）{
.卡{
弯曲方向：行；
对齐项目：中心；
背景：#e2f0d9；
}
}
    

这工作。 随着父大小缩小，卡片包装到两行，卡片项目会展开，容器查询触发，并应用必要的样式。

容器查询确实有副作用
------------------------------------

与所有事物一样，容器查询会带来一些副作用或警告，您将需要在触摸它们之前注意它们。

### 1\ 容器需要额外的包装器

容器查询需要类似于父子关系的东西才能按预期运行。 假设我们有这个标记：

    <div class="card">
<div class="card-content">...</div>
    </div>
    

我们实际上无法查询 `.card` 组件以调整 `.card-content`，如下所示：

/* 不起作用 */
.卡{
容器名称：卡片；
容器类型：内联大小；
}
    
@Container卡（最小宽度：400像素）{
.卡{
显示：弹性；
}
}
    

这不起作用，因为容器无法查询自己。 在最后一个示例中，我们正在查询 `card` 容器，然后尝试根据其大小调整该容器的显示。 这是一个无限循环。

相反，我们需要一个额外的包装器，使 `.card` 成为容器的后代：

    <div class="cards">
      <div class="card">
<div class="card-content">...</div>
      </div>
    </div>
    

从那里，我们可以查询 `.cards` 容器并相应地调整 `.card` 布局：

.卡片{
容器名称：卡片；
容器类型：内联大小；
}
    
@Container卡（最小宽度：400像素）{
.卡{
显示：弹性；
}
}
    

在媒体查询中，这并不重要，因为 `@media` 不关心您在块内设置哪个元素。 它唯一关心的是视口，它始终可用。 因此，您可以在任何元素上放置一个条件并收工。

### 2\。 查询容器的 `size` 可能会折叠您的布局

当查询容器的 `size`（即其块或垂直大小）而不是 `inline-size` 时，会发生这种情况：

/* 即使里面有内容，它也会折叠到 0px */
.英雄横幅{
容器类型：尺寸；
}
    

为什么？ 因为浏览器在不查看其子级的情况下计算容器的尺寸。 如果我们不给 `.hero-banner` 一个明确的 `height`（或 `min-height` 或 `aspect-ratio`），浏览器会将高度设置为 `0px`。

出于这个原因，通常最好通过 `inline-size` 来查询容器。 也就是说，除非您真的需要查询容器的块大小。

媒体查询不受此影响，因为它们对待高度的方式与 `@media (min-height: ...)` 相同，即询问视口并继续前进。

### 3\ 查询无法接受自定义属性

另一个容器查询限制：我们无法针对自定义属性值进行查询：

:root {
--breakpoint-lg：1600px；
}
    
/* 不起作用 */
@Container (min-width: var(--breakpoint-lg)) {
/* ... */
}
    

这是因为自定义属性取决于向下层叠 DOM 树的值。 依赖自定义属性的容器查询可能会更改相同的自定义属性。 它很快就会变得复杂：

:root {
--breakpoint-lg：1600px；
}
    
/* 不起作用 */
@Container 卡 (min-width: var(--breakpoint-lg)) {
.卡{
--breakpoint-lg：1000px；
}
}
    

何时访问媒体和容器查询
-------------------------------------------

我认为任何项目都不应该批发使用 `@container` 而不是 `@media`。 媒体查询在响应式布局中仍然起着重要作用。 这是关于理解关注点的分离。

当组件在多个布局上下文中使用时，我倾向于使用容器查询。 例如，`.card` 元素可以存在于全宽网格或较窄的侧边栏中。 如果是这种情况，那么我们将希望组件的内容确定何时调整，而不是查看外部视口的媒体查询。

同样，当组件仅存在于页面级别时，我会访问媒体查询。 这将是一个总是位于页面顶部的主导航。 它直接受视口大小的影响，这意味着当导航需要调整时，视口是可靠的参考。 同样，这一切都与“宏”布局与“微”布局有关。

总结
-----------

归根结底，容器查询看起来与媒体查询非常相似的核心原因只是熟悉度。 它们并不完全是“新的”，但与媒体查询相比，它们的理解和采用率要低得多。 但媒体查询有很多自己的局限性； 否则，我们不需要容器查询来填补这些空白。

我们拥有的是一个更有效的功能，用于检测特定组件的上下文何时发生变化，以及根据其内容调整样式的方法，因为当该组件可以存在于多个上下文中时应该如此。
