当前端开发人员和 UX 工程师的任务是构建一个感觉触觉、有弹性或破坏性的 Web 界面时，行业的本能几乎总是相同的：使用物理引擎。 Matter.js、Cannon.js 或自定义 WebGL 解决方案等框架已成为创建身临其境的游戏化网站的黄金标准。

当我们 [Isadora Agency](https://isadoradigitalagency.com/) 的团队着手建立压力释放时，一种数字缓解压力的玩具，旨在让精疲力竭的创意人员粉碎、拉伸和扭曲动画 UI 角色，我们最初探索了这条路线。 目标是建立一个**高度触觉的体验**，每次点击都会产生令人满意的、柔软的反应。

但是当我们开始原型制作时，我们意识到了一些重要的事情：物理引擎会产生合理的运动，但在我们的例子中，动画师产生了**意向运动**。

我们不需要我们的角色像逼真的橡皮球一样在画布周围不受控制地弹跳。 我们需要他们以非常具体、高度设计的方式做出反应。 所以，我们完全放弃了物理引擎。

在本文中，我们将分解如何构建一个实时的压力缓解挤压玩具**没有单一的 WebGL 或 Matter.js**，完全依赖于程序化的 Lottie 状态控制、DOM 操作和基于距离的数学。

设计要求：故意动感
-----------------------------------------

我们对 _stress release_ 的核心要求是 **绝对确定性控制**。 我们的动画师制作了定制的 `.json` Lottie 文件，需要精确的逐帧排序。

例如，我们的“Mega Squeeze”反应需要精确的 181 帧构建，然后是特定的释放序列。 为了纪念这种设计，我们需要一种不会用算法近似覆盖动画师制作的关键帧的架构。

点击反馈循环越紧（单击 → 挤压 → 分数），您就越需要确定性帧控制。 通过使用 Lottie 的本机 API 选择编程状态控制，我们确保交互层作为动画层的完美触发器。

创建触觉反馈：将 DOM 元素映射到 Lottie 状态
------------------------------------------------------------

因为我们的架构依赖于Lottie和标准的DOM，所以渲染由Lottie Runtime直接处理，它在内部以SVG的形式播放基于JSON的矢量动画。 我们通过 id 和 css 类直接选择元素，使用 lottie 动画片段、css 变换和点击事件数学的组合来驱动它们的行为。

为了在击中角色时获得非常令人满意的“触觉”，我们使用了**径向输入映射**。 第一步是将来自页面坐标的点击转换为角色的本地坐标空间。

每次点击都针对角色的中心点进行测量，然后转化为分数、反馈强度和爆炸位置：

// 自己的坐标空间中的字符中心点
var x_center = parsefloat($("#playchar").width() / 2);
var y_center = parsefloat($("#playchar").height() / 2);
    
// 单击相对于角色左上角的位置
var 偏移量 = $("#playchar").offset(); // 文档相对位置
var x = parsefloat(e.pagex - offset.left);
var y = parsefloat(e.pagey - offset.top);
    
// 从中心到点击点的向量
var a = parsefloat(x - x_center);
var b = parsefloat(y - y_center);
    

然后我们使用毕达哥拉斯定理计算来自点击中心的直线距离：

var 距离 = math.hypot(a, b);
    

这个单一的数字驱动一切：得分、反馈强度和爆炸动画出现的位置：

结果是一个同心区域系统——一个完美的评分圆环围绕角色的中心，类似于飞镖。 Lottie SVG 的视觉复杂性与命中检测完全无关； 命中框始终是一个干净的圆圈。 至关重要的是，爆炸洛蒂动画被重新定位到 (a, b) — 用于评分的相同向量，因此它总是显示在玩家点击的位置。 这种空间准确性完全通过数学和 DOM 定位创造了触觉“我击中了那个”_ 感觉。

交互处理：控制叙事
--------------------------------------------

由于体验使用了 DOM 管理的 SVG 元素，因此可以直接通过本地事件侦听器处理桌面点击和移动点击。 这避免了额外的光线投射或坐标重新映射层，同时保持交互模型与动画的渲染方式对齐。

由于游戏需要在特定点进行视觉反应，因此 Lottie 通过其动画曲线在内部处理所有挤压和弹跳的感觉。 每个角色都有一组定义为帧范围的动画部分（空闲循环、反应帧和结束状态）。 当点击落地时，我们会直接跳到与当前游戏状态匹配的确切段：

// 定义为每个字符的帧范围的动画部分
常量 play_segments = [{
小麦：0，
部分：{
空闲：[0, 40], // 循环空闲状态
Squeeze1: [41, 80], // 轻反应
Squeeze2：[81, 120], // 中等反应
Squeeze3: [121, 160], // 剧烈反应
},
PlayOrder: ["squeeze1", "squeeze2", "squeeze3"],
（161、200）
}]；
    

每次点击时，我们都会通过播放顺序并触发下一个部分：

函数 stepanim() {
让 p = play_segments[0];
让 i = p["playorder"][curr_order_play];
让 PlayNow = p["部分"][i];
    
playchar.stop(); // 立即停止当前段
playchar.loop = 假； // 无循环 - 播放一次并停止
playchar.playsegments(PlayNow, true); // 跳转到精确帧，立即强制
    
curr_order_play++；
canplayAnim = 0； // 锁定进一步的点击中动画
    
if (curr_order_play > p["playOrder"].length - 1) {
curr_order_play = 0; // 循环回到序列的开始
}
}
    

当段完成时，控制返回到空闲循环：

playchar.oncomplete = 函数（） {
CanPlayAnim = 1； // 再次解锁点击
如果 (!playend) playIdleState();
};

}

DOM 元素的响应优势
------------------------------------

我们的架构决策的另一个主要因素是**响应行为**。 因为我们在 DOM 中构建了 _stress release_，所以我们绕过了跨不同设备的缩放边界框和冲突向量的复杂性。

我们完全通过 **css 变量**处理响应调整大小。 通过在每个调整大小上重新计算 CSS 自定义属性，布局只是对更新后的变量做出反应，Lottie SVG 在容器中自然扩展而不会丢失其状态：

常量应用高度 = () => {
const doc = document.documentElement;
doc.style.setProperty("--doc-height", `${window.innerHeight}px`);
doc.style.setProperty("--doc-width", `${doc.clientWidth}px`);
};
window.addEventListener("调整大小", AppHeight);
AppHeight(); // 立即在init上运行
    

移动性能优化：Lottie的成本
-----------------------------------------------

虽然这种架构给了我们对艺术方向的完全控制，但它带来了一个不同的挑战：**文件大小**。

Lottie JSON 文件可能很重。 我们有 21 种不同的角色动画，以及多个需要加载的爆炸变体。 为确保体验保持流畅——尤其是在移动设备上——我们实施了一些激进的优化策略：

*   **连接监控**
我们使用 `performance.now()` 跟踪初始资产加载时间，以检测加载时间超过 5 秒时的缓慢连接和标志。
*   **顺序资产加载**
我们不是同时初始化所有 21 个字符动画，而是使用 await 成对加载它们，仅在每对完成时才进行。 这可以防止同时网络请求的爆发和渲染工作阻塞低端设备上的浏览器。
*   **攻击性内存管理**
我们没有将我们的沉重爆炸动画保留在记忆中，而是在飞行中摧毁和重新创建它们。 这将很小的实例化成本换取更低的空闲内存占用空间。
*   **动态质量降低**
质量降低是在每个货架字符加载后立即应用的单个 API 调用。 关键是根据角色在场景中的角色应用不同的质量级别：

结论：为设计选择合适的技术
----------------------------------------------

在确定游戏化 Web 体验的堆栈时，让设计要求决定技术至关重要。
