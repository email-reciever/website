想象这样一种情况：你刚刚发布了一个版本，所有的单元测试都通过了，仪表盘都是绿色的。你坐回去放松，但突然你的电话开始响个不停：生产环境出了问题。

Cloudflare DNS 团队亲身经历过这种情况。在服务发布 DNS 记录到边缘网络的一个版本中，一个调度 bug 导致一些记录更改几个小时都没有发布。服务保持正常运行和健康，但新的主机名解析速度慢，证书无法颁发，直到 bug 被解决。

DNS 故障难以捕捉，因为它们很慢，分布在网络中，并且只对某些区域产生影响。我们需要找到一种方法来测试 DNS，就像客户体验到的那样：不断地，从每个数据中心，并且针对生产环境。

对于我们来说，答案是扩展 Flamingo，我们已经在使用的端到端测试框架，每天对 Cloudflare 的边缘网络运行数百万个测试。这篇文章介绍了 Flamingo 的模块化设计如何让我们添加 DNS 支持，我们如何测量传播情况，以及这些测量结果如何决定一个版本是否发布或回滚。

## 一个简短的背景介绍

在 Cloudflare，我们痴迷于提高客户的性能和安全性。确保我们的代码不断被测试，无论是大规模测试还是在真实的 Cloudflare 边缘环境中测试，对于我们来说都是至关重要的。这也是我们创建一个叫 Flamingo 的工具的原因之一：测量我们的生产环境的行为，并确保较低层级环境中的代码表现如预期。

我们已经 [写过](https://blog.cloudflare.com/20-percent-internet-upgrade/#step-2-testing-and-automated-rollouts) 一些关于这个工具在升级我们的 CDN 栈时的使用方法。然而，这只是我们内部使用 Flamingo 的一个小部分。Flamingo 的一个特点是其模块化的架构，能够让团队扩展工具的功能以支持其他网络协议。在我们的例子中，我们希望利用这些模块化的能力来测试 DNS。

## 什么是 Flamingo？

测试很困难。当你有一个广泛分布的系统时，测试的难度会更大。有很多复杂的路径供请求选择，并且每个网络请求都必须经过多个系统才能到达源头。单元测试 alone是不够的，我们需要对真实系统进行持续的自动化测试，并测量这些请求的结果，以便对服务的健康状况做出明智的决定。

进入 Flamingo 的世界。最初，Flamingo 是围绕复杂的多步骤 HTTP 测试构建的，其功能和范围随着时间的推移而大大增加。Flamingo 从底层就考虑到了 Cloudflare 的基础设施，我们构建了控制平面和调度器，以便团队可以针对特定的环境、数据中心或金属设备的百分比。我们需要将其集成到自定义的报告、指标和分析工具中。此外，它需要是一个具有可预测性能的工具，并能够在资源受限的环境中的裸机服务器上运行良好。

### 被喜爱的体验

当我们构建内部工具时，我们努力创造一个愉悦的开发者体验。内部工具应该尽可能容易使用，同时也要足够强大，以处理超过80%的所有用例。并且，为了使新的边缘接受测试框架成功，它需要以一种方式构建，这样可以强制团队遵循共同的指南，并在稳定、可扩展、管理复杂性的环境中构建可重用的脚本。

有一件不愉快的事情是调试测试。如果您允许用户使用传统的编程语言编写测试，当他们的测试失败时，他们需要同时调试被测试的上游系统和测试本身。这就是为什么我们构建了 Flamingo 使用一个自定义的领域特定语言（DSL），它由一个简单的设置-请求-响应格式组成。

例如，让我们假设我们要确保将所有未加密的流量重定向到其加密的对应项。

```text
TEST test-redirect
SET $hostname www.cloudflare.com

GET "http://$(hostname)/"

ASSERT STATUS IS 301
ASSERT HEADER Location IS "https://$(hostname)/"
```

这里我们可以看到 DSL 的强大之处。仅用五行代码，我们就可以编写出一个可以在 Cloudflare 边缘运行并扩展到每分钟数千个请求的脚本。我们可以将这从数百万个数据点生成的数据转化为一个图表，定义我们的服务在现实世界中的实际性能。

从上面的 setup-request-response 测试格式出发，并稍作修改，我们可以将 Flamingo 用于不仅仅是 HTTP 测试。我们不再将中间步骤视为请求，而是将其视为一个 **操作**。现在，我们已经将系统从仅能发送 HTTP 请求的东西转变为可以执行我们想要测量结果的任何操作的东西。

在 Flamingo 中，我们将这些称为 **模块**，并投入了大量精力使其尽可能容易被任何人编写。Flamingo 是用 Rust 编写的，这得益于其一致的性能特征和强大的类型系统。特别是类型系统使得这种模块化成为可能，通过允许我们在 Flamingo 操作运行器中使用强类型的枚举作为输入和输出：

```text
pub enum Action {
  Query {
    method: String,
    url: Expression,
    parameters: Vec<http::QueryParameters>,
  },
  DnsQuery {
    query_name: Expression,
    query_type: Expression,
    parameters: Vec<dns::DnsQueryParameters>,
  },
}

pub enum ActionOutput {
  Http(http::FetchResponse),
  Dns(dns::QueryResponse),
}

pub type ActionHandlerFunction = Arc<
  dyn Fn(
      Action,
      Arc<Ctx>,
      InterpreterConfig,
    )
      -> BoxFuture<'static, Result<ActionOutput>>
    + Send
    + Sync
    + 'static,
>;

pub type ActionHandlerLUT = Arc<
  dyn Fn(&Action) -> ActionHandlerFunction
    + Send
    + Sync
    + 'static,
>;
```

我们这里所做的就是将执行一个动作（在这种情况下是一个 HTTP 请求）的逻辑解耦到一个动态调度的函数中，我们可以独立于其他动作来调用它。这使得测试调度和资源管理等事情成为更高层次的操作，实现一个模块的人不需要担心这些。作者只需要专注于逻辑。

```text
pub async fn query(
  action: Action,
  ctx: Arc<Ctx>,
  cfg: InterpreterConfig,
) -> Result<ActionOutput> {
  let Action::Query {
    method,
    url,
    parameters,
  } = action
  else {
    bail!("Invalid action for module-http::query: {action:?}");
  };
  ...
}

pub async fn execute_module<F>(
  ctx: Arc<Ctx>,
  cfg: &InterpreterConfig,
  handler_lut: F,
) -> Result<ActionOutput>
where
  F: (Fn(&Action) -> ActionHandlerFunction),
{
  let func = handler_lut(action);
  let action_out = (func)(action.clone(), ctx.clone(), cfg.clone()).await?;
  ...
}
```

### 使用 Flamingo 探测 DNS

谚语说，当问题出现时，[总是 DNS 的问题](https://isitdns.com/)。像很多笑话一样，它背后总有一个真理的核心。DNS 是互联网中一个非常重要的部分，由于它依赖于一个复杂的相互连接的真理源网络，因此当一个小的错误发生时，很容易导致一连串的失败。

DNS 可能是一个特别难以预测的系统，因为它具有层次结构。当您更改 Cloudflare 区域的 DNS 记录时，例如，该记录需要传播到权威服务器，以便更新的记录被广泛使用。为了减少延迟，记录存储在物理上更近的缓存中。这些记录具有生存时间（TTL），它告诉本地 DNS 缓存在何时之前需要从权威服务器重新获取该记录。任何延迟都将影响像证书颁发和流量故障转移等对时间敏感的操作。

我们已经提到，我们构建了 Flamingo 以实现可扩展性。今天使用的第一个也是最有影响力的模块是专门为此用例构建的。我们的团队能够添加代码以扩展 Flamingo，以便我们不再发送 HTTP 请求，而是发送 DNS 查询。通过这样做，我们免费获得了其他一切。DNS 团队不需要担心管理新的探测服务。他们不需要将其集成到我们的报告管道中。所有事情都能正常工作。

为了探测 DNS，我们测量客户记录更改传播到权威名称服务器和公共解析器（1.1.1.1）的速度。该测试持续更新一个 TXT 记录的时间戳，并从每个数据中心查询三个权威名称服务器 IP 和 1.1.1.1，断言权威名称服务器在 90s 内和解析器在 600s 内的新鲜度。

```text
TEST test-propagation-delay-direct-108-162-193-62
MOD dns

SET $hostname "some.probe.domain"
SET $authNs 108.162.193.62:53 # amir.ns.cloudflare.com

QUERY $hostname TXT
TARGET $authNs

ASSERT DNS.RCODE IS NOERROR
ASSERT DNS.FLAGS CONTAINS AA
ASSERT DNS.ANSWERS[0] GT SUBTRACT(TIMESTAMP(), "90")
```

## 捕获错误（SLO 和稳定）

为了确保我们的多个系统按照预期运行，我们定义了服务级别目标（SLOs），用于观察诸如可用性或延迟等指标。SLOs 是某个指标的百分比，用于作为目标。此外，SLOs 通过服务级别指标（SLIs）进行测量，SLIs 是实际的一系列测量，专注于用户与系统交互时的端到端体验。

通过不断地向我们的生产系统发送合成 Flamingo 流量，我们可以开始使用这些信息来构建我们实际终端用户的体验图景 —— 并为我们的 SLO 提供这些数据。当合成流量遇到问题时，我们可以相当确信 Cloudflare 客户也遇到了问题，并相应地进行故障排除。

一旦我们拥有这些信息，就可以在发布服务时做出明智的决定。SLO 以错误预算和消耗率的形式运作。错误预算是服务愿意容忍的停机时间百分比，而消耗率是预算在任何给定时间的变化率。这使得自动化系统能够理解问题的严重性。例如，在三天内消耗 10% 的错误预算可能是某个长期运行的问题，虽然不紧急，但会影响客户，需要处理。但如果您在一小时内消耗 10% 的错误预算，则意味着发生了事件，如果不立即解决，客户影响将会很大。

使用这些数字，我们可以在部署时查看我们的 SLOs，并就服务的健康状况做出明智的决定。根据这些信息，我们可以告诉我们的发布系统 либо推广更改， либо将其回滚。

## 前进的道路

通过将 DNS 监控移至 Flamingo，我们创建了一个可以在 DNS 问题扩散到 Cloudflare 边缘之前主动检测它们的系统。如果 Flamingo 检测到特定金丝雀数据中心的传播延迟激增，我们可以在新软件版本影响整个互联网之前自动停止其发布。

DNS 只是 Flamingo 扩展的开始。我们目前有用于测试 TCP、UDP、WebSockets 等的模块。拥有快速测试和监控服务的工具使团队能够在无需人类不断监控的情况下安全地部署大规模更改。
