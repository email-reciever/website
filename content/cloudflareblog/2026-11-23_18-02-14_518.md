想象这样一种情况：你刚刚发布了一个版本。所有的单元测试都通过了，仪表盘也是绿色的。你坐回去放松，但突然你的手机开始不断响起：生产环境出了问题。

Cloudflare 的 DNS 团队亲身经历过这种情况。在发布一个将 DNS 记录发布到边缘的服务时，一个调度 bug 导致一些记录更改在几个小时内未被发布。服务保持正常运行和健康，但新的主机名解析速度很慢，直到 bug 被解决之前，证书无法被颁发。

DNS 故障难以捕捉，因为它们很慢，分布在网络中，并且只对某些区域产生影响。我们需要找到一种方法来测试 DNS，就像客户体验它一样：不断地，从每个数据中心，并且针对生产环境。

对于我们来说，答案是扩展 Flamingo，我们已经在使用的端到端测试框架，每天运行数百万个测试来针对 Cloudflare 的边缘。这篇文章介绍了 Flamingo 的模块化设计如何让我们添加 DNS 支持，我们如何测量传播情况，以及这些测量结果如何决定是否发布一个版本或将其回滚。

## 一个小背景

在 Cloudflare，我们痴迷于提高客户的性能和安全性。确保我们的代码不断被测试，无论是在大规模还是在真实的 Cloudflare 边缘环境中，对于我们的用户来说都是至关重要的。这就是为什么我们创建了一个叫 Flamingo 的工具：来衡量生产环境的行为，并确保较低层级环境中的代码表现如预期。

我们已经 [写过](https://blog.cloudflare.com/20-percent-internet-upgrade/#step-2-testing-and-automated-rollouts) 一些关于这个工具如何被用于升级我们的 CDN 栈的内容。然而，这只是我们内部使用 Flamingo 的一个小部分。Flamingo 的一个特点是其模块化的架构，允许团队扩展工具的能力以支持其他网络协议。在我们的例子中，我们希望利用这些模块化的能力来测试 DNS。

## 什么是 Flamingo？

测试很难。 当您有一个广泛分布的系统时，规模化测试更为困难。 请求有很多复杂的路径，并且每个网络请求必须经过多个系统才能到达源服务器。 单元测试alone是不够的。 我们需要对真实系统运行不断的自动化测试，并测量这些请求的结果，以便就服务的健康状况做出明智的决定。

进入 Flamingo 。最初，它围绕复杂的多步骤 HTTP 测试构建，其功能和范围多年来大大增加。 Flamingo 从底层开始就考虑了 Cloudflare 的基础设施。 我们构建了一个控制平面和调度器，允许团队针对特定的环境、数据中心或金属的百分比。 我们需要将其与自定义的报告、指标和分析工具集成。 此外，它需要是一个具有可预测性能的工具，并且能够在资源受限的环境中的裸机服务器上运行良好。

### 被愉悦

当我们构建像这样的内部工具时，我们努力创造一个愉快的开发者体验。内部工具应该尽可能地易于使用，同时也要足够强大，以处理超过80%的所有用例。并且，为了使新的边缘接受测试框架成功，它需要以一种方式构建，这种方式迫使团队遵循共同的指南，并在稳定、可扩展、管理复杂性的环境中构建可重用的脚本。

有一件事不是很愉快，那就是调试测试。如果你允许用户使用传统的编程语言编写测试，当他们的测试失败时，他们需要同时调试被测试的上游系统和测试本身。这就是为什么我们构建了 Flamingo 使用一种自定义的领域特定语言（DSL），它由一个简单的 setup-request-response 格式组成。

例如，假设我们想确保将所有未加密的流量重定向到其加密的对应项。

```text
TEST test-redirect
SET $hostname www.cloudflare.com

GET "http://$(hostname)/"

ASSERT STATUS IS 301
ASSERT HEADER Location IS "https://$(hostname)/"
```

这里我们可以看到 DSL 的强大之处。仅用五行代码，我们就可以编写一个可以在 Cloudflare 的边缘运行并扩展到每分钟处理数千个请求的脚本。我们可以将这从数百万个数据点生成的数据转换成一个图表，定义我们的服务在现实世界中实际的性能表现。

从上面的 setup-request-response 测试格式中借鉴并稍作修改，允许我们将 Flamingo 用于不仅仅是 HTTP 测试。我们可以将中间步骤从请求改为 **操作**。现在，我们已经将系统从仅仅发送 HTTP 请求的东西转变为可以执行我们想要测量结果的任何操作的东西。

在 Flamingo 中，我们将这些称为 **模块** ，并投入了大量精力使其尽可能容易被任何人编写。Flamingo 是用 Rust 编写的，因为其一致的性能特征和强大的类型系统。特别是类型系统使得这种模块化成为可能，通过允许我们在 Flamingo 操作运行器中使用强类型的枚举作为输入和输出：

```text
pub enum Action {
  Query {
    method: String,
    url: Expression,
    parameters: Vec<http::QueryParameters>,
  },
  DnsQuery {
    query_name: Expression,
    query_type: Expression,
    parameters: Vec<dns::DnsQueryParameters>,
  },
}

pub enum ActionOutput {
  Http(http::FetchResponse),
  Dns(dns::QueryResponse),
}

pub type ActionHandlerFunction = Arc<
  dyn Fn(
      Action,
      Arc<Ctx>,
      InterpreterConfig,
    )
      -> BoxFuture<'static, Result<ActionOutput>>
    + Send
    + Sync
    + 'static,
>;

pub type ActionHandlerLUT = Arc<
  dyn Fn(&Action) -> ActionHandlerFunction
    + Send
    + Sync
    + 'static,
>;
```

我们在这里所做的就是将执行某个操作（在这种情况下，是一个 HTTP 请求）的逻辑解耦到一个动态调度的函数中，我们可以独立于其他操作来调用它。这使得测试调度和资源管理等事情成为更高层次的操作，实现模块的人不需要担心这些。作者只需要专注于逻辑。

```text
pub async fn query(
  action: Action,
  ctx: Arc<Ctx>,
  cfg: InterpreterConfig,
) -> Result<ActionOutput> {
  let Action::Query {
    method,
    url,
    parameters,
  } = action
  else {
    bail!("Invalid action for module-http::query: {action:?}");
  };
  ...
}

pub async fn execute_module<F>(
  ctx: Arc<Ctx>,
  cfg: &InterpreterConfig,
  handler_lut: F,
) -> Result<ActionOutput>
where
  F: (Fn(&Action) -> ActionHandlerFunction),
{
  let func = handler_lut(action);
  let action_out = (func)(action.clone(), ctx.clone(), cfg.clone()).await?;
  ...
}
```

### 使用 Flamingo 探测 DNS

谚语说，当问题出现时，[总是 DNS 的问题](https://isitdns.com/)。像许多笑话一样，它背后总有一个真相的核心。DNS 是互联网的一个非常重要的部分，由于它依赖于一个复杂的相互关联的真相来源网络，因此一个小小的失误就可能导致一连串的故障。

DNS 可以是一个特别棘手的系统，因为其具有层次结构。当您更改 Cloudflare 区域的 DNS 记录时，例如，该记录需要被传播到权威服务器，以便更新的记录被广泛使用。为了减少延迟，记录被存储在物理上更近的缓存中。这些记录具有与之关联的生存时间（TTL），它告诉本地 DNS 缓存在需要从权威服务器重新获取该记录之前需要等待多长时间。任何延迟都将影响时间敏感的操作，例如证书颁发和流量故障转移。

我们已经提到，我们构建了 Flamingo 以实现可扩展性。今天使用的第一个也是最有影响力的模块专门为此用例构建。我们的团队能够添加代码以扩展 Flamingo，使其代替发送 HTTP 请求发送 DNS 查询。通过这样做，我们免费获得了其他一切。DNS 团队不需要担心管理新的探测服务，他们也不需要将其集成到我们的报告管道中。所有事情都正常工作。

为了探测 DNS，我们测量客户记录更改传播到权威命名服务器和公共解析器（1.1.1.1）的速度。测试持续更新一个 TXT 记录的时间戳，并从每个数据中心查询三个权威命名服务器 IP 和 1.1.1.1，断言在 90s（权威）和 600s（解析器）内的新鲜度。

```text
TEST test-propagation-delay-direct-108-162-193-62
MOD dns

SET $hostname "some.probe.domain"
SET $authNs 108.162.193.62:53 # amir.ns.cloudflare.com

QUERY $hostname TXT
TARGET $authNs

ASSERT DNS.RCODE IS NOERROR
ASSERT DNS.FLAGS CONTAINS AA
ASSERT DNS.ANSWERS[0] GT SUBTRACT(TIMESTAMP(), "90")
```

## 捕获 bug（SLO 和稳定）

为了确保我们的多个系统按照预期运行，我们定义了服务级别目标（SLOs），用于观察诸如可用性或延迟等指标。SLOs 是某个指标的百分比，用于作为目标。另外，SLOs 通过服务级别指标（SLIs）来衡量，SLIs 是实际的测量系列，专注于用户在与系统交互时的端到端体验。

通过不断地向我们的生产系统发送合成的 Flamingo 流量，我们可以开始使用这些信息来构建我们实际终端用户的体验图景 —— 并为我们的 SLOs 提供这些数据。当合成流量遇到问题时，我们可以相当肯定 Cloudflare 客户也遇到了问题，并据此进行故障排除。

一旦我们拥有这些信息，就可以在发布服务时做出明智的决定。SLOs 以错误预算和消耗率的形式运作。错误预算是服务愿意容忍的停机时间百分比，而消耗率是预算在任何给定时间的变化率。这允许自动系统理解问题的严重性。例如，在三天内消耗 10% 的错误预算可能是某个长期运行的问题，虽然不紧急，但会影响客户，需要处理。但如果您在一小时内消耗 10% 的错误预算，则意味着发生了事件，如果不立即解决，客户影响将会很大。

使用这些数字，我们可以在部署时查看我们的 SLOs，并就服务的健康状况做出明智的决定。根据这些信息，我们可以告诉我们的发布系统 либо推广更改， либо回滚。

## 前方的道路

通过将 DNS 监控移动到 Flamingo，我们创建了一个可以在 DNS 问题扩散到 Cloudflare 边缘的其他部分之前主动检测它们的系统。如果 Flamingo 检测到特定金丝雀数据中心的传播延迟激增，我们可以在新软件版本影响整个 Internet 之前自动停止其滚动发布。

DNS 只是 Flamingo 扩展的开始。我们目前有用于测试 TCP、UDP、WebSockets 和其他几个的模块。拥有快速测试和监控服务的工具使团队能够在不需要人类持续监控的情况下安全地部署大型更改。
