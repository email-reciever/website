2026 年 11 月 18 日，F5 和 Nginx.org 披露了 Nginx 中的十个漏洞。 其中五个由 Xint 研究团队详细介绍并以 **nginx2root** 的名称发布，是未经身份验证的攻击者可以用来使 nginx 工作人员崩溃的内存损坏缺陷，或者根据 Xint 的研究，在服务器上运行命令。 Xint 还发现了一个 Linux 内核错误，它将该立足点转换为主机上的 root，包括从 Docker 容器内部。 其他团队独立发现了两个 HTTP/2 错误：F5 还将 CVE-2026-123007 的 Rapid7、Wiz Research 和 Ikotas Labs 归功于 Metnir、Wiz Research 和 Palo Alto Networks 42 单元 CVE-2026-123633。

Nginx 是一个 HTTP Web 服务器，它还用作反向代理、内容缓存、负载均衡器、TCP/UDP 代理服务器和邮件代理服务器。 Nginx 运行着世界上很大一部分的 Web 服务器，所以这是一个补丁事件。 但是，如果您的 Nginx 服务器只能通过 Cloudflare 的代理访问，则攻击者无法访问最严重的这些错误的易受攻击的代码路径，从而在您更新服务器时为您提供保护。

这是 Cloudflare 的位置、保护覆盖的内容、停止的位置以及错误的工作方式。

## 短版

*   **Cloudflare 的 Edge 不受影响。** 处理我们边缘的客户流量的许多代理现在在 FL2 上运行，用 Rust 编写。 在披露之前，我们回顾了仍然在我们大量修改的 Nginx 分叉上构建的部分，并在泄露之前完成了在全球范围内完成相关代码路径的更新。 相同的版本修复了其他五个 Nginx CVE，包括 CVE-2026-118899，这是一个无限循环，同时通过 TLS 1.3 读取请求正文。
*   **Cloudflare 的 HTTP 代理背后的原点被 HTTP/2 和 HTTP/3 攻击屏蔽。** 对于代理主机名，Cloudflare 在我们的边缘终止每个客户端 HTTP/2 和 HTTP/3 连接，并打开与源的单独连接。 攻击者的帧永远不会到达你的nginx。
*   **解析器和邮件代理漏洞取决于特定配置。** Nginx 的许多配置不会受到攻击，但最安全的方法是更新您的安装或禁用功能。
*   **您仍然应该修补。** 更新到 nginx 1.30.7 或 1.31.9（或您的供应商的固定版本）并重新启动。 下面介绍的某些配置不受代理保护。

CVE-2026-123007 是最需要担心的一种。 它只需要打开 HTTP/2，这通常在 TLS 部署上启用，并且自 1.9.5 中提供 HTTP/2 支持以来，它一直在每个 Nginx 版本中。 Xint 针对 AWS、GCP 和 Azure 上的服务器在公共 Internet 上运行漏洞。 Xint于11月10日在披露前搜查了Shodan，并找到了5670万台匹配`product:nginx`的主机。 在报告版本的 1194 万份中，有 98.9% 下降到受影响范围内。 截至 11 月 19 日，Censys 的 [nginx2root exposure tracker](https://nginx2root.censys.com/) 统计了大约 880 万个服务，运行了一个可能受影响的版本，启用了 HTTP/2。 版本字符串并不能证明主机是易受攻击的，因为发行版可以修复，但曝光量很大。

同样的 Nginx 版本还修复了其他五个错误。 最严重的CVE-2026-118899是在Nginx 1.13.0及更高版本中读取TLS 1.3上的请求体时的无限循环，该循环允许未经身份验证的攻击者停止工作人员。

Linux 内核错误是 nginx2root 的第六部分。 xint 在内核的 sctp 发送路径中发现了一个 use-after-free，自 Linux 4.15 (2018) 以来存在：当发送操作等待时，它的 SCTP 关联可以移动到另一个套接字，等待的发送可以释放它。 已经以nginx工作者身份运行代码的攻击者可以使用它在主机上获取root，而xint是从docker容器中运行的nginx执行的。 许多发行版在第一次程序打开 SCTP 套接字时自动加载 SCTP 模块，因此从未使用 SCTP 的主机仍然可以公开。 截至 11 月 18 日，没有可用的内核修复程序，Xint 保留了详细信息，直到有一个。

截至 11 月 19 日，五个 nginx2root cves 都没有在 CISA 已知的利用漏洞目录中，我们还没有看到野外剥削的报道。 Xint 和 Wiz Research 尚未发布他们的漏洞利用。 Rapid7 发布了一个概念验证，它将其描述为仅适用于演示针对新启动的本地容器的攻击。 假“利用”也在 GitHub 上流传。

## 为什么 Cloudflare 的代理保护您的源

Nginx2Root 最危险的错误存在于 Nginx 如何解析和管理 HTTP/2 和 HTTP/3 连接。 要触发它们，攻击者必须将精心排序的协议帧流直接发送到 nginx 进程：数十亿 `WINDOW_UPDATE` 帧，一个保存响应数据的设置帧，填充发送缓冲区的 ping 帧，部分标头帧，`RST_STREAM` 瞬间。

当您的 DNS 记录通过 Cloudflare 代理时，该连接将在我们的边缘结束。

Cloudflare 读取客户端的 HTTP 请求，应用您的安全性和缓存规则，然后通过 Cloudflare 控件向您的源发出自己的请求。 攻击者发送的流控制帧、ping、设置和流重置被我们的边缘消耗。 他们没有转发。 您的 nginx 只会看到 Cloudflare 选择发送的请求，以 Cloudflare 框架的方式构建。 当 Cloudflare 通过 HTTP/2 连接到您的源时，这也适用：Cloudflare 在该连接上运行自己的流控件，并仅根据自己的流量需要发送 `WINDOW_UPDATE` 和 `RST_STREAM` 帧，因此客户端无法使其中继数十亿 `WINDOW_UPDATE` 帧的攻击 需要。

Rapid7在CVE-2026-123007的分析中提出了同样的观点：如果HTTP/2连接被代理，攻击者的帧“可能不会以允许利用的方式被重新传输”。 这打破了 HTTP/2 和 HTTP/3 的每一个攻击。

### 保护不适用的地方

在几种情况下，Cloudflare 的 HTTP 代理不提供保护。

*   **Spectrum TCP/UDP 应用程序。** 对于这些配置，来自 Internet 的流量将未经修改地传递到您的来源。 如果您的源运行 Nginx，请修补或禁用受影响的功能。
*   **nginx 邮件代理。** Cloudflare 的 HTTP 代理不携带 IMAP、POP3 或 SMTP。 将邮件侦听器限制在受信任的网络直到修补。
*   **CVE-2026-123634 (Resolver).** 这取决于您的配置如何从请求中构建 `proxy_pass` 目标，并结合仔细计时的 HTTP 请求取消。 通过 Cloudflare 的代理传递您的流量会使利用此功能变得更加困难，但无法提供完全保护。 无论如何更新。
*   **仅 DNS（灰色云）、内部或非代理 Nginx。

**Cloudflare 的 WAF 规则与这些漏洞无关。** 这些是协议级错误。 由于 Cloudflare 的代理处理解析 HTTP 协议消息，并创建新消息以从源服务器获取信息，因此 Cloudflare 的 HTTP 代理背后的 Origins 可以免受 HTTP/2 和 HTTP/3 错误的影响。 因此，我们没有发布托管规则。 保护来自连接终止，而不是模式匹配。

## 现在该怎么办

1.  **查找每个 Nginx 服务器。** 包括 Nginx Plus、分发包、容器图像和设备。 在每个上运行 `nginx -V` 和 `nginx -T` 并注意 HTTP/2、HTTP/3/QUIC 侦听器、`proxy_pass` 带有变量加 SSI 或 `mirror` 和任何 `mail` 块。
2.  **patch.** 将 Nginx 开源更新为 1.30.7 或 1.31.9，将 Nginx Plus 更新为 37.0.8.1 或 37.3.0.1，或您的发行版的固定软件包。 F5 将 Nginx Plus R34 到 R36 列为没有固定版本的受影响，因此将其移至固定的 37.x 版本。 然后 **重新启动** nginx 或完成二进制升级。 配置重新加载不会替换正在运行的二进制文件。
3.  **仔细检查后向端口版本。** 分发通常在不更改版本 `nginx -v` 报告的情况下修补。 将完整的软件包版本与您的发行版的建议进行比较。
4.  **确保您的源只能通过 Cloudflare 访问。** 使用隧道、IP 允许列表或经过身份验证的来源拉取。
5.  **如果您还不能修补，请禁用您不需要的内容。** `http2 off;` （nginx 1.25.1 及更高版本；在较旧的版本中，从 `listen` 指令中删除 `http2` 块） CVE-2026-123007 和 CVE-2026-123633。 移除 QUIC 侦听器和设置 `http3 off;` 阻止 CVE-2026-121810。 点 `proxy_pass` 在 CVE-2026-123634 的固定上游组中。 不要单独依赖 `mirror_request_body`：Xint 的测试设置将其设置为 `off`，默认 `on` 停止了该漏洞，但 SSI 和其他子请求仍然可以到达该错误。 将邮件侦听器绑定到 CVE-2026-113425 的受信任网络。 重新启动如此旧的连接关闭。
6.  **如果您不使用它，则阻止 SCTP。** 将 `install sctp /bin/false` 添加到 `/etc/modprobe.d/` 中的文件以阻止内核模块加载。 这不会卸载已加载的模块或禁用内核中内置的 SCTP。 当您的分发为 SCTP 错误提供内核更新时，安装它并重新启动。 在那之前，阻塞模块是权宜之计。

Cloudflare 雷达 [Zero Wire entry for nginx2root](https://radar.cloudflare.com/zero-wire/nginx2root) 有完整的清单，一个提示，您可以让代理人对您的机队进行只读评估，并链接到每个供应商咨询。

## 技术深度潜水

让我们通过查看代码来深入了解五个错误的细节。 我们正在查看 Nginx 1.31.8（提交 140AA94），这是修复之前发布的最新代码，并将其与 1.31.9 中的修复进行比较（也包含在版本 1.30.7 上的版本中 稳定的分支）。

关于方法的说明：我们基于公共建议的分析，并验证我们对代码的读取，我们使用 AddressSanitizer 构建了公共 1.31.8 和 1.31.9 版本，并对五个错误中的四个（流量控制，HTTP/2）进行了测试 使用后使用，解析器和邮件代理）。 每一个故障在 1.31.8 上，并在 1.31.9 上运行干净。 我们没有重现 HTTP/3 错误； 该部分基于修复提交和已发布的分析。

### 一种模式，在四个地方

五个错误中的四个是免费的使用后的错误。 这是在没有语言支持的情况下手动管理内存的程序的常见问题：代码的一部分释放了另一部分仍在使用的对象。

Nginx 是事件驱动的。 处理程序运行，调用其他代码，并将该代码返回给处理程序。 当被调用的代码拆除连接或请求处理程序正在处理的请求时，会出现三个错误。 第四，第二个连接仍然保持指向该对象的指针。

*   **CVE-2026-123633 和 CVE-2026-121810。** 请求需要一个连接插槽才能到达其上游。 Nginx 的插槽不足，因此它会关闭一个空闲连接以释放一个。 它选择的连接是请求所属的连接。
*   **CVE-2026-123634.** 解析程序回调结束请求。 该请求的清理释放了解析器将要调用的第二个解析器上下文。
*   **CVE-2026-113425.** 当对邮件客户端的写入失败时，客户端连接关闭，而与身份验证服务的连接仍指向其会话。

如果地址空间布局随机化 (ASLR) 被禁用或绕过，并且在其测试中，Xint 报告具有 Nginx 工作人员的权限的代码执行，F5 将所有四个都视为潜在的代码执行。

第五个错误，CVE-2026-123007，是另一种类型：一个会计错误，成为长度错误。

### CVE-2026-123007：两个看起来正确的流量控制件

HTTP/2 流量控制限制了服务器可能发送的响应数据量。 Nginx 跟踪每个流的发送窗口，一个用于连接的发送窗口，`h2c->send_window`。 客户端用一个window\_update框架放大一个窗口，协议将每个窗口限制在2^31 - 1。

nginx在window\_update到达时强制执行该上限(ngx\_http\_v2\_state\_window\_update())：

```plaintext
if (window > NGX_HTTP_V2_MAX_WINDOW - h2c->send_window) {
   /* logs "client violated connection flow control" */
   return ngx_http_v2_connection_error(h2c, NGX_HTTP_V2_FLOW_CTRL_ERROR);
}
```

就其本身而言，此检查是正确的。 但连接窗口也在第二个位置增长。 当 Nginx 为流对数据帧进行排队时，它会从窗口中减去它们的长度。 如果流在这些帧消失之前被取消，`ngx_http_v2_filter_cleanup()` 将它们从队列中移除并返回信用：

```text
h2c->send_window += window;
```

没有什么能限制这条线。 正如 FIX 提交所描述的，如果客户端在帧排队后和流终止之前扩大连接窗口，退款将窗口推送到 2^31 - 1 之后。

从那时起，第一次检查不再有效。 `h2c->send_window` 是一个无符号的 `size_t`，因此 `NGX_HTTP_V2_MAX_WINDOW - h2c->send_window` 包装成一个非常大的数字，并且每个后续窗口\_update 都被接受。 然后，客户端可以根据需要升高窗口。

该窗口未签名，但大小数据帧的代码将其作为有符号值进行比较（`ngx_http_v2_send_chain()`）：

```plaintext
if (limit == 0 || limit > (off_t) h2c->send_window) {
   limit = h2c->send_window;
}
...
if ((off_t) frame_size > limit) {
   frame_size = (size_t) limit;
}
```

在窗口通过 2^63 后，它为 `off_t` 为负。 帧大小本身成为窗口值，一个介于 2^63 和 2^64 之间的数字，nginx 构建一个缓冲区，其 `last` 指针位于 `pos` 指针之前。

在 TLS 上，该缓冲区在 `ngx_ssl_send_chain()` 中达到该长度的 `memcpy()`。 我们的 TLS 测试在 AddressSanitizer 下的该点停止。 Xint 的文章解释了当窗口推到接近 2^64 时，这会变成受控的越界写入和地址泄漏，以及 Xint、Rapid7 和 Wiz 的每个报告代码执行情况。 这篇文章只不过是错误。

在明文 HTTP/2 上，同一无效缓冲区遵循不同的输出路径。 我们的明文测试也在 1.31.8 的 AddressSanitizer 下出现故障，并在 1.31.9 上运行干净。 公开写入解决了 TLS 案例。

#### 已知攻击需要多少流量

window\_update 可以采取的最大步骤是 2^31 - 1，并且 window\_update 帧是 13 字节。 因此，在其顶部附近放置一个 64 位窗口需要大约 2^33 帧：大约 86 亿帧，或大约 112 GB (104 GiB)。

Rapid7 发布了一个概念证明，给出了相同的数字，并补充说，Nginx 限制了相对于连接上的其他流量的控制帧流量，因此它的运行还发送了大约 15 GiB 的其他请求流量。 它的总数约为 128 GB 的 HTTP/2 数据：在 10 Gbit/s 链路上大约 2 分钟，在 1 Gbit/s 时大约 17 分钟。 Rapid7 估计在大约 2^32 帧或 52 GiB 的 104 GiB 数字中的一半处，需要达到 2^63 所需的窗口\_更新流量。 它还指出，这些数字描述了它的路线，并不是被证明的最低限度。

对于防御者来说，这是有关该错误的有用事实。 在此卷中，已知的攻击很难隐藏：Nginx 通过一个长期连接从单个客户端接收数十亿字节的攻击，并且发送的回送很少，远远超过访问日志帐户中的请求。

#### 为什么很难找到

自 2015 年 HTTP/2 支持在 1.9.5 到达以来，Nginx 中一直存在退款行。有两件事让人难以注意到。

首先，每件作品看起来都是正确的。 对 window\_update 的检查是正确的检查。 退款是正确的退款。 错误是支票依赖于退款没有保留的假设。

其次，等待崩溃的测试不太可能到达，因为崩溃需要数十GB的输入。 不良状态本身就可以在很少的流量下到达：Censys 发布了一个明文测试，该测试通过 5.69 MB 的捕获达到了它所谓的损坏的流控制状态。 一个测试表明“发送窗口永远不会超过其协议最大值”，每帧一到测试序列就会标记错误状态。 等待内存损坏的测试不会。

#### 修复

修复（添加了 6 行）为排队但尚未发送的数据引入了一个计数器 `h2c->send_queued`。 window\_update 检查现在包括窗口中的那些字节：

```text
if (window > NGX_HTTP_V2_MAX_WINDOW - h2c->send_window - h2c->send_queued) {
```

从客户的角度来看，排队的帧仍然计入窗口，因此客户无法再重新填写 Nginx 即将退款的信用额度。 在固定版本上，尝试因流控制错误而被拒绝。

### CVE-2026-123633：两个保护相互作用的地方

Nginx 工作人员具有固定数量的连接插槽 (`worker_connections`)，客户端和上游连接共享。 从 1.19.2 开始，当空闲插槽（总数的 1/16 或更少）时，`ngx_get_connection()` 调用 `ngx_drain_connections()`，它关闭标记为“可重用”的连接：没有进行中的连接，例如空闲的保持连接。

仅当可重用的连接确实没有进行中时，这才有效。 对于 HTTP/2，情况并非总是如此。 2021 年 2 月同一天登陆了两个提交，并在 1.19.7 中一起发布：

*   “HTTP/2：修复了与活动请求的连接重用”修复了一个明文 HTTP/2 连接在有请求时可以保持可重复使用的情况。
*   “HTTP/2：具有不完整帧的连接的复用”在等待部分接收的帧的剩余部分时，将连接注册为可重用的连接，使得客户端不能容纳部分帧的插槽。

第二个变化是相关的。 正如 FIX 提交所解释的，如果该帧的其余部分是标头帧，则会创建一个流，但在连接下一次处于空闲状态之前，不会重置可重用状态。 然后连接有一个请求并保留在可重用队列中。

如果该请求被代理，Nginx 请求上游连接的插槽。 如果插槽很短，则该通话内的漏极会运行，并且可以选择相同的连接。 排水管指示连接关闭，Nginx 尝试发送 Goaway。 如果该发送失败，nginx 将释放连接和其上的每个流。 然后控制返回上游代码，该代码继续使用它所调用的请求。

每一个改变都是有意义的。 他们之间的互动是微妙的，直到今年才被忽视。 F5 的咨询学分了 Metnir 的 Albert Ebb、Wiz Research 的 Nir Ohfeld、Xint.io 和 Palo Alto Networks Unit 42 的 Memn0ps； Nginx.org 的 Changelog 归功于 Vexera AI 的 Albert。

#### 修复

添加了两行：`ngx_http_v2_create_stream()` 现在调用 `ngx_reusable_connection(h2c->connection, 0)`。 具有流的连接永远无法重复使用，无论之前处于何种状态。

### CVE-2026-121810：同样的想法，在 QUIC

根据修复提交和 Xint 的分析，HTTP/3 错误通过不同的路由到达相同的结果。

在 Nginx 的 QUIC 代码中，每个 QUIC 连接使用一个连接插槽，每个流使用另一个流。 只有当其树中剩余的每个流都可以被取消时，才能排出 QUIC 连接，Nginx 通过行走连接的流树来确定这一点。

`ngx_quic_create_stream()` 从可重用队列中删除 QUIC 连接，然后为新流请求一个插槽。 在修复之前，新的流仅在此之后添加到树中。 如果插槽请求触发了另一个关闭相同 QUIC 连接的空闲流的漏极，则处理关闭流的代码未找到正在创建的流，得出结论，连接处于空闲状态，并使其再次可重复使用。 例如，当新请求连接到其上游时，稍后的漏极可以在该请求运行时关闭 QUIC 连接。

F5 的建议指出，剥削“还取决于攻击者无法控制的条件”。 Xint 写道，该错误“由一种与 HTTP/2 的略有不同的机制触发”。

#### 修复

添加了四行：在请求插槽之前流进入树中，并在错误路径上再次取出。

### CVE-2026-123634：在步行期间释放列表的下一个项目

当 `proxy_pass` 包含变量时，nginx 在处理请求时解析主机名。 如果已进行相同名称的查找，则新请求将在同一解析器节点上等待。 当答案到达时，nginx 将等待的上下文列表分开，并依次调用：

```plaintext
next = rn->waiting;
rn->waiting = NULL;

while (next) {
   ctx = next;
   ...
   next = ctx->next;

   ctx->handler(ctx);
}
```

循环在处理程序调用之前存储 `next`，因此处理程序可以释放自己的上下文。 当处理程序在同一列表中释放不同的上下文时，问题就开始了。 当两个上下文属于一个请求时，就会发生这种情况，例如请求及其 `mirror` 子请求解析相同的名称（Xint 测试的情况；F5 还列出了 SSI 子请求）。 如果第一个处理程序结束请求，则请求的清理调用 `ngx_resolve_name_done()` 用于第二个上下文。 该函数在节点的等待列表中搜索上下文，没有找到它，因为该列表已分离，并且无论如何都可以释放上下文。 循环然后前进到释放的上下文。

通常 nginx 会记录这个。 在易受攻击的版本上，当搜索失败时，它会写入

```text
could not cancel <name> resolving
```

到警报级别的错误日志。 这条线值得寻找。 无论哪种方式都不是证明：FIX 提交指出，在遵循 CNAME 的情况下，一种变体没有产生警报。

#### 修复

当它位于分离列表中时取消的上下文将不再立即被释放。 它的处理程序被换成一个，当循环到达它时释放它（添加了 31 行）。 该修复还将警报降级为调试消息，因此上述行仅在未修补的版本上显示在警报级别。

### CVE-2026-113425：两个连接，一个会话

使用 `auth_http`，邮件代理要求 HTTP 服务验证每个登录。 在等待期间，它为一个会话保存两个连接：客户端连接和与身份验证服务的连接。 第二个指向会话并使用客户端连接的内存池。

在修复之前，协议处理程序为客户端准备的回复在身份验证请求进行时保持队列，并且客户端的写入处理程序仍然 `ngx_mail_send()`。 如果该处理程序运行并且由于客户端重置连接而导致写入失败，则会关闭客户端连接并破坏会话。 身份验证连接仍然指向会话，该连接上的下一个事件使用了释放的内存。

Xint 描述了两个条件：客户端的写入事件必须已经注册（例如，因为客户端停止读取回复），并且必须在事件循环的同一通道中处理 login 命令和重置。 不需要有效的凭据，因为这发生在检查登录之前。

#### 修复

当认证请求开始时，添加了两行丢弃排队的回复。 同一个版本包含在代理等待身份验证响应时阻止客户端写入的三个进一步提交，同时它连接到上游并读取其问候语，并且在解析 SMTP 客户端的地址和名称时。

### 修复共享的内容

五个修复每个都涉及对代码的少量修正。 他们每增加 2 到 31 行，邮件代理修复还提供了三个进一步的提交。 无需设计更改。 每个修复程序都恢复了其余代码已经依赖的不变量：

*   发送窗口永远不会超过协议的最大值
*   与正在进行的请求的连接永远不可重复使用
*   其他代码将要使用的对象不会从其下方释放出来

在每种情况下，一条代码路径都未能保留其余代码所依赖的规则，而修复使该路径保持该规则。 随着时间的推移，代码会被修改，这类规则很容易被破坏。

### 注意什么

尝试利用它通常会触发一些特征日志消息。 其中三条消息（两条在 `info` 处，另一封在 `warn` 处）低于 Nginx 的默认 `error_log` 级别 `error`，并且仅在设置较低级别时才会出现。 默认情况下会记录 `alert` 消息。

**错误**

**记录消息或其他信号**

CVE-2026-123007

一个长寿命的 HTTP/2 连接，Nginx 从客户端接收数十千兆字节并发送回很少，远远超过其记录的请求帐户。 在固定版本上，被拒绝的尝试日志 `client violated connection flow control: received WINDOW_UPDATE frame with window increment ... not allowed for window ...`（级别 `info`；较旧的版本对普通违规有相同的消息）。 `http2 flood detected` （级别 `info`）在这种连接上可能是一次失败的尝试，但 Nginx 还会记录该消息的其他几个限制。

CVE-2026-123633，CVE-2026-121810

`worker process <pid> exited on signal 11` （级别 `alert`）在接受 HTTP/2 或 HTTP/3 并代理到上游的服务器上，以及 `worker_connections are not enough, reusing connections`（级别 `warn`）。 使用后不总是崩溃。

CVE-2026-123634

`could not cancel <name> resolving` （级别 `alert`，仅未修补版本）。 缺少此消息并不排除该错误。

全部五个

由 Nginx 工作人员进程启动的意外程序，例如从 `execve` 上的 `execve` 规则中为工作者用户提供。 Xint 建议进行此检查，这是成功攻击的最强迹象。

## 虫子会继续出现

CVE-2026-123007 在 NGINX 上坐了十多年。 自2018年以来，SCTP错误一直存在于Linux内核中。Xint表示，其一位研究人员手工发现了CVE-2026-123007，自动Xint扫描发现了其他四个Nginx错误。 其他几个团队独立地发现了两个 HTTP/2 错误。 与此同时，Nginx 的咨询名单已从 2025 年的两个参赛作品到今年的 36 篇。 人工智能辅助研究正在比以前更快地在经过大量审查的代码中发现错误，并且更多像这样的披露即将到来。
