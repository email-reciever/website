今天，通常可以使用针对私有起源的 Cloudflare 服务。 将代理 DNS 记录指向私有 IP，Cloudflare 到达您现有的 [Cloudflare One connection](https://developers.cloudflare.com/cloudflare-one/networks/connectivity-options/) 上的原点。 您的来源保持私密性，而 Web 应用程序防火墙 ([WAF](https://www.cloudflare.com/products/waf/))、[caching](https://developers.cloudflare.com/cache/)、[bot management](https://developers.cloudflare.com/bots/get-started/bot-management/) 和 [Workers](https://developers.cloudflare.com/workers/) 与公共起源一样有效。

6 月，为了解决我们不断听到客户听到的问题：他们的内部 API、AI 代理后端、MCP 服务器和操作工具不是面向互联网的，但这些服务仍然需要通过 Internet 接受合作伙伴、客户或代理的请求。 在测试版之前，将 Cloudflare 放在这些服务前面意味着暴露公共 IP、打开防火墙端口或在源端运行 `cloudflared`。

这些要求常常使私有应用程序没有它们用于公共应用程序的保护和控制，包括 WAF、机器人管理、速率限制、缓存、流量加速、重写和工作人员。

### 今天普遍可用的东西

在封闭测试期间，符合条件的客户通过其客户团队请求访问权限。 今天，我们正在开放超出该测试组的访问权限。

在私有 IP 处代理 A 或 AAAA 记录，Cloudflare 的应用程序服务与公共起源一样工作：

*   WAF和托管规则
*   机器人管理
*   速率限制
*   缓存
*   转换和重写规则
*   工人

一些限制仍然存在。 不支持 [Argo Smart Routing](https://developers.cloudflare.com/argo-smart-routing/) 和 [Dedicated CDN Egress IPs](https://developers.cloudflare.com/smart-shield/configuration/dedicated-egress-ips/)，并且起点健康检查需要 [Load Balancing](https://developers.cloudflare.com/load-balancing/)。 有关当前限制的完整列表，请参阅 [developer documentation](https://developers.cloudflare.com/dns/private-origins/)。

您的源保留其私有 IP，无需入站防火墙例外。 对于 [Cloudflare WAN](https://developers.cloudflare.com/cloudflare-wan/)，不需要原点上的连接器软件。 使用 [Cloudflare Mesh](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-mesh/)，连接器在您的专用网络中运行，可以服务于多个源。

### 它是如何工作的

创建指向您的出处的代理记录。 对于受支持的专用 IP 范围，**使用** ** 私有网络路由** 将自动启用。 如果您的 Origin 使用只能通过您的专用网络访问的公共 IP，您可以手动启用该设置。

请求流的其余部分保持不变：TLS 终止、WAF、规则和缓存继续在 Cloudflare 的网络上运行。

RFC 1918 专用 IPv4 地址、RFC 6598 CGNAT 地址 (100.64.0.0/10) 和 RFC 4193 唯一本地 IPv6 地址 (FC00::/7) 设置自动打开。 对于这些范围，它不能关闭； 尝试通过 API 禁用它会返回错误。

### API的外观

对于通过 API 自动化部署的客户，私有路由只是标准 DNS 记录上的附加属性。

```plaintext
POST /zones/{zone_id}/dns_records
{
 "type": "A",
 "name": "app.example.com",
 "content": "10.0.0.50",
 "ttl": 300,
 "proxied": true,
 "private_routing": true
}
```

在幕后，Cloudflare 的代理平台通过查询 Cloudflare 的 Origin API 来确定将 `app.example.com` 发送到哪里的流量。 响应包括指示应通过专用网络路径到达目的地的元数据：

```json
{
 "zone_name": "example.com",
 "ipv4_addresses": ["10.0.0.50"],
 "private_routing": true
}
```

`private_routing` 标志是关键信号。 当我们的代理看到它时，它没有尝试通过公共互联网直接连接到私有 IP 地址，而是将请求传递给我们的私有网络层，然后将连接通过客户现有的私有网络连接路由，无论是 [IPsec](https://www.cloudflare.com/learning/network-layer/what-is-ipsec/)、[GRE](https://www.cloudflare.com/learning/network-layer/what-is-gre-tunneling/)、[Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/)、[CNI](https://developers.cloudflare.com/network-interconnect/)， 或 Cloudflare 网格。

[beta post](https://blog.cloudflare.com/private-origins-dns-routing/) 更详细地涵盖了路由层。

### 开始

在开始之前，您需要：

1.  您帐户上的私人起源权利。 请您的帐户团队打开它。
2.  [Cloudflare One connectivity](https://developers.cloudflare.com/cloudflare-one/networks/connectivity-options/) 使用 IPsec、GRE、CNI、Cloudflare 隧道或 [Cloudflare Mesh](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-mesh/)。
3.  在您的帐户上启用了统一路由，除非您通过 Cloudflare 隧道连接（隧道不需要它）。 新帐户和现有帐户可以通过其帐户团队进行升级。
4.  如果您通过 Cloudflare WAN 或 Cloudflare Mesh 连接，请为 Cloudflare 的源范围配置返回路由：100.64.0.0/12 的 IPv4 和 2606:4700:CF1:5000::/64 用于 IPv6。 然后，为专用 IP 创建代理 A 或 AAAA 记录，并确认已启用 **使用专用网络路由**。 您现有的 WAF、缓存和机器人管理配置适用于该主机名，无需进一步更改。

然后，为专用 IP 创建代理 A 或 AAAA 记录，并确认已启用 **使用私有网络路由**。 您现有的 WAF、缓存和机器人管理配置适用于该主机名，无需进一步更改。

测试版中的一张注释：如果请求超时并且没有到达原点，请先检查返回路线。 Cloudflare 源范围的缺失路线是我们看到的最常见的设置故障。

启用后，请遵循我们的 [developer documentation](https://developers.cloudflare.com/dns/private-origins/)，它会完成完整的设置。

### 接下来会发生什么

今天的版本涵盖了到达私人起源的公共交通。 接下来，我们正在处理私有到私有的流量：通过 Cloudflare 的应用程序服务，在专用网络上的用户、服务和 AI 代理，到达其他专用网络上的应用程序。

工程工作正在进行中，我们的目标是在 2027 年初进行封闭测试。如果您想参与，请与您的客户团队联系。

目标是为私有应用程序提供与公共应用程序相同的保护和控制。 例如，员工职位 `wiki.company.internal` 可以从 WAF、速率限制和 BOT 管理中受益。 云和数据中心之间的服务到服务流量也可以使用这些控制，即使双方都没有接触到公共互联网。

目前，今天的版本将您用于公共应用程序的 WAF、缓存、机器人管理和工作人员带到您已经操作的连接的私有来源。
