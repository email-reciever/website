2026 年 11 月 17 日，安全研究公司 Calif 披露了 [Java4Shell (CVE-2026-114938)](https://calif.io/java4shell/)，这是一个使用最广泛的 Java 运行时的 Base64 解码器中的内存腐败漏洞。 在 Common Vulnerability 评分系统 (CVSS) 4.0 下，它的得分为 9.2 分（满分 10 分）。 漏洞影响Java。 OpenJDK 发布了 [security advisory](https://openjdk.org/groups/vulnerability/advisories/2026-11-17)，Oracle 在其 [November 2026 Critical Patch Update](https://www.oracle.com/security-alerts/cspunov2026.html) 的 [November 2026 Critical Patch Update](https://www.oracle.com/security-alerts/cspunov2026.html) 中在 UTC 21:00 发布了修补版本。

该漏洞允许没有凭据的远程攻击者将畸形的 Base64 数据发送到 Java 应用程序，并覆盖解码输出旁边的内存。 Calif 将该覆盖变成了类似于 [Heartbleed](https://www.heartbleed.com/) 的堆内存泄漏，并将其转化为远程代码执行。 加利福尼亚州在默认配置中展示了针对 Keycloak、Atlassian Jira、Atlassian Confluence、JFrog Artifactory、Jenkins 和 PingFederate 的预验证远程代码执行以及验证后的远程代码执行 Apache Kafka、Apache Solr、Elasticsearch、Gerrit 和 Spinnaker。

Cloudflare 在 Cloudflare 托管规则集中发布了一组新规则，旨在检测与此漏洞相关的畸形 Base64 输入模式。 这些规则在 Pro、Business 和 Enterprise 计划上可用，并且默认启用日志操作，因为格式错误的输入和一些良性应用程序特定的令牌格式可能类似于利用尝试。 因此，默认阻止可能会破坏合法流量。 客户现在可以查看安全事件中的匹配请求，并在确认其不影响合法流量后将“规则”操作更改为“阻止”。

WAF 是额外的防御层，而不是补丁的替代品。 Java4Shell 可以通过 WAF 看不到的路径到达，如出站 TLS 响应，唯一完整的解决方法是更新 Java 运行时。 我们的分析师继续监控攻击活动，并将随着新技术和变化的出现而更新规则。 您可以跟踪 [WAF changelog](https://developers.cloudflare.com/waf/change-log/changelog/) 中的规则更改，并获取有关漏洞在专用 [Cloudflare Zero Wire briefing](https://radar.cloudflare.com/zero-wire/java4shell) 上如何发展的更多信息。

到目前为止，我们还没有看到 Java4Shell 在 Cloudflare 基础设施上被利用的迹象。

我们对漏洞的了解
----------------------------------

base64 是将二进制数据表示为文本的常用方法。 Java 应用程序在处理身份验证标头、令牌、文件上传和许多网络消息时对 Base64 进行解码。 为了更快地解码它，OpenJDK 用专门的机器代码替换了常用的代码，称为内在函数。 在支持的 x86-64 处理器上，Base64 Intrinsic 使用 AVX-512 指令一次处理 64 个字节。

该错误位于处理输入的最终字符的手写组件中。 当输入的尾部在有效 base64 从未放置它们的位置包含填充字符 (=) 时，该例程将计算负输出长度。 该无效长度变为完整的 64 字节写入。 对于一个 65 个字符的输入，由 64 个字符后跟一个 =，OpenJDK 分配一个 50 字节的输出数组，然后在其结束时写入 62 个字节。

Java 最终拒绝输入无效并引发异常。 到那时，相邻的内存已经被覆盖了。 应用程序自己的输入验证没有帮助，因为在应用程序可以拒绝数据之前，损坏发生在解码器内部。

最简单的触发器是 64 个字符后面跟着 =。 在 OpenJDK 17 上，触发器需要 128 个字符后跟 =，因为快速代码路径的阈值更高。

剥削不是傻瓜式的。 覆盖的字节大多是固定值，攻击者仅控制写入的位置。 为了构建一个有效的漏洞，Calif 安排了 Java 堆，以便溢出的相邻数组，这首先为它们提供了一种读取堆内存的方法，然后是一种写入选定字节的方法。 每个目标应用程序都需要自己的利用链。 Calif 报告说，在 AI 代理的帮助下，在大约三个小时内开发了第一个工作本地漏洞，因此我们希望其他攻击者能够快速构建漏洞利用链。

Java4Shell 仅在以下所有条件为真时才影响系统：

**条件**

**详细信息**

java运行时

OpenJDK 17.0.6 或更高版本，包括从 OpenJDK 构建的发行版：Amazon Corretto、Eclipse Temurin、OpenJDK 的 Microsoft 构建、Azul Zulu、Bellsoft Liberica、SAP SapMachine、Red Hat OpenJDK、Oracle OpenJDK、Oracle Java SE 和 Oracle GraalVM for JDK。
  
检查受影响的 Oracle 构建的确切列表 [Oracle's advisory](https://www.oracle.com/security-alerts/cspunov2026.html)。

处理器

支持 AVX-512 VBMI 的 x86-64，例如英特尔至强冰湖、蓝宝石急流、翡翠急流和花岗岩急流，或 AMD EPYC 和 Ryzen Zen 4 或更新版本。 ARM64 处理器不受影响。

键入

该应用程序使用标准 Java 解码器解码攻击者控制的 Base64 数据。

许多应用程序捆绑自己的 Java 运行时，容器映像附带一个固定的 Java 开发工具包 (JDK)。 升级系统 Java 包不会更新这些副本，也不会替换已运行的 Java 虚拟机 (JVM)。 每个更新的服务都需要重新启动。

如果您无法立即修补，请缓解
--------------------------------------

如果无法立即更新，CALF 记录了两个删除易受攻击的代码路径的 JVM 启动标志：

*   `-XX:-UseBASE64Intrinsics` 禁用硬件加速的 Base64 编码和解码。
*   `-XX:UseAVX=2` 禁用 AVX-512。 仅在 x86-64 主机上应用此标志。 ARM 上的 OpenJDK 无法识别它并且将无法启动。
    

这两个标志都需要重新启动，并且可能会降低对大量 base64 进行解码的工作负载的性能。 他们在您修补时争取时间。 他们不会取代更新。

修补时保护您的基础设施
-----------------------------------------

修补每个 Java 运行时都需要时间，尤其是当 JDK 捆绑在应用程序和容器映像中时。 Cloudflare WAF 可以在您修补时减少曝光。 一种新的托管规则，在付费计划中可用并在日志模式下启用，它会检测到触发 Java4Shell 的畸形 Base64 输入。 对于企业和企业客户，[WAF attack score](https://developers.cloudflare.com/waf/detections/attack-score/) 添加了一个机器学习层，对远程代码执行有效负载的每个请求进行评分，这有助于捕获基于签名的规则可能错过的变化和绕过尝试。

### 新的托管规则

付费计划的保护已作为 Cloudflare 托管规则集（规则集 ID EFB7B8C949AC4650A09736FC376E9AEE）的一部分发布。 默认情况下，该规则启用了日志操作，因为默认情况下阻止可能会导致合法的 base64 流量出现误报。 要查看其匹配项，请转到安全性 > 安全性分析 > 事件并按规则 ID 进行筛选。 如果匹配不合法的流量，请将规则操作更改为阻止：转到安全 > 设置，编辑 Cloudflare 托管规则集，搜索 CVE-2026-114938 并将规则操作设置为阻止。 或者，您可以点击 [review your configuration on the Zero Wire](https://radar.cloudflare.com/zero-wire/java4shell#cloudflare-coverage) 简报的链接。

我们正在为 Cloudflare 免费托管规则集制定规则，并将在可用时更新此帖子。

当格式错误的 Base64 到达通过 Cloudflare 的 HTTP 请求时，WAF 可以阻止该漏洞利用。 它不能阻止易受攻击的解码器的每条路径，包括：

*   **编码或嵌套数据。
*   **non-HTTP 协议。** 一些受影响的产品，例如 Apache Kafka Broker，接受通过自己协议的流量。
*   **Outbound Connections.** Calif 还共享了一个客户端漏洞：打开与恶意服务器的 TLS 连接的 Java 程序可能会受到损害，即使它自己没有任何服务。
*   **绕过 Cloudflare 的流量。** 这包括服务之间的内部流量。

### 通过WAF攻击得分加深防御力

虽然托管规则是在边缘阻塞畸形 Base64 触发器的主要方法，但 [Cloudflare WAF Attack Score](https://developers.cloudflare.com/waf/detections/attack-score/)（特别是其远程代码执行子分数 cf.waf.score.rce 可在企业计划中可用）可以提供额外的互补保护层。

因为 CVE-2026-114938 (Java4Shell) 是一个二进制堆腐败漏洞，攻击者很少使用单个 65 字节（或 129 字节）触发器实现完整、可靠的远程代码执行 一个人。 在有线上，初始触发器看起来像一个不透明的、畸形的 base64 字符串，包含堆腐蚀字节，而不是传统的 Web 层注入语法。 因此，在应用层注入模式下训练的机器学习模型不会孤立地标记 RAW Base64 触发器。

相反，将有界 JVM 堆溢出转换为 HTTP 上的远程代码执行几乎总是需要多阶段或多参数的漏洞利用链，这会创建更多 WAF 攻击分数可以检查和标记的指纹，包括：

*   堆梳理和触发：破坏JVM堆上的可预测的相邻对象（例如字符串或字节\[\]长度头），攻击者经常在触发器之前发送重复参数或头部，以塑造内存布局 越界写。
*   第二阶段有效负载：一旦堆损坏使攻击者控制执行流或对象引用，该漏洞仍然需要命令、脚本或Java小工具运行。 如果一个漏洞利用链将初始堆腐败触发器与第二阶段的有效负载配对，例如 shell 执行原语（/bin/sh -c, cmd.exe, reverse-shell strings）或Java类加载小工具 （java.lang.runtime、ProcessBuilder、Serialized Object Streams） 隐藏在另一个标头、查询参数或请求正文中，cf.waf.score.rce 可以检测到该二级有效负载并将其评分为恶意。
*   后期开发活动：即使初始堆读取或损坏请求滑过边缘过滤器，尝试与内存中的WebShell 交互或将操作系统命令传递给受攻击的JVM的后续HTTP请求仍对WAF攻击评分直接可见。

部署保护和补丁
-----------------------------

因为复杂的内存漏洞仍然可以执行原始 shellcode 或操纵字节码，而无需通过 HTTP 发送明文 shell 命令，WAF 攻击分数应与显式 Base64 规则和 JVM 修补一起使用。

您可以在 [our WAF guide](https://developers.cloudflare.com/waf/get-started/) 中找到有关如何部署托管规则和攻击分数的更多信息，但简而言之：

1\。 将 Cloudflare 托管规则集（专业计划及以上）中的 CVE-2026-114938 规则设置为阻止。 默认情况下，它在日志模式下启用，因此请先在安全事件中查看其匹配项。 使用 Cloudflare 零线页面上的链接查看您的规则状态。

2\。 层 [Attack Score](https://developers.cloudflare.com/waf/get-started/#2-create-custom-rule-based-on-waf-attack-score) 获取基于 ML 的远程代码执行 (RCE) 检测：创建具有低 RCE 攻击分数的自定义规则阻塞或具有挑战性的请求（例如，企业计划上的 cf.waf.score.rce le 20 或 cf.waf.score.class eq “攻击”业务计划）以捕获多阶段漏洞利用链和开发后的命令流量。

3\。 在运行时进行修复：升级到修补的 OpenJDK 版本（或设置 -xx:+unlockDiagnosticVMoptions -xx:-usebase64Intrinsics 作为临时解决方法）以消除易受攻击的 AVX-512 代码路径 完全。 按照 [OpenJDK advisory](https://openjdk.org/groups/vulnerability/advisories/2026-11-17) 和 [Oracle's Critical Patch Update](https://www.oracle.com/security-alerts/cspunov2026.html) 并尽快安装 Java 供应商的固定版本。 有关提示，您可以为 AI 代理提供清单，请参阅 [Java4Shell page on Cloudflare Zero Wire](https://radar.cloudflare.com/zero-wire/java4shell)。

对 Cloudflare 基础设施的影响
---------------------------------

Cloudflare 还运行 Java，因此当 [Java4Shell](https://calif.io/java4shell/) 被披露时，我们检查了自己的系统。 该漏洞只能在特定的硬件配置中触发，即支持 AVX-512 VBMI 的 x86-64 处理器，因此只有当两者都为真时，系统才会暴露。 我们的调查发现，我们的大部分 Java 工作负载都没有安排在易受攻击的系统上； 我们立即采取行动保护其余的人。

在发布补丁大约一个小时后，我们开始推出一个 JVM 启动选项，该选项关闭包含所有 Java 工作负载上的错误的加速 base64 例程，因此解码会回到标准实现。 为安全起见，我们正在向所有机器推出修补配置，无论硬件如何作为预防措施。 到目前为止，我们还没有看到 Java4Shell 在 Cloudflare 基础设施上被利用的迹象。

立即更新每个 Java 运行时
-----------------------------

Java4Shell 将 Java 运行时中的性能优化转变为远程执行代码的路径，并且现在公开的技术细节，我们希望漏洞利用尝试能够快速进行。 修复是更新每个 Java 运行时并重新启动使用它的服务。 修补时，检查新的托管规则的匹配项，如果您处于付费计划，则将其切换为阻止，并使用攻击分数来捕获签名可能遗漏的远程代码执行有效负载。

随着新技术的出现，我们的 WAF 分析师将继续更新保护措施。 按照[WAF changelog](https://developers.cloudflare.com/waf/change-log/changelog/)进行规则更新和[Java4Shell page on Cloudflare Zero Wire](https://radar.cloudflare.com/zero-wire/java4shell)获取有关此漏洞的最新信息。
