Cloudflare 上的全局 `astro:env`
--------------------------------

自 Astro 5 以来，您已经能够使用 `astro:env`](https://docs.astro.build/en/guides/environment-variables/#type-safe-environment-variables) 访问 [type-safe 环境变量。 但是，Cloudflare 中的环境变量只能在请求中访问 - 限制您可以使用它们的时间和地点。 例如，如果您想使用共享 API 客户端实例，则无法在请求之外实例化环境变量。 这可能会令人困惑，并且与我们的其他适配器不同。

Astro 5.6 解除此限制，这意味着您现在可以在整个服务器代码中全局访问环境变量，并使 Cloudflare 适配器与其他官方适配器保持一致。 这要归功于现在在 Astro 中实现的 [enhancements in Cloudflare Workers](https://developers.cloudflare.com/changelog/2025-03-17-importable-env/)。

从“astro:middleware”中导入 { definiMiddleware }；从 './client.js' 中导入 { createClient }；
// Astro 5.5：未定义// Astro 5.6：StringConst Client = createClient(api_url);
导出 const onRequest = defineMiddleware((ctx, next) => { ctx.locals.client = client; return next();});

这种改进可以在所有 Astro Server 环境中创建更一致的开发人员体验，这意味着您无需担心确定什么是请求范围或全局范围。

Cloudflare 的实验课程
---------------------------------

[Astro sessions API](https://docs.astro.build/en/reference/experimental-flags/sessions/) 是一种实验性功能，可让您在请求之间轻松存储用户数据。 它使用可插拔的后端进行存储，在使用节点或 Netlify 适配器时会自动配置这些后端。

借助 Astro 5.6，我们也为 Cloudflare 带来了这种简化的集成。 当您使用 Cloudflare 适配器的会话时，Astro 现在会自动配置 Cloudflare KV 存储。 这意味着您的会话数据可以通过最少的配置在 Cloudflare 的全球网络中可靠地存储和访问。

入门分为三个步骤：

1.  使用 Wrangler CLI 创建 KV 命名空间：
    
NPX Wrangler KV 命名空间创建“会话”
    
2.  在您的牧马人配置中声明 KV 命名空间：
    
牧马人.json
    
{ "kv_namespaces": [ { "绑定": "会话", "id": "<SESSION_ID>" } ]}
    
3.  在Astro Config中启用实验会话：
    
astro.config.mjs
    
导出默认 defineConfig({ 适配器：Cloudflare(), 实验性: { sessions: true, },});
    

然后，您可以在服务器代码中使用会话：

---export const preRender = false;const cart = await astro.session.get('cart');---

有关详细信息，请参阅 [experimental sessions docs](https://docs.astro.build/en/reference/experimental-flags/sessions/)。

新的预取渴望选项
-----------------------------

借助 Astro 的新型预取急切控件，找到速度和资源使用之间的完美平衡。 启用实验性 [`clientPrerender`](https://docs.astro.build/en/reference/experimental-flags/client-prerender/) 标志后，您可以使用 `prefetch()` 上的 `eagerness` 选项向浏览器建议它应该预取/预渲染链接目标的急切程度。

这个与浏览器的 [Speculation Rules API](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/script/type/speculationrules) 一致的新选项让您可以对浏览器预取或预渲染链接的进取程度进行细粒度控制：

------<script>// 控制预取 eagernessImport { prefetch } from 'astro:prefetch';
// 让我们对这个资源密集型的 pagePrefetch('/data-heavy-dashboard', { eagerness: 'conservative' });
// 此页面对用户旅程至关重要，请尽快加载！prefetch('/product-details'); // 默认为 `{ eagerness: 'immediate' }`
// 对于大多数页面来说，平衡的方法最有效的是 Prefetch('/about', { 急切性: 'moderate' });</script>

您可以从三个渴望级别中进行选择：

*   `'immediate'`：如果资源限制允许立即预取
*   `'eager'`：可能需要链接，所以尽快获取
*   `'moderate'`：让浏览器决定何时预取
*   `'conservative'`：仅在极有可能需要的情况下进行预取

在处理大量链接时，此功能特别有价值，否则您可能会遇到 [browser limits in place to guard against over-speculating](https://developer.chrome.com/blog/speculation-rules-improvements#chrome-limits)。

感谢社区成员 [Marocco2](https://github.com/Marocco2) 贡献了此功能！

预渲染错误页面的自定义提取选项
--------------------------------------------

当按需渲染页面需要显示错误时，您的适配器可能需要从服务器以外的其他地方获取预渲染的错误页面。 目前，这是通过使用默认的 `fetch` 实现来发出请求来完成的，这可能不适合所有用例。 例如，页面可以从不能递归调用的位置提供，或者该页面可以存储在其他地方。

Astro 5.6 在适配器 API 中添加了一个新的可选 `prerenderedErrorPageFetch` 选项，以允许适配器提供用于获取预渲染错误页面的自定义实现。

以下示例为 `500.html` 和 `404.html` 提供了自定义 fetch，从磁盘读取它们而不是执行 HTTP 调用：

return app.render(request, { PreRenderedErrorPageFetch: async (url: string): Promise<Response> => { if (url.includes("/500")) { const content = await fs.promises.readFile("500.html", "utf-8"); fs.promises.readFile("404.html", "utf-8"); 返回 new response(content, { status: 404, headers: { "content-type": "text/html" }, });

如果没有提供值，Astro 将使用 `fetch`，并根据需要向 `/500` 或 `/404` 提出请求。 这与以前版本的 Astro 中的行为相同。

在 [Adapter API reference](https://docs.astro.build/en/reference/adapter-reference/#prerenderederrorpagefetch) 中阅读有关此功能的更多信息。

感谢 [Yury Michurin](https://github.com/yurynix) 贡献此功能！

实验会话的新方法`load()`
-------------------------------------------

使用 [the experimental Sessions API](https://docs.astro.build/en/reference/experimental-flags/sessions/) 时，您通常不需要担心管理会话 ID 和 Cookie：Astro 会自动读取用户的 cookie 并在需要时加载正确的会话。 但是，有时您需要更多地控制要加载的会话。

新的 `load()` 方法允许您按 ID 手动加载会话。 如果您自己处理会话 ID，或者您想在不使用 cookie 的情况下跟踪会话，这很有用。 例如，您可能希望从其他设备上的登录用户恢复会话，或者使用不使用 cookie 的 API 端点。

src/pages/api/cart.ts

从“astro”导入类型 { apiroute }；
导出 const get: apiRoute = async ({ session, request }) => { // 从头部加载会话 const sessionId = request.headers.get('x-session-id'); 等待 session.load(sessionid); const cart = await session.get('cart'); 返回 response.json({ cart });};

如果不存在该 ID 的会话，将创建一个新的会话。 如果需要，这允许您在客户端中生成会话 ID。

有关详细信息，请参阅 [experimental sessions docs](https://docs.astro.build/en/reference/experimental-flags/sessions/)。

改进的配置验证
---------------------------

Astro 现在在每次集成运行后验证您的配置，从而更容易及早发现问题并确定任何问题的来源。 这在使用多个集成时特别有用，因为它有助于确保它们彼此兼容，并与您的 Astro 项目兼容。

对实验 SVG API 的破坏性更改
------------------------------------------

[experimental SVG RFC](https://github.com/withastro/roadmap/pull/1035) 一直在进行激烈的讨论，为此我们感谢大家的参与！ 作为讨论的结果，我们决定_暂时_删除某些功能。 有时这就是实验性API的使用方式！

但是，这并不意味着他们永远消失了！ 现在在这个早期阶段删除它们让我们有时间根据您的反馈进行单独的讨论和构建功能，在 DX、可访问性最佳实践和合理的默认设置之间取得适当的平衡。

这些项目不再可用，必须从您的代码中删除：

*   在我们可以确定开发人员体验和可访问性之间的正确平衡之前，`title` 属性已被删除。 请用 `aria-label` 替换组件上的任何 `title` 道具：
    
        <Logo title="My Company Logo" /><Logo aria-label="My Company Logo" />
    
*   Sprite 模式已被暂时删除，同时我们考虑了一种新的实现，该实现解决了如何在实践中使用此功能。 这意味着不再有多个 `mode` 选项，并且所有 SVG 都将内联。 必须从项目中删除所有 `mode` 实例，因为您无法再控制模式：
    
<Logo mode="inline" /><Logo /> // 始终内联
    
从'Astro'导入{defineConfig}
导出默认的 defineConfig({ 实验性: { svg: { mode: 'sprite' }, svg: true }});
    
*   由于开发人员的反馈，不再应用默认 `role`。 请根据需要在每个组件上单独添加适当的 `role`：
    
<Logo /><Logo role="img" /> // 保留以前默认应用的角色
    
*   已移除 `size` 属性以更好地与 `viewBox` 和其他样式/属性结合使用。 请将 `size` 替换为显式 `width` 和 `height` 属性：
    
        <Logo size={64} /><Logo width={64} height={64} />
