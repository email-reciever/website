**Astro 6 在这里！** Astro 6 引入了一系列新功能，包括内置字体 API、内容安全策略 API，以及通过统一的 Astro 内容层对与外部托管的内容一起使用的实时内容集合的支持。

除了这些新功能，我们还完成了 Astro Dev Server 和大部分构建管道的主要重构。 Astro 由 Vite 的新环境 API 提供支持，现在可以在开发过程中运行您的确切生产运行时间。 这意味着更少的“在开发中工作，在产品中突破”的惊喜——尤其是在 Cloudflare Workers、Bun 和 Deno 等非 Node.js 运行时。

完整版本的亮点包括：

*   **[A 重新设计 `astro dev`](#A 重新设计-Astro-Dev)**
*   **[Improved Cloudflare support](#a-redesigned-astro-dev)**
*   **[Built-in Fonts API](#built-in-fonts-api)**
*   **[Live Content Collections](#live-content-collections)**
*   **[Content Security Policy](#content-security-policy)**
*   **[Upgraded Packages](#upgraded-packages)**
*   **[Experimental: Rust Compiler](#experimental-rust-compiler)**
*   **[Experimental: Queued Rendering](#experimental-queued-rendering)**
*   **[Experimental: Route Caching](#experimental-route-caching)**
*   **[Community](#community)**

**还有一件事**：Astro 6 包括一个 [experimental new Rust compiler](#experimental-rust-compiler) — 我们最初的基于 Go 的 `.astro` 编译器的继任者。 现在还为时过早，但结果已经令人印象深刻（在某些情况下，甚至比我们当前的 Go 编译器更可靠）。 我们将继续在 6.x 发布线上投资于 Rust 驱动的工具，以提高大型站点的性能和可扩展性。

现在升级
------------

要将现有项目升级到 Astro 6，请使用自动 `@astrojs/upgrade` CLI 工具：

    # 推荐：NPX @ASTROJS/升级
    # 手动：npm 安装 astro@latest

对于新项目，只需使用：

npm 创建 astro@latest

重新设计的 `astro dev`
-------------------------

Astro 的开发服务器最初是为 Node.js 构建的——对于大多数 Astro 用户来说，效果很好。 但随着 Cloudflare Workers、Bun 和 Deno 等非节点运行时的吸引力，这种假设成为了一个盲点。 针对这些平台的开发人员无法在开发过程中运行其实际生产运行时，因此您在本地看到的行为并不总是与您的运送内容相匹配。

Astro 6 改变了这一点。 通过利用 Vite 的新环境 API，`astro dev` 现在可以在开发过程中运行自定义运行时环境。 开发服务器和构建管道现在共享相同的代码路径，统一您的生产经验。

对于 Cloudflare 用户来说，这种差距尤其令人痛苦。 开发服务器在 Node.js 上运行，但生产在 Cloudflare 的 `workerd` 运行时运行。 只有在部署后才会出现错误。 Cloudflare 绑定——KV、D1、R2、耐用对象——在开发过程中根本不可用。 你是盲目的编码，希望它能在生产中工作。

重建的 `@astrojs/cloudflare` 适配器现在在每个阶段运行 `workerd`：开发、预渲染和生产。 您可以使用 `cloudflare:workers` 直接针对 Cloudflare 的平台 API 进行开发，并在本地完全访问绑定。 没有更多的模拟层，也没有更多的 `Astro.locals.runtime` 解决方法。 这项工作源于我们去年宣布的 [official partnership with Cloudflare](/blog/cloudflare-official-partner/)，目标是让 Cloudflare 成为一流的 Astro 运行时。

内置字体 API
-------------------

几乎每个网站都使用自定义字体，但正确处理它们非常复杂。 有性能权衡、隐私问题和十几个容易出错的小决定。

Astro 6 添加了一个内置的字体 API，为您处理困难的部分。 您可以从本地文件或 Google 和 FontSource 等本地文件或提供商配置字体，Astro 处理其余部分：下载和缓存以进行自托管、生成优化的回退以及添加预加载链接 - 使您的网站保持快速和用户的数据私密性。

首先，使用一种或多种您想在项目中使用的字体配置 `fonts` 对象：

astro.config.mjs

从 'astro/config' 导入 { defineConfig, FontProviders };
导出默认 defineConfig({ 字体：[ { name: 'roboto', cssvariable: '--font-roboto', provider: fontProviders.fontSource(), }, ],});

然后，在您需要的任何地方添加 `<Font />` 组件和样式 - 全局布局、单个页面或您网站的特定部分：

src/组件/head.astro

---import { font } 来自 'astro:assets';---
<Font cssVariable="--font-roboto" preload /><style is:global> 正文 { 字体系列：var(--font-roboto); }</style>

在幕后，Astro 下载字体文件，生成优化的后备字体，并添加了正确的预加载提示——因此您无需自己配置即可获得最佳实践字体加载。

要了解更多信息，请查看[fonts guide](https://docs.astro.build/en/guides/fonts/)。

实时内容集
-------------------------

实时内容集现在在 Astro 6 中很稳定，为 Astro 的统一内容层带来了请求时间的内容。

自 2.0 以来，内容集合一直是 Astro 的核心部分。 但当内容发生变化时，他们总是需要重建。 实时内容集合在请求时使用相同的 API 获取内容，无需重建步骤。 您的内容在发布的那一刻会更新，而无需触及您的构建管道。 这意味着 CMS 内容、API 数据和编辑更新都立即上线。

使用 `defineLiveCollection()` 在 `src/live.config.ts` 中定义实时源：

src/live.config.ts

import { defineLiveCollection } 来自“astro:content”；从“astro/zod”导入{z}；从'./loaders/my-cms'导入{CMSLoader}；
const updates = defineLiveCollection({ loader: cmsloader({ apiKey: process.env.my_api_key }), schema: z.object({ slug: z.string(), title: z.string(), excerpt: z.string(), 发表于：z.coerce.date(), }),});
导出常量集合 = { 更新 };

然后使用内置错误处理在页面中查询实时内容：

---import { getLiveEntry } 来自“astro:content”；
const { 条目：更新，错误} = await getLiveEntry('updates', astro.params.slug,);
if (error || !update) { return astro.redirect('/404');}---
<h1>{update.data.title}</h1><p>{更新

实时内容集合使用与构建时集合（`getCollection()`、`getEntry()`、模式、加载器）相同熟悉的 API，因此没有新的心理模型可以学习。 如果您的内容需要实时新鲜度，请使用 Live Loader 定义实时收藏，您的内容会根据每个请求进行实时发布。 如果没有，请继续使用构建时集合以获得最佳性能。 两者都可以在同一个项目中共存。

有关实时内容集合的更多信息，请参阅 [content collections guide](https://docs.astro.build/en/guides/content-collections/)。

内容安全策略
------------------------

Astro 的内容安全策略 API 现在在 Astro 6 中是稳定的。ASTRO 是最早在服务器和无服务器环境中为静态和动态页面提供内置 CSP 配置的 JavaScript 元框架之一。

CSP 在像 Astro 这样的框架中难以实现。 它需要了解页面上的每个脚本和样式，以便它们可以被散列并包含在策略中。 对于静态页面，可以在构建时计算。 但是对于动态页面，内容可以根据请求进行更改——这意味着动态散列并在运行时注入正确的标头。 在单个统一的 API 中支持两种模式是为什么其他元框架以前没有这样做的原因。

入门很简单。 使用单个标志启用 CSP，Astro 处理其余部分 - 自动散列页面中的所有脚本和样式并生成适当的 CSP 标头：

从“astro/config”导入 { defineconfig }；
导出默认 defineConfig({ 安全性：{ csp: true }, 实验性: { csp: true },});

这就是大多数网站所需要的。 当您需要更多控制时——自定义散列算法、外部脚本或样式的附加指令——完整的配置 API 可用：

从“astro/config”导入 { defineconfig }；
导出默认的defineConfig({安全性：{ csp：{算法：'sha-512'，指令：["default-src'self'", "img-src 'self' https://images.cdn.example.com", ], styleDirective: { 哈希: ['sha384-stylehash'] }，scriptDirective：{哈希：['sha384-scriptHash'] }, }, },});

作为这种稳定的一部分，CSP 还与 Astro 的 [responsive images](https://docs.astro.build/en/reference/configuration-reference/#imageresponsivestyles) 开箱即用。 响应式图像样式在构建时计算并使用 CSS 类和 `data-*` 属性应用，因此它们可以自动散列并包含在您的 CSP 策略中 - 无需额外的配置。

详情见[security configuration reference](https://docs.astro.build/en/reference/configuration-reference/#security)。

升级包
------------------

Astro 6 包括对几个核心依赖项的重大升级：

*   **Vite 7** 现在跨 Astro 和所有 `@astrojs` 软件包使用。 如果您的项目固定了自定义 Vite 版本，请在升级之前将其更新到 V7 或更高版本。
*   **Shiki 4** 现在为 `<Code />` 组件和 Markdown/MDX 代码块中的代码突出显示。
*   **ZOD 4** 现在为内容架构验证供电。 在定义模式时，从 `astro/zod` 而不是 `astro:content` 导入 ZOD。

Astro 6 现在还需要 **Node 22** 或更高版本，放弃对已达到或接近使用寿命的节点 18 和节点 20 的支持。 Node 22 更快、更安全，让我们可以为较旧的 Node 版本放弃 polyfills——从而实现更小、更易于维护的软件包和更好的性能。

有关详细的迁移步骤，请参阅 [upgrade guide](https://docs.astro.build/en/guides/upgrade-to/v6/#dependency-upgrades)。

实验：Rust 编译器
----------------------------

Astro 6 包括一个实验性的新 Rust 编译器——我们最初的基于 Go 的 `.astro` 编译器的继承者。

在更新我们的Astro 6的Go编译器时，最初是一个人工智能实验，很快就从“这可以工作吗？” “为什么这不是默认的？” 新编译器速度更快，产生更强的诊断功能，在某些情况下甚至比我们当前的 Go 编译器更可靠。 我们希望在未来的主要版本中将其设置为默认值。

您可以通过启用 `rustCompiler` 标志并安装 `@astrojs/compiler-rs` 包来立即尝试：

npm 安装@astrojs/compiler-rs

从“astro/config”导入 { defineconfig }；
导出默认 defineConfig({ 实验性: { RustCompiler: true, },});

我们正在积极探索 Astro 中更多的 Rust 驱动工具，很快就会分享更多内容。

阅读我们关于 [the Rust compiler](https://docs.astro.build/en/reference/experimental-flags/rust-compiler/) 的参考文档以获取更多详细信息。

实验性：排队渲染
------------------------------

Astro 6 引入了一种实验性的新渲染策略，早期的基准测试显示速度快了 2 倍。

今天，Astro 递归地渲染组件。 渲染函数在组件树上行走时会自行调用。 排队的渲染用两遍方法代替了这一点：第一个传递遍历树并发出一个有序的队列，然后第二遍渲染它。 结果既更快又更高效，我们计划将其作为 Astro V7 中的默认渲染策略。

立即通过启用实验标志来尝试：

从“astro/config”导入 { defineconfig }；
导出默认 defineConfig({ 实验性: { queueDrendering: { enabled: true, }, },});

有关此功能的更多信息，请参阅 [experimental queued rendering documentation](https://docs.astro.build/en/reference/experimental-flags/queued-rendering/)，包括节点池和内容缓存等其他选项。

实验：路由缓存
----------------------------

Astro 6 包含一个实验性路由缓存 API，它为您提供了一种与平台无关的方式来使用 Web 标准缓存语义缓存服务器呈现的响应。

缓存 SSR 今天的响应比应有的难。 每个主机都以不同的方式进行操作，并且没有标准的方法可以从您的应用程序代码中控制它。 路由缓存为您提供了一个与平台无关的 API：在您的路由中设置缓存指令，而无论您部署在哪里，Astro 都会处理其余部分。

通过在 Astro Config 中配置缓存提供程序来启用路由缓存。 缓存提供程序告诉 Astro 将缓存响应存储在哪里。 Astro 附带一个内置的 `memoryCache` 提供程序来帮助您入门：

从“astro/config”中导入 { defineConfig }；从 'astro/config' 导入 { memorycache }；
导出默认 defineConfig({ 实验性: { cache: { provider: memorycache() }, },});

然后使用 `Astro.cache`（或 `context.cache`，在 API 路由中）来控制每个请求的缓存。 您可以设置缓存持续时间、陈旧的同时重新验证窗口和目标失效的标记。 在这个例子中，我们为响应设置了 Cache 标头，自定义为请求：

---Astro.cache.set({ maxAge: 120, // 缓存2分钟SWR:60, //在重新验证标签的同时服务陈旧1分钟: ['home'], // tag to targeted invalidation});---
<html><body>缓存页面</body></html>

这就是 Astro 的统一内容层真正闪耀的地方。 路由缓存直接与 [live content collections](#live-content-collections) 集成，自动跟踪页面和内容条目之间的依赖关系。 当内容条目发生变化时，任何依赖于它的缓存响应都会自动失效：

从 'astro:content';const product = await getentry('products', astro.params.slug);
// 当产品发生变化时，Astro 将使此缓存的页面无效：astro.cache.set(product);

此初始版本包括一个简单的内存缓存提供程序，它与 Node.js 适配器配合得最好。 在接下来的几周内，我们将为所有支持的 Astro 部署平台添加缓存提供商。 我们还希望有社区构建的 CDN 服务提供商以及 Redis 等其他存储类型。 如果您有兴趣建造一台，请联系 [on Discord](https://astro.build/chat)！

有关更多详细信息，请参阅实验 [route caching docs](https://docs.astro.build/en/reference/experimental-flags/route-caching/)。
