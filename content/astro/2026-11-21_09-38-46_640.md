**ASTRO 7 在这里！** 这个版本是关于速度的。 `.astro` 编译器已在 Rust 中重写。 Markdown 和 MDX 处理现在通过新的 Rust 供电管道运行。 渲染引擎已被更快的基于队列的方法所取代。 与 Vite 8 及其新的 Rolldown Bundler 一起，Astro 7 构建在我们的基准测试中速度提高了 15-61%。 最快的构建是根本不会发生的，因此 Astro 7 还稳定了路由缓存，并为 Netlify、Vercel 和 Cloudflare 添加了实验性 CDN 缓存提供商。

Astro 7 还引入了高级路由，为您提供了一个 `src/fetch.ts` 入口点，可以完全控制 Astro 的请求管道。 对于 AI 辅助开发，Astro 现在可以检测编码代理，在后台运行开发服务器，并在代理需要机器可读反馈时输出结构化的 JSON 日志。

    # 手动：npm 安装 astro@latest

npm 创建 astro@latest

有关详细的迁移步骤，请参阅 [upgrade guide](https://docs.astro.build/en/guides/upgrade-to/v7/)。

提议 8
-------

Astro 7 升级为 [Vite 8](https://vite.dev/blog/announcing-vite8)，这是多年来最重要的 Vite 版本。 标题更改：Vite 现在提供 [Rolldown](https://rolldown.rs/)，这是一个基于 Rust 的捆绑器，可以用单个统一的捆绑器替换 esbuild 和 rollup。 rolldown 是 [10-30x faster than Rollup](https://github.com/rolldown/benchmarks) 在基准测试中，同时支持相同的 rollup 和 Vite 插件 API。

对于 Astro 用户，这意味着大多数项目无需更改配置即可更快地构建。 Vite 8 包含一个兼容性层，可将现有的 `esbuild` 和 `rollupOptions` 配置自动转换为它们的下拉等效项。 如果您的项目使用自定义的 Vite 插件，则其中大多数都应该继续工作，因为 Rolldown 支持与 Rollup 相同的插件 API。

表演
------------

Astro 7 是 Astro 迄今为止最快的版本。 随着使用量的增长，越来越多的团队一直在推动使用 Astro 构建什么类型的站点的界限。 在我们发布了 Astro 6 及其大型内部重构后，我们将目光投向了帮助 Astro 扩展到更大、更复杂的站点。

Astro 构建的工作原理是这样的：

1.  将网站的页面、内容和客户端组件捆绑到 JavaScript 中。
2.  像一个小服务器一样运行捆绑的代码，为每个预渲染页面创建请求，并保存生成的HTML。

Astro 7 改进了两个步骤，但重点关注第一个：捆绑网站。 最大的好处来自将构建中的一些最慢的部分移动到用 Rust 编写的本机代码中。 生成步骤也更快，这要归功于一种新的渲染策略，它更有效地排队要渲染的部分。

在我们的测试中，整体构建时间提高了 15-61%，一些站点的建设速度是**的两倍多**。 `.astro` 编译和降价处理在构建中占更大份额的站点可以看到最大的收益，因为这些部分正是那些被转移到 Rust 的部分。

### Rust 编译器

我们为 `.astro` 组件格式构建了一个新的编译器，现在用 Rust 编写。 编译器是对我们之前的基于 Go 的编译器的全面重写，它大部分是向后兼容的，除了：

*   ** 没有更多的 HTML 校正。 新编译器按原样对待您的标记。
*   **JSX 风格的严格性。** `<div>Hello` 之类的未关闭标签和 `<div class="Hello >` 之类的未终止属性现在会产生错误，而不是被静默地纠正。 这些是模板中的真正错误，旧编译器会默默地忽略这些错误，以尝试像浏览器一样行事。
*   **JSX 空白处理。** 元素之间的空格现在按照 JSX 约定进行折叠，与 React 和其他基于 JSX 的框架的行为相匹配。 例如，内联元素之间的换行符不再产生可见空间：
    
<!-- 之前：呈现为“Hello World”（有空格）--><!-- 后：呈现为“HelloWorld”（无空间）--><span>Hello</span><span>World</span>
<!-- 要保留空间，请使用显式表达式： --><span>hello</span>{' '}<span>world</span>
    

迁移到 Rust 允许我们为受支持的平台提供原生二进制文件，并为需要它的环境提供 WASM 后备。 这种模式现在是 JavaScript 工具世界中的标准配置，用于 Rolldown 和 Lightning CSS 等项目。 在引擎盖下，新编译器建立在 [oxc](https://oxc.rs/) 上，用于解析和 [Lightning CSS](https://lightningcss.dev/) 用于 CSS 范围。

孤立地，Rust 编译器在 [https://docs.astro.build](https://docs.astro.build) 的构建时间上显示了大约 6% 的改进。 这是因为 `.astro` 编译很少是瓶颈； 降价处理和捆绑通常主导构建时间。 但每一点加起来，尤其是在有数千页的大型网站上，编译器的收益与此版本中的其他性能改进相结合。

### Rust中的Markdown和MDX

Astro 7 将默认的 Markdown 和 MDX 管道替换为 [Sätteri](https://satteri.bruits.org/)，这是一个由 Astro Core 团队成员 [![](/_astro/erika.D_h-VfLk.webp)erika](https://bsky.app/profile/erika.florist "在 Bluesky 上关注 Erika" 的 Rust 驱动的处理器。 将Astro Docs和Cloudflare Docs转换为Sätteri的构建时间缩短一分钟，使Markdown-Heavy网站成为Astro 7的最大赢家。

到目前为止，Astro 的 Markdown 管道运行在 [unified](https://unifiedjs.com/) 上（备注、重新炒作和 JavaScript 依赖项的长尾）。 在有数千页的大型网站上，该管道通常是构建中最慢的阶段：每个文件通过 JavaScript 解析，在整个 AST 上通过插件运行，然后序列化回 HTML。 在 Astro 6.4 中，我们 [made the pipeline pluggable](/blog/astro-640/#new-markdownprocessor-api) 并将 Sätteri 作为选择加入的替代方案。 Astro 7 将其设置为默认值。

在引擎盖下，Sätteri 使用 [pulldown-cmark](https://github.com/pulldown-cmark/pulldown-cmark) 进行 CommonMark 解析，将 [Oxc](https://oxc.rs/) 用于 MDX 表达式解析，均为本机 Rust。 它提供了带有 WASM 回退的平台特定二进制文件，与新的 `.astro` 编译器使用的方法相同。 不过，速度并不是唯一的胜利。 Sätteri 还原生实现了许多以前需要单独插件的 Markdown 功能：

### 排队渲染

Astro 6.0 中引入了队列渲染作为一个实验选项，现在是稳定的和默认的渲染引擎。 它的速度 **~2.4 倍**[1](#user-content-fn-1)！

astro.config.mjs

从“astro/config”导入 { defineconfig }；
导出默认的 defineConfig({ experiment: { queueDrendering: { enabled: true, pooling: true, contentCache: 1000 } }})

以前，Astro 使用递归方法渲染页面，其中使用相同的 `render*` 函数渲染孩子，就像在以下伪代码中一样：

渲染.ts

export function renderComponentToString(node: unknown): string {  let destination = ""; 目的地 += `<${node.name}>`； // 打开标签
// 渲染属性
for (const child of node.children) { // 这是我们通过调用 renderComponentToString destination += renderComponentToString(child); }
目的地 += `</${node.name}>`； // 结束标记
返回目的地；}

新引擎使用队列（或堆栈）和单个循环。 队列中以正确的顺序填充了子节点，并且循环保持渲染节点直到队列被耗尽。 下面的伪代码是真实交易的一个过于简单的版本，但它应该提供一个清晰的画面：

渲染.ts

导出函数 renderComponentToString(root: unknown): string { let destination = ""; 目的地 += `<${root.name}>`； // 打开标签
// 这是我们的队列，在我们渲染时填充和刷新 let stack = [root];
while (stack.length > 0) { const node = stack.pop();
if (array.isarray(node)) { // 末端的节点必须首先呈现为 (let i = node.length - 1; i >= 0; i--) stack.push(node[i]); 继续； }
const nodetype = typeof 节点； if (nodetype === 'string') { 目标 += escapehtml(node as string); } } 目的地 += `</${root.name}>`; // 打开标签返回目的地;}

该策略的第一个实现是在两个阶段进行的：创建一个有序的组件（节点）列表，循环列表并渲染组件。

新实现不再创建完整列表，而是在循环时渲染（刷新）列表。 这最后一种方法比第一次迭代更快，并且与递归方法相比需要更少的内存。

高级路由
-----------------

Astro 最初是一个具有基于文件路由的静态站点生成器。 随着时间的推移，中间件、重定向、重写、操作、会话和 i18n 等功能为 Astro 应用程序提供了更多的服务器端功能，但它们也使请求的生命周期更难控制。 如果您需要在操作之前运行 Auth，日志记录到仅包装页面渲染，或者首先处理某些请求的非 ASTRO API，您必须在管道周围工作而不是直接编写它。

在 Astro 7 中，您现在可以通过向项目中添加 `src/fetch.ts` 文件来完全控制 Astro 的请求管道。 此文件导出由 [Cloudflare Workers](https://developers.cloudflare.com/workers/runtime-apis/handlers/fetch/)、[Deno](https://docs.deno.com/runtime/fundamentals/http_server/) 和 [Bun](https://bun.sh/docs/api/http#bun-serve) 推广的标准 `fetch` 处理程序模式。

src/fetch.ts

从“astro/fetch”导入 { astro, fetchState };
导出默认 { fetch(request: request) { const state = new fetchState(request);
// 将 API 请求转发到后端服务 if (state.url.pathname.startsWith('/api')) { const url = new url(state.url.pathname + state.url.search, 'https://backend-api.example.com'); 返回 fetch(new request(url, request)); }
// 回退到 Astro 页面/终结点 astro(state); }}

API 还兼容 [Hono](https://hono.dev/)，允许您将 Hono 中间件带入您的 Astro 应用程序：

src/fetch.ts

import { astro } 来自 'astro/hono';import { hono } 来自 'hono';import { basicauth } 来自 'hono/basic-auth';
const app = new hono();app.use(basicauth({ username: 'admin', password: 'secret' }));app.use(astro());
导出默认应用程序；

对于高级使用，您可以将单独的 Astro 功能组合为单独的中间件，让您可以完全控制请求管道。 如果您曾经使用过 Astro Middleware 并且对您的 Auth 检查运行 _after_ astro 操作感到沮丧，或者您无法在不自己包装所有内容的情况下记录响应时间，您现在可以将代码准确地放在需要的地方：

src/fetch.ts

import { hono } 来自 'hono';import { actions, middleware, pages, i18n } from './middleware/auth';import { timing } './中间件/计时'；
常量应用程序 = 新的 hono();
app.use(i18n());app.use(auth()); // Auth 在动作之前运行，没有未经身份验证的 CallApp.use(Actions());App.use(MiddleWare());App.Use(timing()); // 仅计时包装页面 renderingApp.use(pages());
导出默认应用程序；

如果您不添加 `src/fetch.ts` 文件，Astro 的行为与今天完全相同。

路由缓存
--------------

缓存按需渲染响应比应有的难度。 每个主机都以不同的方式进行操作，并且从来没有一种标准的方法可以从您的应用程序代码中控制它。 Astro 7 引入了 [route caching](https://docs.astro.build/en/guides/caching/) 来解决这个问题。 首先通过实验发布[in Astro 6](/blog/astro-6/#experimental-route-caching)，该功能现在是稳定的，并为缓存添加了一个与平台无关的API：在您的路由中设置指令，而Astro无论您部署的是什么。

配置缓存提供程序一次，然后在页面中使用 `Astro.cache`（或 API 路由和中间件中的 `context.cache`）控制每个响应的缓存，基于标准的 HTTP 缓存语义。 Astro 附带一个内置的 `memoryCache()` 提供程序来帮助您入门：

astro.config.mjs

从“astro/config”导入 { defineConfig, memoryCache };
导出默认 defineConfig({ cache: { provider: memoryCache(), },});

src/pages/products/\[id\]].astro

---Astro.cache.set({ maxAge: 120, // 缓存2分钟SWR:60, //在重新验证标签的同时重新验证标签: ['products'], // tag to targeted invalidation});---

您还可以使用 `routeRules` 在配置中以声明方式定义路由组的缓存规则，从而使您的路由代码完全远离您的路由代码：

astro.config.mjs

导出默认 defineConfig({ cache: { provider: memorycache() }, routerules: { '/blog/[...path]': { maxage: 300, swr: 60 }, },});

路由缓存真正闪耀的是它与[live content collections](https://docs.astro.build/en/guides/content-collections/#live-content-collections)的集成。 实时加载器可以将缓存提示附加到它返回的数据，其中包含用于失效的标记和最后修改的新鲜度时间。 将该条目直接传递给 `Astro.cache.set()`，Astro 会为您读取提示，无需手动标头：

src/pages/products/\[id\]].astro

---import { getLiveEntry } 来自 'astro:content';const { entry } = await getLiveEntry('products', astro.params.id);
// Astro 从 entry:astro.cache.set(entry) 中读取加载器的缓存提示；---

缓存的响应可以通过 `cache.invalidate()`、标签或路径按需清除。 例如，您可以公开 CMS 的 Webhook 端点，以便在内容更改时进行调用。 这会映射到每个提供商的失效 API，无需重建即可清除所有受影响的响应：

src/pages/api/revalidate.ts

从“astro”导入类型 { apiroute }；
export const post: apiroute = async ({ request, cache }) => { // 一个真正的实现将验证请求并在无效之前检查一个秘密令牌。
const { slug } = 等待请求.json();
// 使每个标记为 'products' 的响应无效...await cache.invalidate({ tags: ["products"] });
// ...使使用特定条目的每个页面无效...await cache.invalidate({ tags: [`products:${slug}`] });
// ...或直接清除单个路径。 等待缓存.invalidate({ 路径：`/products/${slug}` });
返回新的response('revalidated');};

如果您在实验期间尝试了路由缓存，唯一的变化是将 `cache` 和 `routeRules` 移出 `experimental` 块到配置的顶层。 API 否则不变。 请参阅 [route caching guide](https://docs.astro.build/en/guides/caching/) 以获取完整参考。

### CDN 缓存提供商

在 Astro 6 中提供的路由缓存时，它带有一个内存中提供程序，用于节点适配器。 Astro 7 为 Netlify、Vercel 和 Cloudflare 添加了实验性 CDN 提供商。

这些提供商不是将响应存储在内存中，而是将您的缓存指令推向主机的边缘网络，以获得更快的响应。 然后直接从 CDN 提供缓存命中，而无需调用您的服务器功能。

在未来的版本中，这些提供商将自动启用，但在实验阶段，您应该手动添加它们。 导入适配器的提供程序并将其设置为缓存提供程序：

astro.config.mjs

导入 { defineConfig } 从“astro/config”；从“@astrojs/netlify”导入 netlify；从“@astrojs/netlify/cache”导入 { cachenetlify }；
导出默认 defineConfig({ 适配器：Netlify(), cache: { provider: cacheNetLify(), },});

每个适配器从其 `/cache` 入口点导出一个提供程序：

人工智能增强
----------------

人工智能编码代理现在是许多开发人员工作流程的一部分，他们需要与开发服务器不同的东西，与人类不同。 Astro 7 是我们使 Astro 成为代理驱动开发的更好平台的第一步。

### 背景开发服务器

人工智能代理在长期运行的过程中苦苦挣扎。 它们外挂，等待退出，读取输出，但开发服务器永远不会退出。 代理挂起、启动重复服务器、丢失正在运行的实例或将僵尸进程抛在脑后。 我们也将其视为 Astro 自动化问题分类的一部分，代理有时会花费更多时间在开发服务器上摸索而不是测试代码。

Astro 7 添加了 `astro dev --background`，将开发服务器作为托管后台进程启动。 **ASTRO 还可以检测到它何时在 AI 代理中运行**并自动启用后台模式，因此代理工作流中不需要标志。 如果没有检测到代理，`astro dev` 的行为与以前完全相同。

$ astro dev --backgrounddev 服务器在 http://localhost:4321 (PID 12345) 中运行：ASTRO Dev 停止状态：Astro Dev 状态日志：Astro Dev 日志

该命令会阻塞，直到服务器准备好接受请求，报告 URL 和进程 ID，然后分离。 没有轮询，没有睡眠，没有解析“本地：”的终端输出。

**lockfile** 防止重复实例。 如果代理尝试启动第二个服务器，它会获取现有实例的详细信息，而不是生成冲突的进程：

$ astro dev --backgrounddev 服务器已经在 http://localhost:4321 运行 (PID 12345)

您可以检查状态并从单独的 shell 会话中停止服务器：

$ Astro Dev StatusDev Server 运行在 http://localhost:4321 （PID 12345、Uptime 123s、后台）
$ Astro Dev 停止开发服务器 (PID 12345)。

您还可以使用 `astro dev logs` 读取后台服务器的日志。

每个命令都是幂等和宽容的。 不运行时停止静默成功，并在已运行时启动返回现有实例。 代理通常会失去对流程状态的跟踪，而 CLI 不会因此对其进行惩罚。

所有正在运行的开发服务器还公开了一个 `/_astro/status` 健康端点，代理可以查询该端点以确认服务器是否处于活动状态并准备好接受请求。

### JSON 日志记录

Astro 的记录器现在可以完全配置。 对于代理，当代理检测打开后台模式时，JSON 日志会自动启用。 对于其他所有人，它可通过 CLI 或配置获得：

Astro Dev --JSON

astro.config.mjs

从“astro/config”导入 { defineConfig, loghandlers };
导出默认 defineConfig({ logger: loghandlers.json()})

JSON 日志记录在我们的路线图上 [the most upvoted feature request](https://github.com/withastro/roadmap/discussions/908)，而不仅仅是因为 AI。 将 Astro SSR 部署到生产需求的团队将结构化日志与 Kibana、CloudWatch 和 Grafana/Loki 等日志聚合服务集成。 Astro 以前的日志记录是为了人类的可读性而硬编码的：颜色、框图字符、多行错误格式。 这些都不是机器可以解析的。

新的 Logger API 还支持自定义日志处理程序和 `compose()` API，用于组合多个记录器。 例如，您可以在控制台中保存可读的输出，同时为需要结构化输出的工具编写 JSON 日志：

astro.config.mjs

从“astro/config”导入 { defineConfig, loghandlers };
导出默认 defineConfig({ logger: loghandlers.compose( logHandlers.console(), logHandlers.json() )})

详细了解 [the AI guide](https://docs.astro.build/en/guides/build-with-ai/) 中 Astro 对 AI 工具的支持。
