**昨天我们推出了专为 Astro Web 框架设计的完全托管 SQL 数据库服务。 让我们深入了解 [Astro DB](https://astro.build/db/) 的实现细节：它是如何工作的，我们为什么构建它，以及我们为什么采用 LibSQL。**

我们是如何来到这里的
----------------

Astro 的独特之处在于它专注于构建**内容驱动的网站。** 当然，内容的中心是内容，这就是我们在 Astro 2.0 中发货的原因 [Content Collections](https://astro.build/blog/introducing-content-collections/)。 我们的用户喜欢它作为管理本地内容的一种方式。

WordPress一直是我们的巨大灵感。 使 WordPress 如此特别的原因之一是它的 **内置** **数据库**。 您不只是管理您的文章内容，而是管理数据、页面、块、图像和整个插件生态系统。

我们想要Astro这样的东西，但我们很快意识到我们已经达到了静态回购数据的极限。

查找（和丢失）SQLite
----------------------------

为了通过数据收集和引用来发展内容集合，我们意识到我们正在从文件系统中构建一个类似数据库的 ORM，我们遇到了几个挑战。 核心团队成员 [![](/_astro/erika.D_h-VfLk.webp)erika](https://bsky.app/profile/erika.florist "在 Bluesky 上关注 Erika") 提出了这样的想法：为什么我们不使用数据库，[SQLite](https://www.sqlite.org/)？

我们爱上了Astro本身内置的轻量级数据库的想法。 SQLite 非常适合大多数内容驱动的网站的大量读取工作负载。

我们对这个想法进行了原型，但遇到了一些阻塞者。 SQLite 是一个 C 库，因此需要在 Node.js 中运行本机附加组件。 这对于本地开发来说是可以的，但本地附加组件很难部署到无服务器主机，启动时间令人担忧。 此外，像 [StackBlitz](https://stackblitz.com/) 这样的关键环境将无法完全运行它。

失败了，我们把这个想法放在次要位置上，专注于其他事情。 那是2023年的春天。

寻找（并爱上）LibSQL
----------------------------------------

与此同时——半个世界，我们完全不知道——另一个团队正在研究这个确切的问题。 那个团队是 [Turso](https://turso.tech/)，他们的解决方案是 [libSQL](https://github.com/tursodatabase/libsql)。

Libsql 是 SQLite 的分叉，它引入了运行时的一系列改进，同时保持与经典 SQLite 的兼容性。 libsql 采用了一个用于 JavaScript/TypeScript 的现代数据库客户端，它避免了困扰生态系统其余部分的本机绑定和编译步骤。 它甚至可以通过 Wasm 在 [StackBlitz](https://stackblitz.com/) 上运行。

Turso 还为 LibSQL 数据库提供托管，特别关注我们需要的规模（稍后将详细介绍）。 Astro DB 的愿景开始融合在一起，但直到 2023 年 12 月，所有的碎片才最终会到位。

以Astro方式设计本地数据库
---------------------------------------

启动开发服务器后，Astro DB 会立即为您提供一个完全本地的 libsql 数据库。 以我们作为静态站点生成器的背景，重要的是在启动时可以从头开始构建数据库，以便将来它可以为数据源的内容层提供来自各种位置（包括文件系统）的内容。

当您运行 `astro dev` 时，Astro DB 将：

*   在`.astro/data.db`创建一个空数据库
*   从 `db/config.ts` 中读取您的模式
*   从`db/seed.ts`中获取数据库
*   您的数据库客户端现已准备就绪

工作流程在很大程度上反映了 Astro 用户已经喜欢的内容集合工作流程。 重要的是，数据库本身 (`data.db`) 是 _not_ _persistent_。 每次启动开发服务器时，它都是从头开始创建的。 这为您提供了 _simple、reproducible_ 一次性数据库。

Astro DB 将 Web 框架、模式、种子文件和数据库本身整合到一个单一的凝聚力故事中。 我们甚至为您提供了一个 ORM：毛毛雨。 我们选择了 Drizzle，因为它是一种类型安全的 ORM，可以让您随心所欲地接近金属，并且还可以插入，这允许我们在顶部添加自己的行为。

使用托管数据库进行远程处理
---------------------------------

Astro DB 包含一个托管的 LibSQL 数据库，您可以在本地开发和生产过程中连接到该数据库。 一切都通过我们的 Astro Studio 平台为您管理。 您可以在约 30 秒内为您的项目创建一个新数据库。

为了实现我们知道我们在平台上需要的那种规模，我们与维护 LibSQL 并运营最大的 LibSQL 托管平台的 [Turso](https://turso.tech/) 合作。 他们对“每个租户数据库”模型的承诺非常适合我们按需开发数十万个数据库的需求。

去年我们还花了一些时间对 Cloudflare 的 D1 产品进行原型设计。 我们喜欢这个项目的愿景，但当我们只需要数据库时，我们就在添加了 worker 和 worker 绑定的抽象层时遇到了困难。 我们也犹豫着建立专有的数据库技术（D1），特别是如果这意味着将该技术捆绑到Astro本身中。 最终，我们发现 D1 不适合我们的用例。

零停机模式迁移
------------------------------

您的数据库架构在项目 `db/config.ts` 文件中定义。 当您对架构进行更改时，您需要以消除数据丢失和停机的风险的方式将它们推送到托管数据库。 所以我们建造了`astro db push`

`push` 命令旨在平衡易用性，同时仍鼓励适用于生产大型项目的最佳实践。 在 Astro DB 中，没有要管理的迁移文件。 相反，当您运行 `push` 时，您的架构会自动与托管的生产数据库进行比较，并应用任何新的更改。 如果这些更改无法安全添加或以任何方式面临任何数据丢失的风险，则将不会应用这些更改。

这鼓励了 Astro DB 应用程序中的 [“expand and contract” migration](https://planetscale.com/blog/safely-making-database-schema-changes) 策略。 当然，如果您正在进行快速开发并且不介意根据需要重置数据库，则可以运行 `astro db push --force-reset` 来推送您想要的任何模式更改，包括数据库重置。

在登陆这个最终版本之前，我们经历了一些不同的模式迁移系统的迭代。 有一次，我们甚至有一个 `migrations/` 文件夹，您可以在其中手动创建和检查显式迁移计划文件到您的仓库中。 虽然有些人更喜欢这种模型，但我们发现大多数用户在更改架构时都要记住去创建迁移是一个烦人的额外步骤。

包起来
------------

我们对 Astro DB 的第一次迭代为未来的本地用例奠定根源的同时提供了一种简单的方法来部署生产数据库，我们很满意。 本文遗漏的一个细节是集成如何能够提供自己的表和数据，我们希望在我们继续沿着构建 Astro 中内容和插件的下一次迭代的道路上探索更多内容。

要开始集成您的应用程序，请查看 [docs](https://docs.astro.build/en/guides/astro-db/)。
