一个多月前，我们讨论了可能迁移到 Node.js 测试运行器。 虽然我们对 Mocha 非常满意，但我们一直在寻求让 CI 工作更快。

依靠在我们运行时中烘焙的测试运行器对我们的主要 Monorepo 有一些优势：

*   在我们的 Monorepo 中安装和维护的依赖项较少：`mocha` 和 `chai`。
*   维护性：Node.js 项目中涉及更多的人来维护 Node.js 测试运行器。
*   未来的好处：我们相信测试运行者会随着时间的推移而改善，并最终在我们的 CI 工作流程中节省一些时间。

从一个想法到一个 POC
----------------------

Astro Monorepo 有 500 多个测试套件：在集成测试和单元测试之间，我们有 664 个套件，总共有 1603 个测试。 这些测试中的大多数是**集成**测试。

在我们的Monorepo中，集成测试意味着创建一个小的Astro项目，使用特定环境（开发、静态生成（SSG）或动态生成（SSR））构建此项目，然后在**built**页面上运行断言。 没错，每个集成测试都需要 `vite` 来构建和捆绑项目。

在决定进行这次迁移之前，我们希望确保离开摩卡不是错误。 尽管有怪癖，摩卡还是一个非常有能力的测试跑者！ 它已经存在了很长时间，并且经过了战斗测试。 如果你使用摩卡，你就在很好的手中。

POC的想法是为了理解：

*   Node.js CLI 参数的灵活性以及测试报告器的可定制性。
*   测试套件的执行速度。
*   整体开发者体验。

### 我们是如何开始的

我们首先迁移了尚未使用 `astro` 集成套件的软件包中的 **一个**：`create-astro`。 这是一个很好的机会来使用内置的断言库 `node:assert`，了解它提供的选项，并评估其与 Mocha 相比的性能。

由于 `create-astro` 只有少数测试，因此将测试文件迁移到使用 `node:test` 和 `node:assert` 而不是 `mocha` 和 `chai` 相对容易。 之后，唯一剩下的就是将 `mocha` 命令更新为 `node --test` 以执行测试。 但是，我们使用 `node --test` 命令很快遇到了问题，包括：

*   在传递多个参数（例如 `node --test "test/*.test.js" --test-name-pattern="foo"`）时，它无法解析 glob 语法。
*   无法通过 `--test-concurrency` 标志（仅在 Node.js 21 及更高版本中可用），但可以使用 [programmatic API](https://nodejs.org/api/test.html#testname-options-fn) `concurrency` 选项解决。
*   nitpicking，但参数名称是冗长的：`--test-name-pattern` 而不是 `--match, -m` 参数； `--test-timeout` 代替 `--timeout, -t` 参数等。

因此，为了解决这些问题，我们创建了一个 [custom script](https://github.com/withastro/astro/blob/3757a212c01cee03b8e96e1e9697a187ae7cc290/scripts/cmd/test.js)，可以使用 `astro-scripts test` 命令调用。 这个决定也被证明是有用的，以便您将在后面看到更多的变通方法。

### 打开潘多拉的盒子

成功迁移第一个包后，我们尝试迁移 `@astrojs/node` 包的测试套件。 这种集成是我们下载次数最多的集成之一，因此我们进行了大量测试。 另外，这个包的测试都有**集成测试**，所以这是检查测试运行器性能的好机会。

一旦 PR 准备就绪，我们注意到 _node.js test runner_ **比 mocha 慢得多**。 我们进行了调查，我们发现 Node.js 为每个测试文件生成了一个新进程，以确保每个测试套件都在 **isolation** 中运行。 通常，单独运行测试套件是一种很好的做法，因为它可以确保测试在未受污染的环境中运行。

然而，我们的测试套件已经被隔离了。 事实上，我们能够使用主线程使用 Mocha 运行我们的测试套件，而不会遇到任何典型问题：副作用、污染环境等。不幸的是，Node.js 没有提供在同一线程中运行所有测试的选项。 所以，我们必须想出一个解决慢测试运行的解决方案。 （毕竟，我们不是工程师吗？我们解决问题！）

使用我们的内部 `astro-scripts test` 命令，我们可以通过创建一个 _temporary 文件来解决这个问题，该文件 **imports** 所有测试套件_，我们让 node.js 测试单个文件。 这样，文件只生成了一个进程，我们达到了与使用主进程相同的性能水平。

然而，这个**也有它自己的缺点**：如果测试失败或超时，我们无法分辨出哪个测试是原因。 这是我们发现的主要怪癖，虽然不是每个团队都可能做出了这个选择，但我们接受了这种权衡，以便为我们提供前面提到的好处。 毕竟，我们以前接受过摩卡的怪癖！

### Node.js `assert` 和 `chai`

在迁移过程中，我们必须删除 `node:assert/strict` 的 `chai` 库。 此任务发现，使用 `chai` 可以以不同的方式执行相同的检查。 例如，您可以至少以**四种不同的方式运行相等性检查：

从“chai”导入 { expect }；
expect("foo").to.eq("foo")expect("foo").to.be.eq("foo")exp 。 ect("foo").to.equal("foo")expect("foo").to.be.equal("foo")

一方面，拥有这种灵活性是件好事。 但另一方面，测试的代码变得不一致。 使用 Node.js 断言模块，只有一种方法可以执行此检查：

从“node:assert/strict”导入 { assert };
assert.equal("foo", "foo")

Node.js 断言模块**提供了我们所需的几乎所有功能**，因此从 `chai` 的迁移并没有我们想象的那么痛苦。 我们对 `chai` 的使用非常少。 但是，**我们确实错过了`chai`的`.includes`快捷方式：

从“chai”导入 { expect }；
expect("这是一个美好的一天").includes("fine")

node.js 断言模块不提供这样的实用程序，因此我们最终使用了 `String#includes` 函数的相等性断言：

从“node:assert/strict”导入断言；
assert.equal("这是一个美好的一天".includes("fine"), true)

### 这里是龙

如前所述，我们有很多测试文件，我们几乎每天都会添加新的测试。 开设一次性公关，完成整个单仓的迁移是不可行的。 这将需要一个人的大量工作，并且保持分支更新会带来压力。

所以我们想出了一个简单的计划：

*   首先迁移Monorepo内的小包。
*   通过在同一个 CI 中使用 mocha 和 node.js 测试运行程序，慢慢迁移主包 - `astro`。
*   移除摩卡。

为了实现这一目标，我们**向我们的社区寻求帮助**。 我们认为这是一个**完美**的机会，让**不熟悉 Astro 业务逻辑的人为该项目做出贡献。 而且，我们可以让迁移过程更快。

我们创建并固定了一个 [umbrella issue](https://github.com/withastro/astro/issues/9873) 来协调努力。 每个贡献者**获取单个包的迁移的所有权**，为每个包打开一个单独的 PR。 该项目的两位新的首次贡献者甚至加入了这项工作。 这是一件了不起的事情。 在**一周**，我们能够迁移所有包裹！

迁移主包 `astro` 是一项壮举！ 它是迄今为止包含最多测试数量的包。 为了缓慢而仔细地执行这种迁移，我们必须提出一个开箱即用的解决方案。

我们设置了 Node.js 测试运行器来仅测试名为 `*.nodetest.js` 的文件。 这样做允许我们继续测试 CI 中的所有文件。 然后，其余的只是通过提供（和记录！）一个明确的过程来协调我们的社区，让他们遵循：

*   使用伞式问题告诉其他贡献者您打算迁移哪些文件；
*   将文件重新命名为从`*.test.js`迁移到`*.nodetest.js`；
*   迁移文件；
*   打开 PR，等待审核，如果成功，Astro 维护者将合并 PR。

在 [@log101](https://github.com/log101)、[@mingjunlu](https://github.com/mingjunlu)、[@VoxelMC](https://github.com/VoxelMC)、[@alexnguyennz](https://github.com/alexnguyennz)、[@xMohamd](https://github.com/xMohamd)、[@shoaibkh4n](https://github.com/shoaibkh4n)、[@marwan-mohamed12](https://github.com/marwan-mohamed12)、[@at-the-vr](https://github.com/at-the-vr) 和 [@ktym4a](https://github.com/ktym4a) 的帮助下，我们在**一周内迁移了近 300 个测试套件！

### 结果

我们对结果非常*********************** 我们**没有看到**我们测试的性能**有任何重大的**回归。 Node.js 提供的断言模块具有我们需要的所有实用程序，支持 `describe`/`it` 模式，因此从 Mocha 的迁移顺利。

然而，与使用 Mocha 相比，开发人员体验仍然存在一些问题。

例如，在 Mocha 中运行 _one_ 单一测试套件，使用 `it.only` 就足够了。 使用 Node.js 测试运行器，您必须：

*   使用 `--test-only` 参数运行 CLI。
*   将`.only`添加到包含要运行的`it.only`的`describe`中。
*   如果有多个`describe`的实例，都需要用`.only`标记。

另一个例子是可以改进使用 `--test-name-patterns`。 此参数仅用于运行与特定名称模式匹配的测试。 DX 不是很好，因为 CLI 会在终端上堆满关于 **tests 不匹配**（未运行）的消息。 这使得了解实际运行的测试变得更加困难。 另外，命令 ** 非常慢**仅用于运行与某些模式匹配的测试。

Node.js 测试运行器仍然是**年轻的**，并且有了积极的发展，所有合适的卡片都可以变得更好。 例如，Node.js 项目当前 [**evaluating**](https://github.com/nodejs/node/pull/51579) 在我们 [voiced](https://github.com/nodejs/node/issues/51548) 用例之后使用主进程运行测试。

本着真正开源协作的精神，我们很高兴通过将测试切换到 Node.js 来改进 Astro ，反过来又将改进 Node.js 本身！
