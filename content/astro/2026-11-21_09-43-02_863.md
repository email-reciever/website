**本周我们发布了 Astro 5 的第一个测试版，其中包括一种全新的 Astro 内容处理方式。 这篇文章深入研究了内容层 API，展示了它的工作方式以及如何使用它来构建您的网站。**

Astro 的诞生是为了创建内容驱动的网站。 虽然它现在也可以用于构建各种动态应用程序，但对于围绕大量内容构建的网站来说，它仍然是最好的。 从使用 [Cloudflare](https://developers.cloudflare.com/) 和 [StackBlitz](https://tutorialkit.dev/) 等星光构建的功能齐全的文档网站到 [Porsche](https://www.porsche.com/usa/) 和 [Netlify](https://www.netlify.com) 等品牌的精美营销网站，每天有数百万用户已经在欣赏您可以使用 Astro 构建的快速且可访问的网站，数千名工程师最喜欢 行业开发者经验。

在 Astro 2 中，我们引入了 [Content Collections](https://docs.astro.build/en/guides/content-collections/) 作为组织本地内容、以类型安全性和扩展到数千页的强大新方式。 内容集合为 Markdown 和 MDX 等本地文件提供了一流的开发人员体验，但我们从您那里听说您希望您的所有内容都具有相同的优势，包括远程 API。 同样清楚的是，当许多人在构建具有数千页的网站时，我们的内容集合 API 难以扩展到数万个页面，构建速度较慢且内存占用过多。

在 6 月 [we shared an early preview of our plan](https://astro.build/blog/future-of-astro-content-layer/) 中，通过内容层 API 支持的全新类型内容集合来解决这些问题以及更多问题，该内容为您提供了所需的灵活性。 我们设想在 `src/content` 中仅使用文件集合，并允许您从任何地方加载您的内容。 我们一直在测试扩展到前所未有的尺寸的集合。 从我们的 [first experimental release in Astro 4.14](/blog/astro-4140/#experimental-content-layer-api) 开始，我们一直在努力稳定这个新的 API 以在 Astro 5 中发布。

什么是内容层
--------------------------

内容层 API 是您知道和喜爱的内容集合的未来。 它允许您在构建站点时从任何源加载数据，然后使用简单、类型安全的 API 在您的页面上访问它。

Content Layer API 不关心您的数据存储在哪里。 一个集合仍然可以是本地 Markdown 文件，另一个可以调用 API，而另一个集合可以位于您的文件系统的其他位置。 使用与以前相同的 `getEntry()` 和 `getCollection()` 功能，您可以从同一页面上的许多来源加载数据。 没有性能打击：Astro 在构建之间本地缓存数据，这意味着更新可以快速，并且可以最大限度地减少需要进行的 API 调用的数量。 当然，一切仍然是类型安全的，TypeScript 类型是从您的模式自动生成的。

如果您以前使用过内容集合，您将认识到以下许多概念和术语。 事实上，我们在您的项目中的 _using_ 集合并没有太大变化！ **collection** 仍然是一组共享共同模式的条目。 每个条目都有一个唯一的 ID。 它类似于关系数据库中的表。

但是现在，每个集合都使用 **loader**，它定义了如何加载条目来填充该集合。 加载器可以是返回条目数组的基本内联函数，也可以是处理自己的缓存和数据存储的更高级的对象。 第一批加载器已经在 npm 上作为模块分发。

每当您的站点构建时，都会调用每个集合的加载器，然后更新本地 **数据存储**。 您可以使用熟悉的 **`getCollection()`** 和 **`getEntry()`** 函数查询该数据存储。 这是在预渲染页面的构建时完成的，或者在使用按需适配器的服务器渲染期间完成。 在每种情况下，相同的数据是可用的，即构建时的快照。

内容层生命周期
------------------------

当 `astro build` 或 `astro dev` 运行时，并行调用每个集合的加载器。 这些加载器更新了它们自己的范围内的数据存储，该存储在构建之间保留。

![](/_astro/astro-build.CiM2_OCF_Zybr0B.webp)

Astro 组件和页面然后可以使用 `getCollection` 或 `getEntry` 来查询数据。 数据在那一点是不可变的，因此页面都在查询相同的快照，在构建时编译。 这适用于在构建时预渲染页面，还是按需呈现的服务器。 这里要注意的重要一点是**数据存储仅在构建时更新：部署的站点无法更改数据存储。** 如果数据源需要更新集合，则必须通过触发新构建来执行此操作。

虽然在生产中是不可变的，但在运行 `astro dev` 时，用户可以使用 `s+enter` 热键或通过集成按需更新数据存储。 他们可以通过多种方式执行此操作，例如注册开发刷新端点或向 CMS 打开套接字以监听更新。

装载机的工作原理
-------------------

第一个示例展示了如何构建一个简单的内联加载程序，但您不需要停在那里。 借助 Object Loader API，您可以使用更高级的功能制作功能强大的 Loader。 对象加载器通过数据存储对象与内容层交互。 这是一个范围作用于单个集合的键值存储。 集合只能访问其自己的条目，但可以完全控制这些条目。 如果加载程序知道其数据源没有更改，则可以完全跳过更新，或者它可以更新已更改的条目。

Content Layer API 提供了一些工具来使这变得更容易。 首先是元数据存储，可用于存储任意值，例如“上次修改”时间或同步令牌。 比较这些将允许加载器执行条件 API 请求或使用增量同步 API。

当 _not_ 使用内容集合时
-----------------------------------

以前很清楚内容集合是一个好主意：每当您在页面中使用本地内容时！ 内容层 API 为您提供了更多的功能和灵活性，因为您可以将其用于任何内容源，包括实时 API。 但是，重要的是要记住，只有在构建站点时才会更新数据，因此它不会为每个用例提供服务。

这意味着当您的数据相对较少地变化时，例如博客，集合是完美的。 如果您正在编写托管在 CMS 中的博客，则每当您发布新帖子时，您都可以使用 webhook 触发构建。 内容层的增量更新应该使此构建速度更快。

这同样适用于大多数电子商务网站，当产品被编辑时可以触发构建。 如果您可以等待部署站点以发布更新所需的时间，那么内容集合仍然是您的明显选择。 您将获得最佳性能和出色的开发人员体验。

如果您需要实时更新或使用个性化内容进行更新，那么最好使用按需渲染适配器，最好使用 CDN 缓存标头，以确保页面加载速度超快。 您甚至可以使用 [server islands](https://5-0-0-beta.docs.astro.build/en/guides/server-islands) 将两者结合起来并获得两全其美的最佳效果 - 使用内容集合呈现主要内容，并使用服务器岛来获取实时或个性化内容。

接下来是什么
------------

内容层 API 是 Astro 向前迈出的一大步，但我们才刚刚开始。 目前，数据存储只是一个键值存储，过滤有限。 这速度快但内存效率不高，查询也不是很灵活。 我们的目标是在未来版本中引入基于 Astro DB 的后端，以帮助其扩展到数十万页。 它还将允许我们支持更复杂的查询，甚至可能实时更新。

与此同时，我们很想听听您对 Content Layer API 的反馈！ 尝试迁移您现有的网站以使用它。 ([It’s easy, we promise!](https://5-0-0-beta.docs.astro.build/en/guides/upgrade-to/v5/#legacy-v20-content-collections-api)) 并让我们知道它是如何进行的。 为您最喜欢的 API 尝试一些新的 [loaders built by the community](https://www.npmjs.com/search?q=keywords:astro-loader) 或 [build your own](https://5-0-0-beta.docs.astro.build/en/reference/loader-reference/)。 我们很高兴看到您用它构建的东西！
