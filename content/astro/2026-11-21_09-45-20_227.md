Astro 2.6 已经上市，而且很重要！ 几个实验功能已被标记为稳定，现在在所有 Astro 项目中都可用（不需要“实验性”标志）：

*   **[Middleware](#middleware)**
*   **[Hybrid SSR output mode](#hybrid-ssr-output-mode)**
*   **[Custom client directives](#custom-client-directives)**
*   **[CSS inlining](#css-inlining)**

Astro 2.6 还引入了新功能和改进，包括用于管理重定向的新实验功能：

*   **[Redirects (experimental)](#redirects-experimental)**：在 Astro 配置中设置单个页面重定向。
*   **[Markdoc improvements](#markdoc-improvements)**：MarkDoc 现在与 Astro 中的 MDX 具有功能奇偶校验。
*   **[Language tool improvements](#language-tool-improvements)**：Astro VSCode 扩展获得升级，由 Volar 提供支持。

如果您已经安装了Astro，则可以通过在项目中运行`upgrade`命令（使用您选择的软件包管理器）将其升级到2.6：

npm install astro@latestpnpm 升级 astro@latestyarn 升级 astro@latest

当您使用它时，也可以升级您安装的任何 `@astrojs/*` 集成和适配器！

中间件
-----------

[Middleware](https://docs.astro.build/en/guides/middleware/) 现在是稳定的，并且在没有实验标志的所有项目中可用。 中间件允许您在呈现页面并返回给用户之前或之后运行代码。 这为 Astro 项目带来了新的控制层，并为身份验证、重定向、标头修改等解锁了新的钩子。

src/middleware.ts

export async function onRequest(context, next) { // 在处理请求之前做一些事情。 const response = await next() // 或者，在返回响应之前做一些事情。 返回响应}

Astro 2.6 还引入了一个新的 `locals` 对象来传递来自中间件的数据。 附加到 `locals` 对象的任何数据都将保留并可从任何 Astro Page 组件或 API 端点函数的 `Astro.locals` 全局读取。

以下是如何在中间件中实现基本身份验证检查，将加载的用户上下文传递到页面路由的示例：

src/middleware.ts

// 示例：Middleware.export 异步函数 onRequest({ cookie, locals }, next) { // 检查“sid”用户会话 id cookie 中的简单身份验证检查。 // 如果 cookie 丢失，返回 405（不允许）。 const sessionID = cookies.get("sid"); if (!sessionid) { 返回新响应(null, {status: 405}); } // 使用您自己的 `getUser()` 函数来验证用户。 // 如果用户不真实，则返回 405（不允许）。 const user = await getuser(sessionid); if (!user) { 返回新响应(null, {status: 405}); } // 将加载的用户附加到 `locals` 对象。 // 现在，它可以在页面路由中读取！ locals.user = 用户； // 返回 `next()` 返回响应。 返回 next();}

`locals.user` 对象现在保证在您的项目中存在，并且可以在任何渲染页面或 API 端点处理程序中读取。

src/pages/index.astro

---const { 用户 } = astro.locals---
<h1>你好{user.name}！</h1>

中间件是在Astro 2.4的一个实验标志后面引入的。 API现在稳定，所有没有旗帜的Astro开发人员都可以使用。 阅读我们的 [Middleware documentation guide](https://docs.astro.build/en/guides/middleware) 以了解更多信息。

混合SSR输出模式
-----------------------

Astro 的新型混合 SSR 输出模式现在稳定，所有 Astro 开发人员都可以使用，没有实验标志。 设置 `output: "hybrid"` 允许您将交互式 API 端点和页面混合到站点中，同时默认情况下保持整个项目的静态和预渲染。

astro.config.mjs

导出默认 defineConfig({ 输出：“hybrid”，适配器：netlify(),})

Astro 的新 `"hybrid"` 输出模式有助于弥合静态和动态之间的差距。 混合输出模式在您的项目中解锁与原始 `"server"` 输出模式相同的 SSR 功能，其中一个关键区别是：每个页面将默认为静态预渲染。 这更接近于 `"static"` 构建输出的行为，其中每个页面都预先渲染到 HTML 以获得来自服务器或 CDN 的即时响应。 但与 `"static"` 模式不同，混合输出模式在您的构建输出中包含一个服务器，因此您现在可以向您的站点添加其他动态页面和 API。

例如，一个机构可以使用 Astro 的新混合输出模式，只需几个步骤即可将动态“联系我们”表单处理程序添加到其静态网站。 将 `output` 选项设置为 `"hybrid"` （如果还没有添加 [deploy adapter](https://docs.astro.build/en/guides/deploy/)）。 这将保持与以前相同的“默认”行为，但您现在可以将该表单的 API 端点与 `export const prerender = false` 标记为动态，以便它在每次表单提交时运行。

src/pages/api/form-handler.ts

// 将页面标记为 `prerender = false` 以跳过预渲染// 并在每次提交时在服务器中运行 API 端点。export const prerender = false
导出函数 post({ request }) { // ...}

此功能由 Astro 社区成员 [@MoustaphaDev](https://github.com/MoustaphaDev) 提供，并来自我们的 [public roadmap](https://github.com/withastro/roadmap) 和 RFC 流程。 谢谢!

自定义客户端指令
-------------------------

自定义客户端指令现在是稳定的，所有 ASTRO 开发人员和集成作者都可以使用，没有实验标志。

客户指令是Astro的岛屿建筑的基石。 它们控制交互式 UI 在您的页面上，逐个组件级别加载的方式。 Astro 有许多内置指令，例如 `client:idle`（“嘿 Astro，一旦页面空闲，加载此按钮”）和 `client:visible` （“嘿 Astro，仅在页面上可见时才加载此图像轮播”）。 到目前为止，永远无法定义您自己的自定义客户端指令。

例如，您现在可以定义自己的 `client:hover` 指令，当用户悬停在交互组件上时，它将仅加载和水化交互组件：

astro.config.mjs

从“./directives/client-hover.js”导入“Astro/Config”导入 onHoverDirective { defineConfig }
导出默认 defineConfig({ 集成：[onHoverDirective()],})

添加后，集成将定义 `client:hover` 行为，以便您可以开始在自己的项目中使用它：

    <Counter client:hover />

创建您自己的客户指令，或将其发布到 npm 与他人分享！

自定义客户端指令首先在 Astro 2.5 的实验标志后面引入。 API现在稳定，所有没有旗帜的Astro开发人员都可以使用。 阅读我们的 [Custom client directives guide](https://docs.astro.build/en/reference/integrations-reference/#addclientdirective-option) 以了解更多信息。

css 内联
-------------

Astro 2.6 引入了一个新的配置选项，可以自动将 CSS 的小片段插入到您的 HTML 中。 这种优化可以通过减少加载页面所需的请求数量和外部样式表的数量来加速大多数页面（尤其是在第一次加载时）。 您可以通过在配置文件中设置 `inlineStylesheets: "auto"` 来立即尝试：

astro.config.mjs

从“astro/config”导入 { defineConfig }
导出默认 defineConfig({ build: { inlineStyleSheets: "auto", },})

自动 CSS 内联可能会成为 Astro 3.0 中的默认行为。 阅读我们的 [Configuration Reference](https://docs.astro.build/en/reference/configuration-reference/#buildinlinestylesheets) 以了解有关此选项以及如何为您的项目配置它的更多信息。

此功能由 Astro 社区成员 [@lilnasy](https://github.com/lilnasy) 提供，并来自我们的 [public roadmap](https://github.com/withastro/roadmap) 和 RFC 流程。 谢谢!

重定向（实验）
-------------------------

Astro 2.6 引入了一个实验性的新功能，可以更轻松地在项目中添加重定向。 要使用它，您需要在项目配置文件中启用实验标志 `experimental.redirects`。

astro.config.mjs

从“astro/config”导入 { defineConfig }
导出默认的 defineConfig({ 重定向: { "/old": "/new", }, experimental: { redirects: true, },})

传统上，重定向留给开发人员自己弄清楚。 这为开发人员创造了更多的工作，并且在不同的主机之间以一种在开发和生产中一致运行的方式特别困难。

Astro 的新 `redirects` 功能通过一个 API 来解决这个问题，用于在 Astro Config 中直接管理您的重定向。 这可以在开发和生产中使用，并且可以使用我们现有的 `adapter` API 进一步优化特定主机。 例如，Netlify 适配器会通过 CDN 自动将您的重定向转换为特定于 Netlify 的 `_redirects` 文件，以获得最快的性能。

我们的目标是有一种可靠的方法来配置跨 [all of our supported hosts and adapters](https://docs.astro.build/en/guides/integrations-guide/#official-integrations) 的重定向。 在这个实验期间我们正在寻找反馈，所以请尝试一下，并在 [Discord](https://astro.build/chat/) 上与我们分享您的经验。

MarkDoc 改进
---------------------

[Markdoc](https://docs.astro.build/en/guides/integrations-guide/markdoc/) Astro 的支持随着 `@astrojs/markdoc` 的最新版本继续得到改善。 这个新版本为Astro中的Markdown和MDX带来了完全的功能，包括标题中的自动`id`生成，更好的语法突出显示支持，以及支持`extends`的配置扩展。

我们与 Stripe 的 MarkDoc 团队密切合作，不断改善 Astro 的内容作者体验。 看到 MarkDoc 生态系统的发展令人兴奋，我们很自豪能成为其中的一员！

语言工具改进
---------------------------

Astro 的语言工具通过 `@astrojs/language-server` 和 [2.0 VSCode Extension for Astro](https://marketplace.visualstudio.com/items?itemName=astro-build.astro-vscode&ssr=false#review-details) 的 2.0 版本进行了重大升级。 此版本完成了对 [Volar](https://volarjs.github.io/) 的主要重写和内部迁移，以提高性能、功能和稳定性。

Volar 是 Vue 团队提供的语言工具的通用框架。 使用像 Volar 这样的框架为我们的语言服务器带来了一些好处，类似于 Astro 在内部使用 Vite 的方式。 Volar 让我们花更少的时间精心地围绕工具重新创建轮子，并为我们的用户建立更多时间构建功能。 VSCode、`astro check` 和 Astro Language Server 的所有其他使用者都应该受益于此更改。

Volar 正在迅速成为所有语言都可以构建的标准框架，我们很高兴支持该项目。 我们期待着继续为包括Astro Developers在内的所有人改进Volar。

特别感谢 [Johnson Chu](https://twitter.com/johnsoncodehk) (Volar Manager) 帮助我们完成这个项目！
