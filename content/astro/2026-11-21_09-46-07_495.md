今天，我们很高兴地宣布在 Astro 中对服务器端渲染 (SSR) 进行实验性支持。 在 Astro 中的 SSR 中，我们解锁了全新的用例（电子商务，任何人？）和以前不可能实现的规模。 我们的 SSR 实现将 Astro 独特的服务器优先方法与用户身份验证、登录流程、数据库访问、数据获取等动态功能相结合。

如果您准备好跳入，请前往 [the docs](https://docs.astro.build/en/guides/server-side-rendering/) 并开始使用。

动机
-----------

我们听到了！ 我们最常遇到的问题之一是“Astro能做SSR吗？”

当我们开始构建 Astro 时，我们决定专注于通常称为“JamStack”（也称为静态站点生成或 SSG）的预构建的静态站点架构。 这种方法让我们快速迭代和推出新功能，但有一些重要的限制：

*   大型网站不能在不引入更长的构建时间或更慢的动态内容客户端渲染的情况下预渲染到静态HTML。
*   动态站点无法在数据更改时强迫您重建和重新部署站点的某些部分，从而预先渲染到静态HTML。
*   如果不将所有用户个体化的数据移动到客户端，交互式站点就无法预先渲染到静态 HTML。 当您处理静态的预构建 HTML 时，用户名、头像和权限都变得更加复杂。

电子商务尤其受到上述三个问题的伤害。 在每毫秒加载性能的行业中，如何在没有限制的情况下获得静态 HTML 的出色性能？

从第一天起，我们就知道 Astro 的岛屿建筑方法在解决这个问题方面具有独特的优势。 岛屿允许页面快速加载并懒惰地变得互动； 用户可以更快地看到并能够与页面中最重要的部分进行交互。

输入：服务器端渲染（SSR）
---------------------------------

服务器端渲染是一个很好的解决方案，可以追溯到互联网的早期时代。 SSR 不是灵丹妙药，但如果做得好，SSR 是某些用例的宝贵工具。

以用户身份验证为例。 通过静态站点生成，您有几种不同的方法：

1.  在本地存储中检查cookie或JWT，如果用户没有，则重定向到登录页面。 如果使用 cookie 会阻止使用 `HttpOnly`，请向您开放恶意 JavaScript 攻击。
    
<script> if (!parseCookie(document.cookie).auth) { window.location = "/login" }</script>
    
此外，如果令牌无效，您会怎么做？ 在这种情况下，您仍然需要检查和响应。
    
2.  调用一个 API，它将检查用户是否已登录，例如 `/api/auth`。 走这条路线意味着您需要在等待响应时在每个岛屿中显示加载旋转器。
    
函数 app() { const auth = useauth() if (auth.loading) 返回 <AnnoyingLoadingSpinner /> if (!auth.loggedin) return <LoginPage /> return <UserProfile user={auth.user} />}
    

无论您的方法如何，在客户端进行身份验证总是意味着：

*   如果 JavaScript 被禁用，事情将无法运行。
*   您的服务器只能响应 `200 OK` 响应代码。
*   这很慢。 用户必须等待完整的 HTML 响应（包括 JS、CSS 等），即使他们立即重定向。 这会在用户登陆正确的页面之前创建多个页面请求。

### ASTRO SSR：设计简单

Next.js、Nuxt、Gatsby、Sveltekit 和整个现代 JavaScript 元框架已经对 SSR 有了一些想法。 是什么让 Astro SSR 如此特别？

与在我们之前处理过 SSR 的当前一组以 JavaScript 为重点的元框架相比，Astro 具有一个关键优势：**ASTRO 旨在在服务器上运行。**

借助 Astro，您可以自由地编写您的服务器代码在您的脑海中的工作方式，摆脱其他“通用”SPA-优先框架附带的不必要的抽象。 虽然 Spa-First 思维对于超级有状态的 Web 应用程序（想想仪表板、应用程序、门户）可能非常有用，但大多数以内容为重点的网站最好不付钱是一个成本。

以下是仅使用 5 行 JavaScript 的 Astro SSR 中用户身份验证的工作方式：

src/pages/index.astro

---// 在 Astro 组件 (*.astro) 中，您直接// 在组件的前提下编写服务器代码（这两个 --- 栅栏之间的空间）。
// 1. 导入任何依赖项（对 JavaScript/TypeScript 的全面支持）import { getuser } 从 "../api/index.js"
// 2. 检查用户令牌是否存在且不是 malicious.const user = await getUser(astro.request)
// 3. 如果没有找到用户，则返回重定向。 这会立即//使用正确的状态代码和标头完成响应。if (!user) { return astro.redirect("/login")}
// 4. 如果用户登录，您现在可以使用页面模板中的 `user` object// 显示头像、名称等---
<html> ... <h1>您好 {user.name} 👋</h1> <img src={user.avatar} alt={user.name} /> ...</html>

Astro Front Matter 就像一个函数调用，它接受一个请求并返回一个渲染的模板。 由于它是一个函数调用，您可以处理请求，获取要输入模板的数据，并在需要时提前退出（与重定向一样）。

### API 路线

Astro 的 html 优先的 Web 开发方法将让您自己走得很远，但 Astro 也支持使用您最喜欢的框架（如 React）的交互式 UI。 在为客户端构建时，通常需要端点在用户和服务器之间读取和写入数据。 内置的 API 路由可以满足这种需求。

在 Astro 中，API 路由是 `src/pages/` 文件夹中的 `.js` 或 `.ts` 文件，它接受请求并返回响应。 API 路由旨在实现最大灵活性：

*   为无JS表单提交构建表单提交处理程序。
*   为用户文件提交构建上传处理程序。
*   为客户端构建一个基于JSON的REST API。
*   构建动态资产路线以返回任何文件类型，包括图像和视频。

API 路由通过导出实现 HTTP 方法的函数来工作。 以下是保存用户配置文件的示例 API 路由：

src/pages/api/profile.js

导出异步函数 post(params, request) { const profile = await request.json() await sawait saveprofile(profile) 返回新的响应(json.stringify({ ok: true }), { status: 200, headers: { "content-type": “应用程序/JSON”，}，})}

适配器：在任何地方部署 Astro
------------------------------

现代网络主机为开发人员的体验设定了很高的标准。 开发人员希望框架能够与他们最喜欢的提供商集成，而无需太多配置或设置。

当我们构建 Astro SSR 时，我们评估了其他框架解决此问题的不同方式。 最后，我们决定追随[SvelteKit](https://kit.svelte.dev/)和[Remix](https://remix.run/)的脚步，采用**_Pluggable Host_** **_Adapters_**的想法。 适配器是简单的可插拔集成，可自动配置您最喜欢的主机的构建。

适配器模型不仅易于开发人员设置，而且还允许我们支持尽可能多的不同类型的主机，包括：

*   使用 **Cloudflare** 和 **Deno Deploy** 完全在边缘运行。
*   在**Netlify**和**Vercel**等现代开发平台上运行。
*   在 **AWS**、**Azure** 和 **Google Cloud** 上的裸金属无服务器功能上运行。
*   在 JavaScript 服务器上运行可以像 **node.js** 和 **deno 一样部署自己。**

Astro 中的 SSR 支持仍是实验性的。 在接下来的两个月中，我们很高兴与所有主要的托管服务提供商合作，为用户关心的每个平台推出更多适配器和合作伙伴。 如果您是有兴趣为 Astro 构建自己的适配器的托管服务提供商，请通过 Discord 或通过电子邮件与我们联系：[partner@astro.build](mailto:partner@astro.build)。

为了庆祝这一公告，我们有幸与我们的发布合作伙伴（和官方托管赞助商）Netlify 合作，为 Netlify 平台推出了官方的第一天适配器。 Netlify 适配器将您的 Astro SSR 构建配置为仅使用一行代码在 Netlify 函数上运行：

从“astro/config”导入 { defineconfig } 从“@astrojs/netlify/functions”导入 Netlify
导出默认 defineConfig({ 适配器：Netlify(),})
