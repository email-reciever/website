本报告的目的是查看实际数据，以更好地了解框架选择、性能和网络上的实际用户体验之间的关系。 我们将尝试阐明几个关键问题：

*   现代 Web 框架在实际使用和性能方面的比较如何？
*   框架选择是否会影响网站的核心 Web 生命体征？
*   框架选择与 JavaScript 的有效负载大小有多大相关性，有什么影响？

数据
---------

为此，我们查看了三个不同的公开可用数据集：

*   [The Chrome User Experience Report (CrUX)](https://developer.chrome.com/docs/crux/) 提供真实世界 Chrome 用户如何体验 Web 上热门目的地的用户体验指标。
*   [The HTTP Archive](https://httparchive.org/) 通过定期收集灯塔性能数据跟踪和报告超过 1500 万个网站的性能。
*   [The Core Web Vitals Technology Report](https://discuss.httparchive.org/t/new-dashboard-the-core-web-vitals-technology-report/2178) 从前两个数据集中收集有用的见解。

**所有数据都是从公开的、独立管理的数据集中收集的。** Astro 团队没有直接测量性能数据。 [Learn more about our methodology in the section below.](#methodology--limitations)

框架
---------------

为了创建这份报告，我们决定研究六种流行的基于 JavaScript 的 Web 框架：[Astro](https://astro.build/)、[Gatsby](https://gatsbyjs.com/)、[Next.js](https://nextjs.org/)、[Nuxt](https://nuxtjs.org/)、[Remix](https://remix.run/) 和 [SvelteKit](https://kit.svelte.dev/)。 我们还尽可能包含 [WordPress](https://wordpress.com/) 中的数据，因为它在网络上的受欢迎程度和巨大的市场份额（43.2%）。

由于在我们选择的数据集中没有足够的实际使用情况，不得不忽略一些令人兴奋的新框架，但我们希望在下一个报告中包含更多框架。

核心网络生命体征
----------------

[Google’s Core Web Vitals (CWV)](https://web.dev/learn-core-web-vitals/) 是一组三个标准化指标，可帮助您了解用户如何体验网页。 每个指标都衡量用户体验的不同方面——负载速度、响应能力、视觉稳定性——它们一起量化了网站的整体性能。

谷歌的 [Core Web Vitals Assessment](https://pagespeed.web.dev/) 是一项测试，它着眼于所有三个指标的真实用户测量数据（来自 [CrUX](https://developer.chrome.com/docs/crux/) 数据集），以确定每个网站的整体通过/失败等级。 要使一个网站通过，它必须满足所有三个指标中**“好”**的[associated threshold](https://web.dev/defining-core-web-vitals-thresholds/)。 如果任何指标未能达到阈值，则该网站将无法进行评估。

CWV 评估在使用真实世界用户数据和测量方面是独一无二的。 这使得它更准确地反映了用户实际体验网站的方式，尤其是在较长的会话中。 Lighthouse 和其他实验室测试工具只能测量第一页负载，这无法捕捉到使用网站的全部经验。

在查看所有使用特定框架构建的已知网站时，Astro 和 Sveltekit 超过了所有测试网站的平均通过率（40.5%），而其余框架则没有。 Astro 是通过 Google 的 CWV 评估的唯一超过 50% 的网站的框架。 Next.js 和 Nuxt 分别排在小组底部，大约有 4 分 4 和 1 分之一的网站通过了评估。

网站未通过谷歌核心 Web 生命体征评估的最可能原因是什么？ 我们可以按个别指标分解数据，以深入了解不同框架在 Web 生命体征方面的挣扎（和成功）。

### 第一次输入延迟（FID）

[First Input Delay (FID)](https://web.dev/fid/) 测量从用户首次与页面交互到浏览器能够响应该交互的时间的时间。 谷歌的 CWV 评估寻找 100 毫秒或更少的 FID。 任何较慢的东西都被认为需要改进并未能通过评估。

大多数框架都可以轻松通过这项测试，超过 90% 或更多的网站通过了评估。 在此测试中，没有框架低于 80% 的通过率。 这意味着大多数测试的网站都对第一次用户交互做出了响应。

### 累积布局偏移（CLS）

[Cumulative Layout Shift (CLS)](https://web.dev/cls/) 测量页面上的视觉稳定性。 要通过此评估，您应该将意外的布局转换减少到接近零的位置，以为您的用户提供可靠的视觉体验。

CLS 是 Google 的一个有趣的指标，可以作为三个核心 Web Vitals 之一，因为它与速度或响应性没有严格关系。 它的包含强调了在衡量网络上用户体验的整体质量方面，不仅仅关注性能的重要性。

在这个指标中，所有框架的得分都达到了 50% 或更高。 然而，在这个指标上得分最高的是最年轻的框架（Astro、Sveltekit 和 Remix）。 在所有测试的网站上，这三个指标的评估均得分超过 75%。

### 最大的内容性油漆（LCP）

[Largest Contentful Paint (LCP)](https://web.dev/lcp/) 是三个核心 Web Vitals 中的最后一个，并且可以说在感知性能方面最重要。 它衡量页面的主要内容可能加载的时间点。 通过 Google 的 CWV 评估，需要 2.5 秒或更短的 LCP。 任何较慢的东西都被认为需要改进并未能通过评估。

LCP 是三个指标中最难掌握的指标。 在所有测试的网站中，只有 52% 通过了这个指标。 在我们测试的六个框架中，只有 Astro 和 Sveltekit 超过了这个平均值。 其余的低于平均水平。

### 即将到来？ 与下一个油漆（INP）的交互

**Next to Next Paint (INP)** 是一个实验性的 Web 重要功能，用于评估整体网站的响应能力，类似于第一次输入延迟 (FID)。 两个指标不同的地方在于，INP 观察到用户在页面上进行的所有交互的延迟，而不仅仅是第一个。 低 INP 意味着该页面始终能够快速响应所有或绝大多数用户交互。

虽然 INP 不是今天的官方核心 Web，但 Chrome 团队已发出信号 [their hope](https://www.youtube.com/watch?v=Mizzbsvv8Os&t=378s) 用 INP 取代 FID，作为更全面、更准确的响应度衡量标准。

那么，框架如何抵御这种新的响应度指标呢？

在图表中最明显的是，每个框架都比第一个输入延迟 (FID) 更难实现一个好的 INP 测量。 虽然每个测试框架的 FID 的通过率都达到了 80% 以上，但没有一个框架能够在 INP 上看到同样的 80% 的通过率。 Astro 以 68.8% 的比分最接近。

值得注意的是，所有跟踪网站的平均通过率都惊人地高 60.9%。 虽然 Astro 和 WordPress 看起来像上图中的出色成功，但这些网站实际上的表现只是略高于行业平均水平。 为什么许多测试过的 Web 框架都在这个指标上挣扎？

一个原因可能是单页应用程序 (SPA) 架构作为客户端操作驱动所有通过 JavaScript 进行的导航。 这为没有客户端导航的多页应用程序 (MPA) 提供了输入延迟的机会。 在 MPA 中，导航到新页面会触发来自服务器的完整页面加载，该服务器未归类为输入延迟。 这可以帮助解释为什么 Astro 和 WordPress（图表中的两个 MPA）在该指标上的表现明显优于其他测试框架（所有 SPA）。

RebelMouse 的 Anne Burnes 对 FID 和 INP 之间的区别进行了精彩的文章：

> FID 量化了用户在尝试与无响应的页面交互时的体验，但它仅衡量第一次交互。 根据谷歌的说法，INP 通过覆盖网站的整个交互范围，对网站的响应能力进行更全面的衡量，从页面开始加载到用户离开页面。 这种综合测量使 INP 成为比 FID 更可靠地衡量站点整体响应能力的指标。
> 
> INP的整体性使得解决比FID更具挑战性，因为您的代码必须以保护用户在整个旅程中的响应能力的方式实现，而不仅仅是在第一次加载时。 由于许多交互是通过 JavaScript 完成的，这意味着您的网站必须仔细加载以优化性能。
> 
> 这在移动设备上特别困难。 我们查看了整个行业和我们网站网络中的少数几个网站，发现移动 INP 的分数平均比 FID 差 35.5%。 在同一数据集上查看桌面性能时，平均下降了 14.1%。
> 
> – 安妮·伯恩斯，[RebelMouse](https://www.rebelmouse.com/inp-core-web-vitals)

这将是2023年值得关注的一个有趣的指标，谷歌继续权衡将INP作为官方核心网络至关重要。

灯塔性能
-----------------------

[Lighthouse](https://developer.chrome.com/docs/lighthouse/overview/) 是我们可以用来衡量网站用户体验的另一种工具。 HTTP Archive 在模拟移动加载条件下运行 Lighthouse。 这提供了更详细和一致的页面加载性能分析，低至 100 毫秒的几分之一秒。 Lighthouse 没有查看大型“好”与“坏”阈值和水桶，而是为您提供更详细的性能评分，以 100 为单位。

像 Core Web Vitals 这样的真实用户数据仍然是真实用户体验的最佳衡量标准，您可以在下面的一些图表中看到真实体验与实验室体验的不同之处。 然而，Lighthouse 提供的额外细节仍有一些有趣的见解可以学习。 我们来看看数据。

为了一致性，我们保留了上一节的原始订单。 但是，您会注意到，Remix 在 Lighthouse 上的性能似乎比在 CWV 评估中要强得多。 对此的一种解释可能是 Remix 使用 `startTransition` 和 `requestIdleCallback` 到 [defer React hydration on page load.](https://github.com/remix-run/remix/blob/4988875856ba4007d4e1e4219b117ce9c7012489/packages/remix-dev/config/defaults/entry.client.react.tsx) 的方法，这可以理论上转化为在某些实验室情况下（如灯塔）的更好性能，但在其他现实世界的情况下增加了首次输入延迟。

不幸的是，灯塔的中位数表现得分很低。 测试的一半框架的中值表现被认为是“差”（49 岁或以下），而另一半的中值得分“需要改进”（50-89）。 没有框架达到 90+ 的“好”中位数。

在所有跟踪的网站中，绩效中位数为 34/100。 为此，我们测试的框架中有一半（Astro、Sveltekit 和 Remix）确实高于互联网平均水平。

通过按百分位划分数据，我们可以开始看到一些更令人鼓舞的数字，ASTRO 和 SVELTEKIT 在 P90 或 P95 百分位数中达到 90+ 的分数。 然而，数据清楚地表明，所有网站和框架（包括 Astro）仍在努力在现实世界中实现良好的性能。

**JavaScript的成本**
---------------------------

我们想探索的最后一件事是实际使用中框架选择、性能和 JavaScript 总有效负载大小之间的关系。 最快的框架是否倾向于将最少量的 JavaScript 发送给客户端？

数据的趋势很明显：使用 JavaScript 的网站往往表现更好。 然而，有太多的因素在起作用，我们无法自信地将这种趋势与 Web 框架本身的选择联系起来。 一些框架可能会以不同于其他框架的方式鼓励/劝阻 JavaScript，但在我们得出任何结论之前需要进行更多的研究。

方法和局限性
--------------------------

本报告是从几个公开可用的数据集中编制的。 您可以在此处了解有关这些数据集及其方法的更多信息：[HTTP Archive methodology](https://almanac.httparchive.org/en/2021/methodology#dataset)、[CrUX methodology](https://developer.chrome.com/docs/crux/methodology/) 和 [CWV Technology Report methodology](https://discuss.httparchive.org/t/new-dashboard-the-core-web-vitals-technology-report/2178)。

由于容量限制，我们的分析仅查看每个跟踪网站的主页。 此限制的一个好处是每个分析网站的目的和用例的差异较小。 然而，一个缺点是这也意味着内部页面（如 `/about` 和 `/admin/...` 页面），它们使用的技术没有被分析，因此被排除在我们的分析之外。

本报告中未探索的另一个限制是框架的年龄对测量的 Web 性能的影响。 在这里测量的较旧的框架（Gatsby、Next.js、Nuxt）有更长的传统网站，运行其框架中包含的旧版本，这些网站包含在数据集中。 这造成了一种情况，即只有较新的框架（Astro、Remix、Sveltekit）可以从过去 1-2 年中运行更现代的软件版本。 这是对我们可用数据的限制，但这是我们希望在未来的报告中探索的内容。
