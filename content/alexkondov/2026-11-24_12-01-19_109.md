Early in the vibe coding boom, founders claimed that their 10x-ers are shelling out 10K+ lines of code per day. Enormous amounts of logic by all means, even if half of it is boilerplate, schemas, and markdown.

Agents are a typewriter on steroids, but I kept wondering how these people reviewed all their work.

Most of us don’t work on pacemakers or rockets, so failure isn’t the end of the world, but it’s still detrimental. You still need to be able to make sense of what’s going on inside these 10K lines of code, right? They’re not a black box, right?

Wrong.

People were reviewing it like the required reading for literature class - a quick diagonal glance to get the gist in case anyone asks. I admit, I tried it too. But I quickly went back to shipping at the speed of my understanding.

## Reviewing is the bottleneck

If I measure my productivity by the speed at which I get code into the IDE, then I’ve become significantly more productive. If I use voice instead of writing, I can shortcut this even more.

But if I measure it by how often I ship actual code, it’s marginal.

I’m still the bottleneck.

But the selling point of LLMs is shipping quickly, iterating, answering requests, and addressing feedback faster. However, if I need to review their code, I still ship at the speed of my understanding, and I simply can’t improve that tenfold.

## When LLMs do software design

Models are great at outputting code that looks well-designed. It has abstractions, structure, comments even. But there’s a non-zero chance that they leave a logical flaw somewhere under that beauty, and without a good review, I won’t catch it.

The Broken by Default paper (published last month) claims that 55% of LLM-generated code contains at least one vulnerability. Machines propagate the same mistakes we do, and they still need the reviews we give to humans.

Their code can be so good at times that I feel awkward reviewing it.

But I’ve already found myself sitting on a design problem I didn’t catch because I didn’t pay attention, and this matters for software that can’t trade correctness for iteration speed.

At least the parts of the software that can’t do that trade.

Even companies working on highly available systems have internal applications that are prime targets for experimentation and coding agent freedom.

But it seems irresponsible to ship code to humans without validating it, and some of the people in this industry I admire the most are researching ways to solve this through formal verification.

## Formal verification

If we have to review the code the LLM generates, then we’re not getting the maximum possible productivity improvement. We’re becoming more efficient, but we’re not raising the level of abstraction.

I first saw this mentioned by Leslie Lamport while researching his Paxos consensus algorithm. But when I came across the “AI will make formal verification” article by Martin Kleppmann, I thought I should pay more attention.

I did not study computer science in university, so I’ve never had to prove theorems.

But with languages like Lean 4, we can turn our algorithms into theorems that we can prove formally and verify that the code behaves as expected. The only problem is that writing the proof takes as much effort, if not more, than writing the code itself.

Because of that, it’s been largely contained in academia.

But on an abstract level, writing a proof that’s detached from the implementation sounds like a good way to validate LLM code without going through it.

In practice, I’m not sure how it would happen for actual application code with all its side effects. Also, will a formal proof be easier to review than the code itself? What if you can write them in natural language?

But every sufficiently detailed spec is a form of programming, isn’t it?

## Automated formal verification

On a theoretical level, something like formal verification sounds reasonable. But, at least with the current tooling, it doesn’t seem applicable to how commercial software is built.

AlphaVersus is a project that aims to automate this.

> While LLMs have shown great promise in generating code, ensuring the correctness of generated code remains a significant challenge. Bugs and vulnerabilities can have serious consequences. Formal verification offers mathematical guarantees of correctness but is hindered by data scarcity and proof complexity.

But if the model makes a logical flaw in the implementation, how can we trust that it doesn’t work around it in the proof as well? Will reviewing a formal proof be easier than reviewing the code?

## Cost

I never liked the idea of having a paid tool in the core of my software development workflow.

> What, you don’t have $20?

That’s what people told me.

But we’re slowly seeing the real cost of AI as prices rise. Teams are burning through thousands of dollars per month. Yes, a startup with three engineers can afford to throw money at Anthropic to make their prototype faster, but a corporation with a few hundred engineers will get their CFO sweating very quickly.

I’ve worked at companies that took down the dev cluster at 5pm to save money, and now we have spending leaderboards that are widely celebrated as a proxy for productivity.

I’m not an economist, but without a breakthrough in the models, they will only get more expensive, which means that reviewing and polishing will be even more important. When you can’t just throw everything at Claude and you need to be more selective, you need to understand the codebase.

But doesn’t this make us the bottleneck once again?
