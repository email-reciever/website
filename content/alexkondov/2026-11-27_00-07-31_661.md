2025 年，我们一直专注于对 AI 的推测，学习如何与代理合作，以及适应不断变化的环境。但是在今年的最后一期新闻通讯中，我想把你的注意力转移到真正重要的事情上 - 构建良好的软件以及我们如何实现它。

在东欧长大，超级英雄文化仅限于主流角色。当时没有人翻译漫画书，而且它们几乎找不到，所以你最好希望在为学校做准备的早晨抓住那一集《蜘蛛侠》。

当我在超级英雄电影热潮期间玩我的《守望者》盗版拷贝时，我期待着一个遵循我以前见过很多次的公式的故事。坏人以恶棍的身份出现，完美的英雄初次失败，只为他们在最后变得更强并赢得胜利。

《守望者》并不是这样的。

它为超级英雄类型带来了黑暗的转折，这也是我第一次看到“超级英雄”被描绘成不完美的存在，具有人类的缺陷、需求和个人议程。

但阿兰·摩尔并不是偶然创造了这个故事。

## 读一切

摩尔打破了公式，因为他比任何人都更了解它。他重塑了超级英雄，不是因为他忽略了该类型的历史，而是因为他理解得足够好，以至于可以将其转变为新东西。

而这就是艾伦·摩尔给未来的作家的建议——阅读一切。阅读经典、诗歌、哲学、通俗小说、漫画、报纸和晦涩的神秘文本。阅读好的书，但也要阅读坏的书。

尤其是坏书，在形成你对写作的品味方面是非常重要的。

> 也要阅读糟糕的书，因为它们可能比好的书更有启发性……通过分析为什么它们做得这么糟糕，这将极大地帮助你的写作风格。你会发现所有不该犯的错误。
>
> 艾伦·摩尔

作家在尝试写自己的书之前会阅读数百本书。

而我们作为开发人员，另一方面，却相当于上了一门语法课就开始写“战争与和平”。想象一下作家不阅读经典著作。不坚持读完“白鲸”，也不忍受“罪与罚”。

这样一来，作家不可能创造出伟大的作品。最多也就是按照我一开始提到的公式写出一个超级英雄故事。

## 编程更像艺术而非科学

Paul Graham 有一篇很好的文章叫《黑客与画家》（Hackers and Painters），他在其中论述编程更接近创意领域，而非传统的工程学，因为我们的工作是由品味、迭代和直觉驱动的，而非严格的流程。

程序员拒绝接受他们的工作可以被视为艺术，而艺术家们则难以承认他们的工作中包含了应用数学。

但是，如果你读了这篇文章，并且它能够说服你，即使只有一点点，那么我们应该认真对待艾伦·摩尔（Alan Moore）的建议，并像作家一样对待我们在这门手艺中的提高。

> 我不认为艺术、写作、音乐和魔术之间真的有所不同。我特别强调魔术和写作之间的联系。我认为它们是深刻相关的。
>
> 艾伦·摩尔

良好的语法是必要的，但写一个好故事需要的不仅仅是语法 - 还需要情节、人物、语调。同样，掌握一门编程语言是不可商量的，但构建软件需要的不仅仅是语言 - 还需要架构、规模、可维护性。

像艺术家一样，我们通过迭代，处理真实的、现实中的软件，而不是隔离的代码片段，来建立我们对好的软件的直觉。

当我开始写作时，人们告诉我我需要读卡缪、陀思妥耶夫斯基、契诃夫和斯坦贝克，但没有人告诉我应该读哪些代码库来了解人们如何构建软件。

## 建立直觉

大多数开发人员自然而然地通过更换公司来建立他们对好的软件的品味——他们看到哪些模式有效，哪些无效。

这就是为什么我仍然认为多年的经验有一定的价值。

你在行业中度过的时间越长，你就会看到越多的项目。你会了解他们的领域如何在代码库中被建模，挑战和真实软件的外观。

你会看到可怕的失败和混乱的代码库，但它们也同样重要。就像通俗小说和机场书籍，你在打开第一页之前就已经知道结局一样，负面的数据点也同样有价值。

> 实践经验是无可替代的，如果你想写关于人的东西，你应该放下那本漫画书，去外面认识一些人，而不是研究斯坦·李或克里斯·克莱蒙特如何描绘人。
>
> 阿兰·摩尔

我发现那些快速成为熟练的软件开发人员的人，往往无意中找到了一种方法来加速他们的学习过程，并建立他们的直觉。

通过在自己的副项目上工作，承接自由职业项目，并为开源项目做出贡献——所有这些都会让他们接触到更多的领域，更多的协作问题和更多的边缘情况。

## 阅读开源

当我22岁的时候，我可以轻松地完成9-5的工作，然后在晚上继续编码到早上，但是现在，我有了家庭和工作以外的责任，我发现很难遵循相同的时间表。

我不能再利用空闲时间构建东西或在第二家公司兼职。这太耗费精力了，我也一直在与倦怠症斗争。

但是开源是一个充满优质阅读材料的宝藏，我可以像读一本好书一样享受阅读这些项目。我不需要像学习教材一样研究它们，分析它们，或者甚至运行它们。我可以像早上读书一样浏览代码库。

开源对于我来说似乎很令人生畏。

我觉得自己不配读它。那些被所有人审查的开放代码一定很复杂，并且被极其小心地编写。

是的，试图在没有先前知识的情况下阅读 React 的代码库，可能会让你感到更加困惑，而不是有所收获。

但是，想想你每天使用的所有小型库和工具，它们是把整个系统连接在一起的枢纽。

我认为它们值得阅读。

## 阅读 Lodash

第一个我敢于超出 README 文档探索的开源库是 Lodash - 一组在过去 JavaScript 标准库较为贫瘠时非常有价值的实用函数。

我从它开始，因为我希望它会更简单，但我没有预料到整个库会被放在一个 17K 行的单个 JavaScript 文件中。

这是一个每周有 8000 万+ 次下载的库。

但是，他们并没有发布这个巨大的文件，因为它会占用太多网络带宽。Lodash 的复杂性在于其构建过程。他们有一个 CLI 工具，可以将文件转换为不同的格式并构建。

在行业中，这样的文件会被认为是一个巨大的反模式，我以前从未见过这样实现的工作软件。

我喜欢它吗？不。

但是我学到了，你交付的东西不必与你写的东西相同。

## 阅读 React-Query

过了一段时间，我也这样做了，针对 react-query，这是一个在 React 生态系统中流行的数据获取库。

我不知道如何开始处理一个大型、复杂、陌生的代码库，所以我像工作中一样做了同样的事情 - 我跟踪了其中一个公开的 API。

我找到他们最常用的函数被导出的地方，并且跟踪了它的实现，直到底层，通过命令点击函数和层次，直到到达底部。

而且我发现它实际上在底层使用了类。

是的，类。

在一个用于前端的 JavaScript 库中。轻量级的函数式编程已经主导了生态系统多年，面向对象的代码是我最不期望的东西。

我是否开始在我的 React 项目中使用类？我没有。

但是阅读这个代码库教会了我，你可以在 React 组件生命周期之外处理数据。

## 软件工程师的词汇

这不是那种能够帮助你通过 FAANG 面试的知识。这是能够帮助你构建实际软件的知识。

如果你不阅读，你就不会有词汇来写代码，如果你不学习实际的软件，你就不会学习构建模式。

工程博客是获取信息的良好来源，但我觉得它们过于精心打造。每个无菌、过度工程化的REST API都有比领域逻辑更多的样板代码，这些都受到博客文章的启发。

成功和突破是令人感兴趣的阅读材料，但实际的软件有时会有17K行长的JS文件，没有人急着写关于它们的内容。

我们研究理论上的最佳场景，然后期望根据在真空中讨论的想法构建实际的生产软件。这是不现实的。软件失败大多数情况下是想象力的失败和我们无法处理复杂性的结果，而这种想象力是在你阅读越来越多的内容时培养出来的。

仅在更换公司时熟悉新想法就像只每隔几年读一本书一样。

我们需要不断研究现有的项目，直到我们理解质量的形状并培养出对好软件的品味。

因为这种品味才是长久的。
