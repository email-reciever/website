[JavaScript 框架的 AI 成本](https://reactdigest.net/links/23666/rss)\
*16 分钟* by Nolan Lawson

Web 开发选择往往是由直觉驱动的，而不是数据驱动的。Nolan 的基准测试了 AI 编码代理在 12 个 JavaScript 框架中构建相同的 Pokémon 应用的成本、性能和代码大小。像 Astro 和 Hono+htmx 的 MPA 框架在速度、JavaScript 大小和构建成本方面始终优于 SPA 框架，而 Angular 在几乎所有指标上排名最后。结果表明，框架选择应该受到更多的审查，尤其是现在开发人员不再手写代码。

[不要为速度牺牲质量（ElevenLabs绝不会这样做）](https://reactdigest.net/links/23667/rss)\
*由 Meticulous 赞助*

代理正在比以往任何时候都更快地编写代码。它们甚至会审查自己的工作。但是谁在审查它们？一个代理做了一份合格的工作并发布了一个有缺陷的修复，下一个代理就会复制它。缺陷会比任何人都能捕捉到的更快地传播。Dropbox、Notion 和 ElevenLabs 的领导层拒绝将质量换取速度。使用 Meticulous，每个更改都会经过彻底的验证，而无需开发人员付出任何努力。

[异步 React 与渐进式服务器操作](https://reactdigest.net/links/23668/rss)\
*6 分钟* by Jacob Ebey

React 现在支持使用 "use server" 指令直接在组件模型中运行服务器端表单操作。像 useActionState 和 useOptimistic 这样的新钩子可以清晰地处理待处理状态和即时 UI 更新。只要服务器操作最终成为表单的 action 属性，表单仍然可以在没有 JavaScript 的情况下工作。这为 React 提供了一种统一的方式来构建在 JavaScript 加载之前和之后都能正常工作的体验。

[React.lazy，Suspense 和隐藏的 300 ms 延迟](https://reactdigest.net/links/23669/rss)\
*13 分钟* by Matthew Wong

这个浏览器扩展的所有脚本都在 100ms 内加载，但是小部件直到 380ms 才出现。罪魁祸首原来是 React 内置的 300ms 延迟，它批量处理挂起的内容以防止闪烁。解决方法很简单：直接渲染占位符，而不是让 React 挂起，因此每个小部件在其代码到达时就会出现。这将第一个可见的小部件内容提前了大约 240ms，而减小包大小并没有带来可测量的差异。

[React 的工作原理](https://reactdigest.net/links/23670/rss)\
*10 分钟* 由 Sina Salahshour

React 的渲染、状态更新和钩子都遵循明确的内部规则 —— 一旦你理解了它们，令人困惑的行为就会变得有意义。这门课程用简单的语言解释了 React 背后的核心思想：渲染期间实际发生了什么，为什么状态在设置后立即似乎过时，以及为什么钩子存在的规则。无需阅读源代码。这门课程还配有一个伴侣课程，用于逐行浏览 React 的代码，以便那些想要深入了解的人。

[跨标签保持 TanStack 查询的新鲜度](https://reactdigest.net/links/23671/rss)\
*3 分钟* 由 Idan Shalem

当你在一个浏览器标签页中更新数据时，其他标签页会保持不同步，直到它们重新获取数据。解决方案是通过 BroadcastChannel API 广播一个信号，告诉其他标签页查询已经过时，让每个标签页自己获取新数据。Idan 建议只发送查询键，而不是数据本身，因为每个标签页都处理自己的获取逻辑。同样的方法也适用于注销，清除所有打开的标签页中的私人数据。
