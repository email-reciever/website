[JavaScript 框架的 AI 成本](https://reactdigest.net/links/23666/rss)\
*16 分钟* 由 Nolan Lawson

Web 开发的选择往往是由直觉而不是数据驱动的。Nolan 的基准测试了 AI 编码代理在 12 个 JavaScript 框架中构建相同的 Pokémon 应用的成本、性能和代码大小。像 Astro 和 Hono+htmx 的 MPA 框架在速度、JavaScript 大小和构建成本方面始终优于 SPA 框架，而 Angular 在几乎所有指标上排名最后。结果表明，框架选择值得更严格的审查，尤其是现在开发人员不再手写代码。

[不要为了速度牺牲质量（ElevenLabs 肯定不会这样做）](https://reactdigest.net/links/23667/rss)\
*由 Meticulous 赞助*

代理正在比以往任何时候都更快地编写代码。它们甚至会审查自己的工作。但是，谁在审查它们呢？一个代理做了一份还过得去的工作并发布了一个有 bug 的修复，下一个代理就会复制它。bug 会比任何人都能抓住得更快传播。Dropbox、Notion 和 ElevenLabs 的领导层拒绝为了速度而牺牲质量。使用 Meticulous，每个更改都会被彻底验证，而无需开发人员付出任何努力。

[异步 React 与渐进式服务器操作](https://reactdigest.net/links/23668/rss)\
*6 分钟* by Jacob Ebey

React 现在支持在组件模型中直接使用 "use server" 指令运行服务器端表单操作。像 useActionState 和 useOptimistic 这样的新钩子可以清晰地处理待处理状态和即时 UI 更新。表单仍然可以在没有 JavaScript 的情况下工作，只要服务器操作最终成为表单的 action 属性。这样，React 就有了一个统一的方式来构建在 JavaScript 加载之前和之后都能正常工作的体验。

[React.lazy、Suspense 和隐藏的 300 ms 延迟](https://reactdigest.net/links/23669/rss)\
*13 分钟* by Matthew Wong

所有此浏览器扩展的脚本都在 100ms 内加载，但小部件直到 380ms 才出现。罪魁祸首原来是 React 的内置 300ms 延迟，它批量挂起内容以防止闪烁。解决方法很简单：直接渲染占位符，而不是让 React 挂起，因此每个小部件都会在其代码到达时立即出现。这使得第一个可见的小部件内容提前了大约 240ms，同时减小包大小并没有带来可衡量的差异。

[React 的工作原理](https://reactdigest.net/links/23670/rss)\
*10 分钟* 由 Sina Salahshour

React 渲染、状态更新和钩子都遵循明确的内部规则 —— 一旦你理解了它们，令人困惑的行为就会开始变得有意义。这门课程以简单的术语解释了 React 背后的核心思想：渲染期间实际发生了什么，为什么状态在设置后立即似乎过时，为什么钩子存在这些规则。无需阅读源代码。这门课程还配有一个伴侣课程，用于逐行浏览 React 的代码，以便那些想要深入了解的人。

[在多个标签页中保持 TanStack 查询的新鲜性](https://reactdigest.net/links/23671/rss)\
*3 分钟* 由 Idan Shalem

当你在一个浏览器标签页中更新数据时，其他标签页会保持不一致，直到它们重新获取数据。解决方法是通过 BroadcastChannel API 广播一个信号，告诉其他标签页查询已经过时，让每个标签页自己获取最新数据。Idan 建议只发送查询键，而不是数据本身，因为每个标签页都处理自己的获取逻辑。同样的方法也适用于注销，能够同时清除所有打开的标签页中的私人数据。
