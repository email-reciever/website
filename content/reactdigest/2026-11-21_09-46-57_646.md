[Still writing tests manually? Meticulous AI is here.](https://www.meticulous.ai/?utm_source=react-digest&utm_medium=newsletter&utm_campaign=26q1&utm_content=primary)  
_由细致的赞助

大多数团队被迫在更好的覆盖范围和更多的维护工作之间进行权衡。 但像 Notion、Dropbox、WealthSimple 和 LaunchDarkly 这样的顶级工程团队已经发现了一种新的测试范式。 由Ex-Palantir工程师构建，精心创建和维护E2E UI测试，无需任何开发人员的努力即可覆盖您的Web应用程序的每个边缘情况 - 使其成为提高产品质量和开发速度的唯一工具。

[Making React ProseMirror really, really fast](https://smoores.dev/post/making_react_prosemirror_really_really_fast/)  
_14 分钟_ 通过肖恩·弗里德曼

Shane 描述了 React 如何与 ProSemirror 集成并针对速度进行了优化。 他说，主要问题是太多的重新渲染导致大文件滞后。 通过记忆组件、避免改变道具和使用稳定的引用，系统会显着减少渲染。 这使得编辑器的速度足够快，可以顺利处理非常大的文本。

[Two React design choices developers don’t like—but can’t avoid](https://dev.to/playfulprogramming/two-react-design-choices-developers-dont-like-but-cant-avoid-d6g)  
_11分钟_瑞恩·卡尼亚托

信号应该解决开发人员讨厌 React 的两件事——延迟状态更新和手动依赖数组。 但 Building Solid 2.0 表明这些不是糟糕的设计选择。 它们是真正的发现。 一旦 async 进入一个反应图，你不能让推测写入在值稳定之前到达 UI，并且 effects 必须在运行前预先声明所有的依赖关系。 这些规则适用于任何 UI 系统，而不仅仅是 React。

[Error handling in Next.js with catchError](https://aurorascharff.no/posts/error-handling-in-nextjs-with-catch-error)  
_6分钟_由Aurora Scharff

如果您在 Next.js 应用程序路由器中使用过 react-error-boundary，那么您可能已经在服务器组件中遇到了它的限制。 它捕获不应该的错误，并且其恢复机制不会重新获取服务器数据。 unstable\_catcherror from next/error 是处理这两个问题的框架感知替代方案。 在这篇文章中，Aurora 介绍了她之前使用的中断、解决方法以及 CatchError 如何修复它。

[Why we rolled our own React server components framework](https://www.aha.io/engineering/articles/why-we-rolled-our-own-rsc-framework)  
_19 分钟_ 乔什·威尔逊

Josh 解释了为什么一个团队使用 React Server 组件用一个小的自定义框架替换了一个标准的 React 框架。 他们的方法在简化开发的同时显着缩短了 JavaScript 和加载时间。 他探讨了框架的优缺点，展示了现代工具如何使自定义设置更容易，并认为在现有的框架不适合您的需求时，构建自己的框架可能是一个不错的选择。
