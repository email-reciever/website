十八个月的 React 编译器
====================================

第554章 2026年4月26日

> 弧线，辩论，以及下一步是什么

[React compiler at eighteen months](https://saschb2b.com/blog/react-compiler-year-in-review)  
_9 分钟_ 萨沙·贝克尔

Sascha 回顾了 React 19 之后的 18 个月 React 编译器。他解释了它如何减少手动记忆化、提高性能以及更改了诸如缺失依赖项等常见错误。 他还讨论了框架中的采用、迁移步骤和旧库的剩余挑战。 最后，他探讨了 React 工具和编译器控制方面的持续辩论和未来可能的改进。

[Lessons Learned from Security Incidents in Mobile Apps](https://www.vpdae.com/redirect/r86wvpx7r02k4gly8bayvqaqe)  
_由守卫广场赞助_

5 月 12 日，与安全研究员和渗透测试人员 Jan Seredynski 一起，他将剖析银行、食品交付和电子商务中的真实安全事件。 从面部验证旁路到位置欺骗，他将分解漏洞的解剖结构以及团队可以采取哪些不同的方式来解决这些问题。

[Moving Railway's frontend off Next.js](https://blog.railway.com/p/moving-railways-frontend-off-nextjs)  
_5分钟_维克多·拉米雷斯

铁路将其整个前端从 Next.js 切换到 Vite 和 TanStack 路由器。 耗时超过 10 分钟的构建现在在 2 岁以下完成。 此举是有道理的，因为该产品是大量客户端，而 Next.js 服务器优先功能大部分未使用。 迁移覆盖了 200 多条路线，并在两次拉取请求中发货，没有停机时间。

[use client in Next.js](https://punits.dev/blog/use-client-in-nextjs/)  
_7 分钟_ 通过 Punit Sethi

punit 解释了 next.js 中“使用客户端”指令的作用。 他表明它仍然在服务器上渲染，但添加了像钩子和事件一样的浏览器交互性。 他还讨论了更大的 JavaScript 捆绑包、水化成本和延迟数据加载等权衡，并得出结论，“使用客户端”应该仅在需要交互性的地方使用。

[Benchmarking bundle bloat patterns across 500 repos](https://stackinsight.dev/blog/bundle-bloat-empirical-study/)  
_15分钟_ 梁高新

Ko-hsin 对 500 个存储库中的五种常见 JavaScript 导入模式进行了基准测试。 只有两种模式——使用 lodash 和 moment.js——导致显着的捆绑膨胀，将大小增加到 17 倍。 其他经常受到批评的模式，如 Barrel 或 Namespace 导入，对现代捆绑器没有真正的影响。 研究结果表明，开发人员应该专注于替换重型库，而不是更改导入样式。

[Encoding dynamic data into URLs in Next.js](https://aurorascharff.no/posts/the-precompute-pattern-encoding-dynamic-data-into-urls-in-nextjs/)  
_12 分钟_ 通过 Aurora Scharff

在 Next.js 16 之前，一次调用共享布局中的 cookie 会迫使每个嵌套页面都进行动态渲染。 预计算模式通过解析中间件中的请求数据并将其编码到URL中来解决此问题，因此可以为每个已知变体静态生成页面。 较新的缓存组件在大多数情况下解决了这个问题，但是当内容必须因地区、货币或功能标志而异时，这种模式仍然很重要。 即将推出的名为 rootparams 的功能将消除将编码值向下传递到每个组件的主要痛点。
