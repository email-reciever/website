C++继任仪式的现场镜头

谷歌想要构建 C++ 的打字稿
-----------------------------------------

上周在多伦多的一次 C++ 会议上，一切都发生了（是的，我检查过）。

Chandler Carruth（C++、Clang和Google的LLVM团队的领导者）上台给[the keynote speech](https://www.youtube.com/watch?v=omrY53kbVoA)，慢慢地与观众中的每个人对视，并传达了一个消息：“C++确实很糟糕。”

好吧，他没有这么说。 但他确实说过，这种语言的 [stated goals](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2020/p2137r0.html#goals) 的“不足”——包括软件和语言进化，创建易于编写和理解的代码等等。

**为什么？** 就像你的父母一样，大多数 C++ 问题都源于它很老而且不愿意/无法改变（仍然爱你，妈妈）。

该语言被技术债务的 _decades_ 所困扰，但它需要专注于向后兼容性（以增加改进为代价），以确保它不会破坏所有使用它来供电的低级系统…… _(\*checks notes\*)_ 的现代世界。

在概述了所有 C++ 问题之后，Chandler（又名 [Chan-C](https://www.pokemon.com/us/pokedex/chansey)）还提供了一个解决方案，他一直在谷歌和他的朋友们一起做饭：C++ 的一种实验性“继承语言”，称为 [Carbon](https://github.com/carbon-language/carbon-lang)。

这种方法类似于 JavaScript → Typescript 和 Java → Kotlin：它专为与 C++ 和大规模采用/迁移的紧密互操作而设计，同时让 Carbon 可以自由地更快地进行改进。

**亮点：**

*   性能匹配C++，因此不会牺牲任何速度
    
*   简化了语法和关键字，因此更容易学习和使用
    
*   与C++无缝的双向互操作性
    

**底线：** 现代低级编程语言有很多很棒的选择（Rust、Go、Kotlin 等）。 但 C++ 生态系统不会很快消失，尤其是现在谷歌已经介入了。 继续关注。

设计系统支持组

Radix 发布 v1.0，因此您可以停止假装自己构建自己的
------------------------------------------------------------

还记得大约 2 年前，当每个前端开发人员都想在设计系统上工作时，却意识到这基本上就像在 [Lumon Industries](https://lumon-industries.com/) 的地下室工作一样？

幸运的是，Radix UI（拉丁语表示 [round](https://youtu.be/Pk-kbjw0Y8U?t=7)）刚刚发布了他们的原始、非样式的 React UI 组件集的 v1 ——这样我们就可以停止假装自己构建自己的 🙏。

**是什么让 Radix 如此出色？** 每个 React 应用程序的样式都不同，这可以使某些组件库不行。 然而，Radix 是非风格的，这使得它易于采用和定制。

每个组件都封装了标记和核心 UI 行为，同时确保键盘导航、焦点管理和屏幕阅读器等可访问性功能开箱即用（也就是您的 PM 会从范围中删除的所有内容，因为“我们需要快速移动并破坏事物”）。

基本上，Radix 让您过上自己的生活，而他们 [earn the finger traps](https://www.modulz.app/blog/modulz-acquired-by-workos) 提供一些开箱即用的顶级好东西：

*   26 不同的组件，包括工具提示和模态（弹出式）等基本要素，但也有像门户这样的原语来帮助您编写自己的组件。
    
*   对 React 18 的强大 SSR 支持，确保了屏幕阅读器的快速 TTI。
    
*   小捆绑包尺寸 — 您可以一次采用一台组件并节省一些比特。
    
*   不错的附加组件，包括 [accessible icon library](https://icons.radix-ui.com/) 和 [color palette generator](https://www.radix-ui.com/colors)。
    
*   适用于任何样式或动画解决方案，但团队也构建了自己的零运行时 [css-in-js](https://stitches.dev/) 解决方案。
    

**底线：** 如果像 Vercel、Linear 和 Supabase 这样的大 Bois 已经在使用它，那么您就知道组件库必须很棒 _before_ radix 已经发布了 v1。 很高兴看到它从这里去哪里🚀。

发现错误解决方案 — 由 [Appwrite](https://appwrite.io/?utm_source=newsletter&utm_medium=homepage&utm_campaign=bytes) 赞助
-------------------------------------------------------------- --------------------------------------------------------------

如果您运行原始代码，您将获得“未捕获的 TypeError：无法读取未定义的属性（读取‘长度’)”。 我们使用的唯一位置 `.length` 是在 `reduceLanguages` 函数中，因此我们可以推断 `this.languages` 是 `undefined` 并且我们错误地使用了 `this` 关键字。

每当您试图弄清楚 `this` 关键字引用的内容时，您需要查看使用 `this` 关键字的函数在哪里被调用。 在我们的示例中，我们不知道，因为它是在 `reduce` 的实现中。 为了确保在正确的上下文中调用 `reduceLanguages` 并因此具有正确的 `this` 绑定，我们有两个选择。 首先，老派的方式-使用`.bind`。

问候（）{
常量 Hello = `Hello, my name is ${this.name} and I know`;
    
const langs = this.languages.reduce(reduceLanguages.bind(this), "");
    
返回 Hello + Langs；
}
    

其次，更好的方法 - 使用箭头函数。

问候（）{
常量 Hello = `Hello, my name is ${this.name} and I know`;
    
const langs = this.languages.reduce((str, lang, i) => {
如果 (i === this.languages.length - 1) {
返回 `${str} and ${lang}.`；
}
    
返回 `${str} ${lang},`；
}, "");
    
返回 Hello + Langs；
}
    

之所以有效，是因为在箭头函数中`this`是_lexically_确定的。 箭头函数没有自己的`this`。 相反，就像变量查找一样，JavaScript 解释器将查看封闭（父级）范围以确定 `this` 应该引用的内容。

想阅读更多？ 退房[Understanding the “this” keyword, call, apply, and bind in JavaScript](https://ui.dev/this-keyword-call-apply-bind-javascript)。
