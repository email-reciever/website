### 真正谈论Edge™️

如果您本周一直在 Tech Twitter 上，那么您可能已经看到了关于 SSR 应用程序的不同边缘计算方法的优势和权衡的多场辩论。 Remix 和 Vercel 的创始人都分享了他们的看法，以及我们仍然假装尊重的其他不太富有/受欢迎的工程师。

但辩论是什么？ 我们已经写过关于“The Edge”如何只是花哨营销的故事来代表“靠近您的用户的运行服务器”的故事，那么服务器渲染您的应用程序是否总是更快地接近您的用户，这不是总是更快吗？

好吧，这取决于您要构建的内容。 我们还需要记住，我们在这里处理两个不同的服务器——应用程序服务器和数据库服务器。

考虑到这一点，让我们看看当今在 JavaScript 中构建 SSR 应用程序的三种主要架构方法。

**Origin App Server + Origin DB Server：** 将您的应用程序服务器和数据库服务器彼此相邻，让您的应用程序与数据库（或同一地区的其他服务）来回移动，而无需与物理定律作斗争。 不利的一面是，您的用户离您的来源越远，每个客户请求的时间就越长。

**Edge App Server + Origin DB Server：** 最近，在 Edge™️（又名最接近最终用户的服务器）上托管您的应用程序服务器变得很流行。 这使您可以为用户提供动态内容，而不会延迟到您的来源。 这在理论上听起来很棒，但是如果您的Edge应用程序必须频繁地前往原点获取数据，在某些情况下，它最终可能会比Origin + Origin方法慢。

**Edge App Server + Edge DB 服务器：** Cloudflare、Turso 和 Fly 等公司正在支持这种新方法。 这是两全其美的，对吧？ _对吗？_可能是对于某些应用程序，但缺点是您必须处理分布式数据库和诸如最终一致性之类的事情（或者我喜欢称之为“立即不一致”）。

**底线：** Edge™️ 很棒，但它并没有为我们提供一种可以保证每种情况的最佳性能和 DX 的银弹方法。 所以现在，我们仍然需要评估权衡并为我们正在构建的特定应用程序做出最佳选择。

或者，正如 Jerry Seinfeld 曾经说过的那样，“找到你感到舒服的折磨。”

发现错误：解决方案
-----------------------

#### 赞助[P0 Security](https://p0.dev/blog/service-account-key-origins?utm_campaign=bytes_dev_nov_16&utm_source=email&utm_medium=presenting_sponsor&utm_content=nov_16_spot_bug)

在原始代码中，Service Worker 在安装时缓存资产，但当资产发生变化时，它不会更新缓存。 这意味着如果您更新 CSS 或 JS，服务工作者仍将提供旧版本。

要解决此问题，我们可以使用 `cache.put()` 方法在资产发生变化时更新缓存。

// service-worker.js
const cache_name = "site-static-v1";
const assetsToCache = ["/", "/index.html", "/css/style.css", "/js/script.js"];
    
// 安装事件
self.addEventListener("安装", (Event) => {
事件.等待直到（
caches.open(cache_name).then((cache) => {
cache.addAll(assetStocache);
})
);
});
    
// 获取事件
self.addEventListener("获取", (事件) => {
event.respondWith(
caches.match(event.request).then((CacherEsponse) => {
返回（
缓存响应 ||
fetch(event.request).then((fetchResponse) => {
返回 caches.open(cache_name).then((cache) => {
cache.put(event.request.url, fetchResponse.clone());
返回获取响应；
});
})
);
})
);
});
    

在你过于自信之前，请记住，服务工作者的创建是为了让你保持谦虚（据称）。
