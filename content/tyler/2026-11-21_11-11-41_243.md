开发人员试图弄清楚如何使用服务器组件

### 野生动物群

它终于发生了。 经过多年的讨论，我们开始看到 React Server 组件进入了狂野。

而“The Wild”，我的意思是“一些不同程度的不同的元框架。” 所以就叫我奈杰尔·索恩伯里吧，让我们一起来仔细看看：

*   Next.js [13.4](https://nextjs.org/blog/next-13-4) 上个月引入了 App 路由器的稳定性，其中包括在 RSCS 之上构建的全新架构作为原语。 这只是 RSCS 的一种潜在应用，但它是当今唯一可用于生产的实际实现。
    
*   RedwoodJS刚刚宣布，他们已经决定去[all in on RSCs](https://tom.preston-werner.com/2023/05/30/redwoods-next-epoch-all-in-on-rsc.html)并“抛开他们的JamStack优化的SPA根源，支持服务器优先的全栈React Framework。” （我的曾祖父登陆埃利斯岛时也说了同样的话。）
    
*   Remix 还没有分享很多具体的服务器组件计划。 但为了夺回他失去的 Twitter 追随者的勇气努力，Ryan Florence（Remix 的共同创建者）一直 [tweeting](https://twitter.com/ryanflorence/status/1663587026384584704) 在他们的 WIP 方面取得了一些有希望的发展 [RSC implementation](https://github.com/jacob-ebey/remix-rsc-do-not-use)。
    

很明显，在未来，服务器组件将构成每个 React 元框架的基础。 那么这对生态系统意味着什么？

Devon Govett 上周分享了一篇[interesting take](https://twitter.com/devongovett/status/1662891364873388032)，讨论这可能导致框架变得“更加专业化，因为将其区分开来的情况会更少。”

如果每个框架都建立在服务器组件上，它们将具有相同的标准化方法来获取数据、路由、DX 甚至性能。 这可能导致他们选择通过加倍使用一种高度特定的用例（如电子商务）并为该用例构建更多固有的功能来选择区分。

**底线：**我们仍处于服务器组件的第一局，因此希望听到更多关于它们以及它们将在未来几个月和几年中产生的涟漪的信息。

发现错误：解决方案
-----------------------

#### 赞助[Datadog](https://www.datadoghq.com/bytes/)

函数 removeElement(array, elementToRemove) {
for (let i = 0; i < array.length; i++) {
if (array[i] === elementToRemove) {
array.splice(i, 1);
}
}
}
    
让 myArray = [1, 2, 3, 2, 4];
removeElement(MyArray, 2);
    

这个解决方案并不理想，因为它没有考虑到阵列正在被迭代时被修改的事实。 当索引 `1` 处的元素被移除时，索引 `2` 处的元素被移至索引 `1`。

有很多方法可以让这一切变得更好，所有这些都是不同的权衡。 这可能是最好的一种，它使用 JavaScript 的 `filter` 方法在过滤掉 `elementToRemove` 后返回一个新数组。

函数 removeElement(array, elementToRemove) {
返回 array.filter((元素) => element !== elementToRemove);
}
