### React 19 刚刚被延迟

与 _Dune 2_ 不同，这不是因为作者的罢工。 这是因为一个意想不到的英雄领导了一场叛乱，一群追随者因正义的原因而团结起来。

好的，有点像 _dune 2._ 让我们分解一下。

**发生了什么：** 上个月的 React 19 RC 添加了许多新功能 [we already covered](https://bytes.dev/archives/284)，加上我们没有的一个鬼鬼祟祟的更改。

如果您不熟悉，`<Suspense />` 是一个 React 组件，可让您显示回退，直到其子级完成加载（或获取他们需要的任何数据）。

从历史上看，`<Suspense />` 子组件中的所有请求都会并行进行——这对于像 React Query 这样的库来说非常方便，其中通常在嵌套组件级别进行提取。

但是，使用 React 19 RC，而不是并行获取，所有子组件都按顺序获取。 正如您可以想象的那样，使用过去并行运行的东西并按顺序运行可能会产生相当大的性能影响——如 Tkdodo [discovered](https://tkdodo.eu/blog/react-19-and-suspense-a-drama-in-3-acts)。

**这是如何发生的：** 在过去的几年中，React 团队推动了像 RSC 这样的服务器端功能，作为获取数据的#blessed 方式。 但今天，大多数 React 开发人员仍在客户端获取数据，从而在 React 团队对库的未来愿景与当前现实之间形成了差距。

这解释了为什么当 TKDODO 和其他人首先 [complained](https://github.com/facebook/react/pull/26380) 关于新的悬念问题时，React 团队推迟了——说悬念是 [never intended](https://x.com/sebmarkbage/status/1801258093327593717) 用于客户端数据获取。

**接下来会发生什么：** 谢天谢地，经过 72 小时的对峙后，React 团队 [relented](https://x.com/en_JS/status/1803480672327311425)。 他们没有破坏像`@tanstack/react-query`和`@react-three/fiber`这样的流行库，而是选择延迟React 19的一般版本，直到他们可以使用`<Suspense />`为SPA提出更好的解决方案。

**底线：** [It would be a bad outcome if the React community’s reaction to this saga is “haha, we bullied React into changing their position on lazy fetching”. You should still design APIs that encourage/support prefetching as the default.](https://x.com/acdlite/status/1803551296974168171) – 至少，这是我被告知的。
