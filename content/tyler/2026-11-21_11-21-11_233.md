打字稿版本 v4.3
-------------------------

TypeScript 上周为我们提供了 V4.3，它附带了一个 [announcement post](https://devblogs.microsoft.com/typescript/announcing-typescript-4-3/)，就像一部 19 世纪的俄罗斯小说，混合了 CVS 收据——它一直在继续。

**快速审查：** 如果您是 TypeScript-Land 的新手，请知道它允许您将 _types_ 添加到您的代码中，以便您可以捕捉到逻辑错误和错别字等错误。 这有点像你的小联盟棒球教练“只是因为他在乎而对你大喊大叫”，但饮酒问题较少。

让我们进入** TS 4.3的亮点：**

*   **new `override` 关键字** — 如果用 `override` 标记一个方法，它将检查基类中是否存在同名的方法。 这可以防止在您无法明确您是否打算添加一种全新方法或覆盖现有方法时出现的常见错误。 它还带有一个新的 `--noImplicitOverride` 标志，如果您尝试在不使用 `override` 的情况下覆盖方法，它允许 TypeScript （亲爱地）向您大喊大叫。
    
*   **在属性上分隔写入类型** — 对在存储它们之前转换传入值的 API 进行建模总是非常棘手的，因为 TypeScript 迫使您在优化 _reading_ 值或 _writing_ 值之间进行选择。 但是现在您可以指定读取 _and_ 写入属性的类型。 两全其美。
    
*   **Template String 类型改进** — 这些是新的类型，它们可以通过连接来构造新的类似字符串的类型，或者它们匹配其他类似字符串的模式。 TypeScript 4.3 对 TypeScript 推断这些 TST 的方式和时间进行了一些改进。
    

### 底线

像 Blink-182 一样，很多人一开始有点讨厌打字稿，但随着时间的推移会变得爱和欣赏它。 V4.3 是另一个坚实的版本，继续支撑各种打字边缘案例。

Jest 27 有新的默认值
-------------------------

Web 的 [most popular](https://2020.stateofjs.com/en-US/technologies/testing/) JavaScript 测试框架上周发布了 V27——这是他们两年多来的第一个主要版本（修复我的测试框架中的重大更改是我的扭结）。

这里的大新闻是 Jest 正在将默认测试环境从 `"jsdom"` 更改为 `"node"`。 有很多事情要做，但 TL;DR 是大多数开发人员会看到大大的性能提升，因为他们将不再在不知不觉中使用他们（通常）不需要的昂贵的 DOM 环境。

**其他新东西：**

*   您现在可以一次性地通过一次失败的测试（听起来像我的中学家长-教师会议）
    
*   您现在可以进行内联快照，而无需将 Prettier 作为强制性先决条件（Jest 最需要的功能之一）
    
*   最近更新和改进的假定时器实现成为Jest 27中的默认值（以前是选择加入的）
    
*   每个测试文件的初始化速度比Jest 26快70% 👏
    

### 底线

此版本解决了一些长期存在的性能问题，并标志着自 2016 年年中以来，测试框架首次更改了任何默认设置 - 也就是说，当时 _Jest_ 处于第 15 版并且 _Jess_ 在 New Girl 的第 5 季中担任陪审员。

js提示：== vs ===
------------------

在编写软件时，更简单的解决方案几乎总是更好的解决方案。 如果为了使用一个功能，我首先必须学习并记住与之相关的 [list of rules](https://ui.dev/this-keyword-call-apply-bind-javascript)，我会尽力避免它。 不是因为该功能可能没有价值，而是因为我不相信自己会记住每一个细微的规则。 该逻辑是为什么我总是使用 Triple Equals (`===`) 而不是 Double Equals (`==`) 的主要决定。 他们都完成了类似的事情，但是三重等于的[Pit of Success](https://english.stackexchange.com/questions/77535/what-does-falling-into-the-pit-of-success-mean)要大得多，让我们看看原因。

### 身份运算符（三等于，===）

使用 Triple Equals `===` 时，您需要记住两个规则 - 严格等式（用于比较原始值时）和引用相等性（用于比较参考值时）。

### 严格平等

严格相等性检查 **Type** (`number`、`string`、`boolean` 等) ** 和 **VALUE** 是相同的。 如果 **type** 相同但不是该值，您将得到 false。 如果 **value** 是相同的，但不是类型，您将得到 false。 如果 **Value** 和 **Type** 都相同，您将得到 true。

5 === 5 // true。 相同的类型，相同的值。
5 === 4 // 假。 相同类型，不同值。
5 === "5" // 假。 不同的类型，相同的值。
    
true === true // true。 相同的类型，相同的值。
true === false // 假。 相同类型，不同值。
true === 'true' // 假。 不同的类型，相同的值。
    

看起来很简单，但是如前所述，当我们开始比较参考值（或不是原语的值）时，此规则会分解。

### 参考平等

正如我们在前面的示例中看到的，原始语由它们的值进行比较。 但是，如果您使用 Triple Equals 和参考值，它将比较 **References**（或内存中的点）。

{} === {} // 错误。 相同的类型，相似的值，不同的参考。 ❌
[] === [] // 假。 相同的类型，相似的值，不同的参考。 ❌
{ name: 'meg' } === { name: 'meg' } // 错误。 相同的类型，相似的值，不同的参考。 ❌
    

尽管上面的每个示例都具有相同的类型，并且 ****** 看起来是相同的值，但因为它们是引用值，JavaScript 会比较内存中的引用，而不是实际值。 在每个示例中，内存中的引用或位置都是不同的，这就是为什么我们总是会得到错误的原因。

我们可以通过将两个变量分配给内存中的相同引用，然后在它们上使用身份运算符来进一步看到这一点。

常数用户 = {
名称：“泰勒”
}
    
常人 = 用户
    
person === 用户 // true。 相同的类型，相同的值，相同的参考。
    

在示例中，`person` 和 `user` 都引用了内存中的同一个点，这就是我们得到 `true` 的原因。

总而言之，当使用标识符（`===`）时，假设您知道引用相等性，一切都按您的预期工作。 这是一个平等表来证明这一点。

### 等式运算符（双等于，==）

与身份运算符 (`===`) 不同，除非您非常熟悉它，否则相等运算符 (`==`) 的行为可能与您期望的不一样。 这里只是一些例子，

"1" == 1 // true
null == 未定义 // true
0 == '' // true
'0' == false // true
[1] == true // true 🤷‍♂️
    

那么这里到底发生了什么？ 请注意，在不同类型之间进行了每次比较。 正如我们之前使用的身份运算符（`===`）所看到的，所有这些都会返回 false，因为它们都是不同的类型。 使用等式运算符（`==`），就不是那么简单了。 当类型不匹配时，它不会返回 false，而是尝试将它们转换为相同的类型。

所以在第一个示例中，`"1" == 1` 因为 JavaScript 引擎会将字符串“1”转换为数字 1，然后计算为 `1 == 1` 为 true。

正是这种类型的强制阶段使等式运算符（`==`）变得如此不可预测。 这是我们之前看到的相同的相等表，除了现在`==`。

[![Double equals equality table](https://ui.dev/post-images/double-equals.png)](https://dorey.github.io/JavaScript-Equality-Table/)

如果您和任何在您的代码库中工作的人都对 JavaScript 的所有类型强制规则充满信心，请随意使用您想要的任何运算符。 但是，如果您像我一样使用可以按照您期望的方式工作的工具，请坚持使用身份运算符（===）。
