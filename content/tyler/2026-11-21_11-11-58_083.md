### 让我们准备好捆绑

Bun 又迈出了一大步，成为您梦想中的多合一 JavaScript 运行时——这次，通过发布自己的内置 JS/TS 捆绑器和迷你器。

您可以将它与 `bun build` CLI 命令或其自己的 `Bun.build()` JavaScript API 一起使用 - 是的，它是 [very fast](https://github.com/oven-sh/bun/tree/main/bench/bundle)。

但是，当 Esbuild 和 Turbopack 等其他下一代工具仍然比 Webpack 和 Parcel 等 OG 快得多时，为什么 Bun 会花时间从头开始构建捆绑器呢？

根据 Bun 创建者 Jarred Sumner 的说法，有 [three main reasons](https://bun.sh/blog/bun-bundler?cb#yes-a-new-bundler)：

*   **凝聚力：** 通过将捆绑带入 JS 运行时，Bun 可以消除困扰大多数传统捆绑器的许多复杂性 _(\*curses in webpack\*)_。 它以一些方式做到这一点——例如生成针对 BUN 运行时进行优化的预传输文件，并使用适用于捆绑和运行时的统一插件 API。
    
*   **性能：** 通过利用他们现有的代码库创建自定义捆绑器，BUN 能够获得比他们尝试与现有捆绑程序集成的更快的性能。
    
*   **开发人员经验：** Jarred 明智地指出，“没有人喜欢使用捆绑器配置”，因此他们故意将速度和稳定性置于 API 的功能完整性上。 但是这个测试版仍然涵盖[most modern use cases](https://bun.sh/blog/bun-bundler?cb#the-api)。
    

API 目前支持三个目标（`"browser"`、`"bun"` 和 `"node"`）、最常见的文件类型，并且它得到了对 React Server 组件的实验性支持。 还没有 HMR，但这应该会在接下来的几周内到来。

**底线：** 这可能是迄今为止最大的 Bun 版本，但它显然只是一个更雄心勃勃的“超级 API”的垫脚石，它将与 Bun HTTP 服务器和文件系统路由器拼接捆绑器。

如果这不行，他们总是可以将“超级 API”的版权卖给华纳兄弟，这样他们就可以制作一部没人看的 3 小时超级英雄电影。

`Woof Woof` 记录。

在 JavaScript 将属性的查找委托给构造函数的 `prototype` 之前，它首先检查该属性是否存在于从构造函数返回的对象上。 在这种情况下，它会调用它。

欲了解更多信息，请查看 [A Beginner’s Guide to JavaScript’s Prototype](https://ui.dev/beginners-guide-to-javascript-prototype)
