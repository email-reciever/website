#### 2021年6月（#52）

### ASTRO 正在运送网站 _without_ javascript？？

无论您是尝试建立更快的网站还是在苏伊士运河中减少流量，建议都是一样的：_Just less Ship_。

但如今，随着产品经理_用户（？）_需要越来越多的需要[more and more JavaScript](https://httparchive.org/reports/state-of-javascript#bytesJs)的功能，这变得更加困难。 Astro 希望通过其“默认提供零 JavaScript”的新 [static-site generator](https://astro.build/) 来改变这一切。

**TF 是如何工作的？** Astro 将您的整个站点呈现为静态 HTML，并且仅通过 [Islands Architecture](https://jasonformat.com/islands-architecture/) 方法将 JavaScript 运送到您网站上需要它的部分。 交互式组件（如图像传送带和购物车）被 Astro 加载 - 但如果用户从未看到交互式元素，他们将永远不会加载运行它所需的 JavaScript。 （这对我来说类似于代码拆分，但这与“我们提供零JavaScript”的环不太相同。）

**但是我的宝贵框架呢？** [Calm yourself, Iago](https://www.youtube.com/watch?v=3Gd2ch1FsPU)。 您仍然可以使用您想要构建 UI 组件的任何框架或 npm 包。 Astro 只是在构建过程中将不需要 JavaScript 的所有内容呈现为静态 HTML。

**底线：** Astro 由 [Fred K. Schott](https://twitter.com/FredKSchott) 建造——Snowpack 的创造者和 _Using-your-middle-initial-makes-you-smarter_ 理论的明确支持者。 Snowpack 连接很有趣，因为 Astro 的“按需 JavaScript-on-Demand”方法之所以成为可能，是因为这些更新、捆绑较少的构建工具，如 Snowpack、Parcel、Esbuild 等。

**今天的更新：**这是我们第一次写关于 Astro 或任何其他下一代“饮食 JavaScript”框架的文章——这些框架在今天的生态系统中继续稳步发展。 这也是我最后一次观看了所有名人在黑暗时期唱歌_imagine_的视频。 我很想再看一遍，但我不确定我的身体能否再次剧烈呕吐。

#### 2022年7月(#108)

### 太阳出来了，包子出来了

谁会赢？ 基于 Rust 和 V8 的 JavaScript、TypeScript 和 Wasm 的运行时，并从世界上最好的 VCS 中提出了 [$26,000,000 in funding](https://techcrunch.com/2022/06/21/deno-raises-21m-to-launch-a-fully-managed-runtime-service/) 或 [one determined boi](https://twitter.com/jarredsumner/status/1544821137128927232)？

**Meet** [Bun](https://bun.sh/)：全新的多合一 JavaScript 运行时，可以安装 npm 包的速度比 yarn 快 20 倍，比 `npm install` 快 49 倍，每秒能够捆绑超过 100 万行的 JS，并且声称比两者都快 3 倍 deno 和节点。 哦，这一切都是由[one person](https://twitter.com/jarredsumner)建造的。

BUN 是 Node 和 Deno 的替代运行时。 但它的目标是最终包括一个捆绑器、翻译器和包管理器——这将使其成为其他构建工具（如 Webpack）的可行替代品。 **让我们分解功能：**

*   bun 带有内置的 Web API，例如 `fetch` 和 `WebSocket`（提醒 Node 几个月前几乎没有添加本机 `fetch` 支持）。 它本机实现了 90% 的 node-api 函数，它还带有一个超快的内置 sqlite3 客户端。
    
*   它实现了节点的模块解析算法，因此您可以在 BUN 中使用大多数 npm 包。
    
*   每个文件都被转译，因此TypeScript和JSX可以正常工作。
    

这已经很多了，但这只是乐趣的一半。 让我们放大 Bun 让 Bun 如此令人麻木的速度：

1.  与 Node 和 Deno 不同，Bun 使用 WebKit 的 JavaScriptCore 引擎而不是 V8。 JSC 以比 V8 更难使用而闻名，但在某些情况下要快一些。
    
2.  它是用 Zig 编写的，而不是 Rust 或 C++。 根据 Jarred Sumner（创作者）的说法，Zig 之所以出色，是因为它“对内存的低级控制和缺乏隐藏的控制流，这使得编写快速软件变得更加简单。” （我们会相信他的话。）
    
3.  Jarred 从头开始写出大部分的 Bun，并且痴迷于对所有的基准测试和手工优化。
    

**底线：** 唯一比面包运行时间移动得更快的东西是 Bun Hype 列车——在上周的 v0.1.0 测试版的前 24 小时内，GH 仓库从 1,700 颗恒星降至 _13,000 以上 释放。 而且它看起来不会很快放慢速度。

**今天的更新：**自从我们第一次写到它们以来，Bun Hype 火车绝对没有放慢速度。 回购量高达 42.2k 星，Jarred 筹集了 700 万美元的 VC 并聘请了一个团队，他们正在比 _The Great British Bake Off 更快地制作新的 Bun 版本。

#### 2020年7月（#3）

### VC 和 OSS

开发人员在做出技术决策时喜欢抛出诸如“取决于”和“权衡”之类的短语。 当然，有些框架/库比其他项目更适合某些项目，但第一目标是避免写一篇关于如何 [“we chose the wrong technology 2 years ago and now we’re screwed because of it”](https://medium.com/airbnb-engineering/react-native-at-airbnb-f95aa460be1c) 的思考。

然而，开发人员在做出技术决策时似乎从未考虑过的一个数据点是特定技术背后的公司如何融资——以及它们的稳定性（或可能不稳定）。

还记得[Famo.us](https://techcrunch.com/2013/03/03/famous-series-a/)吗？ 这是一个专门从事[building a fancy Periodic Table of Elements](https://web.archive.org/web/20130329055024/http://www.famo.us/) HTML5性能的JavaScript框架。 它筹集了 100 万美元的种子轮次，然后是 400 万美元的 A 轮融资，然后是 2500 万美元的 B 轮融资，然后它就死了。 如果你买了炒作并建立在 famo.us 之上，你，嗯，可能死于它（或者至少觉得你在里面死了）。

流星呢？ 它筹集了 2000 万美元，然后它的增长停滞不前，它卖给了 Tiny Capital，我认为是美元的几美分。 如果你买了炒作并建立在流星之上，那么你可能会死于它。

不过我们现在很好，对吧？ 现在是2020年——Kanye竞选总统，我们正在参加派对，就像我们没有处于全球大流行之中，我们使用的所有OSS都得到了拥有坚实财务基础的健康公司的支持。

等等，那是什么？ 什么都没有改变？ 哦。

*   盖茨比 - [$46.8m raised](https://www.crunchbase.com/organization/gatsby-e828)
*    维塞尔 - [$21m raised](https://www.crunchbase.com/organization/vercel)
*   阿波罗 - [$53.2m raised](https://www.crunchbase.com/organization/meteor)
*   网络化 - [$97.1m raised](https://www.crunchbase.com/organization/netlify)

**底线：** 我并不是说风险投资总是很糟糕。 [Cloudflare](https://www.crunchbase.com/organization/cloudflare)、[Firebase](https://www.crunchbase.com/organization/firebase)、[MongoDB](https://www.crunchbase.com/organization/mongodb-inc) 都是成功的、VC 支持的技术平台。 我要说的是，风险投资初创公司的设计要么是快速成长，要么是死而复生——所以我们都应该在做出技术决策时考虑到潜在的缺乏稳定性。

**今天的更新：** 大声笑。 早在 2020 年 7 月，我不知道我们将经历一生中最疯狂的 VC + OSS 消费狂潮（以及随后的崩溃和燃烧）。 但无论如何，我试图警告你们！

记录什么？

让 sharedVariable = “初始”；
    
setTimeout(() => {
sharedVariable = "由第一个超时更新";
}, 500);
    
setTimeout(() => {
if (SharedVariable === "初始") {
console.log("共享变量尚未更新");
} 其他{
console.log("共享变量已更新");
}
}, 500);
    

在 JavaScript 中，具有相同延迟的 `setTimeout` 回调的执行顺序不是确定性的。 这意味着我们不能保证第一个超时回调将首先执行（这可能是一些令人讨厌且难以重现错误的原因）。 实际上，它几乎总是您所期望的（“共享变量已经更新”），但最好不要依赖这种行为。

这是 Philip Roberts 的 [famous talk](https://www.youtube.com/watch?v=8aGhZQkoFbQ)，用于了解有关事件循环以及 JavaScript 如何处理异步代码的更多信息。
