### 欢迎来到服务器岛

可悲的是，我不是在指一个新的真人秀节目，一群来自 Chili's 的服务员试图在他们所到之处携带炙手可热的墨西哥卷饼时寻找爱情。 我说的是 Astro [Server Islands](https://astro.build/blog/astro-4120/) 的一个实验性新功能，它提供了一种更灵活的服务器渲染方法。

**我们是如何到达这里的：** 从第一天开始，Astro 就一直在 [islands architecture](https://jasonformat.com/islands-architecture/) 上。框架静态地呈现每个页面的内容，并将交互部分提取到小的 JavaScript 包中，当页面加载时可以水化。

服务器岛做同样的事情……但在服务器上。 这是它的工作方式：

*   **Bundling Magic** – 在构建应用程序时，Astro 将使用 `server:defer` 的组件，用后备替换其内容，并创建一个 API 路由来获取动态 HTML。
    
*   **从 CDN 中提供静态内容** – 应用程序的静态部分被推送到 CDN 并立即提供给用户。
    
*   **在运行时获取动态HTML** – Astro 注入了一个小脚本，用于读取延迟组件上的属性，从 API 中获取动态 HTML，然后将新的 HTML 注入（几乎）没有 JavaScript 的页面。
    

如果这听起来很熟悉，那是因为这几乎是 Next.js 的 [Partial Prerendering](https://vercel.com/blog/partial-prerendering-with-next-js-creating-a-new-default-rendering-model) 的确切方法。 主要区别在于，Next 从初始请求中开始渲染其动态内容并在内容中流，而 Astro 在页面加载后获取动态内容。

Astro 团队声称，尽管在生命周期的后期开始，他们的 _simpler_ 方法更快，但如果您想进行自己的研究，您可以将 [Next.js demo](https://www.partialprerendering.com/) 与 [Astro demo](https://server-islands.com/) 进行比较。

**底线：** 这种“两全其美”的服务器渲染方法似乎是 eComm 站点的新标准，但看看服务器岛和 PPR 是否会超越这一点会很有趣。

发现错误：解决方案
-----------------------

函数最终失败（时间）{
setTimeout(() => {
抛出错误（“哎呀！”）
}，时间）
}
    
试试{
最终失败(1000)
} 捕获（错误）{
控制台.error(error.message)
}
    

`try/catch` 是同步的。 当我们的错误为 `throw`n 时，`try/catch` 块将消失 - 离开我们 `Uncaught Error: Oops!`。 为了解决这个问题，我们希望依靠允许我们进行更多异步控制的 Promise。

函数最终失败（时间）{
返回新的承诺((res, rej) => {
setTimeout(() => {
rej(error("哎呀！)")
}，时间）
})
}
    
最终失败(1000)
.catch((原因) => console.error(reason.message))
