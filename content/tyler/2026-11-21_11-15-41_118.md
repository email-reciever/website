### 100%真实故事

早在 2017 年，这是一个黑暗而暴风雨的万圣节之夜。一个男人独自坐在他的办公室里，在 90 年代在 Ozzfest 现场播放 Slayer 的 Slayer 现场视频，因为他忽略了所有愚蠢到可以响起的不给糖就捣蛋的人 他的门铃。

对不起，孩子们，还有工作要做。 这些实用程序不会自己写，我们的疯狂科学家需要为自己保存所有有趣的士力架，如果他有希望在早上之前推出 v0.1 的话。

但最后，在他的电脑前呆了好几天（并获得了足够的蓝光来破坏他一年的睡眠时间表）之后，亚当·瓦森将最终更新推送到 GitHub，将回购转为公开，并尖叫着“[Eureka!](https://twitter.com/adamwathan/status/925556466475401216)”——当电源激增和火花飞扬时 到处。

弗兰肯斯坦的怪物 _tailwind css_ 还活着。

一些开发人员立即讨厌它——大概是因为它是新事物，而对于拥有 7 年以上经验的开发人员来说，新事物总是很恶心。

但是许多开发人员渴望一个新的CSS框架，它会给他们提供比[Ol’ Bootie](https://getbootstrap.com/docs/3.4/css/)更多的灵活性和更容易的定制，但仍然让他们不必实际#useThePlatform。

**快进到今天，** 和 Tailwind 现在每周的 NPM 下载量超过 400 万次（在过去 12 个月中增长了 4 倍）。 但它甚至不是第一个基于实用程序的 CSS 框架——那么它为什么会如此受欢迎呢？

*   **better tooling:** 通过结合 postCSS 和 purgecss，Tailwind 能够将生成的 CSS 的默认大小从 [190kb to 10kb](https://www.youtube.com/watch?v=BeZbMx9y1FE&t=5527s) 减小。 这让他们增加了越来越多的灵活性，而不必担心文件大小。
    
*   **更好的开发人员体验：** 在看到一些初步成功后，Tailwind 引入了即时编译器 [linter](https://tailwindcss.com/blog/introducing-linting-for-tailwindcss-intellisense) 和 VS Code 扩展，使其更易于使用。
    
*   **更好的设计：** Tailwind 为您提供开箱即用的最佳实践，在颜色、排版、间距等方面具有非常惊人的默认设置。 他们的高级 UI 套件现在每年可赚取数百万美元的收入，并支持一个由 7 名工程师组成的完全自力更生的团队。
    

**底线：** 所以我猜你妈妈错了——有时好事_do_ 发生在万圣节晚上 11 点之后，毕竟。

![Apollo vs GraphQL vs React Relay vs Urql](https://bytes.dev/images/content/graphql-trends.jpg)

我们是否达到了峰值 GraphQL？ – 数据 [npmtrends.com](https://npmtrends.com/@apollo/client-vs-graphql-vs-react-relay-vs-urql)

乍一看，看起来 GraphQL 是向上和向右。 “小学，我亲爱的沃森。” 但是在运行了一些计算（通过运行 FTW 上升）之后，我们看到 GraphQL（Facebook 外部）的增长确实逐渐减少。 我们只能关闭公共 npm 数据，因此我们不知道它在 Zuckerverse 中的使用量是多少，但 GraphQL 的增长肯定总体上放缓了。

以下是可能出现这种情况的几个原因：

*   **Client Server 模型**：去年最大的两个转变是向服务器渲染和边缘移动。 GraphQL 的主要前提是防止“过度获取”——也就是只获取渲染 UI 所需的数据。 但是有了 SSR 和 Edge（以及 React Server 组件之类的东西），在服务器上呈现 UI 并发送回 HTML 而不是 JSON 时发生了显着转变，这否定了 GraphQL 提供的许多好处。
    
*   **移动应用程序**：GraphQL 的另一个核心租户是移动应用程序和 Web 应用程序可以共享相同的 API，但提供不同的体验。 但是，移动应用程序已经使用了 [been on the decline](https://www.forbes.com/sites/victoriacollins/2019/04/05/why-you-dont-need-to-make-an-app-a-guide-for-startups-who-want-to-make-an-app) 数年，许多公司选择专门创建 Web 应用程序。
    
*   **公共 API 的采用率很低**：当 GitHub 宣布将 GraphQL 用于其公共 API 时，GraphQL 取得了巨大的胜利。 但在 GitHub 之外，GraphQL 从未真正为公共 API 起飞。 因此，GitHub 似乎已经放弃了 GraphQL 的努力，并且对于大多数端点来说都是 [now using REST](https://docs.github.com/en/rest/guides/getting-started-with-the-rest-api)。
