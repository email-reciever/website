### 以新的方式结合旧事物

如果开发人员喜欢一件事，那就是花几个小时拍摄和发布他们的 WFH 设置的照片，这样他们就可以在 Twitter 上获得 4 个赞（其中 3 个来自加密机器人）。

但是，如果开发人员喜欢另一件事，那就是将旧技术结合到新的框架中，以解决（人们可能会争论）已经解决的问题。 但是，嘿，有时这就是伟大的软件诞生的方式，所以我们支持它。

此现象的图表 A 是 [htmx](https://htmx.org/) — 一个新的 (ish) 框架，它结合了 Ajax、WebSockets 和服务器发送的事件，并将它们直接放入您的 HTML 中，以便您可以构建丰富的客户端应用程序 _without_ JavaScript。

如果这对您来说听起来很熟悉，那可能是因为它与 [Phoenix LiveView](https://github.com/phoenixframework/phoenix_live_view) 和 Ruby on Rails 的 [Hotwire](https://hotwired.dev/) 非常相似。 但是`htmx`本周引起了很多关注，尤其是在[conference talk](https://www.youtube.com/watch?v=3GObi93tjZI)之后，大卫·吉洛特（David Guillot）热情洋溢地谈论将他的团队的 SaaS 产品从 React 迁移到 `htmx`。

**这是如何工作的？** 而不是发送 JSON 并使用 JavaScript 将其转换为 HTML，`htmx` 只是发送 HTML——但它的架构允许您将小片段（仅更新或交互所必需的）发送给客户端。 服务器处理所有应用程序状态（因此它不会在客户端和服务器上重复）并发送特殊的 HTTP 标头，让客户端知道要进行哪些更新。 客户如何做到这一点？ 它与“Lavascript”押韵，但不破坏叙事🤫。

**为什么有人会想要这个？** 如果您是一个真正讨厌编写 JavaScript 的开发人员，这可能适合您。 它使您的客户端超轻，并真正尝试利用 HTML 所提供的所有功能。 这意味着更小的捆绑包，更少的代码等——而且你几乎在后端完成了所有的工作。

**什么是权衡？** 最大的权衡是这种方法使您的应用程序更加依赖网络交互。 这也意味着 UI 和后端耦合在一起（因此您的移动应用程序需要一个新的 API）。

**底线：** 就像 Dori-Dew 一样，这对我们中的一些人来说可能看起来像是一种憎恶，但对于其他人来说，这可能正是医生的要求。

![apexcharts vs chart.js vs d3 vs echarts](https://bytes.dev/images/content/chart-trends.jpg)

数据可视趋势 – 数据 [npmtrends.com](https://npmtrends.com/apexcharts-vs-chart.js-vs-d3-vs-echarts)

今天，我们正在获得真正的元数据并使用图表来比较 Dataviz 库。 除了捆绑大小、下载、GitHub 明星、Twitter 炒作和最新更新的通常嫌疑人之外，我们应该如何确定哪个库最适合我们的需求？

在这种情况下，事实并没有真正给我们一个明确的“赢家”，所以让我们更详细地分解它，让你决定。

**细分：**

**简单与强大** — 数据可视化具有非常宽的表面积，需要考虑的主要权衡之一是功能与易用性。 D3 多年来一直是标准，但近年来更简单的 Chart.js 通过了它。 尽管 D3 更具表现力和功能，但 Charty（正如我们喜欢称之为）却超级简单且易于使用。

**SVG vs Canvas** — Dataviz 库通常按照他们想要渲染的方式进行拆分。 在这种情况下，chart.js 和 echarts 是基于画布的，而 D3 和 ApexCharts 主要依赖于 SVG。 这对您是否尝试服务器渲染可视化有影响（SVG往往更容易服务器渲染）。 它还可以影响性能，而画布往往在动画中表现更好。

**交互与静态** — 在交互时可以绘制相同的线。 像 Apex 这样的库可以让您轻松完成 [dead simple static charts](https://apexcharts.com/javascript-chart-demos/)，但如果您查看一些 [EChart examples](https://echarts.apache.org/examples/en/index.html#chart-type-custom)，您会看到它们如何变得非常疯狂。
