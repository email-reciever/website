### JSR是选择的之一吗？

经过几代的预言_A Buzz_几周，Deno终于发布了[JSR](https://jsr.io/#why-jsr)的开放测试版，这是其用于现代JavaScript和TypeScript的开源软件包注册表。

JSR 代表“JavaScript Registry”，但考虑到其网站的第一行指出“JSR 是为 TypeScript 设计的”，它更适合称之为 TSR。 我不是品牌专家，但这感觉就像我知道第一个肯德基实际上是 [started in Utah](https://www.atlasobscura.com/places/first-kfc-restaurant-m) 而不是肯塔基州的时候。

但是每个人都在想的更大的问题是**_为什么_我们需要一个新的包注册表吗？**

Ryan Dahl 比任何人都更清楚 JS 生态系统自 2009 年创建 NPM（和节点）以来发生了多大的变化。从那时起，我们看到了 TypeScript、ES 模块和新的 JS 运行时等极具影响力的技术的出现——但 npm 没有构建 考虑到这些。

因此，Deno 工作人员决定自己建立一个新的注册表，就像肯德基的 [donut chicken sandwich](https://www.thesouthafrican.com/lifestyle/kfc-50th-birthday-kentucky-town-zinger-doughnut-burger-twitter-reviews-photos/) 一样，包含了现代性的全部力量。 以下是如何：

*   **Native TypeScript Support** — 我已经给了这个，但是 JSR 做了很多工作 [behind the scenes](https://deno.com/blog/jsr_open_beta#publishing-to-jsr) 让您在 TypeScript 中编写您的包，并将 ts 源代码直接发布到 JSR，而无需构建步骤。
    
*   ***仅限模块**——就像保罗·阿特雷德斯曾经告诉弗雷曼军队一样，“成为你希望在世界上看到的改变。”
    
*   ** 适用于任何运行时** — JSR 希望在 JavaScript 工作的任何地方都能工作，而不需要作者手动转译和分发类型。 它已经与 Node、Deno、BUN、Cloudflare 工作人员和其他 npm 环境一起使用，并计划继续扩展支持。
    
*   ** 建立在 npm** 上** — 就像 TypeScript 与 JavaScript 的关系一样，JSR 是 npm 的 _superset_，而不是 fork。 这意味着它被设计为 [interoperate with npm-based projects](https://jsr.io/docs/npm-compatibility)，而 JSR 模块可以从 npm 导入依赖项。
    

**底线：** 在许多方面，JSR 背后的动机与 Ryan 的 [motivations](https://www.youtube.com/watch?v=M3BM9TB-8yA) 相似，将 Deno 构建为更现代、更安全且对打字稿友好的 Node 版本。 现在判断任何一个项目是否会达到真正“解决”前辈问题的临界数量还为时过早，但 JSR 的早期回报看起来非常有希望。
