### TypeScript 5.0 beta 🚀

2020 年 7 月，我们在第三个字节问题中写了关于 TypeScript 4.0 测试版的文章——当我们在 Totino 的披萨卷上生存并为游戏的热爱制作 JavaScript 模因时。

在过去的 30 个月里，TypeScript 和字节都增长了很多，所以上周的 [TS 5.0 beta release](https://devblogs.microsoft.com/typescript/announcing-typescript-5-0-beta) 在某些方面对我们俩来说都是一个里程碑。 但在其他方面，我们真的没有长到这么多——我还在用熔岩卷制作模因和燃烧味蕾，而 Typescript 仍然拒绝遵循 Semver。

这意味着 TS 5.0 在技术上不是“主要版本”，尽管它确实带来了一些比平时更多的突破性变化和一些很酷的新功能，这些功能让类型的书呆子在嘴里起泡。

**这里有亮点：**

*   **装饰师** — 这些是您在 2016 年学到的东西，然后忘记了现在。 它们以 `@` 符号开头，可以放在类和类成员的前面（如方法、getter 和 setter），允许我们以可重用的方式对其进行自定义。 这个新的 TypeScript 实现是在第 3 阶段 ECMAScript 提案中建模的，并替换了 TS 曾经拥有的实验装饰器。
    
*   **const annotations** — 您现在可以将 `const` 修饰符添加到类型参数，当传递要缩小的内容作为其文字时，可以是 [really helpful](https://twitter.com/mattpocockuk/status/1616480628307787793?s=20&t=Vnm8BYV67OaMtWpozEfjfw)。
    
*   **速度改进** — 由于 Typescript 从命名空间迁移到模块，大多数代码库的速度提升应该达到 10-20%，这使得它能够利用现代构建工具进行优化，如范围提升。
    

**底线：** 对于大多数开发人员来说，装饰器将成为这里的头条新闻。 有些人甚至想知道他们是否可以帮助使基于课堂的编程再次流行起来。 是的，“那些人”是指 Java 开发人员。

在编写软件时，更简单的解决方案几乎总是更好的解决方案。 如果为了使用一个功能，我首先必须记住一个规则列表，我尽量避免它。 不是因为该功能可能没有价值，而是因为我不相信自己会记住每一个细微的规则。 该逻辑是为什么我总是使用 Triple Equals (`===`) 而不是 Double Equals (`==`) 的主要决定。 他们都完成了类似的事情，但是三重等于的[Pit of Success](https://english.stackexchange.com/questions/77535/what-does-falling-into-the-pit-of-success-mean)要大得多，让我们看看为什么。

### 身份运算符（三等于，===）

使用 Triple Equals `===` 时，您需要记住两个规则 - 严格等式（用于比较原始值时）和引用相等性（用于比较参考值时）。

### 严格平等

严格相等性检查 **Type** (`number`、`string`、`boolean` 等) ** 和 **VALUE** 是相同的。 如果 **type** 相同但不是该值，您将得到 false。 如果 **value** 是相同的，但不是类型，您将得到 false。 如果 **Value** 和 **Type** 都相同，您将得到 true。

5 === 5 // true。 相同的类型，相同的值。
5 === 4 // 假。 相同类型，不同值。
5 === "5" // 假。 不同的类型，相同的值。
    
true === true // true。 相同的类型，相同的值。
true === false // 假。 相同类型，不同值。
true === 'true' // 假。 不同的类型，相同的值。
    

看起来很简单，但是如前所述，当我们开始比较参考值（或不是原语的值）时，此规则会分解。

### 参考平等

正如我们在前面的示例中看到的，原始语由它们的值进行比较。 但是，如果您使用 Triple Equals 和参考值，它将比较 **References**（或内存中的点）。

{} === {} // 错误。 相同的类型，相似的值，不同的参考。 ❌
[] === [] // 假。 相同的类型，相似的值，不同的参考。 ❌
{ name: 'meg' } === { name: 'meg' } // 错误。 相同的类型，相似的值，不同的参考。 ❌
    

尽管上面的每个示例都具有相同的类型，并且 ****** 看起来是相同的值，但因为它们是引用值，JavaScript 会比较内存中的引用，而不是实际值。 在每个示例中，内存中的引用或位置都是不同的，这就是为什么我们总是会得到错误的原因。

我们可以通过将两个变量分配给内存中的相同引用，然后在它们上使用身份运算符来进一步看到这一点。

常数用户 = {
名称：“泰勒”
}
    
常人 = 用户
    
person === 用户 // true。 相同的类型，相同的值，相同的参考。
    

在示例中，`person` 和 `user` 都引用了内存中的同一个点，这就是我们得到 `true` 的原因。

总而言之，当使用标识符（`===`）时，假设您知道引用相等性，一切都按您的预期工作。 这是一个平等表来证明这一点。

### 等式运算符（双等于，==）

与身份运算符 (`===`) 不同，除非您非常熟悉它，否则相等运算符 (`==`) 的行为可能与您期望的不一样。 这里只是一些例子，

"1" == 1 // true
null == 未定义 // true
0 == '' // true
'0' == false // true
[1] == true // true 🤷‍♂️
    

那么这里到底发生了什么？ 请注意，在不同类型之间进行了每次比较。 正如我们之前使用的身份运算符（`===`）所看到的，所有这些都会返回 false，因为它们都是不同的类型。 使用等式运算符（`==`），就不是那么简单了。 当类型不匹配时，它不会返回 false，而是尝试将它们转换为相同的类型。

所以在第一个示例中，`"1" == 1` 因为 JavaScript 引擎会将字符串“1”转换为数字 1，然后计算为 `1 == 1` 为 true。

正是这种类型的强制阶段使等式运算符（`==`）变得如此不可预测。 这是我们之前看到的相同的相等表，除了现在`==`。

[![Double equals equality table](https://ui.dev/post-images/double-equals.png)](https://dorey.github.io/JavaScript-Equality-Table/)

如果您和任何在您的代码库中工作的人都对 JavaScript 的所有类型强制规则充满信心，请随意使用您想要的任何运算符。 但是，如果您像我一样使用可以按照您期望的方式工作的工具，请坚持使用身份运算符（===）。
